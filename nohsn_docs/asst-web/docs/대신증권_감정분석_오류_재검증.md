# 대신증권 감정분석 장애 — 원인 재검증 및 회의 대응 정리

- **목적**: 2026-07-01 감정분석/요약 미표시 장애의 원인을, 프론트엔드 코드로 재검증하여 확정. 고객사(대신증권/포털 담당자) 회의 대응용 내부 정리.
- **작성일**: 2026-07-04
- **관련 문서**: `docs/대신증권_감정분석_장애_소명.md` (고객 제출본) — **본 재검증 결과, 소명 문서의 원인 진술은 유효함(수정 불필요).**

---

## 0. 한 줄 결론

> **assist-stream(SSE) 경로는 토큰을 옛 값으로 "캐싱"하지 않는다. 매 발화마다 sessionStorage의 토큰을 다시 읽어 보낸다. 문제는 그 통화 구간에 sessionStorage 토큰 자체가 갱신되지 않아, 저장소에 남은 만료 토큰을 그대로 실어 보낸 것이다.**

원인이 포털이든 어드바이저 앱이든, **토큰이 만료된 상태에서도 실시간 상담 기능에 영향이 가지 않도록(최소화)** 앱 차원의 방어선(조치 ①②③)을 마련·적용했다.

---

## 1. 코드로 확인된 사실 (파일·라인 근거)

### 1-1. 앱에는 `/auth/refresh`를 직접 부르는 토큰 재발급 경로가 3개 있다
| # | 경로 | 트리거 | 근거 |
|---|------|--------|------|
| 1 | **포털** (앱 외부) | 20분 주기 | 앱 코드 밖 (포털이 sessionStorage로 전파) |
| 2 | **일반 API 반응형** (`service` 클라이언트) | 응답이 401(code 107) 나면 즉시 `/auth/refresh` → 저장소 갱신 → **원래 요청 재시도** | `src/api/modules/request.ts:59, 102-149`, `token.ts:9-13`, `path.ts:20` |
| 3 | **선제 재발급 타이머** (조치 ③⑴) | 만료 약 3분 전 `/auth/refresh` | `src/utils/tokenRefreshTimer.ts` |

- 세 경로 모두 **동일한 `/auth/refresh`**(= `GATEWAY_SERVER + AUTH_PREFIX + /refresh`, **인증 서버**)를 직접 POST한다. `path.ts:20`
- 재발급 성공 시 새 accessToken/refreshToken을 저장소에 기록한다. `request.ts:155-157`

### 1-2. assist-stream(SSE)은 위 3개 경로 어디에도 걸리지 않는다
- **raw `fetch`로 구현** (axios 인터셉터 밖). `src/api/apis/assist-stream.api.ts:41-46`
- 발화 1건 = `handleAssistStream()` 1회 = `callAssistStream()` 1회 = **fetch POST 1건** (장수명 SSE 연결 아님). `useChatAssist.ts:229, 389`
- 매 호출 시작에서 **토큰을 그때그때 새로 읽는다**: `getCurrentAccessToken()`. `assist-stream.api.ts:27`
- 401을 받아도 **재발급/재시도 로직이 없다** — 그냥 error 핸들러 호출 후 종료. `assist-stream.api.ts:48-56`

### 1-3. 두 경로(일반 API·assist-stream)는 같은 저장소를 읽는다
- `getCurrentAccessToken()` → `Cookie.getCookie("accessToken")` → **`sessionStorage`** (`VITE_COOKIE_USE_AT=false`, 전 환경 동일). `apiPlugin.ts:29-37`, `cookies.js:40-51`, `.env.prd`
- 즉 assist-stream은 저장소가 갱신돼 있으면 **새 토큰을 그대로 집어서 보낸다.** 옛 토큰을 붙잡는 구조가 아니다.

---

## 2. 완성된 인과 사슬 (왜 assist-stream만 만료 토큰이 나갔나)

1. 일반 API(`service`)는 401이 나면 **반응형으로 자동 재발급 + 재시도**하며 저장소 토큰을 최신으로 되살린다.
2. 그러나 **통화 중에는 일반 API(`service`) 트래픽이 없다** — 발화 스트리밍(assist-stream)만 돈다. → 반응형 재발급이 **트리거되지 않는다.** (`tokenRefreshTimer.ts:14-16` 주석과 일치)
3. 장애 시점에는 선제 재발급 타이머(조치 ③)도 아직 없었고, **포털의 20분 갱신값이 앱 sessionStorage로 전파되지 않았다.**
4. → 저장소에 **만료된 토큰이 그대로 남는다.**
5. assist-stream은 매 발화마다 그 저장소 값을 읽어 보내므로, **만료 토큰을 계속 실어 보낸다.** → 401 반복 (로그: 204초 동안 104건, `exp 14:19:38`)

**핵심 프레임: "assist가 옛 토큰을 캐싱해서"가 아니라 "저장소가 안 갱신돼서"다.**

## 3. 원 소명 문서 검증 결과

소명 문서 **본문 2장(발생 원인) / line 32** 은 재검증 결과 **유효**하다. "재발급(reissue)" 관점으로 읽으면 각 문장이 참:

| 소명 문서 문장 | 판정 |
|---|---|
| 실시간 스트리밍 경로가 토큰 자동 갱신(재발급) 대상에 포함 안 됨 | ✅ 참 (assist-stream은 raw fetch, 재발급 없음) |
| 일반 화면과는 다른 스트리밍 전용 통신 방식 사용 | ✅ 참 |
| 이 경로엔 만료 전 자동 갱신 미적용 | ✅ 참 (조치 ③ 전) |
| 갱신할 수단이 없어 만료 토큰이 계속 전송됨 | ✅ 참 (로그로 증명) |

- **부록 ④**(재발급 흔적이 어드바이저 로그에 없음 / 인증서버·프론트 로그 확인 필요)도 정확하다. `/auth/refresh`는 **인증 서버**로 나가므로 어드바이저(asst-service) 로그에 남지 않는다. `path.ts:20`
- 유일한 표현상 정밀도: 일반 경로의 재발급은 **반응형(401 이후)** 이고, "만료 전"이라는 표현은 **조치 ③(선제 재발급)** 에 해당한다. 큰 틀은 정확.

## 4. 회의 대응 스크립트

### 4-1. 기본 설명 (이대로 말하면 됨)
> "포털은 20분마다 토큰을 재발급해 관리하고, 어드바이저 앱의 일반 API도 401을 받으면 `/auth/refresh`로 **자동 재발급 후 재시도**해 저장소 토큰을 최신으로 유지합니다. 그런데 **실시간 상담보조(SSE) 경로엔 그 재발급 트리거가 없습니다.** assist-stream은 호출할 때마다 저장소 토큰을 그대로 읽어 보내는데, 통화 중엔 SSE만 돌아 **저장소를 갱신할 계기가 없어**, 저장소에 남은 만료 토큰을 계속 실어 보내 401이 났습니다. 조치 ③(선제 재발급)으로 트래픽과 무관하게 앱이 스스로 토큰을 갱신하도록 해 해결했습니다."

### 4-2. 예상 반박 → 답변
| 상대 주장 | 대응 |
|---|---|
| "SSE라서 갱신된 토큰을 못 읽는 구조 아니냐" | ❌ 그건 아님. assist-stream은 **매 발화마다 저장소를 다시 읽음**. 저장소만 최신이면 새 토큰을 보냄. 문제는 **저장소 미갱신**이지 읽기 능력이 아님. |
| "우리 포털은 20분마다 갱신하는데 왜 20분 만에 만료됐나" | 포털이 자기 토큰은 갱신했더라도, **그 값이 어드바이저 앱의 sessionStorage로 전파되지 않았음.** 백엔드 로그상 앱은 발급 후 20분에 만료되는 토큰을 계속 보냈음 = 앱은 갱신을 못 받고 있었음. 조치 ③으로 **앱이 자체 재발급**하게 만들어 이 전파 의존성을 제거함. |
| "그럼 어드바이저 앱 버그 아니냐" | 앱 로직은 매 요청 최신 토큰을 읽으려 함(캐싱 없음). 다만 **실시간 경로에 자체 재발급 트리거가 없던 것**이 개선 포인트였고, 조치 ③으로 보완함. |

### 4-3. 책임 프레임 (핵심)

## 6. 잔여 리스크 (손에 쥐고 갈 것)

- 조치 ③⑴(선제 재발급 타이머)은 **앱이 자체 refreshToken을 sessionStorage에 보유해야만 작동**한다. `tokenRefreshTimer.ts:63` (`if (!hasRefreshToken()) return`)

# 현구조의 refresh token을 우리 회사 인증서버에서 진행하는 방법

> **작성 보강일**: 2026-07-05
> **목적**: "우리 인증서버가 refresh token을 발행해야 하냐 / 못 하면 인증을 빼야 하냐"는 논의를 정리. 비개발자 담당자에게도 설명 가능하도록 기초부터 서술.

---

## 7-0. 한 줄 결론 (먼저 읽을 것)

> **지금 구조에선 우리 인증서버가 refresh token을 "발행"할 필요가 없다.** 포털이 access·refresh 토큰을 모두 발행하고, 우리 앱은 그걸 **소비(갱신 호출)만** 하면 된다. 이번 장애는 우리 프론트의 **조치 ③(선제 재발급 타이머)** 로 이미 완결된다. **"인증을 빼자"는 불필요하며, 이 문제 해결에 인증서버 담당자가 새로 할 일은 없다.**

---

## 7-1. 기초: JWT는 "암호화"가 아니라 "서명된 공개 데이터"다 (가장 헷갈리는 지점)

refresh token(그리고 access token)은 **JWT**다. JWT를 오해하면 논의 전체가 틀어지므로 여기부터 못을 박는다.

- JWT는 `헤더.페이로드.서명` 세 조각이다.
- **페이로드는 암호화가 아니라 `base64url` 인코딩일 뿐이다.** 키 없이도 누구나 읽는다. (브라우저 콘솔, 중간에 낚아챈 누구든)
- **서명(RS256 = RSA + SHA256)은 "내용을 숨기는" 게 아니라 "위·변조를 막는" 것이다.**
  - 읽기(read)는 **열려 있다.**
  - 발행(write/재서명)은 **개인키를 쥔 자만** 할 수 있다 → 그래서 위조가 불가능한 것이지, 내용이 비밀인 게 아니다.

### 실제 우리 토큰 디코딩 예시 (키 없이 그냥 읽힘)

```
HEADER  : { "alg": "RS256" }         ← 알고리즘만. typ도 없음
PAYLOAD :
  sub  : "1231"      (사용자 ID)
  acc  : "agent40"   (계정)
  cId  : 60          (회사 ID)
  cd   : "POC4"      (테넌트 코드)   ← 테넌트 정보가 토큰 안에 이미 들어있음
  ad   : "261051"
  role : "AGENT"
  exp  : 1783253130  (만료 시각, Unix time)
```

> **비개발자용 비유**: JWT는 "**투명한 봉투에 든, 위조방지 스탬프가 찍힌 서류**"다. 안의 내용(이름·소속·만료일)은 봉투 밖에서 다 보인다(암호화 아님). 하지만 그 서류를 **새로 발급하거나 내용을 고쳐 다시 스탬프를 찍는 건, 스탬프(개인키)를 가진 발급기관만** 할 수 있다.

---

## 7-2. "refresh 재발행"의 정체 = "다시 인코딩"이 아니라 "개인키로 다시 서명"

가장 흔한 오해: *"payload에서 exp만 늘려서 base64로 다시 인코딩해 돌려주면 되잖아?"* → **틀리다.**

- 그렇게 하면 payload와 서명이 안 맞아 **검증 단계에서 전부 튕긴다(reject).**
- 게다가 그게 통한다면 아무나 토큰을 위조할 수 있게 되어 인증 자체가 무의미해진다.

정확한 재발행 흐름:

1. refreshToken 수신
2. **공개키로 서명 검증** (위조 아님을 확인)
3. `exp` 확인 (만료 안 됐으면 통과)
4. payload에서 claim(`sub`, `cId`, `cd`, `role`)을 꺼냄 — **조회할 것도 없이 토큰 안에 다 있음**
5. 그 claim으로 새 access/refresh 토큰을 만들고 → **발급기관의 개인키로 RS256 재서명** → 반환

**핵심: 5번의 "개인키로 재서명"이 재발행의 본질이다. 이게 되려면 발급용 개인키(RSA private key)를 보유해야 한다.**

---

## 7-3. 현 구조 정리: 발행은 포털이, 우리는 해석(tenant)만

| 주체 | 역할 |
|---|---|
| **고객사 포털 (SSO, 최상위)** | access·refresh 토큰을 **모두 발행(서명)**. `/auth/refresh` 재발행도 **이미 운영 중**. 20분 주기 갱신도 포털이 함. |
| **우리(팀벨) 인증서버** | 포털 SSO 우산 아래 입주한 여러 앱 서비스 중, 우리 몫 서비스에 대해 **토큰을 해석해 tenant 정보를 리턴**. = **발행자가 아니라 해석자.** |
| **어드바이저 앱 (프론트, 내 담당)** | 포털이 준 토큰을 sessionStorage에 갖고, API 호출 시 사용. 만료 시 `/auth/refresh` 호출해 갱신·재시도(인터셉터). |

**확정된 사실**: 포털이 access·refresh를 **둘 다** 발행해 우리 앱에 준다. → 즉 **우리 인증서버는 토큰 발행자가 아니다.**

### 이게 왜 이번 문제의 답을 닫는가

- 우리 앱 인터셉터는 **평소에 이미 `/auth/refresh`를 호출해 새 토큰을 받아 저장하고 재시도**한다(정상 동작 중, `request.ts:155-157`).
- 이건 **그 refresh 경로가 실제로 새 토큰을 뱉는다는 증거**다. (안 그럼 평소 재시도가 안 됐을 것)
- 장애의 유일한 원인은 → **통화 중엔 SSE(assist-stream)만 돌아 인터셉터를 때릴 일반 API 트래픽이 없어서** 갱신이 트리거 안 된 것뿐.
- → **조치 ③(시간 기반 선제 타이머)** 이 바로 그 구멍만 메운다. **같은(검증된) `/auth/refresh` 경로**를, 401 대신 타이머로 부르는 것.

> **결론: 이 문제는 100% 우리 프론트 안에서 끝난다. 인증서버 담당자가 새로 발행 로직을 만들 필요도, 인증을 뺄 필요도 없다.** (6장 "잔여 리스크"의 *"앱이 자체 refreshToken을 확보하나?"* 도 → **확보함으로 확인됨**. 인터셉터가 refresh를 성공적으로 부르고 있고, 앱이 refreshToken을 실제 보유 중이므로 조치 ③은 no-op이 아니라 진짜 방어선.)

## 7-4. "그럼 우리 인증서버도 발행하려면?" — 필요한 건 '포털 개인키'가 아니다 (두 번째로 헷갈리는 지점)

미래에 우리 인증서버가 **발행 역할까지** 맡고 싶다면, 조건은 아래 둘 중 하나다. **"포털 개인키를 받아오면 된다"는 오해**이니 주의.

| 방식 | 내용 | 채택 여부 |
|---|---|---|
| **(A) 포털 개인키를 공유받아 같은 키로 서명** | 우리 토큰이 포털 토큰과 구분 불가해짐 | ❌ **보안 안티패턴.** 개인키를 하위 벤더에 넘기면 포털이 서명 독점성을 잃음. **현실적으로 포털이 절대 안 줌.** 요청 자체가 부적절하게 비침. |
| **(B) 우리 자체 키쌍을 갖고, 우리 공개키를 포털·앱들이 신뢰하도록 등록** (JWKS / 멀티 issuer) | 개인키는 각자 보유, 상대는 공개키로 검증 | ✅ **정상적인 페더레이션 방식.** 포털 개인키 불필요. 필요한 건 "우리 발급자를 신뢰 목록에 넣어달라"는 **협의**. |

> **정확한 문장(담당자/회의용)**: "우리 인증서버가 발행 역할을 하려면 **포털의 개인키를 가져오는 게 아니라**, **우리 자체 서명키(공개키/JWKS)를 포털 생태계가 신뢰하도록 등록하는 페더레이션 협의**가 선행돼야 한다. (개인키 공유 방식도 이론상 가능하나 보안상 채택하지 않는다.)"

## 부록 A. 우리 인증서버의 가능한 역할 (silent refresh 관점)

> "우리는 할 일 없다"가 현재 결론이지만, *"만약 우리가 refresh를 맡는다면?"* 을 담당자에게 설명하기 위한 정리. **발행범위(우리가 토큰을 직접 서명하느냐)** 에 따라 역할이 갈린다.

### A-0. 먼저: silent refresh는 "구조"가 아니라 "성질"이다

- **silent refresh** = 사용자가 눈치 못 채게, **재로그인 없이 뒤에서 토큰을 갱신**하는 것. UX 성질이지 특정 아키텍처가 아니다.
- **우리는 이미 하고 있다.** 인터셉터(401→refresh)와 조치 ③ 타이머가 곧 silent refresh다. → "새로 만들 기능"이 아니라 "이미 있는 동작"이며, 아래 A/B/C **어느 역할이든 silent refresh는 다 가능**하다. 차이는 "뒤에서 **누가** 갱신하느냐"뿐.

### A-1. 발행범위에 따른 3단 역할 스펙트럼

| | 역할 | 발행(서명) 주체 | 포털 refresh 호출 주체 | 우리가 새로 필요한 것 | silent 가능 |
|---|---|---|---|---|---|
| **A** | **해석자 (현재)** | 포털 | **프론트**가 직접 | 없음 (이미 됨) | ✅ |
| **B** | **중계기 / 프록시** | 포털 (그대로) | **우리 BFF/인증서버**가 대리 호출 (front→BFF→우리인증→포털) | 포털이 **서버-투-서버 호출 허용** + 통과 배선. **개인키 불필요** | ✅ |
| **C** | **발행자 (자체 issuer)** | **우리 서버**가 직접 서명 | 우리가 자체 발행 | **자체 서명키 + 포털이 우리 공개키를 신뢰(페더레이션)** | ✅ |

- 기준 한 줄: **발행범위 0 = B(중계기), 발행범위 > 0 = C(발행자).**

### A-2. 역할별 난이도 (핵심 대비)

- **B(중계기)**: 기술적으로 쉬움. **개인키 불필요.** 유일한 관문은 *"포털이 우리 서버발 refresh 호출을 받아주나"* 하나. 보안 이득(refresh token을 브라우저 밖 서버에 보관)이 크고 난이도는 낮음 → **개선하려면 현실적 스윗스팟.**
- **C(발행자)**: 무거움. 서명키 관리 + **포털이 우리를 신뢰 발급자로 등록**(페더레이션) + refresh 회전/폐기 저장소 필요. SSO 주인은 보통 포털이라 하위 벤더가 병렬 IdP가 되는 건 실무에서 잘 안 함. *가능하나* 협의·정당성 비용이 큼.

### A-3. 비개발자용 비유

> 토큰 = "출입증", 출입증을 **찍어내는 발급기(개인키)** 는 포털이 보유.
> - **A(현재)**: 직원(프론트)이 직접 발급창구(포털)에 가서 새 출입증을 받아온다.
> - **B(중계기)**: 우리 안내데스크(BFF)가 직원 대신 창구에 다녀와 준다. **발급기는 여전히 포털 것.** (더 안전·깔끔)
> - **C(발행자)**: 우리가 **우리 발급기**를 갖는다. 단, 그 출입증을 건물 전체가 인정하게 하려면 **건물주(포털)와 협약** 필요.

### A-4. 담당자 설명용 결론

> **"지금은 A(해석자)로 충분하다. 굳이 우리가 refresh를 '하려면' B(중계기)가 가장 현실적이고 개인키도 필요 없다. C(발행자)는 포털과의 페더레이션 협약이 있어야 가능한, 지금 안 할 일이다."**
