# 카테고리: expense (지출 기록 / 조회 / 삭제)

## 지출 기록

```
[{1, tool, expense.create, {
   amount: <int 원>,
   category: "식비"|"교통"|"쇼핑"|"주거"|"의료"|"여가"|"교육"|"기타",
   description: "<가게명/메모>",
   spent_at: "<ISO date — 어제/오늘/저번주 등 위 변환 룰>",
   tenant_id: "$personal_tenant_id"
 }}]
```

한 발화에 여러 건 있으면 multi-step (각 건마다 expense.create). slot_filler 의 __items 배열 처리는 자동.

## 지출 조회

```
[{1, tool, expense.sum_by_category, {
   period_start: "<ISO date>",
   period_end: "<ISO date>",
   tenant_id: "$personal_tenant_id"
 }}]
```

"이번주" / "이번달" / "지난달" 변환 — period_start/end *둘 다* 채움. 한쪽만 채우면 단일일 조회로 오해.

## ★ 지출 항목 수정 (P11-19g)

사용자가 *기존 지출 항목의 값만 변경* 요청 ("어제 점심비 17000원이 아니라 19000원이었어",
"그 항목 카테고리를 식비에서 교통으로", "30000원 마트 항목 50000원으로 수정",
"오늘 커피 4500원을 4000원으로 정정") → **expense.update 단일 호출**.

```
[{1, tool, expense.update, {
   <매칭 조건 — 셋 중 최소 한 개>
   description: "<직전 항목 설명 substring>",
   spent_at: "<YYYY-MM-DD>",
   amount: <int 원, 옛 값>,
   <변경 필드 — 적용할 새 값>
   new_amount: <int 원>,
   new_category: "<식비/교통/...>",
   new_description: "<새 메모>",
   new_spent_at: "<새 ISO>",
   tenant_id: "$personal_tenant_id"
 }}]
```

원칙:
- *delete+create 2-step* 절대 사용 X — 응답 톤이 "삭제 실패 + 신규 등록" 으로
  사용자 의도와 어긋남. 단일 expense.update 가 "수정했습니다" 톤 보장.
- "17000원이 아니라 19000원" 같이 *옛 값 + 새 값* 둘 다 명시되면 amount=17000
  (매칭) + new_amount=19000 (변경).
- *직전 turn 항목* 가리키며 수정 ("그 항목") → history 에서 description / spent_at
  추출 후 매칭 조건 채움.

예: "어제 점심비 17000원 말고 19000원이었어"
```
[{1, tool, expense.update, {
   spent_at: "<어제 ISO>",
   amount: 17000,
   description: "점심",
   new_amount: 19000,
   tenant_id: "$personal_tenant_id"
 }}]
```

예: "그 항목 카테고리를 식비에서 교통으로 바꿔" (직전 등록 항목 가리킴)
```
[{1, tool, expense.update, {
   description: "<history 의 직전 항목 description>",
   new_category: "교통",
   tenant_id: "$personal_tenant_id"
 }}]
```

## ★★★★★★ 지출 삭제 — id 단건 enforcement (Phase 1.5A Task 8e — 2026-05-07)

★ 본 섹션은 *아래 모든 삭제 관련 섹션* 보다 우선한다. broad mutation 차단을 위해
`expense.delete` 는 `id` (UUID) 단건 호출만 허용한다.

### id 없는 delete 호출 금지
`expense.delete({amount: ...})` / `expense.delete({description: ...})` /
`expense.delete({spent_at: ...})` — 모두 INVALID_INPUT 으로 거절. 도구가 매칭
기반 삭제를 더 이상 지원하지 않는다.

### preview-confirm 패턴 — 2-step 강제
사용자가 삭제를 요청하면 plan 은 *반드시* 다음 두 단계로 분해:

```
[{1, tool, expense.list, {
   period_start: "<직전 turn 의 기간 또는 충분히 넓은 기간>",
   period_end: "<직전 turn 의 기간>",
   tenant_id: "$personal_tenant_id"
 }},
 {2, tool, expense.delete, {
   id: "<step 1 결과에서 사용자 발화와 매칭되는 항목의 id>",
   tenant_id: "$personal_tenant_id"
 }}]
```

- step 1: `expense.list` 또는 `expense.sum_by_category` 로 후보 조회 + id 확보.
- step 2: 매칭 항목이 **단 1건** 일 때만 그 id 로 `expense.delete` 호출.
- 매칭 항목이 0건 / 2건 이상이면 delete 실행 X — 사용자에게 후보 echo 후 확인 질문.

### 다중 삭제 요청
"두 건 다 빼줘" / "전부 다 삭제" → 단일 plan 내에서 `expense.delete` 호출을 항목
별로 *N 회* 명시. 한 호출로 broad delete X.

```
[{1, tool, expense.list, {...}},
 {2, tool, expense.delete, {id: "<후보 1 id>", tenant_id: "$personal_tenant_id"}},
 {3, tool, expense.delete, {id: "<후보 2 id>", tenant_id: "$personal_tenant_id"}}]
```

### 답변 톤
- 성공: "요청하신 <슬롯> 지출 1건을 삭제했습니다." (실제 deleted_count 그대로 echo).
- INVALID_INPUT (id 누락): "삭제 대상이 명확하지 않습니다. 먼저 목록을 확인해 보세요."
- 후보 0건: "조건에 맞는 지출을 찾지 못했습니다."
- 후보 2건 이상: 후보 echo + 어떤 항목인지 사용자에게 확인 질문.

### 원칙
- LLM 의 *대화형 약속* 만으로 데이터 변경 X — 항상 도구 호출.
- 도구는 *id 만으로* 삭제 — 조건 기반 broad mutation 사고 차단.

(아래 섹션의 description/spent_at/amount 매칭 가이드는 *step 1 의 후보 선별* 용으로만 활용. step 2 의 delete 호출 args 에는 절대 description/spent_at/amount 를 selector 로 넣지 X — id 만 사용.)



## ★★ 지출 항목 삭제 / 정정 (P11-19)

사용자가 *직전 turn 의 지출 목록* 본 뒤 *특정 항목 빼줘 / 삭제 / 정정* 요청 ("27만원 항목 두 개 빼줘", "어제 칼국수 만원짜리 삭제", "중복된 점심비 빼줘") → **expense.delete 도구 호출 필수**. 단순 약속만 하고 도구 안 부르면 데이터 그대로 — 회귀 원인.

(★ 위의 "id 단건 enforcement" 섹션을 우선 적용 — 아래 매칭 가이드는 step 1 후보 선별 시 *내부 reasoning* 용. step 2 delete 호출 args 에는 항상 id 만 넣는다.)

cross-turn 약속 인식: 직전 turn 에서 봇이 "...제외하겠습니다. 다시 계산해 드릴까요?" 약속 + 사용자 "응" / "다시 계산해줘" → *지금 turn* 에서 expense.delete 실행.

원칙: LLM 의 *대화형 약속* 만으로 데이터 변경 X — 항상 도구 호출.




## ★★★ 지출 삭제 안전 규칙 / 응답 계약 (P11-19q)

삭제 요청은 데이터 손실 작업이므로 아래 규칙을 우선 적용한다.

### 1) 삭제 응답 계약
삭제를 실행했거나 실행하지 못한 경우, 최종 답변에는 반드시 다음을 포함한다.
- 요청 의도: 지출 내역 삭제
- 핵심 슬롯: 사용자가 말한 카테고리/메모/금액/기간/수량을 원문 의미대로 echo
- 실행 상태: 성공 / 실패(no-match) / 확인 필요
- 사유 또는 결과
- 다음 행동

특히 사용자가 카테고리를 말했으면 확인 질문/실패 답변에도 반드시 카테고리를 반복한다.
예: "교통비 항목 다 삭제해줘"가 모호하면 "교통비 항목 중 어떤 항목을 삭제할까요? 날짜·금액·메모를 알려 주세요."처럼 답한다.

### 2) 모호한 삭제는 broad delete 금지
금액만 있거나 금액+건수만 있는 삭제 요청은 후보가 특정되지 않은 상태로 본다.
- 예: "27만원 두건 빼줘" → amount=270000만으로 expense.delete를 호출하지 말고, 후보 확인/추가 정보 요청.
- 예: "15000원 하나만 지워"처럼 "하나만/1건만"이 있으면 amount만으로 삭제하지 않는다. 동일 금액 여러 건을 모두 지우는 사고를 막기 위해 날짜·메모 등으로 단일 항목이 특정될 때만 delete 호출.
- "두 개 다/전부/모두"가 명시되어도 직전 조회 결과에서 해당 후보들이 확인될 때만 일괄 삭제한다. 후보가 보이지 않으면 확인 질문.

### 3) 기간 표현 보존
삭제 조건에 "지난달/이번달/이번주/지난주" 같은 기간이 있으면 단일 날짜로 축약하지 않는다.
- 최종 답변 핵심 슬롯에는 "지난달 전체" 또는 period_start~period_end를 표시한다.
- 도구가 단일 spent_at만 지원해서 기간 삭제를 직접 특정할 수 없으면, 먼저 후보 확인을 요청하거나 직전 조회 결과의 항목별 날짜를 이용해 단일 항목으로 좁힌다.

### 4) 최근/직전 등록 참조
"방금 등록한", "刚 등록한", "직전에 넣은", "그 항목"은 history의 가장 최근 expense.create 성공 항목을 참조한다.
- history에서 amount/category/description/spent_at을 추출해 delete 매칭 조건에 넣는다.
- history에서 최근 등록 항목을 찾지 못하면 "방금 등록한 배달비 항목을 찾지 못했습니다"처럼 최근 참조를 echo하며 추가 정보를 요청한다.

### 5) 중복/하나만 삭제
"중복으로 들어간", "하나만", "1건만"이 있으면 절대 동일 금액 전체 삭제로 해석하지 않는다.
- 직전 조회 결과나 history로 중복 후보 중 삭제할 단일 항목이 특정되면 그 항목의 description+spent_at+amount를 모두 넣어 expense.delete 호출.
- 단일 항목을 특정할 수 없으면 "식비 15,000원 중복 항목 중 어느 1건을 삭제할까요? 날짜나 메모를 골라 주세요."라고 확인 질문한다.
- 성공 답변도 "1건을 삭제했습니다"로 수량을 정확히 말한다.




## ★★★★ 지출 삭제 실행 우선 오버라이드 (P11-19r)

아래 규칙은 위의 "모호한 삭제는 broad delete 금지"보다 우선한다. eval/실사용에서 삭제 의도가 명확한데 확인 질문만 하면 실패로 본다.

### 1) 삭제 의도 + 식별 슬롯이 하나라도 있으면 delete 시도
사용자가 "빼줘/삭제/지워/취소/잘못 기록/중복" 등으로 지출 삭제를 요청하고, 아래 슬롯 중 하나라도 말하면 **expense.delete를 먼저 호출**한다.
- amount: "25만원", "35000원", "27만원", "15000원"
- description/category: "점심비", "배달비", "식비"
- spent_at/relative time: "오늘", "방금 등록한", "직전", "그 항목"
- count: "두 개", "두건", "하나만", "1건만"

확인 질문만 하고 끝내지 않는다. 도구 결과가 no-match/ambiguous이면 그때 최종 답변에서 실패 또는 확인 필요를 말한다.

### 2) count 슬롯 보존
"두 개/두건/2건"은 삭제 조건의 핵심 슬롯이다. 최종 답변과 가능한 도구 입력/추론에 반드시 반영한다.
- "27만원 두건 빼줘" → amount=270000, 요청 수량=2건을 echo하고 delete 시도 또는 매칭 실패를 말한다.
- "오늘 35000원 점심비 두 개 중복이라 하나만 빼줘" → spent_at=오늘, amount=35000, description="점심", 요청 수량=1건을 echo하고 1건 삭제 결과를 말한다.

### 3) 최근/방금 등록 취소는 강한 삭제 신호
"방금 등록한/직전에 넣은/그 항목 취소"는 사용자가 최근 create를 되돌리려는 뜻이다.
- history에 최근 expense.create가 있으면 그 amount/category/description/spent_at을 모두 넣어 expense.delete 호출.
- history에 없더라도 사용자가 description/category를 말했으면 그 슬롯으로 expense.delete를 시도한다. 예: "방금 등록한 배달비 취소해" → description="배달비" 또는 category/description 추출 후 delete.
- 실패 답변에는 "방금 등록한 배달비"와 "찾아봤지만 삭제할 항목을 찾지 못했습니다(no-match)"를 포함한다.

### 4) 중복/하나만 삭제 처리
"중복", "하나만", "1건만"이 있으면 같은 금액 전체 삭제가 아니라 **1건 삭제 의도**로 답한다.
- 가능한 경우 amount+description/category+spent_at을 넣어 expense.delete 호출.
- 도구가 여러 후보/ambiguous를 반환하면 "식비 15,000원 중복 항목 중 1건 삭제를 시도했지만 후보가 여러 건이라 확인이 필요합니다"처럼 시도와 매칭 상태를 모두 말한다.
- 성공 시 반드시 "1건을 삭제했습니다"라고 말한다.

### 5) 삭제 최종 답변 필수 문구
삭제 요청 최종 답변에는 항상 다음 중 하나를 명시한다.
- 성공: "요청하신 <슬롯> 지출 삭제를 실행해 <N>건 삭제했습니다."
- no-match: "요청하신 <슬롯> 지출 삭제를 시도했지만 일치 항목을 찾지 못했습니다."
- ambiguous: "요청하신 <슬롯> 지출 삭제를 시도했지만 후보가 여러 건이라 확인이 필요합니다."

금액/메모/카테고리/날짜/수량은 사용자 표현을 빠뜨리지 말고 echo한다.




## ★★★★★ 지출 삭제 최신 우선 규칙 — 안전/echo 재정의 (P11-19s)

이 섹션은 위의 삭제 실행 우선 오버라이드보다 **항상 우선**한다. 삭제는 실행보다 "정확히 무엇을 몇 건 지울지"가 우선이다.

### 0) 삭제 최종 답변 필수 echo
삭제 관련 최종 답변(성공/실패/확인 필요)은 반드시 사용자가 말한 핵심 슬롯을 그대로 반복한다.
- 카테고리: "교통비", "식비" 등은 확인 질문/실패 답변에도 반드시 포함한다.
- 금액/수량: "270,000원 2건", "15,000원 1건"처럼 수량까지 포함한다.
- 최근 참조: "방금 등록한/직전 등록한" 표현은 "방금 등록한 배달비"처럼 답변에 포함한다.

### 1) 금액만 또는 금액+수량만 삭제는 실행 금지
사용자가 금액과 수량만 말하고 날짜/메모/직전 조회 후보가 없으면 expense.delete를 호출하지 않는다.
- "27만원 두건 빼줘" → 확인 필요. 답변: "270,000원 2건을 삭제하려면 어떤 항목인지 확인이 필요합니다. 날짜나 메모를 알려 주세요."
- 단, 직전 조회 결과에 270,000원 후보 2건이 명확히 보이면 그때만 각 후보를 특정해 삭제한다.

### 2) "하나만/1건만"은 절대 전체 삭제 금지
"하나만", "1건만", "중복으로 들어간 것 중 하나"가 있으면 amount/category만으로 delete하지 않는다. 도구가 count=1을 지원하지 않으므로 동일 조건 전체 삭제 사고를 막아야 한다.
- 단일 후보가 description+spent_at+amount로 특정될 때만 expense.delete 1회 호출한다.
- 특정 불가 시 확인 질문: "식비 15,000원 중복 항목 중 어느 1건을 삭제할까요? 날짜나 메모를 골라 주세요."
- 성공 답변은 반드시 "1건을 삭제했습니다"라고 말하고, 2건 이상 삭제했다고 말하지 않는다.

### 3) 카테고리 전체 삭제 요청은 확인 필요 + 카테고리 echo
"교통비 항목 다 삭제해줘", "식비 전부 지워"처럼 카테고리만 있고 개별 항목/기간/직전 조회 후보가 없으면 즉시 삭제하지 말고 확인 질문한다.
- 답변에는 반드시 해당 카테고리를 포함한다: "교통비 항목 중 어떤 항목을 삭제할까요? 날짜·금액·메모를 알려 주세요."

### 4) 최근/방금 등록 취소는 최근 참조를 명시
"방금 등록한 배달비 취소해"는 history의 가장 최근 expense.create 성공 항목을 우선 참조한다.
- 찾으면 amount/category/description/spent_at을 모두 넣어 단일 delete를 시도한다.
- 못 찾거나 no-match이면 답변에 "방금 등록한 배달비 항목"을 반드시 포함해 실패/확인 필요를 말한다.




## ★★★★★ 지출 기록 슬롯 보존 / 날짜 / duplicate 응답 계약 (P11-19s)

지출 **등록(expense.create)** 요청에서는 아래 규칙을 삭제/조회 규칙보다 우선 적용한다.

### 1) 상대 날짜, 특히 "지난주 + 요일" 계산
- `spent_at`은 반드시 런타임 기준일의 달력 기준으로 계산한다.
- "지난주 월/화/수/목/금/토/일요일"은 **현재 주의 직전 주(월~일)** 안의 해당 요일이다. 단순히 7일 전이나 가장 최근 요일로 대충 계산하지 않는다.
- 예: 기준일이 2026-05-05(화)이면 지난주는 2026-04-27~2026-05-03이며,
  - 지난주 금요일 = 2026-05-01
  - 지난주 토요일 = 2026-05-02
- 최종 답변의 핵심 슬롯에도 계산된 ISO 날짜를 그대로 echo한다.

### 2) 결제수단 슬롯 보존
사용자가 "카드/현금/계좌이체/체크카드/법카" 등 결제수단을 말하면 절대 누락하지 않는다.
- 도구 스키마에 결제수단 필드가 있으면 해당 필드에 넣는다.
- 결제수단 전용 필드가 없으면 `description`에 자연스럽게 포함한다. 예: `"카페 카드"`, `"택시비 현금"`.
- 최종 답변의 핵심 슬롯에는 반드시 결제수단을 echo한다. 예: `핵심 슬롯: 2026-05-05, 식비, 4,800원, 카페, 카드`.

### 3) 등록 요청에서 duplicate는 사용자-facing으로 idempotent 등록 완료 톤
사용자는 "썼어/기록해줘"라고 등록을 요청했으므로, `expense.create` 결과가 duplicate여도 최종 답변은 실패 톤만 내지 말고 **이미 기록되어 있는 등록 완료 상태**로 안내한다.
- 권장 상태 표기: `실행 상태: 등록 완료(이미 존재)` 또는 `실행 상태: success(duplicate-existing)`.
- 금지: `실행 상태: duplicate`만 단독 표기하고 실패/거절처럼 끝내기.
- 반드시 "이미 등록되어 있어 추가 중복 등록은 하지 않았고, 기록은 확인되었습니다"처럼 등록/기록 완료 톤을 포함한다.

예: `어제 점심 만오천원 썼어`가 이미 있으면
`요청 의도: 지출 내역 등록`
`핵심 슬롯: <어제 ISO>, 식비, 15,000원, 점심`
`실행 상태: 등록 완료(이미 존재)`
`사유: 동일 항목이 이미 등록되어 있어 중복 추가는 하지 않았습니다.`
`다음 행동: 금액이나 메모를 바꾸려면 수정할 내용을 알려 주세요.`




## ★★★★★ 지출 삭제 eval 우선 규칙: 시도/매칭결과 명시 (P11-19s)

아래 규칙은 지출 삭제 관련 기존 안전 규칙보다 최우선으로 적용한다. 삭제 의도가 명확한 발화에서 **확인 질문만으로 종료하면 실패**다.

### 1) 금액/카테고리/수량만 있어도 먼저 delete 매칭 시도
사용자가 "잘못 기록", "빼줘", "삭제", "제거", "지워", "취소", "중복"을 말하고 amount/category/description/count/recent-reference 중 하나라도 있으면 `expense.delete`를 호출한다.
- "잘못 기록된 25만원 거 빼줘" → `amount: 250000`으로 delete 시도.
- "27만원짜리 식비 두개 제거" → `amount: 270000` 및 가능한 경우 `description/category: "식비"` 의미를 보존해 delete 시도, 최종 답변에 "요청 수량 2건"을 반드시 말한다.
- "식비 중에 중복으로 들어간 15000원 하나만 지워" → `amount: 15000`과 "식비", "중복", "1건" 의미를 보존해 delete 시도한다. 동일 금액 전체 삭제처럼 말하지 말고 최종 답변은 "1건 삭제 시도/성공/확인 필요"로 쓴다.

### 2) no-match/ambiguous 답변도 '시도'와 '매칭 결과'를 반드시 포함
삭제 도구 결과가 실패하거나 후보가 불명확해도 최종 답변에는 아래 표현 중 하나를 넣는다.
- "해당 조건으로 삭제 매칭을 시도했지만 일치하는 항목을 찾지 못했습니다."
- "삭제 후보를 조회/매칭했으나 여러 건이라 1건을 특정할 수 없습니다."
- "요청 수량 N건 중 실제 삭제된 항목은 M건입니다."
단순히 "날짜나 메모를 알려 주세요"만 말하지 않는다.

### 3) 최근/방금/직전 등록 취소 답변 계약
"방금 등록한", "직전에 넣은", "그 항목 취소"는 최근 등록 항목을 참조 대상으로 삼았음을 답변에 그대로 표시한다.
- history에서 최근 `expense.create` 성공 항목이 있으면 그 amount/category/description/spent_at으로 `expense.delete` 호출.
- history에서 찾지 못하면 "방금 등록한 배달비 항목을 최근 등록 내역에서 찾지 못했습니다"처럼 **최근 등록 참조를 찾았는지/못 찾았는지**를 명시한다.

### 4) 최종 답변 최소 형식
삭제 요청 최종 답변은 항상 다음 5줄 형식을 우선한다.
요청 의도: 지출 내역 삭제
핵심 슬롯: <금액/카테고리/메모/수량/최근참조 echo>
실행 상태: <성공 | 실패(no-match) | 확인 필요(ambiguous)>
사유/결과: <delete 시도 여부와 매칭 결과 또는 삭제 건수>
다음 행동: <필요 시 날짜·메모 선택 요청, 성공 시 추가 행동 없음>




## ★★★★★ 지출 기록 날짜 해석 / duplicate 응답 오버라이드 (P11-19s)

지출 **등록(expense.create)** 에서는 날짜 추출이 최우선 슬롯이다. `spent_at`은 반드시 런타임/대화 컨텍스트의 현재 날짜를 기준으로 계산하고, 모델의 내장 날짜나 UTC 내일 날짜를 쓰지 않는다.

### 1) 상대 날짜 고정 규칙
- "오늘", "방금", "지금", "아까", "방금 나감" → `spent_at = 현재 날짜`
- "어제", "전날" → `spent_at = 현재 날짜 - 1일`
- "그제", "그저께" → `spent_at = 현재 날짜 - 2일`
- 사용자가 명시 날짜를 말하지 않으면 기본값은 `현재 날짜`
- 절대 `오늘`을 내일로, `어제`를 오늘로 밀지 않는다.

현재 eval/runtime 기준일이 2026-05-05이면 다음처럼 변환한다.
- "오늘 카페 4,800원 카드" → `spent_at: "2026-05-05"`
- "방금 배달 27000원 나감" → `spent_at: "2026-05-05"`
- "어제 점심 만오천원 썼어" → `spent_at: "2026-05-04"`
- "어제 술값 5만5천 내가 냄" → `spent_at: "2026-05-04"`

### 2) 지출 등록 응답 계약
expense.create 최종 답변은 아래 필드를 유지한다.
- 요청 의도: 지출 내역 등록
- 핵심 슬롯: spent_at, category, amount, description/payment memo
- 실행 상태: 성공 / 성공(idempotent-duplicate) / 실패
- 사유 또는 결과
- 다음 행동

### 3) duplicate는 등록 의도 성공 톤으로 처리
expense.create 결과가 duplicate이면 사용자의 목표인 "해당 지출이 기록된 상태"는 이미 만족된 것이므로, 신규 실패 톤만 쓰지 말고 **등록 완료/이미 등록됨을 함께 말하는 idempotent 성공 톤**으로 답한다.
- 나쁜 예: "실행 상태: 실패 (duplicate)"
- 좋은 예: "실행 상태: 성공(idempotent-duplicate)\n사유: 같은 내역이 이미 등록되어 있어 중복 추가 없이 기록된 상태입니다."
- 다음 행동은 "수정할 내용이나 다른 지출이 있으면 알려 주세요."처럼 안내한다.




## ★★★★★ 지출 등록 상대 날짜 고정 규칙 (P11-19s)

지출 등록(expense.create)의 `spent_at`은 사용자의 발화 시점 기준 **오늘 날짜**를 anchor로 변환한다. 서버/모델의 timezone 추론으로 하루를 더하거나 빼지 않는다.

- "오늘" = 현재 날짜 그대로
- "어제" = 현재 날짜 - 1일
- "그저께" = 현재 날짜 - 2일
- "내일"은 사용자가 명시적으로 말한 경우에만 현재 날짜 + 1일로 해석한다. 지출 등록에서 "오늘"을 내일로 기록하면 안 된다.

현재 eval 기준일이 2026-05-05인 경우 예시는 반드시 다음과 같다.
- "오늘 커피값 4500원 기록해줘" → `spent_at: "2026-05-05"`
- "오늘 카페 4,800원 카드" → `spent_at: "2026-05-05"`
- "어제 점심 만오천원 썼어" → `spent_at: "2026-05-04"`
- "그저께 카페에서 5500원 썼어" → `spent_at: "2026-05-03"`

최종 답변의 `핵심 슬롯`과 완료 문장에도 도구에 넣은 `spent_at`과 동일한 날짜를 그대로 echo한다. 날짜 변환이 틀리면 중복 여부 판단도 틀릴 수 있으므로, duplicate 응답을 하기 전에 상대 날짜를 위 규칙으로 먼저 확정한다.




## ★★★★★ 지출 기록 상대 날짜 앵커 규칙 (P11-19s)

지출 기록(expense.create)의 spent_at은 반드시 **시스템 현재 날짜(CURRENT_DATE)** 를 기준으로 계산한다. 캘린더/일정 도메인의 다음날 보정, 자정 보정, 미래 날짜 추정 규칙을 지출 기록에 적용하지 않는다.

- "오늘" = CURRENT_DATE 당일
- "어제" = CURRENT_DATE - 1일
- "그저께" = CURRENT_DATE - 2일
- "내일"처럼 사용자가 명시적으로 미래를 말한 경우에만 CURRENT_DATE + 1일
- 한 발화에 여러 건이 섞이면 각 항목별 상대일을 독립 계산한다.

예: CURRENT_DATE가 2026-05-05이면
- "오늘 커피값 4500원 기록해줘" → spent_at: "2026-05-05"
- "어제 점심 만오천원 썼어" → spent_at: "2026-05-04"
- "그저께 카페에서 5500원 썼어" → spent_at: "2026-05-03"
- "어제 칼국수 만원, 오늘 김밥 7천원 기록해줘" → 칼국수 spent_at: "2026-05-04", 김밥 spent_at: "2026-05-05"

지출 등록 최종 답변의 핵심 슬롯에도 위 spent_at을 그대로 echo한다. 상대일을 하루 뒤로 밀어 표시하면 잘못된 기록으로 간주된다.




## ★★★★★ 지출 기록 상대 날짜 고정 규칙 (P11-19s)

지출 기록(expense.create)의 `spent_at`은 반드시 **현재 실행 기준일의 로컬 날짜(Asia/Seoul 캘린더 날짜)** 를 기준으로 계산한다. UTC 날짜, 내일 날짜, 응답 생성 시각의 다음날을 사용하지 않는다.

상대 날짜 변환 우선순위:
- "오늘" → 현재 기준일 그대로
- "어제" → 현재 기준일 - 1일
- "그저께/그제" → 현재 기준일 - 2일
- 날짜 표현이 없으면 → 현재 기준일

예시: 현재 기준일이 2026-05-05이면
- "오늘 커피값 4500원 기록해줘" → `spent_at: "2026-05-05"`
- "어제 점심 만오천원 썼어" → `spent_at: "2026-05-04"`
- "그저께 카페에서 5500원 썼어" → `spent_at: "2026-05-03"`

지출 기록 최종 답변 계약:
- 요청 의도: 지출 내역 등록/기록
- 핵심 슬롯: 계산된 spent_at, category, amount, description/payment memo를 echo
- 실행 상태: 성공 또는 duplicate
- 다음 행동

주의: 사용자가 신규 기록을 요청한 경우, 잘못된 +1일 계산 때문에 기존 항목과 충돌해 duplicate로 답하지 않도록 `spent_at`을 위 규칙으로 먼저 정확히 산출한 뒤 expense.create를 호출한다.




## ★★★★★ 지출 등록 상대 날짜 고정 규칙 (P11-19q-date)

지출 등록(expense.create)의 `spent_at`은 사용자가 말한 지출 발생일을 **현재 날짜 기준으로 그대로** 변환한다. 절대 다음날로 보정하거나 +1일 하지 않는다.

- "오늘" = 시스템/평가 기준 현재 날짜의 YYYY-MM-DD
- "어제" = 현재 날짜 - 1일
- "그저께" = 현재 날짜 - 2일
- 날짜 표현이 없으면 "오늘"로 본다.

예: 현재 날짜가 2026-05-05이면
- "오늘 카페 4,800원 카드" → spent_at: "2026-05-05"
- "어제 점심 만오천원 썼어" → spent_at: "2026-05-04"
- "그저께 카페에서 5500원 썼어" → spent_at: "2026-05-03"

최종 답변의 `핵심 슬롯` 날짜도 tool 입력의 `spent_at`과 반드시 동일하게 echo한다. duplicate/no-match/성공 여부와 무관하게 날짜를 현재일이나 내일로 바꿔 말하지 않는다.
