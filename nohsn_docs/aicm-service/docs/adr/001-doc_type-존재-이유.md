# doc_type 의 존재 이유

> 현재 doc_type 관련 코드는 **dead code** 상태이며, 실제 서비스에서 사용되지 않는다.
> 아래는 해당 코드가 왜 존재하게 되었고, 왜 남아 있는지에 대한 기록이다.

---

## 배경: 초기 요구사항

고객사의 초기 요구사항은 회사 내부의 **"지식문서"** 를 저장·관리·검색할 수 있는 서비스를 만들어 달라는 것이었다.

지식문서의 예시:

- 계약서
- 약관
- 상품 설명서
- 기타 사내 참고 문서 등

---

## 변경: 스크립트 매뉴얼 관리 요청

이후 고객사에서 지식문서 외에 **상담사용 스크립트 매뉴얼**도 함께 관리할 수 있는 기능을 추가해 달라는 요청이 들어왔다.

- 상담사가 상담 시 참고하는 스크립트성 매뉴얼
- 기존 지식문서와는 성격이 다른 유형의 문서

---

## 대응: doc_type 도입

지식문서와 스크립트 매뉴얼을 하나의 시스템에서 관리하되 **문서의 유형(타입)을 구분**해야 했다.

- 카테고리와는 별개로, 문서 자체의 **타입**을 나누어 관리하는 구조를 설계
- 이를 위해 `doc_type` 테이블 및 관련 CRUD 로직을 구현

> **카테고리 vs doc_type**
>
> - 카테고리: 문서의 분류 체계 (예: 보험 > 자동차보험 > 약관)
> - doc_type: 문서의 성격/유형 (예: 지식문서, 스크립트 매뉴얼)

---

## 철회: 고객사 요청으로 제거

구현 후 고객사에서 스크립트를 따로 관리하는 화면이 **복잡하게 보인다**는 피드백을 주었고, 결국 doc_type 구분 기능을 제거하기로 결정했다.

---

## 현재 상태

- `doc_type` 관련 테이블과 로직은 **전혀 사용되고 있지 않다** (dead code)
- 하지만 코드가 여러 레이어에 걸쳐 깊이 관여되어 있어, 완전히 걷어내기 어려운 상태로 남아 있다
- 향후 리팩토링 시 정리 대상

---

## 향후 고려: 상담사 매뉴얼 기능 재도입 시

> 현재 상담사 스크립트 매뉴얼 관리 기능은 제거된 상태이나,
> 추후 해당 기능이 다시 도입될 경우 아래 사항들을 반드시 고려해야 한다.

### 1. 지식문서와 매뉴얼의 검색 방식 차이

지식문서는 **고객 발화의 의도(intent)** 를 기반으로 검색된다.
즉, 고객이 어떤 멘트를 했을 때 그 의도를 캐치하여 관련 문서를 찾아주는 구조이다.

반면 상담사 매뉴얼은 이와 **성격이 다르다.**

- 지식문서: "고객이 이렇게 말했을 때 → 이 문서를 찾아라" (발화 의도 매칭)
- 매뉴얼: "이 상황/유형일 때 → 이 절차를 따라라" (상황·유형 기반 조회)

> 동일한 검색 파이프라인으로 처리하면 매뉴얼 검색 품질이 떨어질 수 있다.

### 2. 매뉴얼은 상황 인지 및 상담 유형 기반 조회가 필요

상담사 매뉴얼은 단순 키워드 매칭이 아니라, **현재 상담 상황**이나 **상담 유형(카테고리)** 에 따라 조회되어야 한다.

- 상담 유형 예시: 해지, 변경, 신규 가입, 클레임 등
- 상황 예시: 고객이 화가 난 상태, 이관이 필요한 상태 등

따라서 매뉴얼 검색은 다음 조건들을 복합적으로 활용해야 한다:

| 조건 | 설명 |
|------|------|
| 상담 유형 | 현재 상담이 어떤 유형인지에 따라 필터링 |
| 상황 컨텍스트 | 상담 흐름에서 현재 어떤 단계/상황인지 |
| 키워드 | 보조적 검색 수단 |

### 3. NLP 학습을 별도로 분리해야 함

지식문서와 매뉴얼은 검색 목적과 방식이 다르기 때문에, **NLP 학습(임베딩, 모델 파인튜닝 등)도 분리**해서 진행해야 한다.

- **지식문서 학습**: 고객 발화 패턴 → 문서 매핑 (의도 분류 중심)
- **매뉴얼 학습**: 상담 유형·상황 → 절차/스크립트 매핑 (컨텍스트 분류 중심)

같은 모델/파이프라인으로 학습시키면 두 도메인의 특성이 섞여 **양쪽 모두 검색 정확도가 저하**될 수 있다.

### 요약

| 항목 | 지식문서 | 상담사 매뉴얼 |
|------|----------|---------------|
| 검색 트리거 | 고객 발화 의도 | 상담 유형·상황 |
| 검색 방식 | 의도 매칭 (intent-based) | 유형·상황 필터 + 컨텍스트 매칭 |
| NLP 학습 | 발화 패턴 → 문서 매핑 | 상담 유형·상황 → 절차 매핑 |
| 학습 파이프라인 | 별도 분리 필요 | 별도 분리 필요 |

> `doc_type` 구분이 제거된 현재 구조에서 매뉴얼을 다시 도입하려면,
> 단순히 doc_type을 복원하는 것만으로는 부족하며 **검색·학습 파이프라인 자체를 이원화**하는 설계가 필요하다.
