# 어드바이저 이중화(HA) — 프론트엔드 영역 (아키텍처 작도용)

> 이중화 구성도를 그릴 때 **프론트엔드 구간에 무엇을 표기해야 하는지** 정리한 문서.
> 기준 코드: `asst-web-portal` (2026-07-28)

---

## 1. 구성도

```
┌─────────────────────────────────────────────────────────────────────┐
│  브라우저 (상담사 / 관리자)                                            │
│                                                                     │
│   ① 정적 자원 (HTML/JS chunk)          ② WebSocket (socket.io)       │
└───────────┬─────────────────────────────────────┬───────────────────┘
            │                                     │
            ▼                                     ▼
    ┌───────────────┐                     ┌───────────────┐
    │      LB       │                     │      LB       │
    │               │                     │ sticky 필요 ★ │
    └───┬───────┬───┘                     └───┬───────┬───┘
        │       │                             │       │
     active  standby                       active  standby
        ▼       ▼                             ▼       ▼
  ┌──────────────────┐                 ┌──────────────────┐
  │  프론트 웹서버     │                 │  게이트웨이/백엔드  │
  │  (정적 배포)      │                 │  (asst-service)   │
  │                  │                 │                  │
  │ ★ 양쪽 빌드 동일   │                 │  socket.io 서버   │
  │   또는 이전 chunk │                 └────────┬─────────┘
  │   보존            │                          │
  └──────────────────┘                          ▼
                                          ┌───────────┐
                                          │   Redis   │
                                          │  pub/sub  │
                                          └───────────┘

★ = 인프라에 요구되는 조건 (3절)
```

**두 경로를 분리해서 그릴 것.** ①은 배포 산출물 문제, ②는 세션·룸 문제로 성격이 완전히 다르다.

## 2. 전환 시 동작

```
 [active 다운]
      │
      ▼
 socket disconnect
      │
      ▼
 자동 재연결  ── 1s → 5s 백오프, 무한 재시도
      │           (reconnectionAttempts: Infinity)
      ▼
 [standby 연결]  connect 이벤트
      │
      ▼
 룸 재조인      ── 클라이언트가 joinRoom 재emit
      │           룸 이름 고정 → 새 세션도 같은 룸 복귀
      ▼
 실시간 수신 재개
```

### 룸 이름 (고정 문자열)
```
{CHANNEL_ENV}:{tenantId}:{receiver_key}:coaching
{CHANNEL_ENV}:{tenantId}:{receiver_key}:coaching_request
```

### 손실 범위

| | 전환 중 | 전환 후 |
|---|---|---|
| 실시간 토스트 | ❌ 유실 | ✅ 정상 |
| 코칭 데이터 | ✅ 보존 (목록 API + 미확인 배지로 복구) | ✅ |

**유실되는 것은 "알림 팝업" 뿐이고 데이터는 사라지지 않는다.**

---

## 3. 인프라 요구사항 (그림에 표기할 것)

| # | 위치 | 요구 | 미충족 시 |
|---|---|---|---|
| 1 | 소켓 LB | **세션 어피니티(sticky)** | polling 폴백 시 핸드셰이크 실패 |
| 2 | 백엔드 | active-**active** 라면 **socket.io Redis 어댑터** | 다른 파드 소켓에 emit 미전달<br>(active/**standby** = 동시 1개면 불필요) |
| 3 | 백엔드 | standby 가 **Redis 구독 요청 수용** 가능 | 채팅(VOC/NLP) 실시간 사망 |
| 4 | 프론트 웹서버 | **양쪽 빌드 동일** 또는 이전 chunk 보존 | 전환 직후 `ChunkLoadError` |
| 5 | 인증 | 쿠키가 전환 후에도 유효 | 재연결 핸드셰이크 실패 |

---

## 4. 프론트엔드가 이미 보장하는 것

| 항목 | 값 / 동작 |
|---|---|
| 재연결 | 무한 재시도 (1s → 5s 백오프, timeout 20s) |
| 룸 재조인 | `connect` 이벤트마다 재실행 (`once` 아님) |
| 재조인 대상 | `agent-status`, agent event, `coaching`, `coaching_request`, 채팅 채널 |
| 채팅 채널 | 재연결 시 **HTTP 구독 API 재호출 → 룸 재조인** 순서 보장 |
| 중복 이벤트 | dedupe 적용 (TTL 5분) → `realtime-event-dedupe-guide.md` |

> **룸 멤버십은 소켓 id 기준이라 서버가 복구해주지 않는다. 재조인은 클라이언트 책임**(백엔드 확인 완료).
> `connectionStateRecovery` 는 **같은 인스턴스 복귀 시에만** 유효 → 전환에선 무용.

---

## 5. 전환 테스트 체크리스트

```
[socket-IO-Plugin] reconnect OK after n tries
[ADMIN] 코칭요청 룸 직접 참가: {채널}      ← 이게 다시 떠야 정상
[chat-sub] 채널 구독 및 룸 참가 완료: ...   ← 채팅은 여기까지
```

- [ ] `reconnect OK` 이후 **룸 참가 로그가 다시 뜨는가**
- [ ] 실제 코칭을 보내 **토스트가 오는가** (로그만으로 판단 금지)
- [ ] 채팅 VOC/NLP 실시간 생존 (가장 먼저 죽는 지점)
- [ ] 페이지 이동 시 `ChunkLoadError` 없는가
- [ ] 끊긴 동안 온 코칭이 목록·배지에 반영되는가

---

## 부록. 알려진 흠 (당장 문제 아님)

- 코칭 재조인 핸들러가 익명 함수라 `off` 불가 → 화면 재진입마다 누적, 재연결 시 join 중복 emit (서버 멱등이면 무해)
- `socketStore` 는 재조인 없음 — 단 해당 경로는 **현재 호출부 없는 죽은 코드**
