# 어드바이저 — callbot-dev ↔ timbel(5090) aicm 연동 구성

## ★ 담당자 검토 요청에 대한 답변

**Q. callbot-dev 어드바이저가 timbel aicm에 검색 요청할 때 x-token 없이 요청하면 되나?**

**A. 네, x-token 없이가 맞습니다. 오히려 넣으면 안 됩니다.**
- 검색(rag_assist)은 **무인증 소비자 모델** — PermissionEnforcer(권한 게이트)를 안 씁니다. 토큰은 "테넌트 해석용"일 뿐 권한 필터가 아닙니다.
- callbot 어드바이저의 토큰은 **포털(callbot) realm**이라, timbel에 넣으면 timbel이 그 토큰으로 **테넌트를 오해석/거부**합니다. 그래서 **x-token 없이 + 대상 workspace_id/repository_id** 로 보내야 합니다.

**단, x-token은 실은 쟁점이 아닙니다. 실검색이 안 되는 진짜 원인은 따로 있습니다:**
- 현재 어드바이저 설정 `SEARCH_REPOSITORY_ID = 00000000-...-001` 은 timbel의 **"Test Repository"(빈 저장소)** 입니다 → **대상 실저장소 id로 교체**해야 실지식이 검색됩니다(§2 표, 예: 한국투자증권 = `15d3e9fe-...`).

**전달받은 내용 중 정정 2건:**
1. "산돌3층(callbot-dev) user-service **미연동**" → 부정확. callbot aicm은 **포털 user-service(portal-service:32021)와 연동**돼 있습니다. 다만 **CE가 없어 워크스페이스 열거만 불가**합니다.
2. "x-token 포함 → user-service 인증 후 처리" → 어드바이저 검색(rag_assist)엔 **부정확**. 검색은 권한 인증을 안 하고 토큰을 **테넌트 해석에만** 씁니다. (권한까지 검증하는 건 웹 문서목록/`get_doc_list` 경로)

상세 근거·구성·향후안은 아래 §1~§6 참조.

## 2. 현재 어드바이저 동작 방식 (as-is)

**timbel aicm 접점이 두 경로다. 둘 다 timbel aicm-service:32012로 프록시된다.**

| 경로 | 소비자 | 대상 | 설정 위치 |
|---|---|---|---|
| **① 백엔드**(asst-service) | 어드바이저 RAG 답변 생성 | **timbel :8173**(직접, 서버-투-서버) | asst-service env `AICM_HOST` |
| **② 프론트/브라우저** | 포털 임베드 화면의 aicm 호출 | 포털 → **게이트 :32099** → `/aicc/aicm-service` → **timbel :8174** | `~/projects/gateway/config/upstreams.dev.yaml` |

- timbel aicm-web nginx: **:8173 = port80(web+API)**, **:8174 = port81(포털+API)** — 둘 다 내부적으로 `/api/aicm` → aicm-service:32012 프록시.

### ① 백엔드 asst-service 실측 설정
```
AICM_HOST            = http://124.194.32.36:8173     # timbel aicm 내부 포트 직접
SEARCH_REPOSITORY_ID = 00000000-0000-0000-0000-000000000001
```
- 워크스페이스 리스트/CE 조회 **없이**, env에 박힌 **timbel aicm 주소 + 고정 저장소 id**로 서버-투-서버 검색.

### ② 게이트(browser) 경로 설정 (upstreams.dev.yaml)
```yaml
# routes.yaml:  path /aicc/aicm-service → service aicm-service, prefixPath /api/aicm/v1
# upstreams.dev.yaml:
aicm-service: http://124.194.32.36:8174   # ❌ 원격 kms-service(timbel) — 로컬 aicm-service 별칭과 다른 백엔드
```
- 게이트(:32099)는 **cookie-jwt 정책이나 현재 Phase1(policy 기록만, 미강제)**. 브라우저가 크로스오리진으로 aicm을 호출할 때 이 라우트를 탄다.

- 검색 엔드포인트(aicm)는 무인증 소비자 모델이라 **x-token 없이** 처리된다(아래 §4).

### ⚠️ 현재 설정 이슈 (반드시 확인)
`SEARCH_REPOSITORY_ID = 00000000-...-001` 은 timbel KMS에서 **"Test Repository"(테스트/기본 저장소, 카테고리 0)** 다. **실데이터 저장소가 아니다.** → 어드바이저가 실지식을 검색하려면 대상 실저장소 id로 교체해야 한다.

### callbot 자체 워크스페이스 ≠ 어드바이저 검색 대상 (혼동 주의)
callbot-dev가 **자체적으로 만든 워크스페이스는 1개뿐**이고, 이는 **어드바이저 검색 대상이 아니다.** 테넌트로 구분된다:

| | callbot이 만든 것 | 어드바이저 검색 대상 |
|---|---|---|
| 테넌트 | **AICM Portal `7717946f`** (포털 완전격리) | **Lucas-KMS Default `00000000-...-001`** (공유) |
| 저장소 | **1개** (callbot 포털 임베드/E2E 데이터, `aicm_portal_*`) | **여러 개** (한투/다이소/대신/ECS = 실지식, §2 표) |
| 용도 | callbot 자체 포털 검증용 | 실제 상담 지식 |

- callbot의 1개 워크스페이스는 **포털 격리 테넌트(7717946f)** 소속 = callbot 자체 테스트 데이터. **어드바이저가 검색할 실지식이 아니다.**
- 어드바이저는 **timbel 공유 테넌트(Lucas-KMS Default, `00000000-...-001`)의 워크스페이스/저장소**를 대상으로 지정해야 한다.
- 따라서 to-be(:32073)에서 callbot `workspace_rag_config`에 넣을 매핑은 **callbot 자기 워크스페이스(7717946f)가 아니라, timbel 공유 테넌트를 가리키는 새 매핑**이다. (테넌트 경계를 넘어 공유 데이터를 참조하는 구성)

## 3. 부트스트랩 체인 (왜 timbel인가)
```
워크스페이스 리스트   ← CE(테넌트 스코프). callbot-dev는 CE 없어 불가 → timbel CE 필요
   → workspace_id
      → 저장소/카테고리/검색   ← workspace_id 만으로 무토큰 동작(테넌트는 workspace_rag_config에서 해석)
```
- **CE/테넌트가 꼭 필요한 건 "워크스페이스 리스트" 단계뿐**이다. 그 아래(저장소·카테고리·검색)는 **workspace_id만 있으면** tenant_id·x-token 없이 동작한다.
- 어드바이저는 대상 워크스페이스/저장소를 **미리 알고 설정**(현재는 SEARCH_REPOSITORY_ID)하므로 워크스페이스 리스트 자체는 건너뛴다.

## 4. API 인증 규칙 (검증 결과)

| API | 테넌트 해석 출처 | x-token |
|---|---|---|
| **검색(rag_assist / internal_search)** | body의 `workspace_id`(없으면), 있으면 토큰 | **불필요**. 무인증 소비자(권한 enforce 안 함). 토큰은 "테넌트 해석용"일 뿐 |
| 저장소·카테고리 조회 | `workspace_rag_config.tenant_id`(workspace_id로) | **불필요**(초기화된 워크스페이스면 토큰 무시) |
| 문서 목록(get_doc_list) | user-service(token)로 요청자 권한 해석 | **필요**(웹 전용, 권한 게이트) |

**cross-realm 주의**: callbot-dev가 가진 토큰은 **포털(callbot) realm**이다. 이걸 timbel aicm에 넣으면 timbel이 그 토큰으로 **테넌트를 오해석/거부**한다. 그러므로 어드바이저는 **x-token 없이 + 대상 workspace_id(또는 저장소 id)** 로 요청해야 한다.

## 5. 향후 구성 (to-be): callbot-dev :32073 경유

**조건: callbot-dev에 테넌트 id(UUID)와 워크스페이스 id가 정리되면**, 어드바이저 `AICM_HOST`를 **`http://106.242.165.142:32073`(callbot-dev 자체 aicm)** 로 바꿔 동작 가능하다.

동작 흐름:
```
어드바이저 → callbot-dev aicm(:32073 nginx → aicm-service:32012)
            → (workspace_rag_config로 tenant·repo 해석)
            → timbel KMS(:32020) 검색
```

필요한 정리(전제):
1. **`workspace_rag_config` 매핑 등록 (핵심)**: callbot-dev의 `workspace_rag_config`에 **(workspace_id → tenant_id + repository_id)** 를 넣는다. 어드바이저 검색 경로는 이 config에서 tenant·repo를 해석하므로, 대상값을 timbel KMS 실제값으로 넣어야 한다.
   - 예(한국투자증권): `workspace_id=019eca26-837d-77b8-bd77-d90f97d6defc`, **`tenant_id=00000000-0000-0000-0000-000000000001`**(Lucas-KMS Default), `repository_id=15d3e9fe-c6d8-4a42-bbd2-2aeffccf74bb`.
2. **테넌트 값 주의(2종 구분)**:
   - **검색용 테넌트 = `workspace_rag_config.tenant_id`** = 대상 저장소 소유 KMS 테넌트(위 예 `00000000-...-001`). 어드바이저 검색은 이것만 쓴다. KMS RLS가 `::uuid` 캐스트하므로 반드시 유효 UUID.
   - user-service의 테넌트(`aicc`)는 **문서목록(get_doc_list)의 권한 판정**에만 쓰이며 어드바이저 검색과 무관하다. (이걸 UUID로 바꾸는 건 별개 이슈)
   - ⚠️ 실데이터(한투/다이소/대신/ECS)는 **공유 테넌트 Lucas-KMS Default(`00000000-...-001`)** 소속이다. 포털 격리 전용 테넌트(`7717946f`, 저장소 1개)와 **다르다** — 어드바이저는 격리 테넌트가 아니라 공유 테넌트 데이터를 검색한다.
3. 위가 되면 어드바이저는 **callbot-dev :32073에 workspace_id만 넘겨(무토큰)** 검색 가능하다. (검색은 무인증 소비자라 x-token 불필요)

즉 **"tenant_id + workspace_id 정리 = callbot-dev workspace_rag_config에 timbel KMS 대상을 매핑"** 이며, 그러면 두 경로 모두 callbot 자체 경유로 통일된다:
- **① 백엔드**: asst-service `AICM_HOST` = `timbel:8173` → **`callbot:32073`(또는 aicm-service:32012)**
- **② 프론트/게이트**: `upstreams.dev.yaml` 의 `aicm-service: timbel:8174` → **`callbot aicm-service:32012`**(로컬 별칭)

(단 callbot aicm-service는 이미 `RAG_SERVICE_URL=timbel KMS:32020`라, 검색 데이터는 여전히 timbel KMS에서 온다. 바뀌는 건 "aicm 진입점"이 callbot 자체가 되는 것뿐이며, tenant·repo 해석을 callbot이 자기 workspace_rag_config로 하게 된다.)
