# 01. 프로젝트 분석

## 개요

**timbloRecApp** — 회의 오디오(마이크 + 시스템 사운드)를 동시 녹음하여
16kHz/mono/PCM16 로 믹싱하고, AES-256-CBC 로 3분 단위 세그먼트 암호화 저장 후
Timblo 서버로 업로드하는 Electron 데스크톱 앱.

주 목적: **Zoom/Teams/Discord 등 회의 앱의 소리 + 내 목소리를 함께 녹음 → STT 문서화**

> 참고: Windows C++ 헬퍼가 원조 엔진이고, macOS Swift 헬퍼가 나중에 추가된 구조입니다.
> (`docs/windows/DEVELOPMENT_STATUS.md` 의 P5 계획에 "macOS 지원 / 4-6주" 로 기재)

## 아키텍처 — 3계층 분리

```
┌────────────────────────────────────────────────────┐
│ Renderer  (Vanilla JS + HTML/CSS, 창 4개)           │
│  UI · 녹음 타이머 · 메모/태그 · 업로드 트리거         │
└──────────────── contextBridge (preload) ───────────┘
                          │ ipcRenderer.invoke / on
┌────────────────────────────────────────────────────┐
│ Electron Main  (Node.js)                           │
│  창/트레이 · SQLite · 업로드 · 딥링크 인증 · 로깅     │
└────────── child_process.spawn + JSON-line ─────────┘
                          │ stdin(명령) / stdout(이벤트)
┌────────────────────────────────────────────────────┐
│ Native AudioHelper  (별도 프로세스)                  │
│  오디오 캡처 · 믹싱 · 리샘플 · AEC · 암호화 · 세그먼트│
│   Windows : C++ .exe  (WASAPI Loopback)            │
│   macOS   : Swift .app (ScreenCaptureKit + AVAudio)│
└────────────────────────────────────────────────────┘
```

### 핵심 설계 결정

**오디오 엔진을 완전히 별도 프로세스로 분리**한 것이 이 프로젝트의 가장 중요한 구조적 특징입니다.

- 통신은 **JSON 한 줄 = 한 메시지** (stdin 명령 / stdout 이벤트, UTF-8)
- UI 프레임워크와 오디오 엔진이 완전히 독립 → 헬퍼 재사용 가능
- 헬퍼 크래시가 UI를 죽이지 않음
- 권한(마이크/화면녹화)을 헬퍼 프로세스에 격리

이 구조 덕분에 UI를 무엇으로 바꾸든(Electron/Flutter/Tauri) 오디오 엔진은 그대로 씁니다.
→ 자세한 함의는 [05-ReactNative-검토.md](05-ReactNative-검토.md)

## 오디오 파이프라인 (이 프로젝트의 핵심 자산)

설계 문서: `docs/recording_architecture_mac_windows_v3.md`
구현: `src/helpers/windows/AudioHelper.cpp` (3,828줄)

### 파라미터

| 항목 | 값 | 이유 |
|---|---|---|
| **마스터 클럭** | **마이크** (20ms 블록) | Windows 루프백은 무재생/뮤트 시 콜백이 끊김 → 타임라인 유실 방지 |
| 시스템 오디오 | 링버퍼 (목표 150ms) + 60ms 프라임 버퍼 | 지터/지연 흡수 |
| 드리프트 보정 | 게이팅 ASRC (±100ppm, ON≥40ms / OFF≤20ms) | 누적 위상 오차 방지 |
| 경계 처리 | 3~5ms 램프 | 클릭/틱 제거 |
| 내부 정규화 | 48kHz / float / mono | |
| **최종 출력** | **16kHz / mono / PCM16** | STT 최적 |
| 게인 | mic=1.0, sys=0.7 | |
| 세그먼트 | 3분 = 2,880,000 샘플 (약 5.76MB) | 샘플 기반이라 크기 일관 |
| 암호화 | AES-256-CBC (Windows BCrypt) | ON/OFF 토글 |
| 최대 녹음 | 3시간 (`TOTAL_RECORD_MS`) | 도달 시 자동 종료 + 업로드 여부 선택 팝업 |

### 캡처 모드 3종

| 모드 | 동작 |
|---|---|
| `MicOnly` | 마이크만. `out = mic * g_mic` |
| `MicPlusSystem` | 둘 다. `out = mic * g_mic + sys * g_sys` |
| `SystemOnly` (MicTimed) | 시스템만 저장하되 **마이크를 g_mic=0 으로 함께 열어 시계 공급** |

`SystemOnly` 에서도 마이크를 여는 이유가 중요합니다 — 시스템 오디오만으로는
무재생 구간에 타임라인이 끊기므로, 마이크를 무음 클럭으로 사용합니다.

### 안정성 기능 (모두 구현 완료)

- **장치 변경 감지** (`IMMNotificationClient`)
  - 시스템 출력 장치 변경 → **자동 재연결** (스피커↔이어폰 전환 시 녹음 안 끊김)
  - 마이크 제거/비활성 → **폴백 금지, 즉시 중단** + 그 시점까지 데이터 저장
- **디스크 잔량 모니터링** — `ok`(≥500MB) / `low`(≥50MB) / `critical`(<50MB)
  - 50MB 미만이면 다음 세그먼트 경계에서 안전 중지
- **무음 감지** — 초반 30초 관찰, 7초 간격 알림
- **레벨미터 / 파형 이벤트**, 음소거 제어

### 주요 이벤트 (Helper → UI)

```
helper_info      프로세스 기동 직후 (version, webrtc_aec 포함)
version_info     version 명령 응답
devices          장치 목록
level            RMS 레벨 (mic/system/mixed)
waveform         파형 데이터
progress         진행 시간/샘플 수
segment_ready    세그먼트 파일 저장 완료  ← 업로드 트리거의 시작점
disk_status      디스크 잔량 상태
device_reconnected / audio_device_change   장치 이벤트
silence          무음 감지
mute_state / level_meter_state / mic_state

```

`level` / `waveform` / `progress` 는 초당 다수 발생하므로
`audioHelperManager.js` 에서 로깅을 0.1% 샘플링합니다.

## 데이터 흐름 (녹음 → 업로드)

```
index.html              장치 선택 → 오디오 헬퍼 기동 → 녹음 시작
   ↓
recordingWindow         녹음 진행 (최대 3시간)
   │                    · 실시간 레벨미터 / 남은시간 바
   │                    · 메모(t_ms 타임싱크) · 태그(최대 10개) 입력
   │                    · 3분마다 segment_ready → recordings 테이블 upsert
   ↓ [완료]
summarizeWindow         언어 / 발화자 수 선택
   ↓
main.serverUpload()     폴더 내 전체 세그먼트 + manual{tag,memo} 를
   │                    multipart 로 POST
   │                    → popupWindow 에 진행률·속도·ETA 실시간 표시
   ├─ 성공 → 로컬 파일 삭제 + jobs 갱신 + 팝업 닫기
   └─ 실패 → jobs 에 남김 → uploadList 창에서 재시도
```

### 엔드포인트

| 용도 | URL |
|---|---|
| 토큰 교환 | `GET {endpoint}/api/auth/recorder/exchange/{code}` |
| 업로드 | `POST {endpoint}/api/contents/upload/encryption/files` |

`endpoint` 는 **딥링크의 `host` 파라미터(base64)로 주입**됩니다 (온프레미스 대응).
즉 로그인 전에는 빈 문자열입니다.

### 인증 (딥링크)

```
웹 → timbloRecApp://connect?code=<code>&host=<base64 endpoint>
   → requestSingleInstanceLock / second-instance / open-url 로 수신
   → host 디코딩 후 GET /api/auth/recorder/exchange/{code}
   → accessToken 획득 (메모리 변수 token)
   → renderer 로 auth-exchanged 브로드캐스트
```

### 크래시 복구

앱 시작 시 `recoveryService.scanAndAutoQueue()` 실행:
- `recordings` 에 있지만 `jobs` 가 없는 항목 스캔
- 파일 있으면 → 업로드 잡 자동 생성
- 파일 없으면 → 레코드 삭제

## 파일 저장 경로

| 항목 | Windows | macOS |
|---|---|---|
| 녹음 파일 | `%USERPROFILE%\Documents\timbloRecApp\recordings\{sessionId}\` | `/tmp/recordings/{sessionId}/` ⚠️ |
| DB | `%APPDATA%\timbloRecApp\app.db` | `~/Library/Application Support/timbloRecApp/app.db` |
| 로그 | `%APPDATA%\timbloRecApp\logs\` | `~/Library/Application Support/timbloRecApp/logs/` |

세그먼트 파일명: `{sessionId}_{n}.pcm` (암호화) 또는 `.raw` (평문)

> Windows 는 `Documents` 하위라 안전합니다. macOS 의 `/tmp` 는 04번 문서 참조.
