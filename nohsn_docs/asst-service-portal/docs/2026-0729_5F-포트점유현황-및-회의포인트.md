# B. 회의 제시 / 견제 포인트

## 견제 1 — 1차 안의 첫 대역부터 5F에선 안 맞음

포탈 대역 32000~32009에 이미 node 2개 + next-server가 점유 중.
**도커 밖에서 뜬 프로세스라 주인을 모름.** 무시하고 배정하면 포트 충돌로 기동 실패.

> 가장 강력한 카드. 대역 하나가 아니라 **1차 안의 첫 항목**이 깨진다는 것이 요점.

## 견제 2 — Asst 대역 실여유는 3개, 그것도 타 제품 때문

32020~29 중 **lucas-kms가 3개(32020/22/24)** 점유. 타 제품이라 우리가 비울 수 없음.
여유는 32023 / 32028 / 32029뿐.

> 이중화까지 보면 도메인당 10개도 빠듯한데 실제 가용은 3개.

## 견제 3 — 인프라 대역 부재로 CE 대역을 인프라가 사용 중

32010~32017을 postgres / redis / minio / nginx가 점유. 정작 ce-service는 32021(Asst 대역)에 있음.
**인프라 대역 신설 없이는 CE 대역 회수 불가.**

> 이중화 시 Redis Sentinel 3벌, PG standby 등으로 배증하므로 인프라 대역은 서비스 도메인보다 넉넉히 잡아야 함.

## 견제 4 — 콜(CTI) 대역이 1차 안에 없음

call-orchestrator(32035), call-bridge(32036)가 갈 곳이 없어 TA 대역에 편입된 상태.
HAIV STT/TTS와 연동되는 영역이라 독립 대역 검토 필요.

## 견제 5 — 5F에 이미 AICC 스택이 한 벌 존재

asst / ce / ta / qa / aicm이 이미 5F 가동 중.
3F 것과 **대체인지 공존인지** 먼저 정해야 필요 포트 수가 산출됨.

- 대체 → 신규 포트 거의 불필요
- 공존 → 도메인당 두 벌치 필요, Asst 여유 3개로는 불가

> **이 결정 없이 대역부터 그으면 숫자가 통째로 틀림.** 포트보다 선행되어야 할 결정.

## 견제 6 — 방화벽 개방 범위 확인이 선행

대역을 배정받아도 방화벽이 열려 있지 않으면 사용 불가.
현재 32020번대만 개방된 것으로 파악. 32xxx 중 실제 개방 범위 확인 필요.

## 선 그을 것 — 정리 주체

"5F 포트 정리"가 우리 업무가 되지 않도록.
**lucas-kms, HAIV는 타 제품**이므로 이동·정리 주체가 우리가 아님. 조사·정리 범위는 AICC 대역으로 한정.

## 유일하게 즉시 가능한 건 — AICM

32050~59가 완전히 비어 있고, 현재 AICM은 8173 / 8174 / 32012로 분산.
**1차 안 취지대로 지금 바로 모을 수 있는 유일한 건.** 타 부서 협조 없이 자체 진행 가능.

# E. 결론 — 서비스앱만 62000번대로 이관 (2026-07-29 회의 확정)

## 회의 결과

| 항목 | 결정 |
|---|---|
| 서비스앱 대역 | **62xxx 사용 확정** |
| 인프라 대역 | **현행 유지** (32010~32017 등 이동 없음) |
| 방화벽 개방 | **담당자가 신청** |
| 5F 기존 AICC 스택 | **제거**. 3F에서 이관해 온 것으로 **대체** (공존 아님) |

> 5F 기존 서비스를 제거하므로, 도메인당 두 벌치 포트는 불필요.
> 앞서 우려했던 "Asst 대역 여유 3개" 문제는 대역 자체가 62xxx로 바뀌면서 해소됨.

## 방침

- 5F는 이미 여러 제품이 32000번대를 나눠 쓰는 범용 서버 → **3F 대역을 그대로 가져올 수 없음**
- 5F의 32xxx를 재정리하는 것은 타 제품 협의가 필요해 현실성이 낮음 → **정리 대상이 아니라 회피 대상**
- **인프라(DB / Redis / MinIO)는 현 위치 유지.** 서비스앱이 빠지면 32xxx는 자연히 "인프라 + 타 제품" 영역으로 정리됨
- **3F 서비스앱만 62000번대로 통으로 이관**
- 인프라 이중화를 5F에서 진행하게 되면 그때 인프라 대역을 별도로 재조정

|---|---|---|
| 32000~09 | **62000~09** | 포탈 |
| 32010~19 | **62010~19** | 에이전트빌더(CE) |
| 32020~29 | **62020~29** | 상담어드바이저(Asst) |

- 담당자 1차 안의 **대역 구조를 그대로 유지** (규칙 변경이 아니라 "5F에선 앞자리만 6")
- 62000~62999 통으로 확보 시 여유 1000개 → 이중화·확장 여지

## 62000번대를 고른 근거 — ephemeral 포트 범위

5F 실측: `cat /proc/sys/net/ipv4/ip_local_port_range` → **32768  60999**

이 구간은 커널이 **아웃바운드 연결의 출발지 포트로 자동 할당**하는 범위다.
이 안에 고정 서비스 포트를 두면, 재기동 시점에 그 포트를 다른 프로세스가 임시로 점유하고 있을 경우
`bind()`가 `EADDRINUSE`로 실패해 **컨테이너가 간헐적으로 안 뜬다.**

| 구간 | 안전 여부 |
|---|---|
| 30000~32767 | 안전 (ephemeral 미만) — 단 32xxx 이미 혼잡 |
| 32768~60999 | **위험 (ephemeral)** |
| 61000~65535 | 안전 (ephemeral 초과) — **62000번대 여기** |

- 현재 AICC 32xxx는 최대 32046이라 안전
- TCP 포트 최댓값은 **65535**. 70000번대 등은 존재하지 않음

> 참고: HAIV의 40000번대는 이 구간 안에 있으나 현재 정상 운영 중이다.
> **타 스택 소관이므로 회의 안건으로 올리지 않는다.** 우리 대역 선정 근거로만 참고.

### 비개발자 대상 설명 (필요 시)

> 서버가 외부와 통신할 때 자동으로 쓰는 번호 구간(32768~60999)이 있습니다.
> 이 안에 서비스 포트를 잡으면 재기동 시 번호가 겹쳐 기동에 실패할 수 있어, 그 구간을 피해 62000번대로 잡았습니다.

# F. 임시 포트 구간(32768~60999)에 고정 포트를 두면 생기는 문제

> "ephemeral port" = **임시 포트 / 동적 포트**.
> 서버가 외부로 연결을 맺을 때 커널이 자동으로 골라 쓰고, 끝나면 반납하는 포트.
> 이 구간에 고정 서비스 포트를 두면 아래 문제가 발생할 수 있다.

## 증상

| # | 증상 | 설명 |
|---|---|---|
| 1 | **기동 실패** | `bind: address already in use` — 도커는 `docker-proxy`가 포트를 잡는데, 이미 다른 연결이 임시로 점유 중이면 컨테이너 생성 자체가 실패. compose 기동 시 해당 서비스만 죽고 나머지는 정상 기동 |
| 2 | **부분 장애** | 전체가 아니라 **1~2개만 실패**하므로 알아채지 못하고 지나감. 며칠 뒤 "특정 기능만 안 된다"로 발현되며, 포트 문제로 의심하기 어려움 |
| 3 | **재현 불가** | 확인하는 사이 임시 포트가 반납되어 재기동하면 성공 → "원인 미상"으로 종결 → 동일 문제 반복 |

## 발생 시점 — 리스크의 핵심

- 서비스가 **떠 있는 동안은 안전**하다. 커널이 사용 중인 포트를 임시 할당에서 제외하기 때문
- 문제가 드러나는 것은 **재기동 순간뿐**
- 그런데 재기동은 보통 **정전 / 서버 점검 / 장애 복구** 시점에 발생

> **이미 장애가 난 상황에서 복구하려는데 서비스가 안 뜬다** — 이것이 실질적 위험.
> 평온할 때가 아니라 가장 급할 때 터진다.

## 확률

- 임시 포트 구간은 약 28,000개
- 그 순간 서버가 맺고 있는 **아웃바운드 연결 수에 비례**해 충돌 확률 상승
- Kafka·모니터링·STT 워커 등 상시 연결이 많은 스택은 동시 연결이 수백~수천 개
- 고정 포트가 20~30개면 부팅 시 그중 하나가 걸릴 확률은 무시할 수준이 아님

## 부수 효과

- 아웃바운드 연결 종료 후에도 로컬 포트가 최대 60초간 `TIME_WAIT`로 점유됨
- 고정 포트를 많이 점유할수록 임시 포트 풀이 그만큼 축소됨 (소규모면 미미)

## 대응 방법

| 방법 | 내용 |
|---|---|
| **권장** | 처음부터 임시 포트 구간 밖에 배정 (61000~65535 또는 32767 이하) |
| 차선 | `net.ipv4.ip_local_reserved_ports`에 해당 포트 등록 → 커널이 임시 할당에서 제외 |
| 차선 | `net.ipv4.ip_local_port_range` 시작점 상향 조정 |

> 차선책 2가지는 sysctl 변경이 필요하므로 인프라 소관.

## 커뮤니케이션 톤

단정("옮겨야 한다")보다 여지를 두는 편이 안전. 당장 정상 동작 중이므로 단정하면 "지금 잘 되는데요"에 막힌다.

# G. 본 저장소(asst-service) 영향 범위

## 우리 서비스 포트

5F 기존 `asst-service-dev(32025)` / `asst-web-dev(32026)` 는 **제거 대상**.
3F에서 이관해 오는 것으로 대체되며, 앞자리 치환 규칙에 따르면:

| 현재(5F) | 이관 후(예상) | 대상 |
|---|---|---|
| 32025 | **62025** | asst-service |
| 32026 | **62026** | asst-web |

> 개별 포트 번호는 아직 확정 전. 대역(62xxx)만 확정된 상태이므로 배정 확인 후 적용.

## 수정이 필요한 파일

| 파일 | 항목 | 비고 |
|---|---|---|
| `docker-compose.dev.5f.yml` | `ports: 32025:3000` | → 62025 |
| `docker-compose.dev.5f.yml` | `CORS_ALLOWED_ORIGINS` (32026) | → 62026 |
| `.env.5f.development` | `CE_HOST`, `CE_API_URL` (32021) | CE 신규 포트로 |
| `.env.5f.development` | `USER_HOST` (32031) | Common 대역 신규 포트로 |
| `.env.5f.development` | `AICM_HOST`, `SEARCH_HOST` (8173) | AICM 신규 포트로 |

## 변경 불필요

**인프라는 현행 유지 결정이므로 아래는 그대로 둔다.**

| 항목 | 현재 값 | 비고 |
|---|---|---|
| `DB_PORT` | 32011 (cis-postgres) | 유지 |
| `REDIS_PORT` | 6379 (호스트 네이티브 redis) | 유지 |

## 착수 전 확인 필요

1. 62xxx 내 **개별 포트 배정표** 확정 (앞자리 치환 그대로인지)
2. 업스트림(CE / user-service / AICM)의 신규 포트 — 우리 `.env` 가 직접 물려 있음
3. 방화벽 개방 완료 시점
4. 5F 기존 스택 **제거 시점** 과 신규 기동 시점의 순서 (다운타임 여부)
