# 2026-08-04 작업 이력 — 감지어 탐지 구축 / assist-stream 장애 수습 / get_user 스키마 대응

## 요약

하루 동안 세 갈래 작업이 있었다.

1. **감지어(키워드) 탐지 기능 신규 구축** — 설계부터 API까지

## 1. 감지어 탐지 기능 (신규)

### 설계 결정

- 관리자가 등록한 4분류 중 **3종만 탐지**한다: `forbiddenWord`(금칙어) / `profanityWord`(비속어) / `issueWord`(이슈어).
  `emotionWord`(화면 라벨 VOC)는 제외 — 감정은 사전 매칭 대상이 아니고 `advisor.callstat_voc` 가 이미 담당한다.
- **실시간 fire-and-forget**. `raw_call.callstats_turn` 이 비어 있어 사후 배치는 스캔할 데이터가 없다.
- **심각도(severity) 제외** — 기획 목업에만 있던 개념이고 등급별 조치 계획이 없다.
- **유사도 매칭 제외** — 발화를 키워드 길이로 잘라 전 구간 비교해야 해서 비용이 크다. 미탐이 실측되면 그때 검토.
- 기능의 존재 이유: 금칙어=자본시장법 부당권유 감시, 비속어=상담사 보호 근거자료.
  코칭/QA/TA 와 겹치지 않는 지점은 **상담사 단위 귀속**과 **결정론적 근거**(LLM 판단은 소명 자료로 못 씀).

### 산출물

| 구분 | 내용 |
|---|---|
| 테이블 | `advisor.keyword_detect_logs` (+ 마이그레이션 SQL, `runSchemaMigrations()` 멱등 생성) |
| 엔티티 | `KeywordDetectLog` — 정적/동적 연결 엔티티 목록 3곳에 등록 |
| 매칭 | `keyword-matcher.ts` — 소문자화·문장부호 제거 후 부분일치. 긴 키워드는 공백까지 제거해 비교, 짧은 키워드는 공백 유지(어절 경계 오탐 방지) |
| 탐지 | `KeywordDetectRealtimeService` — 사전 캐시(TTL 60초) → 매칭 → `ON CONFLICT DO NOTHING` 저장. 전 구간 예외 격리 |
| 배선 | `assist-stream.controller` 에 `setImmediate` + `.catch()` fire-and-forget |
| 조회 | `GET /keyword-detect-logs` (페이징·검색어·분류·상담사·기간, 상담사명 조인), `GET /keyword-detect-logs/stats` (분류별·상담사별·키워드별 집계) |

### 중복 방지 (2중)

- 1차: 통화별 메모리 집합. 키는 `화자 + 정규화 내용 해시`
  (`conversationHistory` 가 매 요청 재전송되므로 상담사 발화가 반복 유입된다)
- 2차: DB 유니크 `(call_id, speaker, content_hash, keyword)`

### 알려진 한계

- 상담사의 마지막 발화 뒤 고객 발화가 없으면 `/assist-stream` 이 호출되지 않아 그 발화는 탐지되지 않는다.
- 활용형(황당하다 → 황당해서)은 잡지 못한다. 등록 가이드로 대응한다.
- 발화 원문은 저장하지 않는다. `call_id` + `turn_idx` 로 `raw_call.callstats_turn` 과 조인할 설계인데
  그 테이블이 아직 비어 있다.

## 2. 감지어 등록 API 보완

- **일괄 등록** `POST /keyword-detects/bulk` 신설 — 최대 1000건, `(type, keyword)` upsert,
  잘못된 항목만 건너뜀(전체 롤백 없음). 요청서(`docs/keyword-detect-bulk-api-request.md`) 기준.
- **단건 등록 중복 방지** — `POST /keyword-detects` 도 같은 `(type, keyword)` 면 새로 만들지 않고 갱신.
  화면의 "키워드 추가"가 이 경로라 중복 행이 쌓이고 있었다. 앞뒤 공백도 제거해 비교한다.
- **목록에 집계 추가** `GET /keyword-detects?withStats=true` → `detect_count`, `last_detected_at`.
  DB 컬럼이 아니라 조회 시점 집계다.

## 3. `/assist-stream` 400 장애 수습

**증상**: 실시간 상담 보조 답변·VOC·감지어가 전부 동작하지 않고, 로그도 남지 않았다.

**원인**: 프론트가 payload 에 `code` 필드를 추가했고 `company.id` 가 비었는데,
전역 `ValidationPipe` 가 `forbidNonWhitelisted: true` 라 **컨트롤러 진입 전에 400 으로 잘렸다.**
전역 예외 필터가 없어 로그도 한 줄 남지 않았다.

**조치**

- `AppValidationPipe` 신설(전역 파이프 교체). 기본은 엄격, **`/assist-stream` 만 미정의 필드 무시**.
  실시간 상담 경로가 프론트 필드 추가로 끊기면 안 된다.
- 검증 실패 시 어떤 필드가 왜 걸렸는지 `warn` 로그.
- `DbCleanupInterceptor` 에러 로그에 method / URL / 예외 본문 추가 (`Bad Request Exception` 만 찍히던 것).
- `AssistStreamCompanyDto.id`, `vendor_tenant_id` 를 선택값으로. 상담 보조(RAG)는 이 값을 쓰지 않는다.
- 감지어 서비스 진입/스킵 사유를 `log`/`warn` 으로 노출(조용히 return 하던 구간 제거).

## 4. `get_user` 스키마 개편 대응

user-service 가 `get_user` 응답 구조를 바꿔 백엔드가 읽던 필드가 사라졌다.

| 코드가 읽던 필드 | 새 응답 |
|---|---|
| `agent.id` | `agent.id` (유지) |
| `agent.cc_cti_id` | `agent.cti.ctiId` (경로 변경) |
| `company.vendor_tenant_id` | `agent.organization.tenant.id` (경로 변경, 숫자) |
| `agent.company_id`, `company.id` | **없음** |

**조치**

- `UserInfoService.toCurrentUser()` 매핑 계층 추가. 호출부 7곳을 고치는 대신 여기서 흡수한다.
  `vendor_tenant_id` 는 숫자 → 문자열로 변환(Redis 채널명 조립에 사용).
- **VOC `cc_cti_id` 하드코딩 폴백 제거** (`56356659`). 특정 상담원 채널로 고정 발행돼
  다른 통화의 VOC 가 그 사람 화면으로 새던 문제. 이제 못 얻으면 발행하지 않는다.
- `POST /todos/auto-create` 가 payload `company.id` 를 X-Tenant-Id 로 쓰도록 연결.
- `SummaryCompanyDto` 필드를 선택값으로(일부만 보내도 400 나지 않게).

**회사 UUID(`company_71900448_...`)** 는 새 응답에도 JWT 에도 없어 프론트가 하드코딩으로 전달한다.
CE 는 이 헤더를 검증하지 않는 것으로 보인다(`company.id=1` 로도 동작 확인).

## 남은 것

### 검증 대기
- 감지어 실제 저장 여부(로그 `[감지어] 진입` / `[감지어] 탐지`)
- 코칭 알림 소켓 복구 여부
- 감지어 매칭 오탐률 — 실데이터가 쌓여야 측정 가능

### 미결
- **`getCurrentUser()` 호출 7곳은 그대로다.** 매핑으로 정상화만 했고 제거하지 않았다.
  제거하려면 프론트 작업 2건 필요(코칭 `vendor_tenant_id`, 즐겨찾기 `agent_id`).
- **토큰 의존도 그대로다.** DB 연결 가드 / 업스트림 인증 / 세션 만료 SSE.
  최소화 2~4단계는 실익이 없어 보류하기로 했다.
- **회사 UUID 근본 대책** — JWT 클레임 추가를 user-service 에 요청할지 미정.
- **`keyword_update_at`** (`/keyword-detect-logs` 응답) — 결국 쓰이지 않는 필드. 제거 여부 미정.
- **기존 실패 테스트 2건** — `assist-stream.controller.spec`, `assist-stream.service.spec`.
  이 작업 전부터 깨져 있었고(인자 개수·X-auth-token 낡은 단언) 수정 승인 미확인.
- **콜 이력 상세 연결** — `keyword_detect_logs.call_id`(예: `698592560905`)와
  `raw_call.callstats_call` 의 키 체계가 맞는지 확인 중.
