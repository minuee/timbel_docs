# Redis / 이중화 대비 점검 및 조치

- **일자**: 2026-07-28
- **대상**: asst-service (어드바이저 백엔드)
- **목적**: Redis 성능 및 이중화(HA) 대비 상태 점검, 미비점 조치

### ★ 전제 — 이 문서가 상정하는 이중화 구조

> **scale-out(부하 분산)이 아니라 장애 대비 active/standby 이중화다.**
> 어드바이저·Redis 모두 동일하며, 서비스는 **1대로 충분히 감당**되는 규모다(상담사 약 300명).
> 두 인스턴스가 동시에 트래픽을 받는 active/active가 **아니다.**
>
> 이 전제가 바뀌면 5-1장의 결론이 달라진다.

---

## 1. 결론 요약

1. **Redis 성능은 판단 보류.** 개발기가 유휴 상태(29 ops/s, CPU 0.7%)라 용량 검증이 불가능하다. 다만 **성능이 병목이 될 가능성은 낮다.**
2. **Redis 이중화는 이미 되어 있다.** sentinel + replica 2대. 단, **Redis 이중화가 어드바이저 이중화를 보장하지는 않는다.**
3. **오늘 작업의 본질은 "Redis가 active/standby로 전환될 때 어드바이저가 살아남는 것"이다.** 어드바이저 자신의 이중화와는 별개 사안이다.
4. **어드바이저 쪽 이중화 대비는 이미 되어 있었다.** active/standby 구조에서는 **추가 코드 작업이 없다.**

## 2. 분석 결과

### 2-1. Redis 인프라 현황

| 항목 | 내용 |
|---|---|
| 구성 | sentinel 기반 HA, **standalone 모드** (Redis Cluster 아님) |
| 복제 | master 1 + replica 2, 모두 online |
| 위치 | AWS. **ElastiCache 아님** (ElastiCache는 sentinel을 쓰지 않음) → EC2/EKS 직접 구성 |
| 접속 | `dev-ecp-redis.langsa.ai`, TLS, DB 11개를 여러 서비스가 공유 |
| 특이사항 | 현재 master는 **replica에서 승격된 노드** → 이 환경에서 failover가 실제로 발생한 이력이 있음 |

### 2-2. STT 데이터 저장 구조

**영구저장이 아니다.** `dev:global:call:stt:events` Redis Stream 하나에 들어가며, 키 자체에는 TTL이 없지만 `MAXLEN ~1000` 트림으로 **최근 약 1,000건만 유지되는 롤링 버퍼**다. (누적 11,360건 중 1,010건만 잔존)

Redis는 **전달 버퍼** 역할이고, 이력이 필요한 데이터는 postgres(`callstat_*`)에 저장된다. 설계 의도대로이며 문제 없음.

### 2-3. 성능

개발기 유휴 상태 측정치이므로 **용량 판단 근거로 쓸 수 없다.** 참고용 수치만 기록한다.

- 평균 29 ops/s, CPU 사용률 0.7%, 메모리 83MB / 7.6GB
- 서버측 명령 지연: GET 2.0µs, HSET 6.0µs, PUBLISH 10.7µs (마이크로초 단위)
- keyspace hit rate 99.0%, 연결 거부·eviction 0건

> 서버측 지연이 µs 단위이므로, 앱에서 Redis가 느리게 느껴진다면 원인은 Redis가 아니라 네트워크·TLS·클라이언트 쪽이다.

### 2-4. 이중화 관점 핵심 진단

> **Redis 이중화는 어드바이저 이중화의 *전제조건*이지 *해결책*이 아니다.**

- Redis가 살아있어야 → 파드 간 이벤트 전파와 중복 방지 락이 동작한다
- 하지만 어드바이저 **프로세스 메모리에 남은 상태**는 Redis가 해결해주지 못한다

failover 시 발생하는 유실은 두 종류로 나뉜다.

| 종류 | 내용 | 대응 |
|---|---|---|
| **① 발행 실패** | 내가 보내려는데 Redis가 못 받음 | 재시도로 대부분 차단 가능 → **이번에 조치** |
| **② 수신 유실** | 남이 보냈는데 내 구독이 끊겨 있었음 | pub/sub은 재전송이 없어 Stream 전환 외 해결책 없음 → **보류** |

## 3. 그동안 이중화를 대비해 처리해 둔 것 〔이식 대상 **아님**〕

> ⚠️ 이 장은 **이번 작업 이전에 이미 반영되어 있던** 항목들이다. 보고용 정리이며,
> 다른 레포에도 대부분 이미 이식되어 있다. **이식 요청 대상은 4장이다.**

### 3-1. 소켓 (Socket.IO)

| # | 처리한 것 | 왜 필요한가 |
|---|---|---|
| 1 | **코칭을 Redis pub/sub으로 전파** → 각 파드가 자기 room에 재전송 | **멀티 파드에서 코칭이 동작하는 핵심 구조.** 모든 파드가 같은 채널을 구독해 각자 뿌리므로, 파드가 늘어도 모든 상담사에게 도달한다 |
| 2 | `connectionStateRecovery` (2분) | 잠깐 끊겼다 재연결되면 room 재참여 없이 상태·STT·VOC 수신이 이어진다 |
| 3 | `pingTimeout` 60초 / `pingInterval` 25초 / `upgradeTimeout` 30초 | K8s·로드밸런서 환경에서 연결이 조기에 끊기지 않도록 |
| 4 | `websocket` + `polling` 폴백 | 프록시·방화벽 환경 대응 |
| 5 | K8s 환경 감지 시 sticky session 경고 로그 | 배포 시점에 설정 누락을 알림 |

### 3-2. Redis

| # | 처리한 것 | 왜 필요한가 |
|---|---|---|
| 6 | **VOC 중복 분석 방지 분산 락** (`SET NX EX 60`) | 인스턴스가 여러 대여도 같은 (call_id, turn_idx)는 **한 대만** 분석·발행한다. 멀티 인스턴스를 전제로 설계된 부분 |
| 7 | 락 키에 환경(env) prefix 포함 | 한 Redis를 여러 환경이 공유해도 환경 간 락 간섭이 없도록 |
| 8 | 락 확인 실패 시 통과(fail-open) | Redis 장애가 서비스 중단으로 번지지 않게 (가용성 우선) |
| 9 | **무한 재연결** (`reconnectStrategy`가 포기하지 않음) | 과거 10회 초과 시 포기 → 영구 미연결로 고착되던 버그 해결 |
| 10 | 연결 판정을 `connect`가 아닌 **`ready`** 기준으로 | `connect`는 소켓만 붙은 상태로, 실제로는 명령을 못 보내는데 연결됐다고 오판했었음 |
| 11 | half-open 감지 (PING + 5초 타임아웃) | LB가 FIN 없이 조용히 끊은 연결을 탐지 |
| 12 | **재연결 후 구독 자동 복구** | failover 후 구독이 살아나지 않으면 조용히 먹통이 된다. **이중화 대비의 핵심** |
| 13 | `quit()` 타임아웃 (`closeClientSafely`) | half-open 소켓에서 `quit()`이 무한 대기해 자가복구가 영구 정지하던 버그 |
| 14 | 재접속 워치독 | 재접속 진행 플래그가 고착돼 자가복구가 멈추는 것 방지 |
| 15 | client / subscriber 커넥션 분리 | 구독 중에도 일반 명령 수행 가능 |

### 3-3. 요약

**소켓 쪽은 "파드가 늘어도 메시지가 도달하는 구조"**(#1)가, **Redis 쪽은 "끊겨도 스스로 복구하고 구독을 되살리는 구조"**(#9~#14)와 **"여러 대가 떠도 중복 처리하지 않는 구조"**(#6~#8)가 이미 갖춰져 있었다.

### 수정 1. 헬스체크에 ROLE 검사 추가 — replica 고착 감지

**문제**: sentinel failover 후 DNS가 구 마스터(승격되어 이제 replica)를 계속 가리키는 동안 재연결이 성공하면, 소켓·PING·SUBSCRIBE는 **전부 정상으로 보이는데 쓰기만 READONLY로 실패**한다. 기존 헬스체크는 PING만 하므로 이를 정상으로 오판하고 자가복구가 발동하지 않는다. "반쯤 살아있는" 상태로 고착된다.

**영향**: VOC 중복 방지 락(SET) 실패 → fail-open 통과 → 중복 발행 지속 / VOC 발행·상담사 상태 HSET 실패

**파일**: `src/common/services/redis.service.ts`

① 클래스 필드 추가 (`healthCheckTimer` 선언 아래)

```ts
  /**
   * 연속으로 replica 접속이 감지된 횟수와, 다음 재연결을 시도할 회차.
   * failover 후 DNS 가 아직 새 마스터로 갱신되지 않았다면 재연결해도 다시
   * 같은 replica 에 붙는다. 그런데 재연결은 구독을 끊었다 다시 맺으므로, 매 헬스체크마다
   * 재연결하면 그 간격마다 pub/sub 메시지 유실이 반복된다(고착보다 나쁨).
   * 그래서 1·2·4·8... 회차에서만 재시도하도록 백오프한다. 마스터 복귀 시 초기화.
   */
  private replicaDetectStreak = 0;
  private nextReplicaReconnectAt = 1;

  /** ROLE 응답 대기 상한(마스터 접속 여부 확인용) */
  private static readonly ROLE_TIMEOUT_MS = 3000;
```

② `checkHealthAndHeal()` 끝부분 수정 — PING 실패 시 `return` 추가하고 3단계 호출

```ts
    // 2) half-open 감지: PING에 타임아웃을 걸어 무응답이면 죽은 연결로 판단
    try {
      await this.pingWithTimeout();
    } catch (error) {
      this.logger.warn(
        `🩺 Redis PING 무응답(half-open 의심) → 자동 재연결: ${
          error instanceof Error ? error.message : String(error)
        }`,
      );
      await this.reconnect();
      return;                      // ← 추가
    }

    // 3) 쓰기 가능 여부(마스터 접속) 확인 — PING 만으로는 절대 감지되지 않는 구간
    await this.checkWritablePrimary();   // ← 추가
  }
```

③ 메서드 신규 추가

```ts
  /**
   * 메인 클라이언트가 마스터에 붙어 있는지 ROLE 로 확인하고, replica 면 재연결한다.
   * ROLE 확인 자체가 실패하면 재연결하지 않는다(일시 오류로 멀쩡한 연결을 끊지 않기 위함).
   */
  private async checkWritablePrimary(): Promise<void> {
    let role: string;
    try {
      const result = await RedisService.withTimeout(
        this.client.sendCommand(['ROLE']),
        RedisService.ROLE_TIMEOUT_MS,
        'ROLE',
      );
      // ROLE 응답의 첫 요소가 'master' | 'slave' | 'sentinel'
      role = Array.isArray(result) ? String(result[0]) : '';
    } catch (error) {
      this.logger.warn(
        `🩺 Redis ROLE 확인 실패(연결은 유지): ${
          error instanceof Error ? error.message : String(error)
        }`,
      );
      return;
    }

    if (role === 'master') {
      if (this.replicaDetectStreak > 0) {
        this.logger.log(
          `✅ Redis 마스터 접속 복구됨 (replica 감지 ${this.replicaDetectStreak}회 후)`,
        );
      }
      this.replicaDetectStreak = 0;
      this.nextReplicaReconnectAt = 1;
      return;
    }

    this.replicaDetectStreak++;
    this.logger.error(
      `🩺 Redis 쓰기 불가 상태 감지: ROLE=${role || 'unknown'} (replica 접속). ` +
        `failover 후 DNS 미갱신 의심 — 연속 ${this.replicaDetectStreak}회`,
    );

    if (this.replicaDetectStreak < this.nextReplicaReconnectAt) {
      return; // 백오프 구간 — 재연결로 구독을 반복해서 끊지 않는다
    }

    this.nextReplicaReconnectAt = this.replicaDetectStreak * 2;
    this.logger.warn('🔄 replica 고착 해소를 위해 재연결 시도');
    await this.reconnect();
  }
```

> **백오프를 넣은 이유**: DNS가 갱신되지 않은 동안 매 주기마다 재연결하면, 재연결할 때마다 구독이 끊겼다 붙으면서 **오히려 메시지 유실이 반복된다.** 고착 상태보다 나쁘다.

### 수정 2. `publish()` 재시도 추가 — 단, 중복은 절대 만들지 않음

**문제**: failover 순간 `publish()`가 실패하면 로그만 남기고 메시지를 버렸다. pub/sub은 재전송이 없어 **영구 소실**된다. (예: 슈퍼바이저가 보낸 코칭이 상담사에게 영영 안 감)

**핵심 설계**: 재시도는 **"아직 명령을 보낸 적이 없음이 확실한 경우"에만** 한다. 전송 후 응답만 못 받은 상황에서 재시도하면 구독자가 같은 메시지를 두 번 받는데, 코칭 알림은 프론트에서 토스트·알림음 같은 1회성 부수효과를 유발하므로 중복이 사용자에게 그대로 보인다. **유실 방지보다 중복 방지를 우선해 at-most-once를 유지한다.**

**파일**: `src/common/services/redis.service.ts`

① 상수 추가

```ts
  /**
   * 발행 재시도 간 대기(ms). 길이 + 1 이 총 시도 횟수가 된다(= 3회).
   * publish 는 HTTP 요청 경로에서 호출되므로 총 추가 지연을 700ms 로 묶는다.
   * ★ 재시도는 "아직 명령을 보낸 적이 없음이 확실한 경우"에만 한다(아래 publish 구현 참고).
   */
  private static readonly PUBLISH_RETRY_DELAYS_MS = [200, 500];
```

② `publish()` 전체 교체

```ts
  async publish(channel: string, message: string): Promise<boolean> {
    const maxAttempts = RedisService.PUBLISH_RETRY_DELAYS_MS.length + 1;

    for (let attempt = 1; attempt <= maxAttempts; attempt++) {
      // 재시도는 여기(미연결 확인)에서만 일어난다.
      // ensureClientReady()가 false 라는 것은 명령을 아직 보낸 적이 없다는 뜻이므로,
      // 대기 후 다시 시도해도 구독자가 메시지를 두 번 받을 일이 없다.
      // (ensureClientReady 는 끊긴 상태면 내부에서 재접속을 걸어두므로, 대기 중 복구되면 성공한다)
      if (this.ensureClientReady()) {
        try {
          const result = await this.client.publish(channel, message);
          if (attempt > 1) {
            this.logger.log(
              `✅ 채널 ${channel} 발행 성공 (${attempt}번째 시도)`,
            );
          }
          this.logger.debug(
            `채널 ${channel}에 메시지 발행 완료 (수신자: ${result}명)`,
          );
          return true;
        } catch (error) {
          // 여기서 실패했다면 명령이 Redis 에 도달했는지 알 수 없다(전달은 됐고 응답만 유실됐을 수 있음).
          // 재시도하면 중복 발행이 되므로 재시도하지 않고 즉시 실패로 끝낸다.
          this.logger.error(
            `채널 ${channel} 메시지 발행 실패 (전송 여부 불명 — 중복 방지를 위해 재시도 안 함): ${RedisService.describeError(
              error,
            )}`,
            error instanceof Error ? error.stack : undefined,
          );
          return false;
        }
      }

      const delayMs = RedisService.PUBLISH_RETRY_DELAYS_MS[attempt - 1];
      if (delayMs === undefined) {
        break; // 마지막 시도까지 미연결
      }
      this.logger.warn(
        `채널 ${channel} 발행 보류 — Redis 미연결(재접속 시도 중). ${delayMs}ms 후 재시도 (${attempt}/${maxAttempts})`,
      );
      await RedisService.delay(delayMs);
    }

    this.logger.error(
      `채널 ${channel} 메시지 발행 최종 실패 (${maxAttempts}회 시도): Redis 미연결`,
    );
    return false;
  }

  /** 재시도 간 대기 */
  private static delay(ms: number): Promise<void> {
    return new Promise((resolve) => setTimeout(resolve, ms));
  }
```

**동작 정리**

| 상황 | 동작 | 중복 가능성 |
|---|---|---|
| 평상시 | 1회 성공 → 재시도 코드 미실행 | — |
| Redis 미연결 (끊긴 걸 인지) | 200ms → 500ms, 최대 3회 | **0** (전송한 적 없음이 확실) |
| `publish()` 중 예외 (전송 여부 불명) | 즉시 실패, 재시도 안 함 | **0** |

### 수정 3. 헬스체크 주기 180초 → 30초

**문제**: `REDIS_HEALTH_CHECK_INTERVAL` 기본값 180초는 sentinel failover(보통 10~30초)보다 훨씬 길어, 마스터가 바뀌어도 **최대 3분간** 모르고 half-open / replica 고착 상태로 남는다.

**파일**: `src/config/redis.config.ts`

```ts
  health_check_interval: parseInt(
    process.env.REDIS_HEALTH_CHECK_INTERVAL || '30000',   // ← 180000 에서 변경
    10,
  ),
  // 기본값: 30초.
  // - NLB idle timeout(약 350초)보다 짧아 keepalive 역할은 그대로 유지된다.
  // - 이전 값 180초는 failover(10~30초)보다 훨씬 길어 최대 3분간 장애를 인지하지 못했다.
  // - 비용은 주기당 PING 2회(client/subscriber)로 무시 가능하다.
```

필요 시 `.env`에 명시적으로 넣어도 된다.

```
REDIS_HEALTH_CHECK_INTERVAL=30000
```

## 5. 남은 과제

### 5-1. 어드바이저 active/standby 전환 — **추가 코드 작업 없음**

standby는 트래픽을 받지 않으므로, 사실상 **Redis 연결만 유지한 채 대기**한다. 코드 확인 근거는 다음과 같다.

| 확인 항목 | 결과 |
|---|---|
| 스케줄러(`@Cron`/`@Interval`) | **없음** → standby가 백그라운드로 실행할 작업 없음 |
| 스트림 소비(`XREADGROUP`) | **없음** → consumer group 경합 없음 |
| 실시간 VOC | **`/assist-stream` HTTP 호출 시에만 동작** (`voc-realtime.service.ts:117` — 상시 `nlp:complete` 옵저버는 제거됨) → 트래픽 없는 standby는 미동작 |
| 코칭 채널 구독 | 구독은 하되 빈 room에 emit → 무해 (로그 경고만 쌓임) |

#### 전환 시 발생하는 일

| 항목 | 무슨 일이 | 회복 |
|---|---|---|
| 소켓 전원 끊김 | 모든 상담사가 standby로 재연결 | **자동** (아래 프론트 구조로 커버) |
| 전환 중 발행된 코칭·공지 | pub/sub이라 재전송 없음 → **유실** | 안 됨 (전환 시간만큼의 짧은 구간) |
| VOC 발화 버퍼(`states`) | 진행 중 통화의 누적 발화 초기화 → 몇 턴간 분석 맥락이 짧아짐 | 새 발화 쌓이며 자동 |
| 토큰·회사 캐시(`callTokens` 등) | 소실 | 다음 HTTP 요청에 자동 재생성 |
| 진행 중 SSE 응답 | 끊김 | 프론트가 재요청 |
| DB 데이터(`callstat_*`) | 영향 없음 | — |
| Redis 상태(`call:status` 등) | 영향 없음 (standby도 같은 Redis 참조) | — |

**일시적 유실만 있고 영구 손상은 없다.** 실제 데이터는 DB와 Redis에 있어 standby가 그대로 이어받는다.

#### 프론트엔드 대응 (확인 완료)

`connectionStateRecovery`(2분 복원)는 인메모리라 **다른 파드로 재연결되면 동작하지 않는다.** 다만 프론트가 아래 구조로 이를 커버한다.

- 소켓 **무한 재접속** + 재연결 시 **room 재join**
- **room(채널)명이 고정**이라 어느 파드에 붙어도 같은 채널을 다시 잡는다

→ 전환 순간 흐르던 메시지만 유실되고, **이후 수신은 자동으로 이어진다.**

#### 참고: 향후 active/active(scale-out)로 전환할 경우에만 필요

> **현재 계획에는 해당 없음.** 아래는 두 인스턴스가 동시에 트래픽을 받을 때만 발생한다.

| 항목 | 위치 | 문제 |
|---|---|---|
| sticky session | 인프라(LB) 설정 | polling 폴백·세션 복원용. 코드 작업 아님 |
| 서버발 이벤트 직접 emit | `agent.service.ts:292`(상담사 상태), `notice.service.ts:55`(공지) | Redis를 거치지 않고 자기 프로세스 room에만 전송 → 접속자의 1/N에게만 도달 |
| 인메모리 캐시 | `voc-realtime.service.ts`의 `callTokens`, `companyUuidByVendor` | `DB_DIRECT_CON=0`일 때만 활성 |

> sticky session만으로는 두 번째 항목이 해결되지 않는다. sticky는 "같은 클라이언트를 같은 파드에 고정"하는 것이고, 그 문제는 "파드 간 이벤트 전파"라 별개다. 코칭에서 쓰는 Redis publish 패턴으로 맞추면 해결된다.

### 5-2. 보류한 항목

**코칭 채널의 Stream 전환** (수신 유실 방지). 보류 사유:

1. 발행·구독이 모두 이 레포에 있는 **코칭 2채널만** 가능하다. `nlp:complete`(외부 발행), VOC 발행(외부 소비)은 다른 저장소 협의가 필요하다.
2. **Stream의 consumer group을 그대로 쓰면 이중화가 오히려 깨진다.** consumer group은 메시지를 **한 대에게만** 배분하므로, 코칭을 파드 A만 받고 파드 B의 상담사는 못 받게 된다. fan-out을 유지하려면 `XREAD` + 파드별 마지막 ID 관리가 필요하다.
3. 수정 1·3으로 유실 구간이 최대 3분 → 약 30초로 줄어 이득이 감소했다.

### 5-3. 프론트엔드 요청 (전달 완료, 작업 중)

> 재접속·room 재join 구조는 이미 반영되어 있다(5-1 참조). 아래는 **중복 수신 방어**에 대한 별건이다.
> 발행 단계 중복은 4장 수정 2로 0이 되었으므로, 아래는 `connectionStateRecovery` 복원 경로에만 해당한다.

`connectionStateRecovery`(2분) 복원 과정에서 이미 처리한 이벤트가 다시 올 수 있다. 이는 백엔드 수정과 무관하게 남는 경로다.

- dedupe 키: `${message.type}:${message.coaching_id ?? message.coaching_request_id}`
- **막아야 할 것**: 토스트·알림음 등 1회성 부수효과
- **막을 필요 없는 것**: 카운트 재조회 (멱등이라 무해)

### 5-4. 인프라 팀 전달 사항 (어드바이저 작업 아님)

**`maxmemory=0`** — 메모리 상한이 없어 Redis가 OOM kill될 수 있고, sentinel 구성이라 그것이 곧 failover로 이어진다. 시스템 메모리는 7.6GB뿐이다.

추가로 정책이 `volatile-lru`인데 asst-service가 쓰는 db2는 **TTL 있는 키가 18%뿐**이라, 상한을 걸어도 evict할 대상이 부족해 쓰기 OOM 에러가 날 수 있다.

> 단, 이 인스턴스는 캐시가 아니라 **운영 상태**(STT 스트림, `call:status`)를 함께 담은 공용 인스턴스이므로, `allkeys-lru`로 바꾸면 운영 상태가 조용히 사라져 원인 불명의 버그가 된다. 정책 변경보다 **상한 설정 + db2 키 TTL 부여**가 적절하다.
