# 토큰 만료로 인한 작업 실패 분석 정리

## 1. 문제 상황

- 어제 감정분석(인지) 작업이 실패로 로그에 기록됨
- 실패 원인은 로그상 **토큰 만료(인증서버 거부)**
- 오류가 찍힌 시각이 **access token 만료 시각과 일치**함 → 이것이 원인 확정의 결정적 단서

## 2. 토큰 구조 (실측으로 확인된 사실)

| 항목 | 내용 |
|------|------|
| 저장 위치 | 프론트엔드 session storage (accessToken, refreshToken 둘 다) |
| access token 수명 | 약 20분 |
| refresh token 수명 | access 만료 시점 기준 +45분 (일반적인 refresh보다 짧은 편) |
| 서명 방식 | RS256 (JWT) |
| 담긴 정보 | sub(사용자), acc, cId, cd, ad(발급 시퀀스로 추정), role, exp |

> 참고: `ad` 값이 발급마다 바뀜 (873758 → 874564 → 467714 → 142156 등). 발급 식별자로 추정.

## 3. 갱신(refresh) 동작 방식 — 핵심

실측 결과, 토큰 갱신은 **된다.** 단, 방식이 중요하다.

- **미리 갱신(proactive)이 아니라, 만료된 후(reactive/lazy) 갱신**된다.
- 즉, access token이 아직 유효한 동안에는 갱신되지 않고 기존 토큰을 재사용한다.
  - (12:05, 12:16 시점 조회 시 만료 전이라 동일 토큰 유지 확인)
- access token이 만료된 뒤, 다음 요청이 나갈 때 비로소 refresh token으로 새 access token을 발급받는다.
  - (12:19:24 만료 → 12:21 조회 시 새 토큰 발급, 만료 12:40:15로 갱신 확인)

## 4. 실패의 원인 (추정, 근거 강함)

**만료되는 순간에 실행 중이던 요청이 401로 튕긴다.**

- 갱신이 "만료 후"에 일어나기 때문에, 만료되는 바로 그 순간에 진행 중이던 요청은
  아직 새 토큰을 받지 못한 상태 → 만료된 토큰으로 요청 → 인증서버가 401로 거부.
- 감정분석처럼 **처리에 시간이 걸리는 작업**은 특히 취약하다.
  - 작업 시작 시점에는 토큰이 유효했더라도,
  - 처리 도중 20분이 지나 만료되면,
  - 해당 요청은 갱신 타이밍을 잡지 못하고 그대로 실패한다.
- 짧은 API 호출은 재시도로 자연스럽게 넘어가지만, 긴 작업은 이 틈에 빠지기 쉽다.
- **오류 시각 = 토큰 만료 시각 일치**가 이 시나리오를 강하게 뒷받침한다.

## 5. 로그에서 추가 확인하면 좋을 것

- [ ] 실패한 작업의 **시작 시각**과 **실패 시각**의 간격이 20분(토큰 수명)에 근접하는가?
- [ ] 실패 직전까지는 정상 요청이었다가 특정 시점부터 401이 몰리는가?
- [ ] 실패한 요청에 쓰인 토큰의 exp가 실패 시각보다 **이전(이미 만료)**인가?

## 6. 대응 방향

시스템 구조(협력사 SSO, 토큰 정책) 자체는 통제 밖이므로, 아래 앱 레벨 방어가 현실적이다.

1. **긴 작업 시작 전 토큰 잔여시간 체크**
   - 작업 시작 전 access token의 exp를 확인, 남은 시간이 작업 예상 소요보다 짧으면
     미리 갱신을 트리거한 후 작업을 시작한다.

2. **401 발생 시 자동 갱신 + 재시도 (retry)**
   - 요청이 401로 실패하면, refresh로 새 토큰을 받은 뒤 원래 요청을 자동 재시도한다.
   - 가장 일반적이고 깔끔한 패턴.

3. **BFF(NestJS)에서 만료 임박 신호 내려주기**
   - 요청마다 access token의 exp를 읽어 남은 시간을 응답 헤더로 프론트에 전달.
   - 프론트는 임계값(예: 2~3분) 밑이면 선제적으로 갱신하거나 작업 저장 유도.

## 7. 보안 관련 참고 (별도 이슈)

- access token뿐 아니라 **refresh token도 session storage에 노출**되어 있음 → XSS 시 둘 다 탈취 가능.
- 다만 이는 이번 실패 원인과는 별개의 이슈이며, 시스템 통제권 문제로 즉시 개선은 어려움.
- 개선 시 방향: 토큰을 BFF 서버사이드에 보관하고 프론트에는 노출하지 않기 (통제권 확보 후 검토).
