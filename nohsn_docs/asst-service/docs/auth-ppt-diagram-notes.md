## 0. 두 그림이 공유하는 전제

| 항목 | 내용 |
|---|---|
| 배포 | **106.242.165.142 단일 서버**에 모든 앱 + **인증서버**까지 (폐쇄망) |
| 테넌트 | **단일 테넌트** |
| 앱 구성 | **프론트만 있는 앱은 없음.** 모든 앱이 **토큰을 검증할 수 있는 백엔드**를 가짐 (BFF형 / 순수 API형 무관) |
| 토큰 | **httpOnly 쿠키에 직접** — 앱들이 공유하는 **단일 소스** |
| 검증 | **브라우저 요청을 처음 받는 백엔드**가 쿠키에서 토큰을 읽어 **공용 공개키(JWKS)로 자체 검증** |
| 갱신 | **요청받은 앱 백엔드**가 인증서버 통해 갱신 → **Set-Cookie** (프론트 관여 없음) |
| Rotation | **채택** + 재사용 감지 + **Grace 윈도우** |
| 서비스간 | **내부망 도커 서비스명** — 사용자 토큰 전달 없음 |

> 단일 서버라 앱들이 포트만 다름 → **쿠키는 포트를 구분하지 않아 자동 공유** → 이게 SSO의 물리적 토대. (그림에 굳이 표기할 필요는 없음)

### 두 그림을 관통하는 규칙 (이 한 줄이 그림의 논리)

> **브라우저 요청을 처음 받는 백엔드가 쿠키에서 토큰을 읽어 공개키로 검증한다.** 그 뒤 내부망은 신뢰 구간.
>
> → 경로가 **BFF 경유든 API 직접 호출이든 동일하게 적용됨** = 혼합구조가 문제되지 않는 이유.
> → 각 앱에 필요한 건 **①쿠키에서 토큰 읽기 ②공개키로 검증 ③갱신** 세 가지뿐. **BFF로 개조할 필요 없음.**

## 1. 다이어그램 1 — SSO 개념도 (`sso_1.jpg` 스타일)

### 원본 구조
`[User + Desktop/Mobile]` → `[Login Single Sign-on]` → `[Intranet / CRM / ERP / PIM / Other Application]`

### 우리 버전

```
┌─────────────────┐                                    ┌──────────────────┐
│                 │                                    │   포털관리        │
│   상담사         │                                    ├──────────────────┤
│   슈퍼바이저      │      ┌──────────────────┐          │   어드바이저      │
│   관리자         │─────▶│   포털 로그인      │────┬───▶├──────────────────┤
│                 │      │      (SSO)       │    │    │   AICM           │
│   [PC 브라우저]  │      └──────────────────┘    │    ├──────────────────┤
│                 │                              ├───▶│   에이전트빌더     │
└─────────────────┘                              │    ├──────────────────┤
                                                 │    │   TA             │
                                                 │    ├──────────────────┤
                                                 └───▶│   QA             │
                                                      └──────────────────┘
```

**왼쪽 박스** (원본 User+Desktop+Mobile 자리)
- **상담사 · 슈퍼바이저 · 관리자**
- 접속: **PC 브라우저** — ※ 원본의 Mobile 아이콘은 **제외** (대상 아님)

**가운데 박스** (원본 Login Single Sign-on 자리)
- **포털 로그인 (SSO)**
- 부제: `인증서버 /auth/*` · `POST /auth/login`
- 부제: `JWT RS256 발급` · `kid: timbel-on-premise-v1`

**오른쪽 박스 6개** (원본 Intranet/CRM/ERP/PIM/Other 자리)

| 순서 | 박스 라벨 |
|---|---|
| 1 | **포털관리** |
| 2 | **어드바이저** |
| 3 | **AICM** |
| 4 | **에이전트빌더** |
| 5 | **TA** |
| 6 | **QA** |

**화살표 라벨**
- 왼쪽 → 가운데: `로그인 1회`
- 가운데 → 오른쪽: `httpOnly 쿠키 (공유)` — **모든 앱이 같은 쿠키를 사용 → 재로그인 없음**

**하단 캡션 (이 그림의 메시지)**
> 로그인 1회 → 모든 앱 이용. 토큰은 **httpOnly 쿠키에만 존재**(JS 접근 불가), 각 앱 백엔드가 **공용 공개키로 자체 검증**.

### 💡 원본과 다르게 표현할 점
원본은 SSO를 "로그인 창 하나"로만 그림. 우리 그림의 차별점은 **"토큰이 어디에 있고 누가 검증하는가"**를 같이 보여주는 것:
- 가운데 → 오른쪽 화살표에 `httpOnly 쿠키` 명시 (AS-IS의 sessionStorage/localStorage와 대비)
- 각 앱 박스 하단에 작게 `JWKS 자체 검증` 뱃지 → **인증서버로 되돌아가는 화살표가 없다**는 게 핵심 (부록 A의 AS-IS에는 USER_HOST로 되돌아가는 ⚠ 화살표가 있음)

### (선택) 어드바이저 박스를 확대한 서브 그림
어드바이저만 상세히 보여주고 싶으면:
```
어드바이저
 ├─ asst-web (프론트)  ── 쿠키 ──▶ asst-service (BFF/NestJS)
 └─ asst-service ── 내부망 (도커 서비스명, 사용자 토큰 없음) ──▶ AICM / CE / LLM 오케스트레이터
```

## 2. 다이어그램 2 — 로그인 ~ 갱신 시퀀스 (`sso_2.png` 스타일)

### 원본 구조
3개 레인: `User` | `App` | `AuthServer`
흐름: Login Credentials → Request Tokens → Access(Short)+Refresh(Long) → **[15 mins later...]** → Send Refresh Token → New Access Token

### 우리 버전 — 레인 4개

`사용자 (브라우저)` | `앱 백엔드 (포털관리·AICM·TA·QA…)` | `어드바이저 BFF (asst-service)` | `인증서버 (/auth/*)`

> **레인 2·3을 나누는 이유 = 혼합구조를 보여주기 위함.** 어드바이저는 BFF를 거치고, 다른 앱은 각자 백엔드로 직접 간다. **그런데 두 경로 모두 같은 쿠키 + 같은 공개키로 동작한다** — 이게 이 그림의 핵심 메시지.

### 흐름 (위 → 아래)

| # | From → To | 라벨 | 표기 |
|---|---|---|---|
| **[로그인]** ||||
| 1 | 사용자 → 앱 백엔드(포털) | `ID / PW` | 실선 |
| 2 | 앱 백엔드 → 인증서버 | `자격증명 전달` | 실선 |
| 3 | 인증서버 → 앱 백엔드 | `access (짧게) + refresh (길게)` · JWT RS256 | 점선 |
| 4 | 앱 백엔드 → 사용자 | ✅ `Set-Cookie: httpOnly · Secure · SameSite` **(토큰 값은 JS에 노출 안 됨)** | 점선 · **초록** |
| 4b | 앱 백엔드 → 사용자 | `get_user 정보 (테넌트 UUID · role · 메뉴)` — 민감하지 않음, 메모리/스토리지 무방 | 점선 · 회색 |
| — | — | **`━━━ SSO 성립 — 이후 모든 앱에 쿠키 자동 첨부 ━━━`** | **구분선** |
| **[어드바이저 사용 — BFF 경유 경로]** ||||
| 5 | 사용자 → 어드바이저 BFF | `API 요청 (쿠키 자동 첨부)` | 실선 |
| 6 | 어드바이저 BFF (자기 박스) | ✅ `JWKS 공개키로 자체 검증` — **인증서버 왕복 없음** | **초록 박스** |
| 7 | 어드바이저 BFF (자기 박스, 오른쪽으로 짧게) | `내부망 (도커 서비스명) → AICM / CE / LLM` — **사용자 토큰 미전달, 내부 헤더만** | **초록 박스** |
| 8 | 어드바이저 BFF → 사용자 | `응답` | 점선 |
| **[타 앱으로 이동 — 직접 호출 경로]** ||||
| 9 | 사용자 → 앱 백엔드 | `같은 쿠키 그대로 → 재로그인 없음` | 실선 |
| 10 | 앱 백엔드 (자기 박스) | ✅ `같은 공용 공개키로 검증` | **초록 박스** |
| **[갱신]** ||||
| 11 | — | ⏳ **`access 만료 임박 (잔여 수명 임계값 이하)`** | ← **원본의 노란 "15 mins later..." 박스 자리** |
| 12 | 앱 백엔드 → 인증서버 | `refresh 전송 (쿠키에서 읽음)` · **single-flight — 동시 요청 N개여도 1회만** | 실선 |
| 13 | 인증서버 → 앱 백엔드 | `새 access + 새 refresh` · **Rotation (이전 refresh 폐기)** | 점선 |
| 14 | 앱 백엔드 → 사용자 | ✅ `Set-Cookie 갱신` | 점선 · **초록** |
| — | — | **`이후 다른 앱은 갱신된 쿠키를 그대로 사용 → 추가 갱신 불필요`** | 주석 |
| **[경합 시 — 작게 곁들이기]** ||||
| 15 | 타 앱 백엔드 → 인증서버 | `(동시에) 같은 old refresh로 갱신 시도` | 얇은 실선 |
| 16 | 인증서버 → 타 앱 백엔드 | 🛡 **`Grace 윈도우: 폐기 대신 "동일 토큰 쌍" 반환`** | 얇은 점선 · **파랑** |

### 그림 캡션

> **사용자 레인에는 아무 일도 일어나지 않는다 = 무중단.**
> 프론트는 갱신에 관여하지 않고(인터셉터 없음), 토큰 값을 만지지도 않는다.

### 강조 포인트 (그림 옆 박스로)

1. **혼합구조여도 인증은 단일** — 어드바이저(BFF 경유)든 타 앱(직접)이든, **같은 쿠키 + 같은 공개키**로 동작
2. **인증서버로 되돌아가는 화살표는 "갱신" 때만** — AS-IS의 "매 요청 왕복"과 대비되는 지점
3. **내부망은 사용자 토큰 없이** — 경계에서 인증이 끝남

## 3. 다이어그램에 쓸 값 (치트시트)

### 토큰
| 항목 | 값 |
|---|---|
| 서명 | JWT **RS256** (개인키 서명 / 공개키 검증) |
| kid | `timbel-on-premise-v1` |
| 클레임 | `sub`(UUID) · `acc` · `cId`(숫자 회사ID) · `cd`(회사코드, "POC4") · `role` · `aName` · `ad`(발급 시퀀스) · `exp` |
| access 수명 | **TO-BE: 5~15분** (현재 정책 60분 / 실측 ≈20분) |
| refresh 수명 | **TO-BE: 정책값 (1~3일)** (현재 정책 14일 / 실측 ≈65분) |
| Grace 윈도우 | **10~30초** — 동일 토큰 쌍 반환 |

### 쿠키 (TO-BE)
| 속성 | 값 |
|---|---|
| httpOnly | **필수** (전 환경) — XSS 방어 핵심 |
| Secure | 운영 HTTPS = ON / 개발기 HTTP = 불가 |
| SameSite | Lax |
| 담는 것 | **access + refresh 토큰 직접** (세션ID 아님 — 세션ID면 타 앱이 해석 못 해 SSO 불가) |

### 엔드포인트
| 용도 | 경로 |
|---|---|
| 로그인 | `POST /auth/login` |
| 갱신 | `POST /auth/refresh` ⚠ **현재 부재 — 신설 필요** |
| JWKS (신설) | `GET /.well-known/jwks.json` |
| 사용자 조회 | `GET {USER_HOST}/api/user/get_user` — **로그인 시 1회** (TO-BE) |

## 4. 그림 그릴 때 틀리기 쉬운 것

**❗ "BFF가 토큰을 서버에 보관"이라고 쓰면 틀림**
쿠키 직접형이라 **서버사이드 보관이 없음.** 토큰은 **httpOnly 쿠키에만** 존재하고, 앱 백엔드는 매 요청 쿠키에서 읽어 씀. XSS 차단의 근거는 "서버 보관"이 아니라 **"httpOnly"**.
→ 부록 B(16장)의 `세션관리(Redis)` 박스는 **삭제 대상**.

**❗ 앱 박스를 전부 "BFF"로 라벨링하면 틀림**
BFF가 하나만 있는 것도 틀리지만, **반대로 전부 BFF로 그리는 것도 틀림.** 어드바이저는 BFF형이고 나머지는 **순수 API 백엔드**여도 무방함 — 공통 조건은 형태가 아니라 **검증 능력**뿐.
→ 라벨은 `앱 백엔드` 처럼 중립적으로. 그림이 "모든 앱을 BFF로 개조하라"로 읽히면 타 앱 팀에 불필요한 반발을 부름.

**❗ 갱신 주체는 앱 백엔드 (프론트 아님)**
프론트에 401 인터셉터를 그리면 안 됨 — 그건 AS-IS. TO-BE에서 프론트는 **갱신 존재 자체를 모름**.

**❗ 내부망 화살표에 토큰을 그리면 틀림**
어드바이저 → AICM은 **도커 서비스명 통신 + 내부 헤더**. 사용자 토큰이 흐르지 않음.
※ 이건 **"내부망은 신뢰한다"는 의도적 신뢰 경계** — 보안팀 설명 시 반드시 질문 나오는 지점이라, 주석으로 달아두는 게 안전.

**❗ AS-IS를 그릴 일이 생기면 (부록 A 보강 시)**
- asst-service는 토큰을 **검증하지 않음** — `auth.middleware.ts:136`에 `🔍 토큰 검증 생략` 명시. **존재만 확인**하고 통과시킴.
- 401은 그 뒤 **USER_HOST 호출 시점**에 터짐 (`getCompanyIdFromToken` → `getCurrentUser`)
- 즉 "BFF가 검증한다"가 아니라 **"아무도 검증 안 하다가 하위 조회가 실패하며 401이 드러난다"**

## 5. 배치 제안

| 그림 | 위치 |
|---|---|
| **다이어그램 1 (SSO 개념도)** | **부록 B(16장) 앞** 또는 16장 대체 — TO-BE 전체상을 한 장으로 보여주는 도입부 |
| **다이어그램 2 (갱신 시퀀스)** | **5장(Refresh 방식) 뒤** — AS-IS 갱신 방식 바로 다음에 TO-BE를 붙여 대비 |

- 색: 현 PPT 톤 유지 — 문제/AS-IS = 주황·빨강, 개선/TO-BE = 초록·파랑
- 노란 박스(원본 `15 mins later...`) → **`⏳ access 만료 임박`** 으로 치환. AS-IS(부록 A)에 대응 그림을 넣는다면 **`⏳ 약 20분 후 — 만료 → 401`** 로 대비시키면 효과적
- 다이어그램 2는 요소가 많으므로, **경합(15·16번)은 회색 얇은 선으로 곁들이기** 정도. 메인 흐름을 가리지 말 것
