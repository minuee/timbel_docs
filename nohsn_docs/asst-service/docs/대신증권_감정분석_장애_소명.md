## 2. 발생 원인

**장시간 상담 중 상담원 인증 토큰(유효시간 20분)이 만료된 것이 직접적인 원인입니다.**

감정분석·요약 기능은 여러 고객사가 함께 사용하는 멀티테넌트(multi-tenant) 환경에서 동작합니다. 이때 **"어느 고객사의 데이터로 처리할지"를 식별하는 정보**(고객사 식별자 = Tenant-ID, 데이터 저장소 접속 정보 등)를 그동안 **인증 토큰에서 꺼내어** 사용해 왔습니다.

통화가 20분을 넘겨 인증 토큰이 만료되면 이 식별 정보를 더 이상 확보하지 못해, 해당 기능이 다음과 같이 **중단(스킵 처리)** 됩니다.

- **고객사 식별 불가** → 감정분석(LLM) 호출에 필요한 Tenant-ID를 얻지 못함
- **데이터 저장소 접속 불가** → 감정·요약 결과의 조회 및 저장 불가
- **실시간 화면 전송(Publish) 불가** → 상담원 화면에 실시간 감정 변화가 표시되지 않음

장애의 근본 원인은 **실시간 상담보조(발화 스트리밍) 경로가 토큰 자동 갱신 대상에 포함되어 있지 않았던 점**입니다. 실시간 발화 응답은 즉시 전달되어야 하므로 일반 화면 기능과는 다른 **스트리밍 전용 통신 방식**을 사용하는데, 이 경로에는 만료 전 토큰 자동 갱신이 적용되어 있지 않았습니다. 그 결과 통화가 20분을 넘겨 액세스 토큰이 만료되면, 실시간 경로에서는 이를 갱신할 수단이 없어 만료된 토큰으로 요청이 계속되었습니다.

> **참고 — 구조적 배경**
> 실시간 발화 응답은 지연 없이 흘려보내야 하므로, 응답을 한꺼번에 받는 일반 통신 방식이 아니라 **스트리밍 전용 방식**으로 구현되어 있습니다. 이러한 특성상 실시간 경로가 토큰 자동 갱신의 적용 범위에 포함되어 있지 않았던 것이 이번 미갱신의 구조적 원인이며, 금번 개선(조치 ③)으로 **이 실시간 경로에도 자동 갱신을 적용하였습니다.**

반면 음성 대화(STT) 처리 경로는 인증 토큰과 무관하게 동작하므로, **상담 자체는 정상적으로 유지**되었습니다.

> **참고 — 즉시 인지가 지연된 이유**
> 시스템에는 특정 기능의 오류가 전체 상담을 중단시키지 않도록 하는 안전장치(예외 격리)가 적용되어 있습니다. 이 설계 덕분에 상담은 중단되지 않았으나, 부가 기능이 오류 메시지 없이 조용히 멈추는(스킵) 형태가 되어 현장에서 원인 파악이 다소 지연되었습니다.

## 부록. 근거 자료 — 장애 시각 서버 로그 발췌

장애 시각의 서버 로그에서, 상담원 요청에 실린 인증 토큰과 그로 인한 오류를 확인하였습니다.
(서버 로그 시각은 UTC이며, 아래는 한국시간(KST)으로 환산하여 표기)

**① 인증 토큰 만료 시각 (토큰 디코드)**

상담원 요청에 실린 인증 토큰(JWT)의 만료 정보(exp)를 디코드한 결과:

- **`exp = 2026-07-01 14:19:38 (KST)`** — 이 시각에 해당 상담원의 인증 토큰이 만료됨
- 토큰(발췌·마스킹): `eyJhbGciOiJSUzI1NiJ9.eyJ…(중략)…`
- 이후에도 동일 토큰이 **14:23:02(KST)까지** 요청에 계속 실려, 만료 후 **약 3분 24초(204초) 동안 만료된 토큰으로 요청**이 이어졌습니다. (해당 구간 요청 약 104건)

**② 토큰 만료 직후 발생한 오류 (14:19:40 ~ 14:19:42 KST)**

| 시각(KST) | 구성요소 | 로그 메시지 (발췌) |
|---|---|---|
| 14:19:40 | 실시간 감정분석(VOC) | `실시간 VOC 처리 실패(무시): Failed to get current user: Unauthorized` |
| 14:19:40 | 상담보조 스트림 | `RAG 업스트림 에러: 502 … "Failed to fetch tenant db url: 401 … /api/configs/get_configs"` |
| 14:19:42 | 테넌트 설정 조회 | `테넌트 설정 조회 실패: 401 Unauthorized` |
| 14:19:42 | 데이터 저장소(DB) 연결 | `DB 연결 생성 실패: 테넌트 설정 조회 실패: 401 Unauthorized` |
| (인증서버 응답) | 인증 서버(User Host) | `토큰 인증 실패: 401: token 만료` |

**③ 해석**

- 토큰이 **14:19:38**에 만료되자, 곧바로(**14:19:40~42**) 인증 서버가 **"token 만료" 401**을 반환하였고,
- 이로 인해 ⓐ 실시간 감정분석(VOC)이 `Failed to get current user`로 실패, ⓑ 테넌트 데이터 저장소(DB) 접속이 401로 실패하여 — 본문 2장에서 설명한 **감정 미표시·데이터 접속 불가** 현상이 실제 로그로 확인됩니다.
- 로그의 **`(무시)`** 표기는 오류가 상담을 중단시키지 않도록 격리(예외 처리)된 흔적으로, **"오류 없이 조용히 멈춤(무증상 정지)"** 의 원인과도 일치합니다.

**④ 토큰 갱신 관련 (참고)**

- 앞 구간에서 만료된 토큰(exp 14:19:38)이 **14:23:02(KST)까지 요청에 계속 실려** 모두 401 처리되었으며, 이 구간 어드바이저(API) 서버 로그에는 **만료 전 자동 재발급(refresh)이 일어난 흔적이 없습니다.**
- 이후 정상 처리된 요청은 오류 확인을 위한 **별도 재로그인** 세션으로, 이번 만료 건의 자동 갱신 동작 여부와는 무관합니다.
- refresh 호출 자체는 어드바이저 서버 로그로는 확인되지 않으므로(아래 참고), **통화 중 자동 재발급 동작 여부는 인증 서버·프론트 로그에서 확인**이 필요합니다.

> **참고 — 로그가 서버별로 나뉘는 이유**
> 어드바이저(API) 서버는 인증 토큰을 **자체 검증하지 않고** 인증/사용자 서버(User Host)로 전달하여 사용합니다. 따라서 토큰 만료 판정(401)과 토큰 재발급(refresh)은 **인증 서버 영역**에서 이루어지며, refresh 호출 자체는 어드바이저 서버 로그에 남지 않습니다(요청이 인증 서버로 나가기 때문). refresh 호출 여부는 인증 서버·프론트 로그에서 확인이 필요합니다.

*※ 토큰 값 및 상담원 식별정보(IP 등)는 보안을 위해 마스킹하였습니다. 원본 로그는 요청 시 별도 제공 가능합니다.*
