# 실시간 VOC 감정분석 — 인증 토큰 만료 이슈 분석 (2026-07-01)

## 1. 현재 상황 (구조)

### 1-1. `/assist-stream` VOC 플로우
- 상담 중 프론트가 발화마다 `POST /assist-stream` 호출 → 두 갈래로 처리
  - **(A) RAG 상담보조** : 외부 AICM(`/api/aicm/v1/search/rag_assist`)로 릴레이 → 근거문서·요약·답변 SSE 스트리밍
  - **(B) 실시간 VOC** : `handleUtterance`가 발화 누적 → LLM 감정/민원/이탈 3축 분석 → 결과를
    - **소켓 publish**(Redis `...:call:voc` 채널) → **통화 중 실시간 감정변화 화면**
    - **`callstat_voc` 테이블 저장** → **통화 종료 후 별도 조회 API로 사용**(실시간 화면과 무관)

### 1-2. VOC가 인증(토큰)을 거치는 이유
인증이 "권한 체크"가 아니라 **멀티테넌트 라우팅 정보의 운반수단**이기 때문:
- **테넌트 식별** : LLM 호출 필수값 `X-Tenant-Id`(회사 UUID)를 `getCurrentUser(token)` → `company_id`로 획득
- **DB 접속** : 테넌트별 동적 DB 연결을 **토큰으로 `db_config`(연결문자열) 조회** 후 접속
- **채널 식별** : publish 채널명 구성값(`vendor_tenant_id`, `cc_cti_id`)도 `getCurrentUser`에서 획득

### 1-3. 포털 토큰 구조
- accessToken **20분** / refreshToken **1시간** (session storage)
- 갱신은 **프론트가 직접 요청**, **서버측 refresh API는 정책상 미구현**
- → 세션 최대 유효시간이 사실상 약 1시간 20분

## 2. 오늘 발생한 내용 & 원인

### 2-1. 증상
- 전화상담 대화는 계속 이어짐 (STT 경로, **토큰과 무관**)
- **실시간 발화에 따른 감정변화(VOC)가 표시되지 않음**
- 통화 종료 후 **summary API도 401**

### 2-2. 원인
- 금일 **14:19:38 (KST)** 기준 토큰 만료 (`exp: 1782883178`)
- 이후 진행되는 **인증 관련 API 작업이 전부 401 인증실패**로 떨어짐
- VOC/summary는 인증에서 테넌트 정보를 꺼내오는 구조라 함께 실패
- 어드바이저 백엔드는 `try~catch` 예외격리 설계 → **실시간 상담은 중단되지 않음**.
  단 부작용으로 **에러 표시 없이 기능만 조용히 멈춤**(시연 중 원인 파악 지연 요인)

## 3. 해결방안

**원칙 : VOC는 "유저 신원"이 아니라 "테넌트 정보"만 필요 → 유저 토큰 의존을 제거한다.**

| # | 항목 | 조치 |
|---|------|------|
| 1 | 테넌트 식별 | 프론트가 `company.id` / `vendor_tenant_id`를 payload로 직접 전달(이미 전달 중) → 토큰에서 안 꺼냄 |
| 2 | LLM 호출 | CE emotion API를 **`x-api-key`(서비스 자격증명) + `X-Tenant-Id`** 로 호출 → **유저 토큰 불필요** |
| 3 | 채널 식별 `cc_cti_id` | 프론트가 주기 어려운 값 → **통화 시작 시점(토큰 유효)에 1회 `getCurrentUser`로 조회 후 callId별 휘발성 캐시** → 만료 후 캐시 재사용 (유저정보 영구저장 X, 통화 단위로만 보유) |
| 4 | DB 저장 | **`db_config`(연결문자열)는 만료되지 않음** → 토큰 유효 시점에 테넌트별로 캐시해두면 토큰 없이 재접속 가능(로컬·개발은 정적연결 사용 중). ※ 살아있는 커넥션 캐시는 idle/cleanup으로 끊길 수 있어 불안정 → 연결문자열 캐시가 안정적 |

### 별개 과제 (유저-스코프 엔드포인트)
- summary 등 **"이 유저가 볼 권한이 있나"를 판정해야 하는** 엔드포인트는 서비스 자격증명으로 대체 불가(접근제어 무력화) → **유효한 유저 인증이 필요**
- 이 영역은 포털 토큰 구조(refresh 1시간·서버 refresh 미구현)와 엮여 있어 **별도 논의 대상**
  - 확인 필요 : 포털의 실제 갱신 방식(전용 refresh API인지 / SSO 재인증인지), refreshToken이 sliding인지 고정 1시간인지

① 테넌트 ID는 프론트 payload로 전달, ② LLM 호출은 서비스 자격증명(`x-api-key`)+테넌트 ID로 처리(토큰 불필요), ③ 채널 식별자(cc_cti_id)는 **토큰 유효한 통화 시작 시점에 1회 조회·캐시하여 만료 후 재사용**, ④ DB 저장은 만료되지 않는 연결문자열(db_config)을 캐시해 토큰 없이 재접속.
→ 유저 권한 판정이 필요한 summary 등은 별도로 **토큰 갱신(refresh) 정책 논의** 필요.

## 부록 A. 토큰 구조에 대한 판단

**결론 : "access 20분"은 유지가 맞다. 문제는 값이 아니라 "갱신 부재"다.**

- **20분 access는 정석** — 탈취 시 피해를 20분으로 제한. PII 다루는 콜센터에선 오히려 짧게 가는 게 맞음. access TTL을 늘리는 건 보안을 깎는 하수.
- **진짜 문제** : ① refreshToken 1시간(다시간 상담과 충돌) ② session storage + 프론트 주도 갱신(스트림 도중 만료 못 막음, XSS에 토큰 노출) ③ 서버측 refresh 부재.
- **바람직한 방향 : httpOnly 쿠키 + BFF(서버) 토큰 관리**
  - 보안 : httpOnly는 JS가 토큰을 못 읽음 → XSS 토큰 탈취 방어(session storage는 JS 접근 가능이라 취약)
  - 안정성/UX : 서버가 만료 감지 → 자동 갱신 → 투명하게 이어감(유저는 만료를 못 느낌)
  - **long-lived 스트림(assist-stream)은 서버측 갱신이 아니면 구조적으로 못 살림** → 이 서비스엔 사실상 필수
- **트레이드오프(선결/유의)**
  - 서버가 갱신 자격(SSO 세션 등)을 쥐어야 함 → 서버측 세션 필요(무상태 일부 포기, BFF 패턴이 원래 감수)
  - httpOnly 쿠키는 CSRF에 노출 → `SameSite` + CSRF 토큰 대비 필요(위협모델이 XSS→CSRF로 이동)
  - **갱신 수단 확보가 선결** : refresh API가 없다면 SSO 재인증 경로라도 있어야 서버측 갱신이 성립

## 부록 B. SSO 환경인데 왜 토큰이 만료됐나 (핵심)

**전제 확정** : 포털 통합로그인(SSO) 구조가 맞음 — 여러 서비스(어드바이저 포함)를 포털에 배포하고, 중앙에서 계정을 관리해 하나의 세션으로 전 서비스를 이용. `get_user` API를 제공하는 서버가 곧 인증서버.

**핵심 오해 정정 : "SSO = 토큰 무한 자동 발행"이 아니다.**
- SSO가 주는 것은 **"재로그인 없이 새 토큰을 받을 수 있는 자격(중앙 IdP 세션)"** 일 뿐, **갱신을 대신 수행해주지는 않는다.**
- 그 자격을 실제로 사용하려면 **누군가가 갱신을 실행**해야 함: ① 프론트 silent 재인증, ② refresh token 교환(갱신 API), ③ 서버(BFF) 갱신.
- 현재는 **셋 다 부재**(프론트 갱신 API 정책상 없음 / 서버 갱신 없음) → IdP 세션은 살아있어도 **새 토큰으로 바꿔오는 주체가 없어** access 토큰이 TTL대로 만료됨.

**비유** : SSO 세션 = 오래 유지되는 멤버십 / access 토큰 = 20분짜리 사물함 열쇠. 멤버십이 살아있어도 열쇠는 저절로 갱신되지 않는다 — 누군가 데스크에 다시 가서 새 열쇠를 받아와야 한다. 오늘은 아무도 가지 않아 열쇠(토큰)가 만료됨.

**왜 포털의 자동 재로그인(401→silent 재인증)이 안 걸렸나** : 통화 중에는 화면 이동이 없어 navigation 기반 재인증이 돌지 않고, VOC/summary의 401은 백엔드 try-catch가 삼키거나 프론트가 재인증 트리거로 잡지 않음 → 조용히 실패.

**결론** : 오늘 만료 로그의 정체는 **"SSO 세션 → 새 access"로 바꿔주는 갱신 장치가 어드바이저 경로에 붙어있지 않은 공백**. SSO가 있어도 자동 갱신은 아니다.

**확인 필요**
- 프로토콜(OIDC / SAML / 커스텀) 및 **silent 재인증 지원 여부**(OIDC면 `prompt=none` authorize 등)
- **IdP 세션 TTL** ← 실제 "로그인 유지 최대시간"의 기준(access 20분·refresh 1시간보다 이 값이 상한)
- 포털 프론트에 "401 → silent 재인증" 인터셉터가 있는지 / 어드바이저 통화 화면에서만 미동작인지

## 부록 C. 정리 — 구조 이해와 대응 방향

- **원인 재확인** : 이번 이슈의 근본은 "SSO 세션을 새 access 토큰으로 잇는 갱신 장치의 부재"라는 구조적 공백이다. 짧은 access + 프론트 세션스토리지 + 갱신 수단 부재라는 인증 구조를 사전에 충분히 파악하지 못한 채 개발이 진행된 부분이 있으며, 이를 인지한 지금 그 구조를 정확히 이해하고 대응 방향을 정리한다.
- **이번 대응** : 이슈를 계기로 인증/토큰 흐름 구조를 파악했고, 보안·BFF 관점에서 타당한 해결방안(httpOnly 쿠키 + 서버측 토큰 관리·갱신)을 도출.
- **진행 주체** : 인증 레이어 운영이 비개발 영역인 점을 고려해, 어드바이저(개발)에서 구조를 분석하고 해결방안을 제시·주도하는 방향으로 진행.
- **적용/제안**
  - (적용 중) 예외격리(try-catch)로 토큰 만료가 실시간 상담을 중단시키지 않도록 방어.
  - (단기) VOC는 유저 토큰 의존을 제거해 만료와 무관하게 동작하도록 개선(본문 3장).
  - (근본) BFF 서버측 토큰 갱신 + httpOnly 전환으로 SSO 세션을 새 토큰으로 잇는 갱신 장치를 마련(해결방안 1).
