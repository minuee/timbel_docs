## 0. 확정된 전제 (전체를 관통 — 이게 바뀌면 아래가 다 바뀜)

| # | 항목 | 내용 |
|---|---|---|
| 1 | **배포 환경** | **106.242.165.142 단일 서버**에 모든 앱 + **인증서버까지** 함께 기동 (폐쇄망 온프레미스) |
| 2 | **테넌트** | **단일 테넌트 확정** (멀티테넌트 아님) |
| 3 | **앱 구성** | **프론트만 있는 앱은 없음.** 모든 앱이 **토큰을 검증할 수 있는 백엔드**를 가짐 (BFF형 / 순수 API형 무관) |
| 4 | **토큰 보관** | **httpOnly 쿠키에 토큰 직접** — 앱들이 **공유하는 단일 소스** |
| 5 | **검증** | 각 앱 백엔드가 **공통 공용 공개키(JWKS)로 자체 검증** — 인증서버 왕복 없음 |
| 6 | **갱신 주체** | **요청을 받은 앱 백엔드**가 인증서버를 통해 갱신 → **Set-Cookie**로 반영 (프론트는 관여 안 함) |
| 7 | **Rotation** | **채택** + 재사용 감지 + **Grace 윈도우** |
| 8 | **서비스간 통신** | 어드바이저 → AICM 등은 **내부망 도커 서비스명** 통신 → **사용자 토큰 전달·인증 경유 제거** |
| 9 | **Heartbeat** | 포털 셸의 20분 주기 heartbeat **제거 예정** |

> **전제 1(단일 서버)의 파급:** 모든 앱이 같은 호스트라 **쿠키는 포트를 구분하지 않으므로 자동으로 공유됨.** 쿠키 도메인 이슈 없음 → 부록 F에서 이 논점은 뺄 것.
> **전제 2(단일 테넌트)의 파급:** 테넌트 UUID가 상수 → env 설정 또는 로그인 시 `get_user` 수령으로 충분. **매 요청 USER_HOST 왕복이 사라짐 (P4 해소).**

### 전제 3을 관통하는 규칙 (문서 전체에서 이 표현으로 통일)

> **브라우저 요청을 처음 받는 백엔드가 쿠키에서 토큰을 읽어 공개키로 검증한다.** 그 뒤 내부망은 신뢰 구간.
>
> → 각 앱에 필요한 건 **①쿠키에서 토큰 읽기 ②공개키로 검증 ③갱신** 세 가지뿐. **BFF로 구조를 바꿀 필요 없음.**

**⚠ "모든 앱이 자체 백엔드를 가진다"는 표현을 쓰지 말 것.** 사실이지만 **"모든 앱을 BFF로 개조한다"로 오독**됨 → 타 앱 팀이 "우리도 프론트 요청을 전부 중계하란 거냐"로 받아들여 불필요한 반발을 부름. 필요한 건 백엔드의 *형태*가 아니라 **검증 능력**임.

## 1. 🔴 구조 전제가 바뀌어 다시 써야 하는 슬라이드

### 1-1. 부록 E (19장) — "정석형(권장)" 표기를 뒤집기  ★1순위

**현재 문구**
```
[ ] 최소형: access/refresh를 httpOnly 쿠키에 직접 담기
[ ] 정석형(권장): 토큰은 Redis, 브라우저엔 세션ID 쿠키만
```

**왜 뒤집어야 하나**
세션ID 쿠키는 **그 세션을 만든 앱 백엔드만 해석 가능**. AICM·TA·QA 백엔드는 세션ID를 받아도 토큰으로 못 풀어 → **앱 간 SSO가 성립 안 됨.**
정석형을 살리려면 모든 앱이 세션 스토어를 공유해야 하는데, 이는 앱 간 강결합 + 공유 Redis라는 새 SPOF를 만드는 것.

**보완**
```
[v] 채택 — 쿠키 직접형: access/refresh를 httpOnly 쿠키에 직접
    → 모든 앱 백엔드가 같은 쿠키를 읽음 = SSO 성립의 메커니즘
[ ] 비채택 — 세션스토어형: 세션ID 쿠키 + 서버 보관
    → 타 앱이 세션ID를 해석 불가 → SSO 불가
```
→ **"최소형/정석형"이라는 명칭 자체를 폐기.** (지금 이름이 "정석 = 권장"을 함의해서 반대 결론으로 읽힘)

### 1-2. 부록 B (16장) — TO-BE 구조도

**현재**: `BFF / GATEWAY (NestJS)` **단일 박스** 안에 `세션관리(Redis)` · `JWKS 캐시` · `Silent Refresh`

**보완**
- 단일 BFF 박스 → **앱별 백엔드 박스 다수** (포털관리 / 어드바이저 / AICM / 에이전트빌더 / TA / QA), 각 박스 안에 `JWKS 자체 검증`
  - ⚠ 박스를 전부 "BFF"로 라벨링하지 말 것. **어드바이저만 BFF형이고 나머지는 순수 API 백엔드**여도 무방함 — 공통 조건은 **검증 능력**뿐. 라벨은 `앱 백엔드` 정도로 중립적으로.
- **`세션관리(Redis)` 박스 삭제** — 쿠키 직접형이라 인증용 세션 스토어가 없음
- 브라우저 ↔ 각 앱 백엔드에 **공유 httpOnly 쿠키** 화살표
- **신규 화살표**: 앱 백엔드끼리 `내부망 (도커 서비스명) — 사용자 토큰 없음, 내부 헤더만`
- `내부 API 서비스 — 인증서버 직접 연결 없음` 문구는 그대로 유효

### 1-3. 8장 3.1 — "BFF 서버사이드 보관"을 정정

**현재**: "BFF가 access·refresh 서버사이드 보관"
**보완**: 쿠키 직접형이므로 **서버사이드 보관이 아님** → **"토큰은 httpOnly 쿠키에만 존재 · JS 접근 불가 · 앱 백엔드가 쿠키에서 읽어 사용"**
(XSS 차단 효과는 그대로 유효 — 근거가 "서버 보관"이 아니라 **"httpOnly"**로 바뀔 뿐)

### 1-4. 부록 D (18장) — 어드바이저 전용 → 공통으로 승격

**현재**: 쿠키·CSRF·BFF를 어드바이저만 하는 것처럼 분리
**보완**: 모든 앱이 검증 가능한 백엔드를 가지므로 **"입주 서비스 공통(백엔드)"으로 승격**
- 쿠키(httpOnly·Secure·SameSite) 세팅 · CSRF 방어 · JWKS 자체 검증 · **갱신 single-flight**
- ※ **BFF 구조로의 개조를 요구하는 게 아님을 명시할 것.** 각 앱은 기존 형태 그대로, 위 4가지만 추가하면 됨.

**어드바이저 고유로 남는 것**
- **SSE(`/assist-stream`) 경로 대응** (→ 3-3 참조)
- 프론트 직접호출 정리
- **`DynamicDatabaseService` 정리** (→ 2-2)

### 1-5. 부록 F (20장) — Redis 블록 삭제, 쿠키 도메인 논점 제외

- **인증 세션용 Redis 주의사항 5줄 → 삭제.** 쿠키 직접형이라 해당 없음. (기존 Redis는 구독배포·소켓 용도로 계속 사용 — 인증과 무관하다는 것만 한 줄로)
- **쿠키 도메인 공유 이슈 없음** — 단일 서버라 포트만 다르고, **쿠키는 포트를 구분하지 않아 자동 공유**됨. 굳이 슬라이드에 넣을 필요 없음.
- 환경별 표는 **Secure / SameSite만** 남기면 됨 (운영 HTTPS = Secure ON / 개발기 HTTP = Secure 불가)
- 롤아웃 순서는 그대로 유효

## 2. 🟡 사실 확인 후 반영

### 2-1. 토큰 수명 — 정책값 vs 실측값 (3·4·5장)

| 항목 | 현재 PPT (정책) | 실측 (`advisor-refresh-token.md`) |
|---|---|---|
| access | 60분 | **약 20분** |
| refresh | 14일 | **약 1시간 5분** (= access +45분 고정) |
| `/auth/refresh` | 존재 전제 | **부재** (담당자 회신) |

PPT는 담당자 회신(정책값), 실측은 개발서버 토큰 디코드값. 두 번의 로그인 모두 간격이 정확히 45분 → 우연 아님.
→ **권장: `정책 60분 / 실측 20분` 병기.** "정책과 실설정이 다르다"는 것 자체가 6장 문제제기의 근거가 됨.
→ `/auth/refresh` 부재가 사실이면 **Phase 1의 최우선 요청 항목**이 됨 (갱신 구조 전체의 전제).

### 2-2. 단일 테넌트 확정의 파급 — `DynamicDatabaseService` 정리  ★어드바이저 최대 변경점

PPT에 **현재 전혀 없는 내용**인데, 단일 테넌트가 확정이면 반드시 들어가야 함.

- **현재**: `AuthMiddleware` → `DynamicDatabaseService.getConnection(token)` → 토큰으로 USER_HOST에서 `db_config` 조회 → **테넌트별 DataSource 동적 생성** (연결을 tenant_id로 캐싱)
- **문제**: 이 구조 때문에 **토큰이 만료되면 DB 연결 자체가 실패**함 (인증 문제가 DB 문제로 번짐)
- **단일 테넌트면**: 동적 연결이 불필요 → **정적 DB 연결로 단순화** (`DB_DIRECT_CON=1` 방식)
- **효과**: P4의 USER_HOST 매 요청 왕복이 **JWKS 때문이 아니라 이 정리 때문에** 사라짐
  - ※ 주의: JWKS 로컬 검증만으로는 왕복이 안 사라짐. 검증은 로컬로 되지만 **테넌트 해석(`get_configs` / `get_user`)이 남기 때문.** 단일 테넌트 정리가 진짜 열쇠.
- → **로드맵(Phase)에 어드바이저 항목으로 신설 필요**

### 2-3. 4장 "BFF 토큰 검증 방식(멀티테넌트 구조)" — 제목부터 재작성

- "멀티테넌트 구조" 전제가 사라짐
- 현재 실제 동작도 명확히: `auth.middleware.ts:136`에 **`🔍 토큰 검증 생략`** 이 명시돼 있음 → asst는 **토큰 존재만 확인**하고 통과시킴. 401은 그 뒤 **USER_HOST 호출 시점**에 터짐(`getCompanyIdFromToken` → `getCurrentUser`).
- 즉 "검증을 위임"이라기보다 **"검증을 아무도 안 하다가, 하위 조회가 실패하면서 401이 드러남"**에 가까움. AS-IS 설명을 이렇게 쓰면 P4·P1의 근거가 더 선명해짐.

## 3. 🟢 신규 추가

### 3-1. 신규 — 서비스간 내부망 통신 (인증 경유 제거)

이번 개선의 핵심인데 PPT에 아예 없음.

- **현재**: 어드바이저가 하위 서비스(AICM/CE/LLM) 호출 시 **사용자 토큰(`x-auth-token`)을 그대로 포워딩** (proxy 컨트롤러들이 `req.token` 전달)
- **개선**: **내부망 도커 서비스명 통신** → 사용자 토큰 전달 제거. 앱 백엔드가 **경계에서 인증을 끝내고**, 내부는 신뢰 구간.
- **필요**: 사용자 토큰 대신 **내부 헤더**(`X-Tenant-Id` 등)로 컨텍스트 전달 → 16장의 "검증된 요청 + 내부 헤더"와 일치
- **⚠ 반드시 명시**: 이건 **"내부망은 신뢰한다"는 의도적 신뢰 경계 설정**임. 내부망 접근 주체는 사용자 사칭이 가능해지므로, 네트워크 정책 또는 방화벽으로 경계를 지킨다는 전제를 같이 써야 함. **보안팀 설명 시 반드시 질문 나오는 지점.**

### 3-2. 8장 3.2 — Grace 윈도우: 필요 이유 + 정확한 스펙

**현재**: "정상 재시도 흡수용 짧은 허용 구간" 한 줄
**보완 — 왜 필요한가**
> access 만료 순간에 **서로 다른 앱이 동시에** 요청하면, 둘 다 쿠키에서 같은 old refresh를 읽어 동시 갱신을 시도함. 하나가 먼저 회전시키면 나머지는 **폐기된 refresh를 내밀게 되어 재사용 감지에 오탐** → 세션 전체 무효화(강제 로그아웃).
> 빈도는 낮지만 **재현이 안 되는 간헐적 로그아웃**으로 나타나 원인 추적이 매우 어려움. 인증서버 설정만으로 막을 수 있어 비용 대비 효과가 큼.

**보완 — 인증서버 담당에게 요청할 정확한 스펙** (이 문구가 빠지면 반쪽이 됨)
> **Grace 기간(예: 10~30초) 내에 같은 refresh가 재요청되면, 새로 발급하지 말고 "먼저 발급했던 그 토큰 쌍을 그대로" 반환할 것.**
>
> 이유: grace가 있어도 매번 새로 회전시키면 병렬 요청 N개가 각각 다른 토큰을 받아 **Set-Cookie를 서로 덮어씀** → 마지막 것만 살아남고 나머지는 고아가 되어 회전 체인이 깨짐. **동일 토큰 반환**이어야 N개가 같은 값을 써서 덮어써도 무해.

**동반 필수 — 앱 백엔드 single-flight** (부록 D 공통 항목에 추가)
> 같은 앱 안의 병렬 요청(화면 로드 시 5~10개 동시)은 **훨씬 흔한 케이스**. 앱 백엔드 내부에서 갱신 Promise 하나를 공유해 **인증서버를 1회만 호출**하면 grace 없이도 해결됨. **동시 갱신의 대부분을 여기서 흡수함.**
> → 정리: **single-flight = 앱 내부 동시성 (흔함) / Grace = 앱 간 동시성 (드묾, 보험)**

### 3-3. 9장 3.3 — SSE 대응을 구체화  ★rotation 채택으로 새로 생긴 이슈

**현재**: "SSE 대응: 인터셉터 밖 경로도 갱신 대상에 포함 (별도 처리)" — 추상적

**보완 — rotation을 넣으면 SSE에 구조적 함정이 있음**
> SSE(`/assist-stream`)는 **응답 헤더가 이미 전송된 뒤**라 스트림 도중에는 **Set-Cookie가 불가능**함.
> 그래서 백엔드가 스트림 중 갱신하면 → 백엔드는 새 refresh(R2)를 갖는데 **브라우저 쿠키엔 폐기된 R1이 잔류** → 다음 일반 요청이 R1을 들고 감 → **재사용 감지 오탐 → 세션 몰살.** Grace(10~30초)로도 못 덮음(스트림이 더 길면).

**해결**
> **SSE 시작 직전에 access 잔여 수명을 확인하고, 임박하면 먼저 갱신(일반 HTTP 응답이므로 Set-Cookie 가능)한 뒤 스트림을 시작.**
> `/assist-stream`은 **발화 단위로 단명**하므로 이 방식으로 충분히 커버됨.

**참고 — AS-IS 실제 사고 사례 (6장 P1의 근거로 쓸 수 있음)**
> 고객사 시연 중 실시간 VOC가 첫 발화 후 멈춤. access 만료(약 20분) → `getCompanyIdFromToken` → USER_HOST 401 → VOC 분석 스킵. `/assist-stream`은 `AuthMiddleware` 제외 경로라 컨트롤러가 `x-auth-token`을 직접 추출하고, fire-and-forget이라 조용히 스킵됨. **코드 버그가 아니라 인증 구조 문제.**

### 3-4. 5장 — Heartbeat 제거를 "부록 C 정책의 성립 조건"으로 배치

**현재**: "포털 — 20분 주기 Heartbeat 체크"가 현 구조 설명으로만 있음 (제거 예정임이 안 보임)

**보완**
> heartbeat는 TO-BE에서 **제거**됨 (갱신은 앱 백엔드가 만료 임박 시 수행).
> 단순 정리가 아니라 **부록 C의 유휴 타임아웃 정책이 성립하기 위한 전제**임:
> **현재는 20분 heartbeat가 계속 갱신을 걸어서, 상담사가 자리를 비워도 세션이 죽지 않음 → 유휴 타임아웃(30분, 공용 PC 보안)이 영원히 발동하지 않음.**
> heartbeat를 제거해야 유휴 타임아웃이 실제로 동작함.
> (부수 효과: 앱 간 동시 갱신 경합의 주요 발생원 하나가 사라짐 → 3-2의 위험이 추가로 낮아짐)

### 3-5. 9장 3.5 — JWKS의 위상 격상

**현재**: JWKS가 "왕복 제거 = 성능·SPOF 해소" 이점으로만 설명되고, Phase 3(중기)에 배치
**보완**: 실제로는 **"모든 앱 백엔드가 공통 공용 공개키로 각자 검증"이 앱 간 SSO를 성립시키는 메커니즘 그 자체.**
→ 성능 개선이 아니라 **이 구조의 전제 조건**이므로, Phase 3에 두는 게 맞는지 우선순위 재검토 필요.

### 3-6. 3장·6장 P5 — "혼합구조" 지적이 해소됨을 명시

**현재**: 3장은 "BFF 경유 요청과 프론트 직접 호출이 혼재 → **인증 경로가 단일하지 않음**"을 문제로 잡고, 6장 P5도 갱신 로직 비일관을 지적함.

**보완**: 전제 3의 규칙(**브라우저를 처음 받는 백엔드가 검증**)을 적용하면 **혼합구조 자체는 더 이상 문제가 아님.**
> 경로가 BFF를 거치든 API를 직접 호출하든, **첫 백엔드가 쿠키를 읽어 공개키로 검증한다**는 규칙 하나로 양쪽이 동일하게 커버됨.
> → "인증 경로가 단일하지 않다"는 지적은 **경로를 하나로 합쳐서가 아니라, 경로마다 규칙이 같아져서** 해소됨.
> → 갱신도 마찬가지 — 어느 백엔드가 받든 동일하게 갱신 후 Set-Cookie. 프론트는 관여하지 않으므로 MFE별 복붙 문제(P5)도 같이 사라짐.

**왜 명시해야 하나**: 이걸 안 쓰면 "혼합구조를 없애야 한다"(= 직접호출을 전부 BFF 경유로 개조)로 읽힘. **실제로는 개조 없이 규칙 통일만으로 해소되므로**, 작업량이 크게 달라 보이는 지점.
