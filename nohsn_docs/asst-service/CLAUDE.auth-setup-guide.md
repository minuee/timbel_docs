# 인증 개선 구현 가이드 (역할별 설치가이드)

> 대상: **포털(인증서비스) 담당 / 입주 서비스 담당(프론트·백엔드)**. 우선 **어드바이저**(asst-web 프론트 + asst-service 백엔드) 기준, 타 서비스는 공통 규칙 + 환경 분기로 커버.
> 준거: `CLAUDE.auth-architecture.md` §3 — RFC 9700(OAuth 2.0 Security BCP) + IETF OAuth for Browser-Based Apps BCP.
> **채택안 = 옵션2(현 `/auth` 최소개조).** 옵션1(표준 OIDC)은 장기 승격안으로 부록에 요약.

---

## 0. 개요 및 범위

- **로그인은 현행 포털 SSO 방식을 유지한다.** 사용자는 포털(`/auth/login`)에서 로그인 후 입주 서비스(어드바이저 등)로 진입하며, 로그인 화면·방식은 변경하지 않는다.
- 개선 범위는 로그인 방식이 아니라 **토큰의 보관·전달·검증 방식**이다.
  - 저장: 프론트 스토리지(session+local) → **httpOnly 쿠키**
  - 검증: 매 요청 `USER_HOST` 위임 → **각 서비스가 공개키(JWKS)로 로컬 검증**
  - 수명: access 단축 + **refresh 회전(rotation)**
- **역할 분리**: 토큰 발급·갱신 = 포털 인증서비스(개인키), 토큰 검증 = 각 서비스(공개키 로컬).

### 환경 분기 (담당자 답변 반영)
| 축 | 상황 | 가이드 |
|---|---|---|
| 접속 방식 | 환경마다 다름(운영 HTTPS+도메인 / 개발기 HTTP+IP) | §5 쿠키 보안 분기 |
| 게이트웨이 | **어드바이저 = 없음(직접)** / 타 서비스 = 있음·없음 혼재 | §3(직접) + §4(게이트웨이) |
| 세션 저장소 | Redis 사용 가능하나 기존 부하 큼 | §6 분리·이중화 주의 |

## 1. 포털 = 인증서비스 담당 작업 (⚠ 선행 — 이게 돼야 나머지가 가능)

> 로그인 자체(`/auth/login`)는 유지. 아래는 "토큰 발급 방식"과 "검증용 공개키 배포"만 손보는 것.

- [ ] **RS256 키쌍 관리**: 개인키는 인증서비스만 보관(서명), **공개키는 외부 배포**. 키 회전 대비해 `kid` 복수 병존 지원. (현 토큰에 `kid:"timbel-on-premise-v1"` 이미 존재)
- [ ] **JWKS 엔드포인트 공개**: `GET /.well-known/jwks.json` → 각 서비스가 여기서 공개키를 받아 캐시하고 로컬 검증. **이 하나가 §2 로컬검증의 전제.**
- [ ] **access 수명 단축**: 60분 → 수 분(예 5~15분, 정책). 짧을수록 로컬검증의 "즉시 폐기 지연" 리스크↓.
- [ ] **refresh 회전 + 재사용 감지**: 갱신 때마다 새 refresh 발급, 폐기된 옛 refresh 재등장 시 **세션 무효화 + 재로그인**. 정상 재시도용 짧은 grace 윈도우. (현 refresh 14일 → 단축)
- [ ] **클레임 최소화 유지**: 토큰엔 신원·role 등 최소만(현 상태 양호). 소속/개인정보는 계속 `get_user` 조회.
- [ ] (옵션2) 로그인 API는 **자체 `/auth/login` 유지**. 응답을 토큰 그대로 줄지, 쿠키로 내려줄지는 §3-A 방식과 맞춰 결정.

## 2. 입주 서비스 공통 규칙 (어드바이저 포함 전 서비스가 지킴)

### 2-A. 백엔드(BFF/API) 공통
- [ ] **JWKS 로컬 검증 도입**: 시작 시(+주기적으로) 포털 JWKS를 받아 캐시 → 요청 토큰의 **서명·만료(exp)·발급자**를 자체 검증. `kid`로 공개키 매칭.
- [ ] **`USER_HOST` 매 요청 검증 위임 제거** (발급/갱신 외 인증서비스 호출 안 함).
- [ ] 검증 실패(만료·위조) → 401 일관 반환.

### 2-B. 프론트 공통
- [ ] **토큰을 sessionStorage/localStorage에 저장 금지** → **쿠키 기반**으로 전환. (현 `aicc-token`/`accessToken`/`aicc-refresh-token` 등 저장 제거)
- [ ] API 호출 시 **`credentials:'include'`** (쿠키 자동 전송). 프론트가 `Authorization`/`X-auth-token` 헤더를 **직접 만들지 않음**.
- [ ] **프론트 refresh 인터셉터 제거** — 갱신은 백엔드가 담당. 프론트는 401 시 재로그인 유도만.

## 3. 어드바이저 구체 작업 (게이트웨이 없음 = 직접 접속 기준)

### 3-A. 어드바이저 백엔드 (asst-service = BFF)
- [ ] **토큰을 httpOnly 쿠키로 관리**: 포털 로그인으로 받은 토큰을 프론트에 노출하지 않고 **BFF가 httpOnly·Secure·SameSite 쿠키로 세팅**. (JS 접근 차단 = XSS 방어 핵심)
  - 최소형: access/refresh를 httpOnly 쿠키에 직접 담기.
  - 정석형(권장): 토큰은 **서버 세션 저장소(Redis)** 에 두고 브라우저엔 **세션ID 쿠키만** — 토큰 자체를 브라우저에서 완전 제거. (§6)
- [ ] **쿠키 → 토큰 부착**: 들어온 요청의 쿠키에서 access를 꺼내 내부/업스트림 호출 헤더(`X-auth-token`)에 부착.
- [ ] **silent refresh(서버측)**: access 잔여수명이 임계값 이하면 BFF가 refresh로 선제 갱신(회전). 실패 시 세션 만료 → 재로그인.
- [ ] **JWKS 로컬 검증**(2-A) 적용, `USER_HOST` 위임 제거.
- [ ] **CSRF 방어**: SameSite=Lax 기본 + 상태변경(POST/PUT/DELETE) 요청에 CSRF 토큰(더블 서브밋 쿠키 등).
- [ ] **SSE/스트리밍 경로**(assist-stream 등)도 쿠키 인증 + 만료 대응 포함 — 인터셉터 밖 경로라 별도 확인.

### 3-B. 어드바이저 프론트 (asst-web)
- [ ] 2-B 공통 전부 적용(스토리지 토큰 제거, `credentials:'include'`, refresh 인터셉터 제거).
- [ ] 로그인 흐름은 **현행 유지**(포털 SSO). 다만 로그인 결과를 스토리지에 저장하지 말고 **쿠키로** 받게 조정.
- [ ] **직접호출(파일 API 등)을 BFF 경유로 변경(a안)**: 브라우저가 서비스 IP:포트를 직접 때리는 호출 제거 → BFF/프록시 경로 추가. (내부망·서비스명 접근이라 라우트만 추가하면 됨)

## 4. 게이트웨이가 있는 서비스(타 서비스용) 추가/대체

> 어드바이저는 해당 없음. nginx/Spring Cloud Gateway 등을 쓰는 서비스용.

- [ ] **인증 종단을 게이트웨이로**: 게이트웨이가 쿠키 검증 + JWKS 토큰 로컬검증 후, 내부 서비스엔 검증된 토큰/신원 헤더를 부착해 전달(각 서비스 중복검증 최소화).
- [ ] **또는** 게이트웨이는 통과만, 각 서비스 백엔드가 §2-A대로 자체 검증(직접 방식과 동일). ← 서비스 특성에 맞게 택1.
- [ ] 직접호출 서비스(파일 API 등)도 게이트웨이 라우트 뒤로 넣어 **쿠키 기반 인증**으로 통일(a안).

## 5. 환경별 쿠키 보안 (접속 방식이 다르므로 필수)

| 환경 | Secure | SameSite | Domain | 비고 |
|---|---|---|---|---|
| 운영 HTTPS + 도메인 | **Secure on** | Lax(동일사이트) / 크로스출처면 None+Secure | 상위도메인(`.xxx.com`)이면 서비스 간 쿠키 공유 | 권장 최종형 |
| 개발기 HTTP + IP:포트 | Secure **불가** | Lax | IP는 도메인 쿠키 공유 안 됨 | **개발기 한정 완화**, 운영은 반드시 HTTPS |

- [ ] **httpOnly는 전 환경 필수**(XSS 방어의 핵심).
- [ ] `[환경확인]` 포털·어드바이저가 **같은 상위도메인**인지 → 쿠키 공유·SameSite 정책 확정.
- [ ] HTTP+IP 개발기는 Secure 불가 → **운영은 HTTPS 전제**임을 못박기.

## 6. 세션 저장소(Redis) 주의

- 기존 Redis가 **구독배포·소켓 등으로 부하 큼** → 인증 세션을 얹을 때 성능·이중화 영향 점검 필수.
- [ ] **권장 분리**: 인증 세션은 **별도 논리 DB(다른 `REDIS_DB`)** 또는 가능하면 **별도 인스턴스**로 기존 트래픽과 격리.
- [ ] 세션 **TTL**(refresh 수명과 연동), 만료·회전 시 정리.
- [ ] `[환경확인]` HA 구성에서 세션 저장소 장애 시 정책(페일오버 / 재로그인) 결정.
- 참고: 3-A "최소형(쿠키에 토큰 직접)"으로 가면 Redis 없이도 시작 가능 — 부하가 부담되면 최소형부터, 이후 정석형(세션스토어)으로 승격.

## 7. 롤아웃 & 하위호환

- **순서**: ① 포털 JWKS·rotation·short access(§1) → ② 각 서비스 로컬검증(§2-A) → ③ 프론트 쿠키 전환(§2-B·§3-B) → ④ 직접호출 프록시화(a안, §3-B).
- **하위호환**: 전환기엔 **쿠키 우선 + 헤더 폴백** 병행(기존 헤더 토큰도 당분간 수용) → 서비스별 순차 전환, 빅뱅 회피.
- **동작 검증**: 포털 로그인 → 어드바이저 API(BFF, 쿠키) → 직접호출(프록시) → access 만료 시 silent refresh → refresh 재사용 시 세션 무효화, 각 단계 실제 확인.

## 8. `[환경확인]` — 구현 확정 전 담당자 확인값

- [ ] 운영/개발기 **접속 URL 형태**(HTTPS+도메인 / HTTP+IP)와 **포털·어드바이저 도메인 관계**(같은 상위도메인 여부).
- [ ] 인증서비스 **JWKS 공개 가능 여부**(자체 서명만 하는 현 상태에서 `/.well-known/jwks.json` 신설 필요).
- [ ] access/refresh **목표 수명값**(예 access 10분 / refresh 며칠) 정책 결정.
- [ ] 세션 저장소: Redis **분리 DB/인스턴스** 가능 여부, HA 정책.
- [ ] 타 서비스별 **게이트웨이 유무**와 파일 API 등 **직접호출 서비스 목록**.

## 부록. 옵션1(표준 OIDC) — 장기 승격안

**한마디로 "구글/카카오 로그인"과 같은 방식이다.** 차이는 로그인 제공자가 외부(구글)가 아니라 **우리 포털**이라는 점 — 포털을 SNS처럼 "로그인 제공자"로 세우는 것이다. (표준 용어로는 OAuth 2.0 Authorization Code + PKCE, 로그인 표준은 OIDC)

**동작 (SNS 로그인과 동일한 흐름):**
1. 사용자가 서비스 접속 → 포털 로그인 페이지로 이동
2. 포털에서 로그인 (비밀번호는 포털만 확인)
3. 포털이 **일회용 인가코드**를 서비스에 전달
4. 서비스 백엔드가 그 코드를 **토큰으로 교환**

> "구글로 로그인 → 구글이 코드 발급 → 우리 서버가 토큰으로 교환"과 동일하며, 여기서 구글 자리에 **우리 포털**이 들어간 것이다.

**옵션2와의 관계:**
- 로그인은 포털 SSO로 동일. 차이는 토큰 전달을 표준 코드 교환 방식으로 바꾸는 것.
- 이점: 자격증명 격리 강화, 표준 SSO, 표준 도구·생태계 활용.
- 비용: 포털에 표준 로그인 엔드포인트 신설 필요.
- 옵션2에서 구축한 JWKS·refresh 회전·access 단축·쿠키 자산은 **그대로 재사용**되므로, 옵션2는 옵션1의 디딤돌이 된다.
