# 하이브리드 검색 쿼리 선택 전략 - 구현 계획서

## 1. 배경 및 문제 정의

### 현재 문제
- `QueryBuilder`가 Context + NER + MeCab 기반으로 생성한 `search_query`가 간혹 실제 문서 검색에 도움이 되지 않는 경우 발생
- 이 경우 오히려 **마지막 발화(query) 원문**이 더 나은 검색 결과를 가져올 수 있음

### 예시

| 상황 | query (마지막 발화) | search_query (생성된 검색어) | 더 나은 쪽 |
|------|---------------------|------------------------------|------------|
| 직접적 질문 | "배송 언제 오나요" | "크림색, 배송" | query |
| 대명사 질문 | "그건 어떻게 해요" | "반품 접수, 방법" | search_query |
| 애매한 경우 | "환불 받고 싶은데요" | "환불, 접수" | 둘 다 비슷 |

### 해결 방향: 하이브리드 방식
- NLP 엔진에서 `search_query`와 `query`의 품질을 사전 비교
- 한쪽이 압도적으로 좋으면 **그것만** Search Engine에 전달 (불필요한 이중 검색 방지)
- 둘 다 애매하면 **둘 다** 전달하고 Search Engine에서 실제 점수 기반으로 최종 결정

## 3. 하이브리드 방식 전체 흐름

```
[호출자] → NLP Engine (query, context)
                ↓
        ┌─ search_query 생성 (기존 로직)
        ├─ query vs search_query 품질 비교 (신규)
        │   → query_similarity_score 계산
        │   → search_mode 결정 ("search_query" | "query" | "both")
        └─ IntegrateResponse 반환
                ↓
[호출자] → search_mode에 따라 Search Engine 호출
        ├─ "search_query" → text=search_query (기존과 동일)
        ├─ "query"        → text=query
        └─ "both"         → text=search_query, alt_text=query
                ↓
        [Search Engine Service]
        ├─ alt_text 없으면 → 기존 로직
        └─ alt_text 있으면 → 이중 검색 + 비교 후 최종 결과 반환
```

## 3-1. 판별 기준: "둘 중 뭐가 더 나은가"를 어떻게 알 수 있는가

### 핵심 아이디어 한 줄 요약

> **"대화 전체의 맥락과 의미적으로 더 가까운 쪽이 더 좋은 검색어다."**

### 비유: 도서관 사서에게 책을 찾아달라고 할 때

도서관에 가서 사서에게 책을 찾아달라고 하는 상황을 떠올려보자.

당신은 친구와 이런 대화를 나누고 있었다:
```
친구: "요즘 허리가 너무 아파서 병원 갈까 봐"
나:   "스트레칭이 좋다던데"
친구: "어떤 스트레칭?"
나:   "유튜브에서 봤는데 되게 좋더라"    ← 마지막 발화 (query)
```

이 대화를 기반으로 **두 가지 검색어**가 만들어진다:

| 후보 | 내용 | 비유 |
|------|------|------|
| **search_query** (NLP가 생성) | `"허리, 스트레칭, 유튜브"` | 대화에서 핵심 키워드를 뽑은 메모지 |
| **query** (마지막 발화 원문) | `"유튜브에서 봤는데 되게 좋더라"` | 내가 마지막에 한 말 그대로 |

자, 이제 사서에게 이 두 메모 중 하나를 건넨다고 하자:
- `"허리, 스트레칭, 유튜브"` ← 맥락 키워드. 사서가 이걸 보면 "아, 허리 스트레칭 관련 영상을 찾는구나" 이해 가능
- `"유튜브에서 봤는데 되게 좋더라"` ← 원문 그대로. 사서가 이걸 보면 "뭐가 좋다는 거지...?" 이해 불가

**이 경우 search_query가 압도적으로 낫다.** 대화의 맥락(허리+스트레칭)을 잘 담고 있으니까.

반대로 이런 대화가 있다면:
```
상담원: "주문하신 상품 안내 도와드릴게요"
고객:   "배송 언제 오나요"    ← 마지막 발화 (query)
```

| 후보 | 내용 |
|------|------|
| **search_query** | `"상품, 안내"` |
| **query** | `"배송 언제 오나요"` |

사서한테 뭘 줄 것인가? `"상품, 안내"`를 주면 엉뚱한 책을 찾아올 것이고, `"배송 언제 오나요"`를 주면 정확히 배송 관련 문서를 찾아줄 것이다.

**이 경우 query(마지막 발화)가 압도적으로 낫다.**

### 그럼 "맥락과 가깝다"를 컴퓨터는 어떻게 측정하는가?

#### Step 1: "대화 전체 맥락"을 하나의 기준점으로 만든다

대화의 context(이전 발화들) + 마지막 발화(query)를 전부 하나의 텍스트로 합친다.
이것이 **"이 대화가 전체적으로 무엇에 대한 이야기인가"**를 나타내는 기준점(Reference)이 된다.

```
reference_text = "배송 언제 오나요 주문하신 상품 안내 도와드릴게요"
                  ^^^^^^^^^^^^^^^^^^^  ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
                  마지막 발화(query)     이전 대화(context)
```

#### Step 2: 세 개의 텍스트를 "의미 공간"에 점으로 찍는다

Sentence Transformer (ko-sroberta-multitask) 모델이 텍스트를 768차원 벡터로 변환한다.
쉽게 말하면, **모든 텍스트를 거대한 지도 위의 한 점으로 변환**하는 것이다.

이 지도에서는:
- 의미가 비슷한 텍스트 → 가까운 점
- 의미가 다른 텍스트 → 먼 점

```
의미 공간 (고차원이지만 2D로 비유)

        "상품, 안내" (search_query)
              ●
             /
            /  거리 = 먼 편
           /
    ★ "배송 언제 오나요 주문하신 상품 안내..."  (reference = 기준점)
           \
            \  거리 = 가까운 편
             \
              ●
        "배송 언제 오나요" (query)
```

#### Step 3: 기준점과의 거리를 코사인 유사도로 측정한다

코사인 유사도(Cosine Similarity)는 두 벡터 사이의 각도를 재는 것이다.
- **1.0** = 완전히 같은 방향 (의미 동일)
- **0.0** = 완전히 무관
- **-1.0** = 완전히 반대 (실제로는 거의 안 나옴)

```python
search_query_score = cosine_similarity(reference, search_query)  # 예: 0.72
raw_query_score    = cosine_similarity(reference, query)         # 예: 0.85
```

이 예시에서는:
- search_query `"상품, 안내"` → 기준점과 0.72 (좀 멀다)
- query `"배송 언제 오나요"` → 기준점과 0.85 (더 가깝다)

#### Step 4: 점수 차이로 승자를 결정한다

```python
score_diff = search_query_score - raw_query_score
           = 0.72 - 0.85
           = -0.13
```

이 차이를 **HYBRID_DOMINANCE_THRESHOLD (기본값 0.15)** 와 비교한다:

```
         -0.15                  0                  +0.15
  ─────────┼──────────────────┼──────────────────┼─────────
  query 압승     ← "둘 다 던지기" 구간 →      search_query 압승
  (query만 사용)       (both)              (search_query만 사용)
```

| score_diff 값 | 판정 | 의미 |
|---------------|------|------|
| **+0.15 이상** | search_query 단독 사용 | search_query가 맥락을 훨씬 잘 반영 |
| **-0.15 ~ +0.15** | 둘 다 던지기 (both) | 비슷비슷해서 판단 어려움 → 실제 검색 결과로 결정 |
| **-0.15 이하** | query 단독 사용 | 마지막 발화가 맥락을 훨씬 잘 반영 |

위 예시에서 score_diff = -0.13 이므로 **"둘 다 던지기"** 구간에 해당한다.
(query가 좀 더 낫긴 하지만, 압도적이지는 않으므로 안전하게 둘 다 보내자는 판정)

### 비유 정리: "취업 면접관이 이력서 2장 중 하나를 고르는 것"

```
면접관 = Sentence Transformer 모델
채용 공고(JD) = reference_text (대화 전체 맥락)
이력서 A = search_query (키워드 조합)
이력서 B = query (마지막 발화 원문)

면접관이 하는 일:
1. 채용 공고를 읽는다 (reference 임베딩)
2. 이력서 A를 읽는다 (search_query 임베딩)
3. 이력서 B를 읽는다 (query 임베딩)
4. "이 채용 공고에 더 적합한 이력서는?" → 코사인 유사도로 점수 매기기
5. 한쪽이 압도적이면 그 이력서만 서류 통과
6. 비슷하면 둘 다 면접 보게 함 (= 둘 다 검색 엔진에 던짐)
```

### 왜 "기준점"에 query(마지막 발화)를 포함시키는가?

의문이 들 수 있다: "기준점에 query가 이미 포함되어 있으면 query 쪽이 항상 유리한 거 아닌가?"

맞다. query 원문은 기준점에 자기 자신이 포함되어 있으니 구조적으로 약간 유리하다.
하지만 이것은 **의도된 설계**다:

- query 원문이 기준점과 높은 유사도를 가지는 것은 **당연하다** (자기 자신이 포함되어 있으니까)
- search_query가 이 "당연한 유리함"을 **넘어설 정도로** 높은 유사도를 가진다면, 그것은 정말로 맥락을 잘 요약한 좋은 검색어라는 뜻이다
- 즉, search_query가 높은 점수를 받으려면 **정말 맥락을 잘 반영해야 한다**는 높은 기준이 적용되는 것

이것은 마치 **홈팀 불리 핸디캡**과 같다:
- query(마지막 발화) = 홈팀 (기본 유리)
- search_query(생성 키워드) = 원정팀 (불리하지만, 이겨도 이긴 것)
- search_query가 이기면 → "진짜 좋은 검색어" 확신 가능
- 비겼거나 애매하면 → 둘 다 보내서 실제 검색 결과로 판단 (안전망)

### "both" 모드일 때: Search Engine에서의 2차 판별

NLP 엔진의 판별은 어디까지나 **사전 예측(Pre-judgment)**이다.
실제로 문서 DB에 어떤 문서가 있는지는 NLP 엔진이 모른다.

"both" 모드에서는 Search Engine이 **진짜 검색 결과**로 최종 판단한다:

```
search_query "반품, 접수"로 검색 → [문서A(0.85), 문서B(0.80), 문서C(0.78)]
query "그건 어떻게 해요"로 검색   → [문서D(0.62), 문서E(0.55)]
```

비교 기준은 단순하다: **상위 K개 문서의 평균 점수**.

```
search_query 평균: (0.85 + 0.80 + 0.78) / 3 = 0.81
query 평균:        (0.62 + 0.55) / 2         = 0.59
→ search_query 승. 이쪽 결과를 기반으로 반환.
```

추가로, **교집합 문서**(두 쿼리 모두에서 발견된 문서)가 있다면 이 문서들이 가장 높은 우선순위를 받는다.
두 방법 모두에서 찾아진 문서는 관련성이 높을 확률이 크기 때문이다.

### 요약: 판별은 2단계로 이루어진다

```
┌─────────────────────────────────────────────────────────┐
│ 1단계: NLP 엔진 (사전 예측)                               │
│                                                         │
│ 기준 = "대화 전체 맥락과 의미적으로 누가 더 가까운가"        │
│ 도구 = Sentence Transformer + 코사인 유사도                │
│ 판정 = 한쪽 압승이면 그것만, 애매하면 "both"                 │
│                                                         │
│ 비유: 면접관이 이력서 보고 "서류 합격" 판단                  │
│ 한계: 실제 문서 DB를 모른다 (예측일 뿐)                     │
├─────────────────────────────────────────────────────────┤
│ 2단계: Search Engine (실전 검증) - "both"일 때만 작동       │
│                                                         │
│ 기준 = "실제로 검색해본 결과 점수가 누가 더 높은가"          │
│ 도구 = Milvus/ES 검색 점수 + 교집합 분석                   │
│ 판정 = 평균 점수 높은 쪽 + 교집합 문서 우선 배치             │
│                                                         │
│ 비유: 면접관이 실제 면접 보고 "최종 합격" 판단               │
│ 강점: 실제 데이터 기반이라 정확하다                          │
└─────────────────────────────────────────────────────────┘
```

## 4. 수정 대상 및 상세 구현

### 4-1. NLP Engine 수정

#### (A) `semantic_scorer.py` - 쿼리 품질 비교 메서드 추가

기존 `SemanticScorer`에 `compare_queries()` 메서드를 추가한다.
`search_query`와 `query`를 각각 Context 기반으로 임베딩하여 코사인 유사도를 비교한다.

```python
# pipeline/keyword_scorer/semantic_scorer.py

class SemanticScorer:
    # ... 기존 코드 유지 ...

    # 하이브리드 모드 임계값 설정
    HYBRID_DOMINANCE_THRESHOLD = 0.15  # 한쪽이 이 값 이상 우세하면 단독 사용
    HYBRID_MIN_SCORE = 0.3             # 최소 유사도 (이하면 해당 쿼리 사용 안 함)

    def compare_queries(
        self,
        search_query: str,
        raw_query: str,
        context: List[Dict[str, str]],
    ) -> Dict[str, Any]:
        """
        search_query와 raw_query(마지막 발화)의 검색 적합도를 비교.

        비교 기준:
        - Context + 발화 전체를 결합한 텍스트와의 코사인 유사도
        - search_query는 키워드 조합이므로, 원래 대화 맥락과의 의미적 연관성 측정
        - raw_query는 자연어 문장이므로, 대화 맥락과의 직접적 연관성 측정

        Returns:
            {
                "search_query_score": float,
                "raw_query_score": float,
                "score_diff": float,           # search_query_score - raw_query_score
                "recommended_mode": str,        # "search_query" | "query" | "both"
            }
        """
        try:
            model = self._get_model()

            # Context 전체 텍스트 결합 (발화 맥락 = 비교 기준점)
            context_text = " ".join([
                turn.get("content", "") for turn in context
            ])

            # 비교 기준: query + context 전체 결합 텍스트
            reference_text = f"{raw_query} {context_text}".strip() if context_text else raw_query

            # 배치 임베딩: [reference, search_query, raw_query]
            embeddings = model.encode([reference_text, search_query, raw_query])

            ref_embed = embeddings[0]
            sq_embed = embeddings[1]
            rq_embed = embeddings[2]

            search_query_score = float(self._cosine_similarity(ref_embed, sq_embed))
            raw_query_score = float(self._cosine_similarity(ref_embed, rq_embed))

            score_diff = search_query_score - raw_query_score

            # 모드 결정 로직
            if search_query == raw_query:
                # search_query와 원문이 동일하면 그냥 하나만
                recommended_mode = "search_query"
            elif score_diff >= self.HYBRID_DOMINANCE_THRESHOLD:
                # search_query가 압도적으로 우세
                recommended_mode = "search_query"
            elif score_diff <= -self.HYBRID_DOMINANCE_THRESHOLD:
                # raw_query가 압도적으로 우세
                recommended_mode = "query"
            else:
                # 애매하면 둘 다 던지기
                recommended_mode = "both"

            result = {
                "search_query_score": round(search_query_score, 4),
                "raw_query_score": round(raw_query_score, 4),
                "score_diff": round(score_diff, 4),
                "recommended_mode": recommended_mode,
            }

            if self.DEBUG_LOG_ENABLED:
                logger.debug(
                    f"[QueryCompare] search_query='{search_query}' ({search_query_score:.4f}) "
                    f"vs raw_query='{raw_query}' ({raw_query_score:.4f}) "
                    f"→ mode={recommended_mode} (diff={score_diff:.4f})"
                )

            return result

        except Exception as e:
            logger.warning(f"쿼리 비교 실패: {e}")
            # 실패 시 안전하게 둘 다 던지기
            return {
                "search_query_score": 0.0,
                "raw_query_score": 0.0,
                "score_diff": 0.0,
                "recommended_mode": "both",
            }
```

    def search_document(self, request_dict: Dict[str, Any]):
        from utils.naturalness_utils import compute_naturalness_score
        query = request_dict.get('text')
        alt_query = request_dict.get('alt_text', None)
        workspace_id = request_dict.get('workspace_id')
        filters = request_dict.get('filters', None)
        top_k = request_dict.get('top_k')
        search_type = request_dict.get('search_type')
        threshold = request_dict.get('threshold')
        boost_filters = request_dict.get('boost_filters', None)
        boost_weight = request_dict.get('boost_weight', 1.5)

        # alt_text 유효성 검사: 동일하거나 비어있으면 단일 쿼리 모드
        use_dual_query = (
            alt_query is not None
            and alt_query.strip() != ""
            and alt_query.strip() != query.strip()
        )

        if not use_dual_query:
            # 기존 로직 그대로 실행 (변경 없음)
            return self._search_single_query(request_dict)

        # ========== 이중 쿼리 모드 ==========
        logger.info(f"[DualQuery] text='{query}' | alt_text='{alt_query}'")

        from concurrent.futures import ThreadPoolExecutor
        with ThreadPoolExecutor(max_workers=2) as executor:
            # 두 쿼리를 병렬로 검색
            future_primary = executor.submit(
                self._search_single_query,
                {**request_dict, 'text': query, 'alt_text': None}
            )
            future_alt = executor.submit(
                self._search_single_query,
                {**request_dict, 'text': alt_query, 'alt_text': None}
            )

            primary_results = future_primary.result()
            alt_results = future_alt.result()

        # 결과 비교 후 최종 선택
        final_results = self._select_best_results(
            primary_results=primary_results,
            alt_results=alt_results,
            primary_query=query,
            alt_query=alt_query,
            search_type=search_type,
            top_k=top_k,
        )

        return final_results

#### (C) `engine_service.py` - 결과 비교/선택 메서드

```python
    def _select_best_results(
        self,
        primary_results: Dict[str, Any],
        alt_results: Dict[str, Any],
        primary_query: str,
        alt_query: str,
        search_type: str,
        top_k: int,
    ) -> Dict[str, Any]:
        """
        두 쿼리의 검색 결과를 비교하여 최종 결과를 결정한다.

        비교 전략:
        1. 각 결과의 top-K 평균 점수 비교
        2. 점수가 더 높은 쪽의 결과를 기본으로 사용
        3. 교집합 문서가 있으면 해당 문서 우선 배치

        Returns:
            검색 결과 + 메타데이터 (어떤 쿼리가 선택되었는지 포함)
        """
        # 결과 추출 (search_type에 따라 키가 다름)
        primary_docs = self._extract_docs(primary_results, search_type)
        alt_docs = self._extract_docs(alt_results, search_type)

        # 평균 점수 계산
        primary_avg = self._avg_top_k_score(primary_docs, top_k)
        alt_avg = self._avg_top_k_score(alt_docs, top_k)

        logger.info(
            f"[DualQuery] primary_avg={primary_avg:.4f} ({len(primary_docs)}건) "
            f"| alt_avg={alt_avg:.4f} ({len(alt_docs)}건)"
        )

        # 결과 병합: 교집합 우선 + 높은 점수 순
        merged = self._merge_dual_query_results(
            primary_docs=primary_docs,
            alt_docs=alt_docs,
            top_k=top_k,
            threshold=primary_results.get('threshold', 0.5),
        )

        selected_query = "primary" if primary_avg >= alt_avg else "alt"

        result_key = "hybrid" if search_type == "hybrid" else search_type
        return {
            'total_cnt': len(merged),
            result_key: merged[:top_k],
            # 디버깅/모니터링용 메타데이터
            '_dual_query_meta': {
                'primary_query': primary_query,
                'alt_query': alt_query,
                'primary_avg_score': round(primary_avg, 4),
                'alt_avg_score': round(alt_avg, 4),
                'selected': selected_query,
                'merged_count': len(merged),
            }
        }

    def _extract_docs(self, results: Dict[str, Any], search_type: str) -> List[Dict]:
        """검색 결과에서 문서 리스트 추출"""
        if search_type == "hybrid":
            return results.get('hybrid', [])
        elif search_type == "vector":
            return results.get('milvus', [])
        elif search_type == "keyword":
            return results.get('es', [])
        else:
            return results.get('hybrid', results.get('milvus', results.get('es', [])))

    def _avg_top_k_score(self, docs: List[Dict], k: int) -> float:
        """상위 K개 문서의 평균 점수 계산"""
        if not docs:
            return 0.0
        top_docs = sorted(docs, key=lambda x: x.get('score', 0), reverse=True)[:k]
        scores = [d.get('score', 0) for d in top_docs]
        return sum(scores) / len(scores) if scores else 0.0

    def _merge_dual_query_results(
        self,
        primary_docs: List[Dict],
        alt_docs: List[Dict],
        top_k: int,
        threshold: float = 0.5,
    ) -> List[Dict]:
        """
        두 쿼리의 결과를 병합한다.
        기존 _merge_and_sort_results와 유사한 교집합 우선 정책.

        1. (document_id, section_id) 기준 dedup
        2. 두 쿼리 모두에서 발견된 문서 (교집합) → 높은 점수 채택, 우선 배치
        3. 한쪽에만 있는 문서 → 점수 순 배치
        4. threshold 미만 제외
        """
        def make_key(obj):
            doc = obj.get('doc', {})
            return (doc.get('document_id', ''), doc.get('section_id', ''))

        primary_dict = {make_key(obj): obj for obj in primary_docs}
        alt_dict = {make_key(obj): obj for obj in alt_docs}

        intersection_keys = set(primary_dict.keys()) & set(alt_dict.keys())

        # 교집합: 점수 높은 쪽 채택
        intersection_list = []
        for key in intersection_keys:
            p_obj = primary_dict[key]
            a_obj = alt_dict[key]
            if p_obj.get('score', 0) >= a_obj.get('score', 0):
                intersection_list.append({**p_obj, 'is_intersection': True})
            else:
                intersection_list.append({**a_obj, 'is_intersection': True})

        # 비교집합
        primary_only = [
            {**obj, 'is_intersection': False}
            for k, obj in primary_dict.items() if k not in intersection_keys
        ]
        alt_only = [
            {**obj, 'is_intersection': False}
            for k, obj in alt_dict.items() if k not in intersection_keys
        ]

        # 정렬
        intersection_sorted = sorted(intersection_list, key=lambda x: x['score'], reverse=True)
        non_intersection_sorted = sorted(
            primary_only + alt_only, key=lambda x: x['score'], reverse=True
        )

        merged = intersection_sorted + non_intersection_sorted
        return [obj for obj in merged if obj.get('score', 0) >= threshold]
```

## 5. 설정 및 튜닝 포인트

### NLP Engine 측 임계값

| 상수 | 위치 | 기본값 | 설명 |
|------|------|--------|------|
| `HYBRID_DOMINANCE_THRESHOLD` | `SemanticScorer` | `0.15` | 점수 차이가 이 값 이상이면 한쪽만 사용 |
| `HYBRID_MIN_SCORE` | `SemanticScorer` | `0.3` | 최소 유사도 (이하면 해당 쿼리 사용 부적합) |

- `HYBRID_DOMINANCE_THRESHOLD`를 **높이면** → "both" 모드가 더 자주 발생 (안전하지만 DB 부하 증가)
- `HYBRID_DOMINANCE_THRESHOLD`를 **낮추면** → 단일 쿼리 모드가 더 자주 발생 (효율적이지만 오판 위험)

### 권장 튜닝 순서
1. 초기에는 `HYBRID_DOMINANCE_THRESHOLD = 0.10` (보수적, "both" 자주 발생)으로 시작
2. 로그에서 `[QueryCompare]`와 `[DualQuery]`를 분석
3. 실제로 "both"에서 교집합이 많이 발생하는지, 한쪽이 항상 이기는지 패턴 파악
4. 패턴에 맞게 threshold 조정

- **NLP Engine**: `query_compare` 필드는 `Optional`이므로 기존 호출자가 무시 가능

- 양쪽 모두 **기존 API 스키마를 깨트리지 않는** 확장(additive change)
