## 2. 엔티티, NER, 태그 — 용어 정리

### 엔티티(Entity)란?

문장 속에서 **의미 있는 정보 덩어리**를 엔티티라고 한다. 상품명, 주문번호, 사람 이름 같은 것들이다.

```
"갤럭시 S25 울트라 주문번호 ORD-2024-001 골드회원 환불해주세요"

엔티티:
  "갤럭시 S25 울트라" → 상품명
  "ORD-2024-001"      → 주문번호
  "골드회원"           → 멤버십
```

### NER은 엔티티를 찾는 기술

NER(Named Entity Recognition, 개체명 인식)은 문장에서 엔티티를 **자동으로 찾아내는 AI 모델**이다. NER이 행위이고, 엔티티는 NER이 찾아내는 대상이다.

### 태그(tag)는 엔티티의 이름표

NER이 엔티티를 찾아냈을 때, 그것이 **무엇인지** 구분해주는 것이 태그다.

```
태그 없으면:
  "갤럭시 S25 울트라" → 상품명? 사람이름? 회사명?
  "ORD-2024-001"      → 주문번호? 전화번호? 회원번호?

태그 있으면:
  "갤럭시 S25 울트라" [PRODUCT]    → 상품명!
  "ORD-2024-001"      [ORDER_ID]  → 주문번호!
```

태그가 있어야 후속 처리에서 **타입별로 다르게 행동**할 수 있다:

| 태그 | search_query에서 | masked_query에서 |
|------|-----------------|-----------------|
| **PRODUCT** | 값 그대로 사용 | 마스킹 안 함 |
| **ORDER_ID** | "주문번호"로 치환 | `********`로 마스킹 |
| **PS** | 아예 제외 | `김**`로 마스킹 |

### 엔티티는 등록해야 한다

NER 모델은 **등록된 엔티티 타입만 인식**할 수 있다. 등록하지 않은 타입은 아무리 문장에 나와도 그냥 지나친다.

```
MEMBERSHIP을 등록 안 한 경우:
  고객: "골드회원인데 할인 안 되나요?"
  NER: 엔티티 없음 (골드회원을 그냥 지나침)

MEMBERSHIP을 등록한 경우:
  고객: "골드회원인데 할인 안 되나요?"
  NER: {text: "골드회원", type: "MEMBERSHIP"}
```

단, Base 엔티티 10종(PS, LC, OG 등)은 시스템에 내장되어 있어 별도 등록 없이 자동 포함된다. **도메인 특화 엔티티만 아래 형식으로 추가 등록하면 된다.**

## 3. 엔티티 정의 파일 형식 (JSON)

### 이게 핵심이다

NER 파이프라인에서 사용자가 준비해야 하는 유일한 필수 입력은 **엔티티 정의 파일** 하나다. "우리 서비스에서 인식해야 하는 엔티티가 뭔지"를 정의하는 파일이다.

### 기본 구조

```json
{
  "entities": [
    {
      "tag": "PRODUCT",
      "name": "Product Name",
      "name_ko": "상품명",
      "description": "고객이 문의하는 상품의 이름",
      "examples": [
        "갤럭시 S25",
        "아이폰 16 프로",
        "맥북 에어 M3"
      ],
      "custom_examples": [
        {
          "text": "갤럭시 S25 울트라",
          "hint": "삼성 최신 플래그십 스마트폰"
        },
        {
          "text": "에어팟 프로 2세대",
          "hint": "애플 무선 이어폰"
        }
      ]
    }
  ]
}
```

### 필드 설명

| 필드 | 필수 | 타입 | 설명 |
|------|------|------|------|
| `tag` | 필수 | string | 엔티티 태그. BIO 태깅에 사용됨 (예: `"PRODUCT"` → `B-PRODUCT`, `I-PRODUCT`) |
| `name` | 필수 | string | 엔티티 영문명 |
| `name_ko` | 선택 | string | 엔티티 한글명 (LLM 프롬프트에 사용) |
| `description` | 선택 | string | 엔티티 설명 (LLM이 참고) |
| `examples` | 선택 | string[] | 일반 예시 목록 |
| `custom_examples` | 선택 | object[] | 커스텀 예시 (hint 포함) |
| `custom_examples[].text` | 필수 | string | 예시 텍스트 |
| `custom_examples[].hint` | 선택 | string | 이 예시가 뭔지 설명 (LLM 가이드) |

### 실전 예시 - 전자상거래 도메인

```json
{
  "entities": [
    {
      "tag": "PRODUCT",
      "name": "Product",
      "name_ko": "상품명",
      "description": "고객이 구매하거나 문의하는 상품의 이름",
      "examples": ["갤럭시 S25", "아이폰 16", "맥북 프로"],
      "custom_examples": [
        {"text": "갤럭시 S25 울트라 512GB", "hint": "삼성 최신 스마트폰 + 용량"},
        {"text": "나이키 에어맥스 97", "hint": "스포츠 신발 브랜드+모델"}
      ]
    },
    {
      "tag": "ORDER_NO",
      "name": "Order Number",
      "name_ko": "주문번호",
      "description": "주문 식별 번호 (숫자 또는 영숫자 조합)",
      "examples": ["ORD-20240101-001", "2024010112345", "A12345678"],
      "custom_examples": []
    },
    {
      "tag": "DELIVERY_NO",
      "name": "Delivery Number",
      "name_ko": "운송장번호",
      "description": "택배 운송장 번호",
      "examples": ["1234567890123", "CJ12345678"],
      "custom_examples": [
        {"text": "6012345678901", "hint": "CJ대한통운 13자리 운송장번호"}
      ]
    },
    {
      "tag": "SERVICE",
      "name": "Service Name",
      "name_ko": "서비스명",
      "description": "고객이 이용하는 서비스 또는 멤버십",
      "examples": ["프라임 멤버십", "새벽배송", "당일배송"],
      "custom_examples": []
    }
  ]
}
```

## 4. examples vs custom_examples 차이

이 둘은 역할이 다르다.

### examples (일반 예시)

```json
"examples": ["갤럭시 S25", "아이폰 16", "맥북 프로"]
```

- **단순 문자열 배열**
- LLM 프롬프트에 "예시: 갤럭시 S25, 아이폰 16, 맥북 프로" 형태로 제공
- LLM이 이 예시를 참고해서 **비슷한 유형의 새로운 엔티티**를 포함한 문장을 만듦
- 생성 배치의 **20%**에 사용

### custom_examples (커스텀 예시 + 힌트)

```json
"custom_examples": [
  {"text": "갤럭시 S25 울트라 512GB", "hint": "삼성 최신 스마트폰 + 용량"},
  {"text": "나이키 에어맥스 97", "hint": "스포츠 신발 브랜드+모델"}
]
```

- **텍스트 + 힌트 쌍**
- LLM 프롬프트에 "반드시 아래 키워드를 문장에 포함하세요" 형태로 제공
- LLM이 이 **정확한 텍스트를 반드시 포함**한 문장을 만듦
- 생성 배치의 **80%**에 사용 (기본 비율)
- **우리 도메인에 반드시 들어가야 하는 키워드**를 보장할 때 사용

### 왜 구분하는가?

```
[examples 사용 → 생성 결과]
프롬프트: "상품명 예시: 갤럭시 S25, 아이폰 16, 맥북 프로"
LLM 생성: "고객님이 주문하신 LG 그램 17인치 배송이 시작되었습니다."
→ LLM이 자유롭게 비슷한 유형의 새 상품명을 생성

[custom_examples 사용 → 생성 결과]
프롬프트: "반드시 '갤럭시 S25 울트라 512GB'를 포함하세요 (힌트: 삼성 최신 스마트폰)"
LLM 생성: "갤럭시 S25 울트라 512GB 재고가 언제 들어오나요?"
→ 정확히 그 키워드가 포함된 문장 생성
```

**사용 전략**:
- `examples`: 다양한 변형을 원할 때 (LLM이 자유롭게 생성)
- `custom_examples`: 우리 서비스에 실제 존재하는 상품명/서비스명 등을 반드시 학습시키고 싶을 때

## 5. Base 엔티티 자동 병합

시스템에는 **기본 내장 엔티티 9종**이 있다. 사용자가 정의한 엔티티와 자동으로 병합된다.

### 내장 Base 엔티티

| 태그 | 이름 | 설명 |
|------|------|------|
| `PS` | Person | 인명 (사람 이름, 별칭, 직책+이름) |
| `LC` | Location | 장소 (도시, 구, 건물명 등) |
| `OG` | Organization | 조직 (회사, 기관명 등) |
| `DT` | Date | 날짜 (2024년 1월 1일, 내일 등) |
| `TI` | Time | 시간 (오후 3시, 30분 후 등) |
| `QT` | Quantity | 수량 (3개, 5만원 등) |
| `PD` | Product | 상품명 |
| `PR` | Price | 가격 |
| `ID` | Identifier | 식별번호 |
| `PH` | PhoneNumber | 전화번호 |

### 병합 규칙

```
1. 같은 tag가 있으면 → 병합
   - name_ko, description: 사용자 정의 우선
   - examples, custom_examples: 양쪽 다 합침

2. Base에만 있는 tag → 그대로 포함

3. 사용자 정의에만 있는 tag → 그대로 추가

예시:
  Base에 "PD" (Product) 있음: examples=["노트북", "스마트폰"]
  사용자 정의에 "PD" 있음: examples=["갤럭시 S25"], custom_examples=[...]

  → 병합 결과: examples=["노트북", "스마트폰", "갤럭시 S25"], custom_examples=[...]
```

따라서 `PS`, `LC`, `DT` 같은 범용 엔티티는 별도로 정의하지 않아도 자동으로 포함된다. **우리 도메인에 특화된 엔티티만 추가하면 된다.**

## 6. LLM이 생성하는 데이터

### 생성 과정

```
엔티티 정의:
  PRODUCT: "상품명" (예: 갤럭시 S25, 아이폰 16)
  ORDER_NO: "주문번호" (예: ORD-2024-001)

    ↓ LLM 생성

생성된 문장:
  "갤럭시 S25 주문번호 ORD-2024-15678 환불 가능한가요?"

    ↓ 위치 자동 계산

{
  "text": "갤럭시 S25 주문번호 ORD-2024-15678 환불 가능한가요?",
  "entities": [
    {"start": 0,  "end": 7,  "label": "PRODUCT",  "text": "갤럭시 S25"},
    {"start": 12, "end": 27, "label": "ORDER_NO", "text": "ORD-2024-15678"}
  ]
}

    ↓ BIO 태깅 변환

tokens: ["갤럭시", "S25", "주문번호", "ORD-2024-15678", "환불", "가능한가요", "?"]
labels: ["B-PRODUCT", "I-PRODUCT", "O", "B-ORDER_NO", "O", "O", "O"]
```

### LLM은 text와 label만 생성한다

중요한 점은 LLM이 **문장(text)과 엔티티의 텍스트(label+text)만** 생성한다는 것이다. `start`/`end` 위치는 **시스템이 자동으로 계산**한다. 따라서 LLM의 위치 계산 오류 문제가 없다.

## 7. BIO 태깅이란?

### 왜 BIO 태깅이 필요한가

NER 모델은 문장을 통째로 보고 "이 문장에 상품명이 있네"라고 판단하는 게 아니다. **각 토큰(단어)마다 하나씩** "이 토큰이 엔티티의 일부인가, 아닌가"를 판단한다. 이걸 위해 모든 토큰에 라벨을 붙여야 하는데, 그 라벨 체계가 **BIO 태깅**이다.

### B, I, O의 의미

| 태그 | 의미 | 설명 |
|------|------|------|
| **B** | **B**eginning | 엔티티의 **시작** 토큰 |
| **I** | **I**nside | 엔티티의 **내부** 토큰 (시작 이후의 이어지는 부분) |
| **O** | **O**utside | 엔티티가 **아닌** 일반 토큰 |

### 예시로 이해하기

#### 예시 1: 기본

```
문장: "홍길동님 환불 부탁드립니다"

토큰:    홍길동   님     환불    부탁드립니다
라벨:    B-PS    O      O      O

→ "홍길동"은 인명(PS) 엔티티의 시작이자 끝 → B-PS
→ 나머지는 엔티티가 아님 → O
```

#### 예시 2: 엔티티가 여러 토큰에 걸쳐있을 때

```
문장: "갤럭시 S25 울트라 환불해주세요"

토큰:    갤럭시    S25     울트라    환불해주세요
라벨:    B-PD    I-PD    I-PD       O

→ "갤럭시 S25 울트라"는 하나의 상품명(PD) 엔티티
→ 첫 토큰 "갤럭시" → B-PD (시작)
→ 이어지는 "S25" → I-PD (내부)
→ 이어지는 "울트라" → I-PD (내부)
→ "환불해주세요" → O (엔티티 아님)
```

#### 예시 3: 엔티티가 여러 개일 때

```
문장: "김민수님이 서울에서 갤럭시 S25를 주문했습니다"

토큰:    김민수   님이   서울   에서   갤럭시   S25   를    주문했습니다
라벨:    B-PS    O     B-LC   O     B-PD   I-PD   O      O

→ "김민수" = 인명(PS) 엔티티 시작 → B-PS
→ "님이" = 조사, 엔티티 아님 → O
→ "서울" = 장소(LC) 엔티티 시작 → B-LC
→ "에서" = 조사, 엔티티 아님 → O
→ "갤럭시" = 상품(PD) 엔티티 시작 → B-PD
→ "S25" = 상품(PD) 엔티티 내부 (갤럭시의 연속) → I-PD
→ "를" = 조사, 엔티티 아님 → O
→ "주문했습니다" = 엔티티 아님 → O
```

#### 예시 4: 같은 종류 엔티티가 연달아 나올 때

```
문장: "홍길동 김영희 두 분 모두 환불 처리했습니다"

토큰:    홍길동   김영희   두   분   모두   환불   처리했습니다
라벨:    B-PS    B-PS    O   O    O     O      O

→ "홍길동" = 첫 번째 인명 → B-PS
→ "김영희" = 두 번째 인명 (새로운 엔티티 시작!) → B-PS (I-PS가 아님!)
→ B 태그가 있기 때문에 "여기서 새 엔티티가 시작되는구나"를 구분할 수 있음
```

이것이 바로 BIO에서 **B(Beginning)가 존재하는 이유**다. 만약 B/I 구분 없이 전부 같은 태그를 붙이면, "홍길동 김영희"가 하나의 엔티티인지 두 개의 엔티티인지 구분할 수 없다.

### 실제 변환 과정 (ConvertBIOStage)

파이프라인에서 자동으로 수행되는 변환 과정:

```
1단계: LLM이 생성한 데이터
┌──────────────────────────────────────────────────────┐
│ text: "박서준 매니저가 서울 강남구에서 회의합니다"       │
│ entities:                                            │
│   - {text: "박서준 매니저", label: "PS"}               │
│   - {text: "서울", label: "LC"}                       │
│   - {text: "강남구", label: "LC"}                     │
└──────────────────────────────────────────────────────┘
                    ↓ 토큰화 (공백/구두점 기준)

2단계: 토큰 분리
┌──────────────────────────────────────────────────────┐
│ tokens: [박서준, 매니저가, 서울, 강남구에서, 회의합니다] │
│ (각 토큰의 원본 텍스트 내 위치도 함께 기록)             │
└──────────────────────────────────────────────────────┘
                    ↓ 엔티티 위치와 토큰 위치 대조

3단계: BIO 라벨 할당
┌──────────────────────────────────────────────────────┐
│ tokens: [박서준,    매니저가,  서울,   강남구에서,  회의합니다]│
│ labels: [B-PS,     I-PS,    B-LC,   B-LC,     O       ]│
│                                                      │
│ "박서준 매니저" = PS 엔티티                             │
│   → 박서준: 시작 → B-PS                               │
│   → 매니저가: 엔티티 영역에 포함 → I-PS                 │
│                                                      │
│ "서울" = LC 엔티티 → B-LC                              │
│ "강남구" = 별도 LC 엔티티 → B-LC (새 엔티티이므로 B)    │
└──────────────────────────────────────────────────────┘
```

### 모델이 학습하는 것

최종적으로 NER 모델은 이런 데이터를 수천 개 보면서 학습한다:

```
입력: ["박서준", "매니저가", "서울", "강남구에서", "회의합니다"]
정답: ["B-PS",   "I-PS",    "B-LC", "B-LC",     "O"        ]

→ 모델은 "박서준 같은 패턴이 나오면 B-PS를 붙여야 하는구나"를 학습
→ 추론 시 새로운 문장이 들어오면 각 토큰에 BIO 태그를 예측
```

## 9. Intent와 NER의 차이 요약

| 항목 | Intent | NER |
|------|--------|-----|
| **입력 데이터** | 인텐트별 예시 발화 (NDJSON) | 엔티티 정의 + 예시 값 (JSON) |
| **LLM이 생성하는 것** | 발화 텍스트 | 엔티티가 포함된 문장 |
| **학습 대상** | 문장 → 인텐트 라벨 | 토큰 → BIO 태그 |
| **베이스 모델** | KoBERT | KoELECTRA |
| **멀티턴 지원** | 지원 | 미지원 |
| **평가 지표** | Accuracy, Macro F1 | Entity-level F1 |
