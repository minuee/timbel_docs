## 1. 핵심 변경 요약

### 한 줄 요약

> 구 엔진이 "사람이 준비한 데이터로 모델을 학습하고 추론까지 수행하는 올인원 서비스"였다면,
> 신 엔진은 **"LLM이 학습 데이터를 자동 생성하고, 멀티턴 대화와 NER까지 학습하는 학습 전용 서비스"**로 변경되었다.

### 주요 변경 포인트

| 구분 | 구 엔진 (nlp_engine_service) | 신 엔진 (nlp_engine_finetune_service) |
|------|------|------|
| **서비스 범위** | 학습 + 추론 통합 | 학습 전용 (추론은 별도 서비스) |
| **데이터 생성** | 사람이 직접 준비한 데이터만 사용 | LLM(GPT-4o + Gemini)이 자동 생성 |
| **대화 유형** | 싱글턴(단일 발화)만 지원 | 싱글턴 + 멀티턴(다중 턴 대화) 지원 |
| **학습 대상** | Intent 분류만 파인튜닝 | Intent + NER + MeCab 사전 모두 파인튜닝 |
| **파이프라인 구조** | 함수 호출 체이닝 (절차적) | Stage-of-Pipeline 패턴 (선언적) |
| **Early Stopping** | 없음 (전체 에폭 실행) | 하이브리드 Early Stopping (loss + F1) |
| **데이터 재사용** | 매번 새로 처리 | 생성 데이터를 MinIO에 저장 후 재사용 가능 |
| **LLM 활용** | 없음 | OpenAI + Google Gemini 하이브리드 |

## 2. 아키텍처 변경

### 2.1 서비스 분리: 올인원 → 학습 전용

#### 구 엔진: 학습 + 추론 통합 서비스

구 엔진은 하나의 서비스 안에서 모델 학습(파인튜닝)과 텍스트 분석(추론)을 모두 처리하는 모놀리식 구조였다.

```
[구 엔진 - 단일 서비스]

┌─────────────────────────────────────────────┐
│              nlp_engine_service              │
│                                             │
│  ┌─────────────────┐  ┌──────────────────┐  │
│  │   학습 (Train)   │  │  추론 (Inference) │  │
│  │                 │  │                  │  │
│  │ • 파인튜닝 요청  │  │ • 텍스트 분석     │  │
│  │ • 모델 학습     │  │ • 의도 분류       │  │
│  │ • 모델 저장     │  │ • 형태소 분석     │  │
│  │ • 모델 평가     │  │ • 엔티티 추출     │  │
│  │                 │  │ • 개인정보 마스킹  │  │
│  └─────────────────┘  └──────────────────┘  │
│                                             │
│  ┌─────────────────────────────────────────┐ │
│  │         공유 리소스                       │ │
│  │ • ML 모델 매니저 (캐싱, 로딩)            │ │
│  │ • MeCab 매니저                           │ │
│  │ • 사전 매니저                             │ │
│  │ • 모델 레지스트리                         │ │
│  └─────────────────────────────────────────┘ │
└─────────────────────────────────────────────┘
```

#### 신 엔진: 학습 전용 서비스

신 엔진은 학습(파인튜닝)만 담당하도록 분리되었다. 추론은 기존 `nlp_engine_service`가 계속 담당한다.

```
[신 엔진 - 학습 전용 서비스]

┌─────────────────────────────────────────────┐
│         nlp_engine_finetune_service         │
│            (학습 전용)                       │
│                                             │
│  ┌──────────┐ ┌──────────┐ ┌─────────────┐ │
│  │ Intent   │ │   NER    │ │   MeCab     │ │
│  │ Pipeline │ │ Pipeline │ │  Pipeline   │ │
│  └──────────┘ └──────────┘ └─────────────┘ │
│                                             │
│  ┌─────────────────────────────────────────┐ │
│  │         LLM 데이터 생성 엔진             │ │
│  │    (OpenAI GPT-4o + Google Gemini)      │ │
│  └─────────────────────────────────────────┘ │
└──────────────────┬──────────────────────────┘
                   │ 학습된 모델 업로드
                   ▼
             ┌──────────┐
             │  MinIO   │
             └──────────┘
                   │ 모델 다운로드
                   ▼
┌─────────────────────────────────────────────┐
│           nlp_engine_service                │
│            (추론 전용으로 역할 축소)          │
│                                             │
│  • 텍스트 분석 (의도 분류 + 형태소 + NER)    │
│  • 모델 캐싱 및 로딩                         │
│  • 사전 관리                                 │
└─────────────────────────────────────────────┘
```

**변경 의도**: 학습과 추론의 관심사를 분리하여 각 서비스가 독립적으로 스케일링/배포될 수 있도록 함. 학습은 GPU 리소스를 많이 사용하므로 별도 관리가 유리하다.

### 2.2 내부 아키텍처: 절차적 → Stage-of-Pipeline 패턴

#### 구 엔진: 함수 호출 체이닝

구 엔진의 파인튜닝은 `IntentPipelineService.run_pipeline()` 안에서 각 단계를 순차적으로 호출하는 절차적 방식이었다.

```
[구 엔진 - 절차적 파이프라인]

run_pipeline():
    1. preprocessor.load_samples()     ← 데이터 로드 + 분할
    2. CSV로 저장                       ← 직접 파일 I/O
    3. trainer.train()                 ← 학습 실행
    4. saver.save_model()              ← MinIO 업로드
    5. 메타데이터 기록                   ← DB 업데이트
```

- 각 단계가 서로 다른 파라미터와 반환값을 가짐
- 중간 데이터를 파일 시스템(CSV)을 통해 전달
- 새로운 단계를 추가하려면 `run_pipeline()` 함수를 직접 수정해야 함

#### 신 엔진: Stage-of-Pipeline 패턴

신 엔진은 각 처리 단계를 독립적인 `Stage` 클래스로 분리하고, 공유 `State` 객체를 통해 데이터를 전달하는 선언적 파이프라인 패턴을 사용한다.

```
[신 엔진 - Stage-of-Pipeline 패턴]

IntentPipelineState (공유 상태 객체)
    │
    ▼
┌──────────────┐    ┌──────────────────┐    ┌──────────────┐
│ LoadDataStage │───▶│ GenerateDataStage │───▶│ SplitDataStage│
└──────────────┘    └──────────────────┘    └──────────────┘
                                                    │
    ┌──────────────┐    ┌──────────────┐            │
    │   EvalStage   │◀──│ SaveModelStage│◀───────────┘
    └──────────────┘    └──────────────┘
                              ▲
                         ┌────┴─────┐
                         │TrainStage │
                         └──────────┘
                              ▲
                     ┌────────┴────────┐
                     │ PreprocessStage  │
                     └─────────────────┘
```

- 각 Stage는 `IntentPipelineState`를 입력받아 처리 후 반환
- Protocol 기반 인터페이스(`IntentStage`)로 타입 안정성 확보
- Stage 추가/제거/교체가 용이 (예: 로컬 테스트 시 `LocalLoadDataStage`로 교체)
- Executor가 Stage 목록을 구성하여 순차 실행

**변경 의도**: 파이프라인의 각 단계를 독립적으로 개발/테스트/교체할 수 있도록 모듈화. 로컬 테스트 모드와 운영 모드를 Stage 교체만으로 전환 가능.

## 3. 학습 데이터 생성 방식의 혁신

### 이것이 가장 큰 변경점이다

구 엔진과 신 엔진의 가장 근본적인 차이는 **학습 데이터를 어떻게 확보하는가**에 있다.

### 3.1 구 엔진: 수동 데이터 의존

구 엔진에서는 사람이 직접 작성한 학습 데이터만 사용했다.

```
[구 엔진 - 데이터 흐름]

사람이 직접 작성한 유사 질의
        │
        ▼
┌──────────────────────────┐
│ MinIO (NDJSON 파일)       │
│                          │
│ {"id": "intent_001",     │
│  "utterances": [         │
│    {"text": "배송 확인", │
│     "type": "similar"}   │
│  ]}                      │
└──────────┬───────────────┘
           │
           ▼
┌──────────────────────────┐
│ IntentPreprocessor       │
│ • NDJSON 파싱            │
│ • text/label 쌍 추출     │
│ • train/val/test 분할    │
│ • CSV 파일 생성          │
└──────────┬───────────────┘
           │
           ▼
     모델 학습 (KoBERT)
```

**한계점**:
- 사람이 작성한 데이터 양에 학습 품질이 종속됨
- 데이터가 적으면 과적합 위험이 높음
- 다양한 표현 패턴을 수동으로 커버하기 어려움
- 싱글턴(단일 발화) 데이터만 생성 가능

### 3.2 신 엔진: LLM 기반 자동 데이터 생성

신 엔진은 원본 시드 데이터를 기반으로 LLM(GPT-4o, Gemini)이 대량의 학습 데이터를 자동 생성한다.

```
[신 엔진 - 데이터 흐름]

소량의 시드 데이터 (사람 작성)
        │
        ▼
┌──────────────────────────┐
│ LoadDataStage            │
│ • MinIO에서 시드 데이터   │
│   로드 (NDJSON)          │
└──────────┬───────────────┘
           │
           ▼
┌──────────────────────────────────────────────┐
│ GenerateDataStage (LLM 데이터 증강)           │
│                                              │
│  ┌────────────────────────────────────────┐  │
│  │        LLM 하이브리드 엔진              │  │
│  │   OpenAI GPT-4o ←──라운드로빈──→ Gemini │  │
│  │   (Rate Limit 분산, 자동 재시도)        │  │
│  └────────────────────────────────────────┘  │
│                                              │
│  생성 유형:                                   │
│  ┌─────────────┐ ┌──────────────┐            │
│  │ 싱글턴 발화  │ │ 멀티턴 대화   │            │
│  │ (단일 질문)  │ │ (1~4턴 context│            │
│  │             │ │  + 질문)     │            │
│  └─────────────┘ └──────────────┘            │
│  ┌─────────────┐                             │
│  │ no_intent   │                             │
│  │ (의도 없음   │                             │
│  │  패턴 생성)  │                             │
│  └─────────────┘                             │
│                                              │
│  • 플레이스홀더 자동 치환 ({이름}→홍길동)      │
│  • depth_path 활용 (상담유형 맥락 제공)       │
│  • 비동기 병렬 생성 (asyncio.gather)          │
│  • 생성 결과 MinIO 저장 (재사용 가능)         │
└──────────────────────────────────────────────┘
           │
           ▼
   대량의 학습 데이터 확보
           │
           ▼
     모델 학습 (KoBERT)
```

### 3.3 LLM 하이브리드 전략 상세

신 엔진은 단일 LLM이 아닌 **OpenAI + Google Gemini 듀얼 플랫폼**을 사용한다.

```
[LLM 하이브리드 전략]

요청 1 ──→ OpenAI GPT-4o
요청 2 ──→ Google Gemini
요청 3 ──→ OpenAI GPT-4o    ← 라운드로빈 순환
요청 4 ──→ Google Gemini
  ...

각 플랫폼별:
• Semaphore로 동시 요청 수 제한
• 429(Rate Limit) / 500 / 503 에러 시 지수 백오프 재시도
• 한 플랫폼 장애 시 다른 플랫폼으로 자동 전환
```

**변경 의도**:
- Rate Limit 분산으로 대량 생성 시 처리량 향상
- 플랫폼 장애에 대한 내결함성 확보
- 두 LLM의 다양성으로 학습 데이터 품질 향상

### 3.4 생성 데이터 재사용

```
[데이터 재사용 흐름]

첫 번째 학습 요청:
  시드 데이터 → LLM 생성 → MinIO 저장 → 학습

두 번째 학습 요청 (하이퍼파라미터만 변경):
  MinIO 저장된 생성 데이터 로드 → 학습 (LLM 생성 스킵!)
```

API에서 `generated_data_path`를 제공하면 LLM 생성 단계를 건너뛰고 기존 데이터를 재사용한다. 이를 통해:
- LLM API 비용 절감
- 동일 데이터로 하이퍼파라미터 튜닝 가능
- 학습 재현성 확보

## 4. 학습 파이프라인 변경

### 4.1 Intent 학습 파이프라인 비교

#### 구 엔진

```
┌──────────────────────────────────────────────────────────────────┐
│                    구 엔진 Intent 학습 흐름                       │
│                                                                  │
│  1. NDJSON 로드 → 2. text/label 추출 → 3. Stratified Split      │
│       → 4. CSV 저장 → 5. 전체 에폭 학습 → 6. 모델 저장          │
│       → 7. 별도 Celery 태스크로 평가                             │
│                                                                  │
│  특징:                                                           │
│  • 사람 작성 데이터 직접 사용                                     │
│  • 단일 발화 텍스트만 학습                                        │
│  • 설정된 에폭 수만큼 전부 실행 (Early Stopping 없음)             │
│  • 학습 후 별도 Celery 태스크로 평가 트리거                       │
│  • Best checkpoint를 에폭 종료 시 선택                           │
└──────────────────────────────────────────────────────────────────┘
```

#### 신 엔진

```
┌──────────────────────────────────────────────────────────────────┐
│                    신 엔진 Intent 학습 흐름                       │
│                                                                  │
│  1. LoadData (NDJSON/재사용 데이터)                               │
│       → 2. GenerateData (LLM 증강: 싱글턴 + 멀티턴 + no_intent) │
│       → 3. SplitData (Intent별 균등 분할)                        │
│       → 4. Preprocess (context_to_text 변환 + CSV)               │
│       → 5. Train (Early Stopping + Warmup)                      │
│       → 6. SaveModel (MinIO)                                    │
│       → 7. Eval (동일 파이프라인 내에서 평가)                     │
│                                                                  │
│  특징:                                                           │
│  • LLM이 시드 데이터 기반으로 대량 생성                           │
│  • 싱글턴 + 멀티턴 + no_intent 3가지 유형 학습                   │
│  • 하이브리드 Early Stopping (val_loss↓ 또는 val_f1↑)           │
│  • 학습과 평가가 하나의 파이프라인 안에서 완결                    │
│  • depth_path로 상담 유형 맥락 반영                              │
└──────────────────────────────────────────────────────────────────┘
```

### 4.2 데이터 분할 방식 변경

#### 구 엔진

```
전체 데이터셋 (모든 intent 섞인 상태)
    │
    ├── test 먼저 분리 (전체에서)
    │
    └── 나머지에서 train/val 분리
        └── 조건부 Stratified Split (label 최소 2개, 종류 2개 이상)
```

- 전체 데이터에서 한 번에 분할하므로 intent별 데이터 양의 불균형이 있을 수 있음

#### 신 엔진

```
Intent별 개별 분할
    │
    ├── Intent A의 데이터 → train/val/test 분할
    ├── Intent B의 데이터 → train/val/test 분할
    ├── Intent C의 데이터 → train/val/test 분할
    │   ...
    └── 각 분할 결과를 합치기

라벨 인코딩: OrderedDict 사용 (순서 보장)
no_intent는 항상 마지막 라벨로 배치
```

- Intent별로 균등하게 분할하여 각 intent가 train/val/test에 고르게 분포
- 라벨 순서가 보장되어 재현성 향상

## 5. 멀티턴 대화 지원

### 이전에는 없던 완전히 새로운 기능

구 엔진은 단일 발화(싱글턴)만 처리할 수 있었다. 신 엔진은 이전 대화 맥락(context)을 포함한 멀티턴 대화를 학습하고 분류할 수 있다.

### 5.1 멀티턴 데이터 생성

```
[멀티턴 데이터 생성 흐름]

턴 분포 설정:
  4턴: 40%  |  3턴: 20%  |  2턴: 15%  |  1턴: 10%  |  0턴(싱글턴): 15%

LLM 프롬프트 → 대화 생성:

  [4턴 예시]
  USER: 주문한 물건이 아직 안 왔어요
  AGENT: 주문번호를 알려주시겠어요?
  USER: 12345678이요
  AGENT: 확인해보겠습니다. 현재 배송 중입니다.
  USER: 언제 도착하나요?
  AGENT: 내일 오전 중으로 도착 예정입니다.
  USER: 배송 시간을 변경할 수 있나요?    ← 이 발화의 intent를 분류
```

### 5.2 멀티턴 데이터의 학습용 변환

멀티턴 대화는 학습 시 하나의 텍스트로 변환된다:

```
[context_to_text 변환]

변환 전 (구조화된 데이터):
  context: [
    {"role": "user", "content": "주문한 물건이 아직 안 왔어요"},
    {"role": "agent", "content": "주문번호를 알려주시겠어요?"},
    {"role": "user", "content": "12345678이요"},
    {"role": "agent", "content": "확인해보겠습니다."}
  ]
  query: "배송 시간을 변경할 수 있나요?"

변환 후 (학습용 텍스트):
  "[USER] 주문한 물건이 아직 안 왔어요 [AGENT] 주문번호를 알려주시겠어요?
   [USER] 12345678이요 [AGENT] 확인해보겠습니다.
   [USER] 배송 시간을 변경할 수 있나요?"
```

- `max_turns` 파라미터로 최근 N턴만 사용 가능
- 학습 시와 추론 시 동일한 변환 로직을 사용하여 일관성 보장

### 5.3 no_intent 처리

신 엔진은 **"의도가 없는 발화"**를 별도로 학습한다.

```
[no_intent 패턴 예시]

• "네 감사합니다" (마무리 응답)
• "알겠습니다" (단순 확인)
• "그렇군요" (감탄/수긍)
• "아 네~" (추임새)

→ 이런 발화는 특정 intent로 분류하면 안 되므로
  no_intent 라벨로 학습하여 구분
```

## 6. NER 파인튜닝 신규 추가

### 구 엔진에는 없던 완전히 새로운 파이프라인

구 엔진에서 NER(개체명 인식)은 사전 학습된 모델(`Leo97/KoELECTRA-small-v3-modu-ner`)을 그대로 사용했다. **도메인에 맞게 파인튜닝하는 기능은 없었다.**

신 엔진은 NER 모델도 도메인 데이터로 파인튜닝할 수 있는 전용 파이프라인을 추가했다.

### 6.1 NER 파이프라인 흐름

```
[NER 파인튜닝 파이프라인]

┌───────────────┐
│ LoadDataStage │  엔티티 정의 + 시드 데이터 로드
│               │  (예: "상품명", "주문번호", "배송지" 등의 엔티티 타입)
└───────┬───────┘
        ▼
┌───────────────────┐
│ GenerateDataStage │  LLM이 엔티티가 포함된 문장 자동 생성
│                   │  • 커스텀 예시 우선 활용 (80% 비율)
│                   │  • 복합 엔티티 문장 생성 유도
│                   │  • 배치 단위 생성 (배치당 10개)
│                   │  • 중복 제거 (text + entities 조합)
└───────┬───────────┘
        ▼
┌───────────────────┐
│  ConvertBIOStage  │  BIO 태깅 형식으로 자동 변환 ★ NER 전용
│                   │
│  입력: "서울에서 홍길동님이 주문하셨습니다"
│        entities: [{text:"서울", label:"지역"},
│                   {text:"홍길동", label:"고객명"}]
│
│  출력: 서울   → B-지역
│        에서   → O
│        홍길동 → B-고객명
│        님이   → O
│        주문   → O
│        하셨   → O
│        습니다 → O
└───────┬───────────┘
        ▼
┌───────────────────┐
│  SplitDataStage   │  Train/Val/Test 분할 + Label 매핑 생성
│                   │  (B-지역=0, I-지역=1, B-고객명=2, ... O=N)
└───────┬───────────┘
        ▼
┌───────────────────┐
│ PreprocessStage   │  토크나이저 인코딩 준비
│                   │  • 라벨 검증 (존재하지 않는 라벨 → "O" 대체)
│                   │  • tokens/labels 길이 정합성 보장
└───────┬───────────┘
        ▼
┌───────────────────┐
│    TrainStage     │  KoELECTRA Token Classification 학습
│                   │  • Warmup Scheduler 사용
│                   │  • Token-level 정확도 추적
└───────┬───────────┘
        ▼
┌───────────────────┐
│    EvalStage      │  seqeval Entity-level F1 평가
│                   │  (토큰 단위가 아닌 엔티티 단위 정확도)
└───────────────────┘
```

### 6.2 Intent vs NER 학습 비교

| 항목 | Intent 파이프라인 | NER 파이프라인 |
|------|-----------------|---------------|
| **태스크** | Sequence Classification (문장 → 라벨) | Token Classification (토큰 → BIO 태그) |
| **베이스 모델** | KoBERT (`monologg/kobert-lm`) | KoELECTRA (`Leo97/KoELECTRA-small-v3-modu-ner`) |
| **데이터 형식** | `{text, label}` | `{tokens[], labels[]}` (BIO) |
| **전처리** | context_to_text 변환 + CSV | BIO 변환 + 라벨 검증 |
| **멀티턴** | 지원 (context 포함) | 미지원 (단일 문장) |
| **평가 지표** | Accuracy, Macro F1 | Entity-level F1 (seqeval) |
| **전용 Stage** | - | ConvertBIOStage (BIO 태깅 변환) |

## 8. 학습 기법 고도화

### 8.1 Early Stopping 도입

#### 구 엔진: 전체 에폭 실행

```
에폭 1 → 에폭 2 → 에폭 3 → ... → 에폭 N (전부 실행)
                                         │
                                   최종 모델에서
                                   best checkpoint 선택
```

- 설정된 에폭 수만큼 전부 실행
- 과적합이 발생해도 멈추지 않음
- 리소스 낭비 가능성

#### 신 엔진: 하이브리드 Early Stopping

```
에폭 1 → 에폭 2 → 에폭 3 → ... → STOP! (조건 충족)
                                    │
                              val_loss↓ 또는 val_f1↑
                              둘 다 개선 없으면 patience 소진 후 중단

판단 기준:
  • val_loss가 감소했으면 → 개선으로 간주
  • val_f1이 증가했으면 → 개선으로 간주
  • 둘 다 아니면 → patience 카운트 증가
  • patience 한도 초과 → 학습 중단
```

- loss와 F1을 동시에 모니터링하는 하이브리드 방식
- 불필요한 학습을 조기 종료하여 리소스 절감 및 과적합 방지

### 8.2 Warmup Scheduler

신 엔진의 NER 학습에서는 Warmup Scheduler를 사용한다.

```
Learning Rate 변화:

  lr │         ╭────────────────╮
     │        ╱                  ╲
     │       ╱                    ╲
     │      ╱                      ╲
     │     ╱                        ╲
     │    ╱                          ╲
     │───╱                            ╲───
     └────────────────────────────────────→ 에폭
       warmup      peak        decay
```

- 초기 학습률을 낮게 시작하여 점진적으로 올림
- 사전 학습 가중치를 보존하면서 안정적으로 파인튜닝

### 8.3 평가 방식 변경

| 항목 | 구 엔진 | 신 엔진 |
|------|--------|--------|
| **평가 시점** | 별도 Celery 태스크로 분리 | 파이프라인 내에서 즉시 수행 |

## 12. 영향 범위 및 유의사항

### 12.1 변경으로 인한 영향

| 영역 | 영향 |
|------|------|
| **학습 요청** | 파인튜닝 API 호출 대상이 `nlp_engine_service` → `nlp_engine_finetune_service`로 변경 |
| **추론** | 기존 `nlp_engine_service`의 추론 흐름은 변경 없음. 멀티턴 추론 시 동일한 `context_to_text` 변환 필요 |
| **NER** | 기존에는 범용 NER 모델만 사용. 이제 도메인 특화 NER 모델 파인튜닝 가능 |
| **LLM 비용** | LLM 데이터 생성으로 인한 API 비용 발생 (생성 데이터 재사용으로 최적화 가능) |
| **인프라** | 별도 서비스 배포 필요, LLM API 키 관리 필요 |
| **데이터 품질** | LLM 생성 데이터의 품질에 따라 모델 성능이 달라질 수 있음 |

### 12.2 하위 호환성

- 구 엔진의 추론 API는 그대로 유지됨
- 학습된 모델의 저장 경로/포맷은 동일 (구 엔진이 로드 가능)
- 구 엔진의 모델 레지스트리/캐싱 메커니즘은 변경 없이 동작

### 12.3 주의사항

1. **멀티턴 일관성**: 학습 시 사용하는 `context_to_text()` 변환과 추론 시 사용하는 변환이 동일해야 함
2. **no_intent 라벨**: 신 엔진에서 학습한 모델에는 `no_intent` 라벨이 포함됨. 추론 서비스에서 이를 처리하는 로직이 필요할 수 있음
3. **NER 모델 교체**: NER 파인튜닝 모델을 사용하려면 추론 서비스의 NER 모델 로딩 로직 확인 필요
4. **LLM API 키**: 테넌트별 LLM API 키 설정이 필요하며, 키가 없으면 데이터 생성 불가
