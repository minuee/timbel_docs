# 이슈 1·2 통합 처리 설계 — 서버 완성도 게이트

**작성일**: 2026-04-20

---

## 1. 배경 및 문제 정의

### 현 상황

- STT 부분 전사가 Redis를 경유해 검색 API로 전달
- 들어오는 쿼리의 약 80%가 문법상 미완성
- 매 발화 조각마다 검색 호출 → 리소스 낭비 + 미완성 쿼리로 품질 낮은 결과 반환
- 상담사에게 실시간으로 도움을 주기 위한 기능인데 품질 이슈로 가치 훼손

### 왜 이 접근인가

두 가지 대안은 모두 원리적 한계가 있음:

- **타이밍 기반 디바운싱**: Redis 경유 구조 + 고객이 뜸들이는 시간 편차로 발화 종료를 시간으로 판단 불가
- **상담사 발화 기준**: 상담사 발화 후 검색 = 이미 답을 시작한 뒤 → 실시간 보조라는 기능 취지와 충돌

남은 유일한 접근: 쿼리 내용 자체의 문법적 완성도로 판단

### 해결할 이슈

| 이슈 | 해결 방식 | 해결 수준 |
|------|-----------|-----------|
| 1. 미완성 쿼리로 검색 품질 저하 | 완성도 게이트로 검색 전 차단 | 직접 해결 |
| 2. 매 발화마다 검색으로 리소스 낭비 | 미완성 조각이 게이트에서 차단 = 검색 호출 자연 감소 | 실질적 부분 해결 (~80% 감소 예상) |

### 명시적으로 범위 외

- STT 인식 자체가 깨지는 케이스 (예: "아 레츠 레이스 테트") — STT 엔진 영역
- 완성된 쿼리들 간의 맥락 조합 및 중복 제거 — 별개 성격의 문제, 후속 과제

---

## 2. 설계 개요

- **위치**: `/api/v1/rag/assist-stream` 엔드포인트 초반, intent gate 앞단
- **방식**: 한국어 종결어미 룰 기반 판정 (pure Python, ~5ms)
- **처리**: 미완성 시 검색·LLM 전부 스킵, `event: incomplete` SSE 1회 emit 후 연결 종료
- **격리**: opt-in 플래그로 STT 클라이언트만 적용, 비-STT 호출자 무영향
- **타이밍**: 대기 없음. 쿼리 도착 즉시 판정, 완성이면 즉시 진행

## 3. 완성도 판정 룰

| 신호 | 판정 | 예시 |
|------|------|------|
| 평서·명령 종결어미 (다/요/죠/네요/세요/랍니다) | 완성 | "알려주세요" |
| 의문 종결어미 (까/나요/인가요/ㄴ가요/죠/는지/ㄹ까요) | 완성 | "가능한가요" |
| 감탄·동의 종결어미 (군요/네요) | 완성 | "그렇군요" |
| 연결어미 (면/니/고/며/는데/면서/라서/지만) | 미완성 | "개설하려는데" |
| 조사로만 끝 (은/는/이/가/을/를/에/서/도/만/로) | 미완성 | "서류는" |
| ≤3자 + 종결어미 없음 | 미완성 | "계좌" |
| 순수 명사 나열 (동사 없음, ≥2 어절) | 보수적 미완성 | "계좌 개설 서류" |

**정확도 기대치**: 80~85%

### 알려진 한계

- STT 인식 깨진 쿼리는 룰이 완성으로 오판할 수 있음 (범위 외로 명시)
- 명사 나열은 미완성으로 처리 → 정답인 경우 놓침 (보수적 선택)
- **STT 비누적형 분절 시 마지막 완성 조각만 검색에 도달 → 앞 맥락 소실**: 본 시스템의 STT는 턴당 조각 1개 전달 방식이며, 동일 논리 발화가 VAD 기준에 따라 여러 turn_idx에 분절되어 들어올 수 있음. 이 경우 앞쪽 분절(미완성)은 차단되어 맥락이 소실되고, 마지막 분절(완성)만 검색에 도달함. (예: "계좌" → "개설하고" → "알려주세요" 분절 전송 시 "알려주세요"만 통과.) 이 케이스의 검색 품질 개선은 턴 간 맥락 조합(후속 트랙)에서 다룸.

## 4. 작업 분해

### Phase 1: 룰 모듈 구현

**파일**: `src/search/sentence_completeness.py`

**인터페이스**:
```python
def is_sentence_complete(query: str) -> tuple[bool, str]:
    """
    Returns (is_complete, reason)
    reason: "sentence_ending" | "question_mark" | "whitelist"
          | "connective_ending" | "trailing_particle"
          | "too_short" | "noun_phrase_ambiguous"
    """
```

**요구사항**:
- 외부 의존성 없음 (순수 정규식 + 내장 사전)
- 실행 시간 ~5ms 이내
- 단위 테스트: 카테고리당 최소 10개 샘플
- 회귀 테스트 세트: 실제 상담 로그에서 짤린 쿼리 30~50개 샘플링

예상 LOC: ~80

### Phase 2: 엔드포인트 통합

**파일**: `src/api/schemas/rag.py`
- `AssistStreamRequest` 스키마 확장: `enable_completeness_gate: bool = False`

**파일**: `src/api/rag_assist.py`
```
요청 진입
  → enable_completeness_gate=True 인지 확인
  → True 이면 is_sentence_complete(query) 호출
    - 미완성: event: incomplete SSE 1회 emit → 연결 종료, 이후 파이프라인 스킵
    - 완성: 기존 intent gate + search 파이프라인 진행 (기존 코드 무변경)
  → False 이면 기존 파이프라인 (무변경)
```

**핵심 원칙**:
- 기존 intent gate·search 코드는 건드리지 않음
- 플래그 OFF 시 동작 완전 동일
- 미완성 판정 시 LLM 호출·검색 둘 다 발생하지 않음

예상 LOC: ~30

### Phase 3: 관측 및 로깅

**Prometheus 메트릭**:
- `assist_stream_completeness_total{decision="complete|incomplete"}`
- `assist_stream_completeness_reason_total{reason="..."}`
- 기존 검색·LLM 호출 카운터로 이슈 2 감소 효과 측정

**로그 테이블** `completeness_logs`:
- `request_id, call_id, turn_idx, query, decision, reason, timestamp`
- 룰 정확도 사후 평가·보강용 (오거절율 측정: completeness_logs ↔ 실제 통화 녹취 샘플 대조)

**대시보드**:
- 완성/미완성 비율 시계열
- reason 분포
- 전체 검색 호출 수 변화 (이슈 2 효과 측정)

### Phase 4: 프론트 협의

프론트 코드 변경 없음이 기본 (단, `event: incomplete` 수신 시 무시 정책 팀 내 합의 완료 필요):

- **추천**: 이벤트 무시, UI 변화 없음 (완성된 다음 쿼리가 곧 올 것이므로)
- **하지 말 것**: "검색 결과 없음" 같은 부정적 피드백 (미완성은 "아직 말하는 중"의 의미)

### Phase 5: 배포 및 검증

1. 플래그 OFF 상태로 머지·배포 → 무영향 확인
2. 스테이징에서 플래그 ON → 실제 통화 샘플로 동작 검증
3. 프로덕션 카나리: STT 클라이언트 1곳만 플래그 ON
4. 1주일 로그 수집 → 정확도·효과 평가
5. 문제 없으면 전체 STT 트래픽 확대

### Phase 6 (조건부): LLM 폴백

**트리거 조건**: Phase 5 평가에서 룰 정확도 <80% 이거나 모호 케이스 >15%

**방식**: 기존 `classify_intent` Gemma JSON 스키마에 `"complete": bool` 필드 추가 → 한 번의 LLM 호출로 intent + 완성도 동시 판정

**주의사항**:
- 기존 intent 분류기 프롬프트는 안정화 상태 → 회귀 위험
- 별도 이슈로 분리, 충분한 테스트 후 진행

## 5. 리스크 및 완화

| 리스크 | 영향 | 완화 |
|--------|------|------|
| 유효한 짧은 질의 오거절 | 상담사가 답 못 받음 | ? 있으면 무조건 완성 + 의문사 whitelist |
| STT 인식 깨진 쿼리 미검출 | 검색 품질 개선 제한 | 범위 외 명시, 별도 트랙으로 분리 |
| 기존 비-STT 호출자 영향 | API 회귀 | `enable_completeness_gate=False` 기본값 |
| 룰 수정 회귀 | 정확도 저하 | 회귀 테스트 세트 + CI 통합 |
| 프론트 UX 혼란 | 상담사 체감 품질 저하 | 프론트 협의로 `incomplete` 이벤트 무시 정책 확정 |
| 완성으로 잘못 판정 | 여전히 엉뚱한 검색 발생 | 보수적 판정 (모호 시 미완성) + 로그로 재현 후 룰 보강 |

## 6. 기대 효과

| 지표 | Before | After (예상) |
|------|--------|--------------|
| 검색 호출 횟수 | 100% (매 조각) | 30~50% (50~70% 감소 예상) |
| 검색 호출 중 미완성 비율 | 80% | 10~15% (룰 오판분) |
| LLM(intent gate) 호출 | 100% | 30~50% |
| 완성 쿼리의 검색 품질 | 낮음 | 조각 단위 기준 정상화 |
| 상담사 체감 응답 지연 | 없음 | 없음 (타이머 대기 없음) |

> **품질 개선 범위 주의**: 검색 품질 개선은 "게이트를 통과한 조각 자체" 기준. 발화가 여러 턴에 분절된 경우, 마지막 통과 조각만으로는 원래 질문 맥락이 부족할 수 있음 (섹션 3 한계 참조).

- **이슈 1**: 직접 해결. 완성 쿼리에 한해 품질 정상화.
- **이슈 2**: 실질적 부분 해결. 검색·LLM 호출 50~70% 감소 예상 (80% 미완성 × 룰 정확도 85% = ~68% 차단).

## 8. 성공 지표

**1주 후**:
- 전체 검색 호출 수 50% 이상 감소 확인 (목표 70%, 이슈 2 지표)
- 완성도 게이트 통과 쿼리의 검색 결과 품질 개선 확인 (상담사 피드백 또는 클릭률)
- 오거절율(실제 완성을 미완성으로 판정) <5%
- 룰 정확도 전반 측정치 확보

**1개월 후**:
- 룰 정확도 평가 완료 → Phase 6(LLM 폴백) 도입 여부 결정
- 남은 이슈(완성 쿼리 간 맥락 조합) 별도 트랙 착수 여부 판단

## 9. 명시적으로 건드리지 않을 것

- 현재 intent 분류기 프롬프트·JSON 스키마 (Phase 6 전까지)
- `/search`, `/rag/context` 등 기존 엔드포인트 (opt-in 플래그로 격리)
- `SearchService` 내부
- STT 수신 서버 / Redis publish 경로
- 프론트 디바운싱·버퍼링 로직 (타이밍 기반 접근 폐기)

## 핵심 원칙 요약

- **무엇을**: 검색 API 진입 시 한국어 종결어미 룰로 쿼리 완성도 판정, 미완성이면 검색·LLM 모두 스킵
- **어디에**: `/api/v1/rag/assist-stream` 엔드포인트 초반, intent gate 앞단
- **왜 이 방식만 가능한가**: Redis 경유 구조에서 타이밍 기반 판단 불가, 상담사 발화 기준은 기능 취지와 충돌 → 내용 기반 판정이 유일한 접근
- **무엇을 함께 해결하는가**: 이슈 1(품질)은 직접 해결, 이슈 2(호출 횟수)는 미완성 조각 차단으로 50~70% 감소 예상
- **무엇을 안 건드리는가**: intent 분류기, 기존 엔드포인트, STT 수신 경로, 프론트 로직
