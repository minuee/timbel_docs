# 외부 마이크 녹음 시 녹음시간 2배 원인 분석

작성일: 2026-10-12

## 1. 현상

- 스마트폰 내장 마이크가 아닌 **외부 마이크**(USB-C/라이트닝/유선 등)로 녹음
- 녹음·업로드는 성공
- 결과물(서버 측) **녹음시간이 실제의 정확히 2배**

## 2. 결론 (요약)

앱은 녹음 데이터를 **헤더 없는 raw PCM(16kHz / 16bit / mono)** 으로 저장·업로드하고,
"길이"는 오직 **바이트 수 ÷ (16000 × 2)** 로 결정됩니다.
외부 마이크 사용 시 네이티브 레이어가 실제로는 **2배 분량의 바이트**(스테레오 2채널 또는 32kHz)를
넘겨주는데, 앱은 포맷을 검증하지 않고 그대로 "16kHz 모노"라고 간주하기 때문에
서버에서 계산되는 재생 시간이 정확히 2배가 됩니다.

반면 앱 화면의 녹음 타이머는 **벽시계 타이머(100ms 단위 카운트)** 라서 녹음 중에는 정상으로 보이고,
업로드 후에야 2배로 보이는 것이 증상과 일치합니다.

## 3. 근거 코드

### 3-1. 포맷 고정 요청, 실제 포맷 검증 없음

`lib/views/recording/crypt_recorder/audio_recorder_service.dart:105`

```dart
const config = RecordConfig(
  sampleRate: 16000,
  encoder: AudioEncoder.pcm16bits,
  numChannels: 1,
);
```

- `record` 패키지에 "16kHz 모노"를 **요청**만 할 뿐, 실제로 받은 스트림이 그 포맷인지 확인하는 코드가 없음
- 외부 마이크(특히 USB 오디오 인터페이스/마이크)는 하드웨어 기본 포맷이 **48kHz·스테레오**인 경우가 많고,
  내장 마이크와 달리 OS/플러그인의 리샘플링·다운믹스 경로가 다르게 동작할 수 있음

### 3-2. 길이 = 바이트 수 기반 계산 (헤더 없음)

`lib/views/recording/crypt_recorder/platform/audio_recorder_io.dart`

```dart
static const int sampleRate = 16000;
static const int bytesPerSample = 2;
static const int channels = 1;
...
_totalSamples += data.length ~/ bytesPerSample;   // 채널 수 고려 없음
...
final seconds = _totalSamples / 16000;            // getCurrentDuration()
```

- 스트림 바이트를 그대로 AES 암호화 → `encrypted_audio_N.pcm` 으로 저장 → 업로드
- WAV 헤더 등 **포맷 메타정보가 전혀 없음** → 서버도 16kHz/mono로 가정할 수밖에 없음
- 3분 단위 파일 분할(`_bufferSize = 16000*2*60*3`)도 바이트 기준이라,
  2배 데이터면 실제 1분 30초마다 파일이 하나씩 생성됨

### 3-3. 앱 타이머는 별개 (벽시계)

`lib/views/recording/recording_controller.dart:893` `formattedDuration`
- `recordDuration`(Timer로 100ms마다 +1) 기반 → 실제 경과 시간
- 따라서 녹음 화면에서는 이상이 보이지 않음

## 4. 왜 "정확히 2배"인가 — 가능한 두 경로

| 경로 | 실제 데이터 | 앱/서버 해석 | 결과 |
|---|---|---|---|
| A. 채널 불일치 | 16kHz **스테레오**(L/R 인터리브) | 16kHz 모노 | 길이 2배, 느리고 낮은 음성 |
| B. 샘플레이트 불일치 | **32kHz** 모노 | 16kHz 모노 | 길이 2배, 느리고 낮은 음성 |

- **A가 가장 유력**: USB 마이크 다수가 스테레오 전용으로 노출되며,
  Android에서는 일부 기기/HAL이 `CHANNEL_IN_MONO` 요청을 무시하고 스테레오 프레임을 그대로 전달하는 사례가 있음.
  iOS에서도 `record` 플러그인이 AVAudioEngine 입력 노드의 하드웨어 포맷(외부 장치 포맷)과
  요청 포맷 간 변환을 처리하는데, 외부 장치 포맷(채널/레이트)이 내장 마이크와 다를 때 변환이 기대대로 안 되는 경우가 보고됨.
- 어느 쪽이든 공통 원인은 **"요청한 포맷 = 실제 포맷"을 가정**하고 검증하지 않는 구조.

> 참고: 이 저장소에는 `record` 패키지 네이티브 소스(pub cache)가 없어 플러그인 내부 변환 로직은 직접 확인하지 못했음.
> 위 A/B 구분은 아래 5번 확인 방법으로 확정 가능.

## 5. 배제한 다른 가능성

- **라우트 변경으로 스트림 이중 구독?** — `restartStreamForRouteChange()`는 기존 구독을 먼저 `cancel()` 하고,
  iOS 블루투스(`HeadphoneListener._shouldRestartForBluetooth`)에서만 호출됨. 유선/USB 외부 마이크는 대상이 아님.
  또한 이중 구독이라면 "정확히 2배"보다 재시작 시점 이후만 늘어나는 형태가 됨.
- **일시정지 묵음 삽입(`addSilenceForPausedDuration`)?** — 일시정지 시간만큼만 추가되므로 정확히 2배가 되기 어려움.
- **iOS `handleRouteChange`의 `"calling"` 전달** — 출력에 `.headphones`가 있으면 calling 상태를 보내 일시정지를 유발할 수는 있으나,
  이는 길이를 줄이거나 묵음을 넣는 방향이지 2배를 만들지는 않음. (단, 외부 마이크 사용 시 의도치 않은 일시정지 이슈는 별도로 존재 가능)

## 6. 확인 방법 (확정용)

1. **업로드된 결과를 재생** — 목소리가 **느리고 낮게(슬로모션)** 들리면 위 A/B 확정.
   정상 속도인데 뒤에 무음/반복이 붙어 있다면 다른 원인이므로 재분석 필요.
2. **로그 비교** — `녹음 파일 저장:` 앱 로그(`AppService.appLog`)의 파일 생성 간격이
   3분이 아니라 **약 1분 30초**면 바이트가 2배로 들어오고 있다는 증거.
3. **A/B 구분** — 원본 PCM을 복호화해 Audacity 등에서 raw import:
   - 16kHz·스테레오로 열어 정상 → A(채널)
   - 32kHz·모노로 열어 정상 → B(샘플레이트)
4. 유저 기기 정보(OS, 기종, 외부 마이크 모델·연결 방식) 확보 시 재현 범위 특정 가능.

## 7. 개선 방향 (참고)

- 녹음 시작 시 **실제 입력 포맷 확인** (Android: `AudioRecord.getChannelCount()/getSampleRate()`,
  iOS: `AVAudioSession.sampleRate / inputNumberOfChannels`, 입력 포트 타입) 후 로그 남기기
- 실제 포맷이 요청과 다르면 앱에서 **다운믹스(스테레오→모노) / 리샘플링** 후 저장
- 또는 업로드 시 **포맷 메타정보(sampleRate, channels)** 를 함께 전달해 서버가 올바르게 해석
- 1차 방어책: 경과 벽시계 시간 대비 수신 바이트가 ~2배이면 경고 로그/이벤트 수집
