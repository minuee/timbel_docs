# 업로드 진행률 66% 정체 — 원인 분석과 대응

녹음 종료 후 업로드가 66%에서 더 이상 올라가지 않는 현상에 대한 코드 기반 원인 분석, 해결 방안, 그리고 사용자에게 되물어야 할 확인 항목 정리.

- 대상 브랜치: `develop`
- 관련 코드: `upload_service.dart`, `audio_recorder_io.dart`, `recording_controller.dart`, `main_container_controller.dart`, `FileUploadManager.swift`
- 상태: **원인 좁혀짐** — 서버 로그 대조로 후보 일부 배제(1장). 남은 확정은 1장 말미의 4가지 확인 항목으로 가른다

---

## 요약

66%라는 숫자는 우연이 아닐 가능성이 높습니다. 이 앱은 녹음을 **3분 단위 청크 파일**로 쪼개 저장하고, 업로드할 때 그 파일들을 **한 번의 요청으로 묶어 전송**합니다. 진행률은 바이트 기준이고 청크 크기가 균일하므로, **청크가 3개일 때 2개를 보낸 지점이 정확히 66%**입니다. 즉 9~10분짜리 녹음이라면 66% 정체는 "세 번째 파일에서 막혔다"는 뜻이 됩니다.

청크 수와 무관하게 항상 66%라면 이야기가 다릅니다. 그때는 화면이 실제 진행률을 못 따라가고 있는 것이고, iOS의 진행률 클램프(원인 A) 또는 변환 팝업의 퍼센트 환산(원인 F)이 유력합니다.

**그래서 가장 먼저 확인할 것은 녹음 길이입니다.** 사용자에게 물어볼 질문도 여기서 시작합니다.

### 알아둘 숫자

| 항목 | 값 |
|------|-----|
| 청크 단위 | 3분마다 파일 1개 (16kHz × 2byte × 180초 ≈ **5.76MB**) |
| 66%가 되는 조건 | 청크 3개(6~9분 녹음) 중 2개 전송 완료 |
| 다른 경계값 | 청크 2개 → 50% / 4개 → 50%·75% / 6개 → 33%·66%·83% |
| 업로드 방식 | 폴더 내 전체 PCM을 1회 multipart POST |
| 타임아웃 | connect 30초 / **send 10분** / **receive 60초** |
| 재시도 | 최대 3회, 각 2초 간격 (실패 판정까지 최대 30분 이상) |

## 1. 서버 로그 대조 결과 (2026-09-02 확인)

서버 파이프라인은 `S3 파일 업로드 → MariaDB 등록 → STT 변환 → MongoDB 대화내용 저장 → LLM 요약` 순서인데, 실제 로그에는 **S3 업로드 성공만 남아 있고 MariaDB 등록 로그가 아예 없으며 등록도 되지 않았습니다.** 그 이후 단계는 당연히 진행되지 않았습니다.

다만 **"로그가 없다"를 곧바로 "실행되지 않았다"로 읽으면 안 됩니다.** DB 등록 코드가 예외를 삼키고 있거나 실패 경로에 로그가 아예 없을 수도 있습니다. 이 두 경우는 원인이 완전히 다르므로, 등록 로직 **진입부에 로그가 있는지**부터 확인해야 합니다.

### 66%라는 숫자를 과신하지 말 것

화면의 66%가 뜻하는 것은 하나뿐입니다 — **UI가 마지막으로 진행률 갱신을 받은 시점이 66%였다.** 전송이 거기서 멈췄다는 뜻이 아닙니다.

- iOS 클램프(`FileUploadManager.swift:576`)는 값이 내려가는 것을 막는다
- 앱이 백그라운드로 내려가거나 종료되면 갱신 자체가 끊긴다

그 뒤로 전송이 100%까지 갔든 실패했든 화면은 66%로 남습니다. **따라서 66%를 바이트로 환산해 "몇 번째 청크에서 멈췄다"고 역산하는 접근은 근거가 약합니다.** 아래 판정도 이 점을 감안해서 읽어야 합니다.

### 이 사실이 원인 후보에 미치는 영향

| 원인 | 판정 | 근거 |
|------|------|------|
| **F. 변환 팝업 퍼센트 환산** | **배제** | DB 등록이 없으면 contentId가 생성되지 않고, contentId가 없으면 SSE 이벤트도 없다. 변환 팝업은 뜰 수 없으므로 사용자가 본 66%는 확실히 **'파일 업로드' 팝업**이다 |
| **D. 401 토큰 만료** | **배제** | 인증이 통과했기 때문에 S3까지 업로드가 진행되었다 |
| **A. iOS 진행률 클램프** | **유효** | 오히려 66%가 실제 전송 위치가 아닐 수 있는 근거. 화면이 멈춘 것과 전송이 멈춘 것을 구분해야 한다 |
| **B. 마지막 청크 미저장** | **유효** | 본문이 끝나지 않아 서버가 파싱을 완료하지 못한 상태와 부합. 단, 확정하려면 아래 ①의 수신 바이트 비교가 필요 |
| **C. 청크 번호 충돌** | **유효** | 위와 동일 |
| **I. 백엔드 후속 처리 실패** | **신규** | 본문을 다 받고도 DB 등록 단계에서 실패·유실했을 가능성. 아래 백엔드 확인 목록으로 판별 |

### 새로 확인된 것 — multipart 필드 순서가 플랫폼마다 반대

`FileUploadManager.swift:260~300`(iOS 네이티브)는 **파일을 먼저 전부 넣고 메타데이터를 맨 뒤에** 붙입니다.

```swift
for (index, filePath) in fileList.enumerated() { ... body.append(fileData) ... }  // 파일 먼저
body.append("...name=\"deviceId\"...")    // 메타데이터는 맨 끝
body.append("...name=\"fileName\"...")
body.append("...name=\"totalNum\"...")
```

반면 Dart의 `FormData`는 dio 5.x 기준으로 finalize 시 **fields를 먼저, files를 나중에** 씁니다.

따라서 **iOS 네이티브 경로에서 전송이 66%에서 멈추면 서버는 `fileName`·`totalNum`·`lang`·`attendeeNum`을 하나도 받지 못합니다.** DB 등록에 필요한 값이 통째로 없으니 등록 로직이 실행될 수 없고, 그때까지 넘어간 파일만 S3에 남습니다. **"S3 로그만 있고 DB 로그는 아예 없다"와 정확히 맞아떨어집니다.**

> dio의 필드/파일 기록 순서는 패키지 소스를 직접 확인하지 못했으므로, 실제 패킷 캡처나 서버 수신 로그로 한 번 검증하는 것이 좋습니다.

### 업로드 경로 분기

| 조건 | 사용 경로 |
|------|----------|
| Android | 항상 Dart/Dio (`uploadFolder`) |
| iOS + `USE_SSL=true` (SKT·팀블로) | **Swift URLSession** — 위 필드 순서 문제 해당 |
| iOS + `USE_SSL=false` (Hynix) | Dart/Dio |

### 앱이냐 백엔드냐를 한 번에 가르는 확인

**액세스 로그에서 그 요청의 `Content-Length` 헤더값과 실제 수신 바이트 수를 비교한다.** (nginx는 `$request_length`, WAS 로그에도 대개 남는다)

| 결과 | 해석 |
|------|------|
| **수신 < Content-Length** | 클라이언트가 끝까지 보내지 못함 → **앱·네트워크 문제** (B·C 및 전송 계층) |
| **수신 == Content-Length** | 서버가 본문을 전부 받음 → **이후는 전적으로 백엔드 문제** (I) |

S3 객체 개수를 세는 것보다 훨씬 명확하다. 이 숫자 하나로 후보의 절반이 잘린다.

### 백엔드에서 확인할 것

앱은 요청을 한 번 보내고 응답을 기다릴 뿐이므로(2장 말미 참조), 남은 조사는 백엔드 핸들러 내부다.

| # | 확인할 것 | 왜 중요한가 |
|---|----------|------------|
| 0 | **DB 등록 로직 진입부에 로그가 있는지** | "도달 못 함"과 "도달했는데 조용히 실패"를 구분하는 출발점 |
| 1 | multipart를 **스트리밍 파싱**하는지, **전체 버퍼링** 후 처리하는지 | 스트리밍이면 부분 수신만으로도 S3 로그가 남는다. 버퍼링이면 S3 로그의 존재 자체가 "본문 전부 수신"의 증거가 되어 **해석이 정반대로 갈린다** |
| 2 | S3 업로드 시점 — 파트별 즉시인지, 전부 받은 뒤인지 | 위와 같은 이유 |
| 3 | S3 업로드와 DB 등록이 **같은 요청 스레드**인지, 비동기 큐로 넘기는지 | 큐라면 큐 유실·워커 장애가 원인이며 앱은 무관 |
| 4 | S3 성공 후 DB 등록까지의 경로에 **예외 삼킴**이 있는지 | 0번과 직결 |
| 5 | `totalNum`과 실제 수신 파일 수 검증, `missingFiles` 응답을 실제로 내보내는 코드가 있는지 | 앱은 이 응답을 받으면 누락분만 재전송하도록 되어 있다. 한 번도 나간 적이 없다면 그 장치는 죽어 있는 셈 |
| 6 | 본문 최대 크기·수신 타임아웃 (게이트웨이/WAS 양쪽) | 50분 회의 약 98MB가 한계선을 처음 넘었을 수 있다 |
| 7 | 200 응답을 **언제** 주는지 — S3 직후인지 DB 등록 후인지 | S3 직후에 준다면 DB 미등록은 후속 처리 문제이고, 앱이 성공 처리하는 것이 정상 동작이 된다 |

### 확인된 것 — 앱은 단일 요청, 후속 호출 없음

녹음 업로드는 `POST /api/contents/upload/encryption/files` **한 번뿐**이고, 응답에서 읽는 값은 `errorCode`, `httpCode`, `data.missingFiles` 세 가지가 전부다. **파일 위치나 키, contentId를 받아 다음 API를 호출하는 코드는 앱에 존재하지 않는다.** 성공하면 곧바로 로컬 폴더를 삭제하고 종료한다. iOS 네이티브도 `missingFiles`만 파싱한다.

다른 업로드 경로(`POST /api/contents/upload`)의 응답 모델이 `data.content.contentId`와 `data.transcribe`를 담고 있는 것으로 보아, 서버 API는 한 번의 요청으로 저장과 등록을 모두 처리하는 설계로 보인다.

> **다만 서버팀에 반드시 확인할 것**: 이 엔드포인트가 S3 저장과 DB 등록을 한 트랜잭션에서 처리하는지, 아니면 파일만 받고 등록은 별도 호출을 기대하는 구조인지. 후자라면 **앱이 두 번째 호출을 누락하고 있는 것**이며, 그것만으로 이번 현상이 전부 설명된다.

### 함께 드러난 부수 문제

- **고아 S3 객체**: DB 등록이 없으니 업로드된 파일은 아무도 참조하지 않는 상태로 남는다. 실패가 쌓일수록 계속 누적되므로 정리 배치나 보상 로직이 필요하다.
- **`missingFiles` 프로토콜 무력화**: 서버가 파일 수 부족을 감지해 재전송을 요구하는 구조인데, 본문이 끝나지 않으면 응답 자체를 보낼 수 없다. 정작 필요한 상황에서 이 장치가 동작하지 않는다.
- **데이터는 보존됨**: 클라이언트가 200을 받지 못했으므로 `upload_yn`은 `N`으로 남고 녹음 폴더도 삭제되지 않는다. 서랍 메뉴 > 녹음 실패에서 재전송이 가능하다.

### 서버 측에 추가로 요청할 것

- 요청 본문 수신 타임아웃 값과, 타임아웃 시 어떤 로그·응답을 남기는지
- multipart 파싱을 **스트리밍으로 처리하는지, 전체 수신 후 처리하는지** (S3 업로드 시점이 달라져 ①의 해석이 달라짐)
- 파일 수가 `totalNum`보다 적을 때 `missingFiles` 응답이 실제로 나가는지, 나간 사례가 로그에 있는지
- DB 등록 실패 시 S3 객체를 되돌리는 보상 처리가 있는지

## 2. 원인 후보

가능성이 높은 순서입니다.

### A. iOS 진행률의 "역행 금지" 클램프 — 화면만 멈춰 보이는 경우

`ios/Runner/FileUploadManager.swift:576`

```swift
if let currentProgress = self.uploadProgressMap[fileId], progress < currentProgress {
    return   // 이전보다 작은 값은 무시
}
```

업로드가 실패하면 `didCompleteWithError`가 `missingFiles`에 **전체 인덱스**를 넣고 처음부터 다시 전송합니다. 실제 진행률은 0부터 다시 올라가지만, 화면은 **이전 최대값 66%를 그대로 붙잡고** 있습니다. 재시도가 66%를 넘길 때까지 완전히 멈춘 것처럼 보이고, 같은 지점에서 계속 실패하면 영원히 66%입니다.

- **판별**: Xcode 콘솔의 `Task N progress:` 값이 0.0x부터 다시 올라가는지
- **특징**: 녹음 길이와 무관하게 "멈췄다가 갑자기 확 오른다"는 제보가 함께 나옴

### B. 마지막 청크가 아직 저장되지 않은 채 업로드 시작

`recording_controller.dart:690` — 저장 완료를 **5초만** 기다리고 타임아웃되면 그냥 진행합니다.

```dart
await _audioService.onSavingComplete.timeout(
  const Duration(seconds: 5),
  onTimeout: () { debugPrint('저장 완료 대기 타임아웃 - 강제로 폴더 처리 진행'); },
);
```

그런데 청크 저장은 `audio_recorder_io.dart:176`에서 `unawaited(_processBuffer(...))` — isolate 암호화 후 비동기로 기록됩니다. 긴 녹음이나 저사양 단말에서 5초를 넘기면:

- 마지막 파일이 목록에 안 잡혀 `totalNum`이 실제와 어긋남 → 서버가 `missingFiles` 판정 → 전량 재전송
- 파일이 잡히더라도 `MultipartFile.fromFile`이 **생성 시점의 파일 크기로 Content-Length를 확정**하므로, 전송 시점에 크기가 다르면 서버가 남은 바이트를 계속 기다림 → **진행률 동결**, send 타임아웃 10분 후 실패

**청크 3개 중 3번째에서 이 일이 생기면 진행률은 정확히 66%에서 멈춥니다.**

- **판별**: 로그에 `저장 완료 대기 타임아웃`, 그리고 `전체 폴더 크기: N bytes, 파일 개수: M` 의 M이 예상 청크 수보다 작은지

### C. 청크 파일 번호 충돌로 파일이 덮어써짐

`audio_recorder_io.dart:169-180`에서 버퍼들을 `unawaited`로 **동시에** 처리하고, `_writeToNewFile`은 `isFinal`일 때 `_fileCounter = 0`으로 되돌립니다. compute isolate의 완료 순서가 뒤바뀌면 마지막 청크가 먼저 끝나 카운터를 0으로 리셋하고, 뒤늦게 끝난 청크가 `encrypted_audio_0.pcm`을 덮어씁니다.

결과적으로 파일 수가 줄고 서버 판정이 어긋나 무한 재시도로 이어집니다. B와 증상이 같아 함께 확인하는 것이 좋습니다.

- **판별**: 녹음 폴더의 파일 번호가 연속인지, 개수가 `올림(녹음분/3)`과 일치하는지

### D. 서버가 본문 수신 도중 조기 응답 (401 / 413 / 504)

업로드 경로에는 **토큰 갱신 로직이 없습니다.** 장시간 녹음 후 액세스 토큰이 만료된 상태로 업로드하면, 서버가 본문을 다 받기 전에 401을 반환하고 소켓 읽기를 중단합니다. 클라이언트는 커널 버퍼가 찰 때까지만 전송하다 **임의의 지점에서 동결**되고, send 타임아웃 10분이 지나서야 예외가 납니다. 재시도 3회를 더하면 30분 넘게 "멈춘 것처럼" 보입니다.

`receiveTimeout: 60초`도 문제입니다. 100MB짜리 업로드를 서버가 60초 안에 처리하지 못하면 **본문은 다 보냈는데** 타임아웃이 나고 전량 재전송됩니다.

- **판별**: 서버 액세스 로그에서 해당 시각의 응답 코드 (401 / 413 / 504)

### E. 네트워크 전환으로 인한 업로드 취소

`upload_service.dart:490` — connectivity 변경을 감지하면 `_cancelCurrentUpload()`로 Dio 요청을 취소합니다. Wi-Fi ↔ LTE 전환만으로도 발생하고, 서버가 이어올리기를 지원하지 않아 **누적 진행률이 전부 버려집니다.** 화면에는 "네트워크 연결 끊김" 문구와 함께 진행률이 멈춘 채 남습니다.

- **판별**: 로그의 `Dio 요청 취소됨`, `업로드 일시 중지`

### F. 사실은 업로드가 아니라 "변환" 팝업

`main_container_controller.dart:492`

```dart
uploadMapData[key]?.processPercentage = (percentage / 100 * 80);  // STT는 최대 80%
```

서버 STT 퍼센트가 83%면 화면에는 **66%**로 표시됩니다. 게다가 SSE(`EventFlux`)는 `maxAttempts: 5`로 재연결을 포기하므로, 그 뒤 이벤트가 끊기면 **66%에서 영구 정지**합니다.

두 팝업의 생김새가 비슷해 사용자가 구분하지 못할 수 있습니다. **팝업 제목이 "파일 업로드 N건 진행 중"인지 "녹음 파일 변환 N건 진행 중"인지 반드시 확인해야 합니다.**

### G. Android 백그라운드 전환 시 포그라운드 서비스 실패

`_startAndroidUploadForegroundService`가 예외를 삼키고 로그만 남깁니다(`upload_service.dart:682`). FGS 시작이 실패하면 Doze/네트워크 제한으로 소켓이 정지하고 진행률이 얼어붙습니다.

- **판별**: 업로드 중 알림 영역에 업로드 알림이 보이는지, 화면을 켜 두면 정상 완료되는지

### H. iOS 메모리 압박 (부수 요인)

`FileUploadManager.swift:303` — multipart 본문 전체를 메모리 `Data`로 만든 뒤 **그 전체를 `String(data:encoding:)`으로 변환해 NSLog에 출력**합니다. 100MB 녹음이면 메모리가 2~3배로 튀어 OS 강제 종료(jetsam) 위험이 큽니다. 직접적인 66% 원인은 아니지만, 릴리즈 빌드에서는 반드시 제거해야 합니다.

### I. 백엔드 후속 처리 실패 (S3 이후 단계)

서버가 본문을 전부 수신했다면 원인은 전적으로 백엔드입니다. S3 업로드와 DB 등록이 같은 트랜잭션인지, 비동기 큐로 넘기는지, 예외를 삼키고 있지 않은지에 따라 갈립니다. 판별 방법은 1장의 백엔드 확인 목록 참조.

### J. 앱의 성공 판정이 지나치게 느슨함 (별개 결함)

`upload_service.dart:1531~1570`

```dart
if (errorCode != null) return false;
// missingFiles 없고 에러코드 없으면 성공
break;   // ← HTTP 200이기만 하면 본문 내용과 무관하게 성공 처리
```

서버가 200을 주면서 본문에 `errorCode`만 없으면, 내용이 무엇이든 앱은 성공으로 간주하고 **녹음 폴더를 삭제**합니다. 서버가 "파일은 받았고 등록은 아직"이라는 취지의 응답을 주더라도 앱은 완료된 것으로 처리합니다.

이번 건의 직접 원인은 아니지만(66%에서 멈춰 이 경로를 타지 않음), 만약 서버가 2단계 설계라면 이 판정 때문에 **녹음이 조용히 사라지는 사고**가 이미 발생했을 수 있습니다. "회의록은 생성되지 않았는데 녹음 실패 목록에도 없다"는 제보가 있었는지 확인이 필요합니다.

## 3. 해결 방안

원인이 확정되기 전이라도 넣어둘 만한 것과, 확정 후에 손댈 것을 나눴습니다.

### 지금 바로 넣을 수 있는 것 (원인과 무관하게 이득)

| # | 조치 | 위치 | 효과 |
|---|------|------|------|
| 1 | 재전송 시작 시 `uploadProgressMap[fileId] = 0`으로 리셋 (클램프 제거) | `FileUploadManager.swift` `updateProgress` / `retryMissingFiles` | 화면이 실제 진행 상태를 반영 — **A 해소** |
| 2 | 저장 완료 대기 5초 → 완료 이벤트 무제한 대기(안전장치로 30~60초) | `recording_controller.dart` `stopRecording` | 마지막 청크 누락 방지 — **B 해소** |
| 3 | `unawaited(_processBuffer(...))` → 순차 `await` 처리 | `audio_recorder_io.dart` `_processPendingBuffers` | 파일 번호 충돌·덮어쓰기 방지 — **C 해소** |
| 4 | 업로드 직전 파일 수 검증 (`파일 개수 == 예상 청크 수`) 후 불일치 시 로그+중단 | `upload_service.dart` `uploadFolder` | 잘못된 요청을 30분간 재시도하는 낭비 제거 |
| 5 | `receiveTimeout` 60초 → 5분 이상으로 상향 | `upload_service.dart` `uploadFolder` / `uploadFile` | 큰 파일 처리 지연으로 인한 헛된 재전송 제거 — **D 일부 해소** |
| 6 | 업로드 시작 직전 토큰 유효성 확인·갱신 | `upload_service.dart` `uploadProcess` | 401로 인한 무한 정체 제거 — **D 해소** |
| 7 | 본문 전체를 문자열로 만들어 NSLog 하는 코드 제거 | `FileUploadManager.swift:303` | 메모리 급증·강제 종료 방지 — **H 해소** |
| 8 | 진행률이 N분 이상 변하지 않으면 UI에 "지연되고 있습니다" 안내 노출 | `upload_progress_widget.dart` | 사용자가 "멈췄다"고 느끼는 시간을 줄임 |
| 9 | **메타데이터 필드를 파일보다 먼저 전송하도록 순서 변경** | `FileUploadManager.swift` `uploadFolder` / `retryMissingFiles` | 전송이 중간에 끊겨도 서버가 `fileName`·`totalNum`을 확보 → 서버가 상황을 인지하고 `missingFiles`로 응답 가능 |
| 10 | 서버: 본문 수신 타임아웃 시 명시적 에러 응답 + 고아 S3 객체 정리 | 서버 | 클라이언트가 무한 대기하지 않고 재시도 UI로 전환 |
| 11 | 성공 판정을 `httpCode == 200` 명시 확인으로 좁히고, 그 외 응답은 실패 처리 | `upload_service.dart` `uploadFolder` | 애매한 200 응답에 녹음을 삭제하는 사고 방지 — **J 해소** |

### 원인 확정 후 검토할 것

- **E(네트워크 전환)**: 연결이 끊기자마자 취소하지 말고 짧게 유예를 두거나, 서버에 이어올리기(resumable upload)를 요청. 현재 구조에서는 100MB를 처음부터 다시 보내는 비용이 너무 큽니다.
- **F(변환 SSE)**: `maxAttempts: 5` 이후에도 폴링으로 상태를 확인하도록 보강. 이미 `syncProcessingStatus()`가 있으므로 포그라운드 복귀 외에 주기적 호출을 추가하는 선에서 해결됩니다. STT 퍼센트를 ×0.8로 환산하는 방식도 사용자 혼란을 줄이려면 재검토할 만합니다.
- **G(Android FGS)**: FGS 시작 실패를 삼키지 말고 로그·지표로 남기고, 실패 시 사용자에게 "화면을 켜 두세요" 안내.
- **분할 업로드**: 근본적으로는 청크 단위 개별 업로드로 바꾸면 A·B·D·E가 한꺼번에 완화됩니다. 서버 API 변경이 필요하므로 별도 과제로 다뤄야 합니다.

## 4. 사용자에게 물어볼 것

현상 제보가 다시 들어오면 아래 순서로 확인하면 원인 구간이 좁혀집니다. **①~③만으로도 후보의 절반이 걸러집니다.**

### 1순위 — 이것부터 물어본다

| # | 질문 | 알 수 있는 것 |

| ① | **녹음을 몇 분 하셨나요?** (대략도 가능) | 청크 수 계산 → 66%가 파일 경계인지 판별. 9분 내외면 **B·C** 유력, 무관하면 **A·F** 유력 |
| ② | ~~멈춘 팝업의 제목이 "파일 업로드"였나요, "녹음 파일 변환"이었나요?~~ | **1장에서 해결됨** — DB 등록이 없어 contentId가 생성되지 않았으므로 '파일 업로드' 팝업으로 확정. 다른 제보 건에서는 여전히 물어볼 것 |

|---|------|--------------|

| ⑥ | 그동안 화면을 켜 두셨나요, 다른 앱을 쓰거나 화면이 꺼졌나요? | **G**(Android FGS) 판별 |

- 사번/계정 (서버 액세스 로그 조회용)
- 서랍 메뉴 > 녹음 실패 목록에 해당 녹음이 남아 있는지 스크린샷

## 5. 사용자 안내 문구 (원인 확정 전 임시 대응)

원인 조사 중에도 현장에서 데이터를 잃지 않도록 안내할 내용입니다.

- 업로드가 멈춰 보여도 **앱을 강제 종료하지 마세요.** 녹음 파일은 기기에 남아 있습니다.
- 업로드 중에는 **화면을 켜 두고 앱을 앞에 두는 것**이 가장 안전합니다.
- 업로드에 실패했더라도 **서랍 메뉴 > 녹음 실패**에서 해당 녹음을 찾아 다시 전송할 수 있습니다. 목록에 남아 있다면 녹음 자체는 보존된 상태입니다.
- 재전송해도 계속 같은 지점에서 멈춘다면, 위 1순위 질문의 답과 화면 녹화를 함께 전달해 주세요.
