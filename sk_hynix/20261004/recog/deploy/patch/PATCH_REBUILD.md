# 망분리 서버에서 소스만 고쳐 재배포하기

> 대상: `mobile-sync-server`가 `install.sh`로 이미 설치되어 돌고 있는 망분리 서버
> 작성 2026-10-04 · 집 PC(Docker)에서 0.0.3 → 0.0.4 교체를 실제로 돌려 확인함

---

## 0. 한 줄 요약

**서버에 이미 있는 `0.0.3` 이미지를 밑바탕으로 깔고, 그 위에 고친 소스만 얹어서
`0.0.4`라는 새 이미지를 서버 안에서 만든다.** 인터넷은 필요 없다.

---

## 1. 원리 — "0.0.3을 활용해서 빌드한다"는 게 무슨 뜻인가

도커 이미지는 **층(layer)을 쌓은 것**이다. 집에서 만든 `0.0.3`은 이렇게 생겼다.

```
mobile-sync-server:0.0.3
┌───────────────────────────────┐
│ ④ 우리 소스 (src/, VERSION)    │  ← 3MB. 고치는 건 여기뿐
├───────────────────────────────┤
│ ③ ffmpeg / ffprobe            │  ← 인터넷에서 받아야 하는 것
├───────────────────────────────┤
│ ② python 3.11                 │  ← 인터넷에서 받아야 하는 것
├───────────────────────────────┤
│ ① 리눅스 기본                  │  ← 인터넷에서 받아야 하는 것
└───────────────────────────────┘
```

처음부터 만들려면 ①②③을 인터넷에서 받아야 한다. 그래서 지금까지 집에서 만들었다.

그런데 서버에는 `0.0.3`이 이미 load되어 있으니 **①②③이 서버 안에 이미 있다.**
그러니 `0.0.3`을 통째로 바닥에 깔고, 맨 위의 소스만 새 것으로 바꿔 끼우면 된다.

```
mobile-sync-server:0.0.4  (서버에서 새로 만듦)
┌───────────────────────────────┐
│ ⑤ 고친 소스 (src/, VERSION)    │  ← 새로 얹은 층
├───────────────────────────────┤
│ mobile-sync-server:0.0.3 전체  │  ← 서버에 이미 있는 것을 그대로 바닥으로
│ (리눅스 + python + ffmpeg + 옛 소스) │
└───────────────────────────────┘
```

이걸 지시하는 파일이 `Dockerfile.patch`이고, 첫 줄이 `FROM mobile-sync-server:0.0.3`이다.
"0.0.3에서 출발해라"라는 뜻이다. 옛 소스는 지우고 새 소스를 넣으므로 섞이지 않는다.

**결과:**
- `0.0.3`은 지워지지 않고 그대로 남는다 → 언제든 되돌릴 수 있다
- 다음에 또 고치면 `0.0.4`를 바닥에 깔고 `0.0.5`를 만든다 (스크립트가 알아서 지금 쓰는 걸 바닥으로 잡는다)

### 이 방법으로 되는 것 / 안 되는 것

| 바꾸는 것 | 서버에서 가능? |
|---|---|
| `src/` 안의 파이썬 코드, `/docs` 화면(`src/recog/static/`) | ✅ 가능 |
| `.env` 설정값 (비프음 파라미터, 워커 수 등) | ✅ 이미지 재빌드도 필요 없음 — `.env` 수정 후 `docker compose --env-file .env up -d` |
| ffmpeg 버전, python 버전 | ❌ 집에서 `deploy/build.sh`로 다시 만들어야 함 |
| pip 패키지 추가 | ❌ (recog는 원래 pip 패키지를 쓰지 않는다) |

## 2. 가져갈 것 (집에서 준비)

`deploy/build.sh`가 이미지 tar를 만들 때 **같은 소스로 키트도 함께 만든다.**

```
dist/mobile-sync-server_<버전>_amd64.tar           ← 이미지 (install.sh 로 설치)
dist/mobile-sync-server_<버전>_amd64.tar.sha256
dist/mobile-sync-server_<버전>_patchkit.tar.gz     ← 이 키트
```

**이미지 tar와 키트는 항상 같은 번호끼리 쓴다.** 키트의 `src/`가 서버에서 도는 이미지보다
옛것이면, `rebuild.sh`가 `src/`를 통째로 갈아 끼우므로 그 사이의 수정이 사라진다.
그래서 새 이미지를 설치할 때마다 옛 `patch/`를 지우고 새 키트를 풀어 둔다.

키트 안에 든 것:

| 파일 | 역할 |
|---|---|
| `rebuild.sh` | 서버에서 실행하는 스크립트. 빌드 → 검증 → 교체 → 확인까지 전부 |
| `Dockerfile.patch` | "지금 이미지 위에 소스만 얹어라"는 빌드 지시서 |
| `smoke_test.py` | 새 이미지로 실제 병합을 한 번 돌려보는 검증 (집 빌드 때 쓰던 것과 같은 것) |
| `src/` | 소스. 서버에서 고칠 대상 |
| `VERSION` | 버전 표기. 스크립트가 자동으로 덮어쓴다 |
| `PATCH_REBUILD.md` | 이 문서 |

## 3. 서버에서 — 키트 풀기 (새 이미지를 설치할 때마다)

### 3-1. 설치 경로 확인

`install.sh`를 실행했던 디렉터리(= `docker-compose.yml`과 `.env`가 있는 곳)다.
기억이 안 나면 돌고 있는 컨테이너에게 물어보면 된다.

```bash
docker inspect mobile-sync-server \
  --format '{{ index .Config.Labels "com.docker.compose.project.working_dir" }}'
```

이하 이 경로를 `<설치경로>`로 쓴다. (예: `/data/timblo/mobile-sync-server`)

### 3-2. 지금 버전 확인

```bash
grep IMAGE_ <설치경로>/.env
#  IMAGE_NAME=mobile-sync-server
#  IMAGE_VERSION=0.0.3          ← 이게 바닥이 된다

docker images mobile-sync-server
#  mobile-sync-server   0.0.3   ...   ← 서버에 실제로 있어야 한다
```

### 3-3. 키트 풀기 (새 이미지를 설치할 때마다)

sftp로 `mobile-sync-server_<버전>_patchkit.tar.gz`를 `<설치경로>`에 올린 뒤:

```bash
cd <설치경로>
rm -rf patch                  # 옛 키트가 있으면 지운다 (옛 소스로 덮어쓰는 사고 방지)
mkdir patch
tar xzf mobile-sync-server_0.0.3_patchkit.tar.gz -C patch
chmod +x patch/rebuild.sh
```

결과 모양:

```
<설치경로>/
├── docker-compose.yml     ← install.sh 가 만든 것 (그대로)
├── .env                   ← install.sh 가 만든 것 (스크립트가 IMAGE_VERSION 만 바꾼다)
└── patch/
    ├── rebuild.sh
    ├── Dockerfile.patch
    ├── smoke_test.py
    ├── VERSION
    └── src/               ← 여기를 고친다
```

> `patch/`를 `<설치경로>` 바로 밑에 두면 스크립트가 설치경로를 알아서 찾는다.
> 다른 곳에 두었다면 실행할 때 `INSTALL_DIR=<설치경로> ./rebuild.sh 0.0.4` 처럼 알려주면 된다.

## 4. 서버에서 — 소스 고치고 재배포 (매번)

### 4-1. 소스 수정

`<설치경로>/patch/src/` 안의 파일을 고친다 (vi 등).
다른 PC에서 고쳤다면 `patch/src/`를 통째로 바꿔 넣어도 된다.

### 4-2. 실행

```bash
cd <설치경로>/patch
./rebuild.sh 0.0.4
```

버전 번호는 **지금 쓰는 것과 다른 새 번호**를 준다. 같은 번호나 이미 있는 번호면 스크립트가 거부한다
(덮어쓰면 되돌릴 이미지가 사라지기 때문).

### 4-3. 스크립트가 하는 일

| 단계 | 내용 | 실패하면 |
|---|---|---|
| 1/6 | 바닥 이미지(`.env`의 현재 버전)가 서버에 있는지 | 중단 |
| 2/6 | **소스 문법 검사** — 오타가 있으면 `src/recog/xxx.py:25` 처럼 위치를 알려준다 | 중단 |
| 3/6 | 새 이미지 빌드 (수 초) | 중단 |
| 4/6 | **새 이미지로 임시 컨테이너를 띄워 실제 병합을 한 번 돌린다** | 중단 |
| 5/6 | `.env`를 백업하고 `IMAGE_VERSION`을 새 번호로 바꾼 뒤 재기동 | — |
| 6/6 | `/health` 응답 확인 (최대 60초) | **자동으로 이전 버전으로 롤백** |

**4/6까지는 서비스를 건드리지 않는다.** 그 전에 실패하면 지금 돌던 컨테이너가 그대로 돈다.

정상이면 마지막에 이렇게 나온다:

```
[rebuild] 4/6 새 이미지 동작 검증 (임시 컨테이너, 서비스에는 영향 없음)
  [smoke] /health 200
  [smoke] status=DONE
  [smoke] 결과 확인: ... / flac / 16000Hz / 3.00초
=== 통과 ===
...
[rebuild] 6/6 기동 확인 (http://127.0.0.1:9995/health)
[rebuild] 정상 기동 — 이제 mobile-sync-server:0.0.4 로 돌고 있다
```

### 4-4. 확인

```bash
docker logs mobile-sync-server 2>&1 | grep '"version"' | tail -1
#  ... "version": "0.0.4" ...      ← 새 버전으로 떴는지
```

## 5. 되돌리기 (수동)

스크립트가 성공했지만 실제로 써보니 문제가 있을 때:

```bash
cd <설치경로>
sed -i 's/^IMAGE_VERSION=.*/IMAGE_VERSION=0.0.3/' .env
docker compose --env-file .env up -d
```

`.env`를 바꾸기 전 원본도 `.env.bak.<날짜-시각>`으로 남아 있다.
데이터(`RUNTIME_DIR`, `merge.db`)는 이미지와 무관하게 호스트에 있으므로 되돌려도 그대로다.

## 6. 문제가 생기면

| 증상 | 원인 / 조치 |
|---|---|
| `3/6`에서 `pull access denied` / 레지스트리 접속 에러 | 빌더가 인터넷에서 바닥 이미지를 찾으려 한 것. 스크립트가 자동으로 구형 빌더(`DOCKER_BUILDKIT=0`)로 한 번 더 시도한다. 구형 빌더는 서버 안의 이미지만 본다 |
| `3/6`에서 `DEPRECATED: The legacy builder ...` 경고 | 위 재시도가 동작한 것. 무시해도 된다 |
| `2/6`에서 문법 오류 | 알려준 파일:줄을 고치고 같은 명령 다시 실행 |
| `4/6`에서 검증 실패 | 소스에 실행 중 오류가 있는 것. 출력된 컨테이너 로그를 사진으로 찍어 오면 집에서 바로 원인을 찾을 수 있다. 서비스는 이전 버전 그대로 돈다 |
| `이미 있다. 다른 번호를 줄 것` | 그 번호로 이미 만든 적이 있다. 다음 번호를 쓰거나, 정말 다시 만들 거면 `docker rmi mobile-sync-server:0.0.4` 후 재실행 (지금 돌고 있는 버전은 지우지 말 것) |
| `.env / docker-compose.yml 이 없다` | `patch/`가 설치경로 밑에 있지 않다. `INSTALL_DIR=<설치경로> ./rebuild.sh 0.0.4` |

## 7. 집에 돌아와서 할 것

서버에서 고친 소스는 **서버에만 있다.** 집 저장소와 어긋나지 않게 맞춰야 한다.

- 고친 파일과 내용을 적어 오거나(사진도 됨), `patch/src/` 전체를 반출할 수 있으면 그걸 가져온다.
- 집에서 같은 수정을 저장소에 반영하고 `VERSION`을 서버와 같은 번호로 맞춘 뒤 커밋한다.
- 다음에 집에서 `build.sh`로 새로 만들 때는 서버의 마지막 번호보다 **큰 번호**를 쓴다.
  같은 번호를 쓰면 서버에서 `install.sh`가 load할 때 서버에서 만든 이미지를 덮어쓴다.

정리하면 **집 저장소 = 서버에서 도는 버전**을 항상 유지하는 것이 원칙이다.

```
집 0.0.3 빌드 ─→ 서버 설치 (0.0.3 + 키트 0.0.3)
                 서버 긴급 패치 → 0.0.4
집에서 0.0.4 수정 반영, VERSION=0.0.4 커밋
집 0.0.5 빌드 ─→ 서버 설치 (0.0.5 + 키트 0.0.5)
```
