# 로그 가이드

> 2026-09-22 · Dozzle로 실시간 모니터링하기 위한 구조화 로그
> 브랜치: `skHynix_nohsn`

---

## 요약

stdout에 **JSON 한 줄씩** 출력한다. Dozzle이 JSON을 인식해 필드별로 펼치고 `level`로 색을 입힌다.

```json
{"ts":"2026-09-22T12:44:46.321Z","level":"INFO","event":"merge_done",
 "message":"merged in 858ms","job":"mrg_4aca10bb","room":"R-001","totalMs":858,
 "durationMs":6562,"alignMode":"beep"}
```

| 키 | 뜻 |
|---|---|
| `event` | **기계가 읽는 안정적인 키.** grep·알림 조건에 쓴다 |
| `message` | 사람이 읽는 짧은 줄. Dozzle이 접힌 행에 보여준다 |
| 나머지 | 이벤트별 필드 |

---

## 작업 전에 어땠나

| 구분 | 이전 |
|---|---|
| HTTP 액세스 로그 | `wsgiref` 기본 핸들러가 stderr에 한 줄. **처리시간도 jobId도 없음** |
| 앱 로그 | `print("INFO ...", flush=True)` 8군데. 레벨 없음, 끌 수 없음 |
| **병합 실패** | **로그가 아예 없었다** |
| 워커 스레드 사망 | 감지 불가 |

**가장 큰 공백은 실패 로그였다.** `merge_job.py`의 두 `except` 절이 작업 상태만 바꾸고
로그를 한 줄도 남기지 않았다. 즉 **Dozzle을 아무리 들여다봐도 병합 실패는 보이지 않았고**,
master-api가 폴링해서 `status: ERROR`를 받아야만 알 수 있었다.
두 번째 `except`는 스택 트레이스까지 버렸다.

## 1. 레벨

`RECOG_LOG_LEVEL` 환경변수. 기본 `INFO`.

| 레벨 | 언제 |
|---|---|
| `INFO` | **평소.** 아래 이벤트 목록이 전부 나온다 |
| `DEBUG` | 문제를 쫓을 때만 잠깐. ffmpeg 전체 커맨드, 트랙별 비프 검출 상세 |
| `WARNING` | 소음을 줄이고 싶을 때. 정상 흐름이 안 보이므로 권하지 않는다 |

바꾸려면 `.env`를 고치고 컨테이너를 재기동한다. 기동 로그에 적용된 값이 찍힌다.

## 2. 무엇이 찍히나

### 2.1 기동

재시작 후 **"내가 고친 설정이 먹었나"**를 한 줄로 답한다.

```json
{"event":"server_start","message":"listening on http://0.0.0.0:8080",
 "version":"0.0.1","workers":3,"maxFiles":5,"jobTimeoutSec":1800,
 "recordTtlDays":90,"beepEnabled":true,"beepTrim":true,"beepFreq":[3000,4200],
 "ffmpeg":"ffmpeg version 7.1.1 ...","logLevel":"INFO","dataRoot":"/var/lib/recog/runtime"}
```

### 2.2 정상 흐름 (INFO)

한 건의 병합이 남기는 줄들이다.

| `event` | 담는 것 | 왜 필요한가 |
|---|---|---|
| `http_request` | method, path, status, **ms** | 기존에 없던 처리시간. 느려지는 순간이 보인다 |
| `merge_accepted` | job, room, files, align, **queueDepth** | 접수 시점. 큐 깊이가 밀리기 시작하면 워커 부족 신호 |
| `merge_started` | job, room, files, source, queueDepth | 워커가 집어간 시점 |
| `merge_downloaded` | participant, bytes, ms, url | 파일별 다운로드 결과 |
| `merge_stage` | stage, progress | **어느 단계에서 오래 걸리는지** — 실시간 모니터링의 핵심 |
| `merge_alignment` | mode, reference, offsets, fallbacks, beepAtMs, trimmedMs | 정렬이 어떻게 됐는지 한 줄로 |
| `merge_done` | totalMs, 단계별 ms, durationMs, sizeBytes, alignMode | 완료 |

`merge_stage`는 **단계가 바뀔 때만** 찍는다. 파일마다 찍으면 타임라인이 묻힌다.

### 2.3 실패 (ERROR) — 전부 신설

| `event` | 언제 | 트레이스 |
|---|---|---|
| `merge_failed` | 병합 실패 (E41xx). code, participant, **실패한 stage** | — |
| `merge_crashed` | 예상 못 한 실패 (E5000) | ✅ **버려지던 것을 살렸다** |
| `merge_download_failed` | presigned 다운로드 실패. participant, code, url | — |
| `ffmpeg_failed` | ffmpeg/ffprobe 비정상 종료. stderr 끝 2KB | — |
| `worker_crashed` | 워커 스레드가 작업 밖에서 터짐 | ✅ |
| `http_crashed` | 요청 처리 중 예외 | ✅ |

`merge_failed`의 `stage` 필드는 **상태를 지우기 전에** 읽는다.
어느 단계에서 죽었는지가 실패 줄에서 가장 먼저 보고 싶은 값이기 때문이다.

### 2.4 경고 (WARNING)

| `event` | 의미 |
|---|---|
| `merge_record_save_failed` | 상태를 DB에 못 씀. **병합은 계속된다** (설계상 best-effort) |
| `beep_detect_failed` | 한 트랙을 비프 탐색하지 못함. 다음 단계로 폴백 |
| `proxy_detected` | 프록시를 거쳐 들어온 요청 |
| `merge_schema_newer_than_code` | 더 새 이미지가 마이그레이션한 DB |

### 2.5 DEBUG

| `event` | 담는 것 |
|---|---|
| `ffmpeg_command` | ffmpeg/ffprobe 전체 커맨드라인 |
| `beep_detected` / `beep_absent` | 트랙별 비프 위치·신뢰도·반복 검출 수 |

## 3. 🔐 presigned URL은 절대 그대로 찍지 않는다

presigned URL의 쿼리스트링에 든 서명은 **사실상 자격증명**이다.
컨테이너 로그는 호스트에 파일로 남고 Dozzle이 브라우저에 그려주므로,
통째로 찍히면 그대로 유출 경로가 된다.

```
실제 URL  http://timblo-minio:9000/default.timblo.io/kms/fileKey?X-Amz-Signature=deadbeef...
로그      http://timblo-minio:9000/default.timblo.io/kms/fileKey
```

**`logs.safe_url()`을 거치지 않은 URL은 로그에 넣지 않는다.**
어느 스토리지의 어느 오브젝트인지는 남으므로 전송 실패를 진단하는 데는 충분하다.

> 테스트(`tests/test_logs.py`)가 이 동작을 고정하고 있다. 서명이 새는 회귀는
> 로그가 지저분해지는 문제가 아니라 스토리지 접근 권한이 새는 문제다.

## 4. Dozzle에서 쓰는 법

### 특정 작업 추적

검색창에 `jobId`를 넣으면 접수 → 시작 → 단계 → 완료가 순서대로 나온다.

```
mrg_4aca10bb4a1f4bc196e9
```

### 실패만 보기

```
merge_failed        병합 실패
merge_crashed       예상 못 한 실패 (트레이스 포함)
"level":"ERROR"     전부
```

### 느려지는지 보기

`merge_stage`를 걸어두면 단계 전환 간격이 그대로 보인다.
`merge_done`의 `processMs`가 평소보다 크면 ffmpeg 쪽이다.

### 큐가 밀리는지 보기

`merge_accepted`의 `queueDepth`. 계속 0보다 크면 `MERGE_WORKERS`를 올릴 때다.

## 5. 왜 이렇게 했나

**① JSON인 이유** — Dozzle이 JSON을 자동 인식해 필드별 검색과 레벨 색칠을 해준다.
`key=value` 평문은 그냥 글자로만 보인다.

**② 전부 stdout인 이유** — stdout과 stderr로 나누면 `docker logs`에서 **두 스트림의
순서가 뒤집혀 보인다.** 실패를 거슬러 읽을 때 정확히 잘못된 일이다.
그래서 `wsgiref` 기본 액세스 로그(stderr)는 아예 껐다 — 우리 `http_request`와 중복이고
처리시간도 jobId도 없다.

**③ `event`와 `message`를 나눈 이유** — `event`는 grep·알림이 거는 안정적인 키이고,
`message`는 Dozzle 접힌 행에 보이는 사람용이다. 둘을 합치면 한쪽이 불편해진다.

**④ 의존성 0개** — 표준 `logging` + `json`. `structlog` 같은 걸 깔지 않았다.
