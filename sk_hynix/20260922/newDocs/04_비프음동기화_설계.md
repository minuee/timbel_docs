# 비프음 동기화 설계

> 2026-09-22 · 여러 기기의 녹음을 하나로 합칠 때 **시작점을 어떻게 맞출 것인가**
> 브랜치: `skHynix_nohsn`

---

## 요약

`/v1/merge`가 참가자별 녹음을 겹쳐 합칠 때, **각 파일의 0번 샘플이 실제로 몇 시였는지**를 알아야 한다.
이 값을 구하는 방법을 **3단계 우선순위**로 정했다.

| 순위 | 방법 | 정확도 | 상태 |
|---|---|---|---|
| **1** | **비프음** — 오디오 안의 공통 기준점 | **수 ms** (합성 실측 2ms) | ✅ 구현 완료 |
| **2** | `startedAt` — 각 기기가 보고한 시작 시각 | 수백 ms ~ 2초 | ✅ 구현 완료, 값 대기 |
| **3** | `none` — 전부 0초에서 겹침 | 수 초 | ✅ 기존 동작 그대로 |

비프음이 있으면 무조건 1순위를 쓴다. 없으면 `align` 값에 따라 2 또는 3으로 내려간다.

---

## 1. 왜 시작점이 문제인가

참가자마다 자기 폰으로 자기 목소리를 녹음하고, 서버가 그걸 하나의 타임라인에 겹친다.
그런데 **파일 안에는 "몇 시에 시작했는지"가 들어 있지 않다.** 파일은 그냥 "0초부터 N초까지의 소리"다.

어긋나면 이렇게 된다.

| 어긋난 양 | 결과 |
|---|---|
| ~100ms | 무해 |
| 300ms | 턴 전환이 겹침으로 바뀌어 STT 인식률 하락 |
| 1초 이상 | 안 겹쳤던 말이 겹치고, 겹쳤던 말이 떨어짐 |
| 수 초 | **발화 순서가 뒤바뀜** — 회의록이 틀어짐 |

자연스러운 대화의 턴 간격이 보통 200ms 안팎이라, 그 수준을 넘어가면 없던 겹침이 생긴다.
겹친 구간은 STT가 가장 못하는 구간이다.

**→ 목표: 100ms 이내.**

### 지금 어긋나는 양

모바일 앱 소스(`newDocs/mobileApp/`)를 직접 읽어 확인한 값이다.

| 원인 | 크기 | `startedAt`으로 잡히나 |
|---|---|---|
| 각자 버튼 누른 시각 차이 | 수 초 | ✅ |
| **백그라운드 서비스 기동 대기** | **0 ~ 2.2초, 기기마다 다름** | ❌ |
| 마이크 오픈 / 버퍼 지연 | 수십 ~ 200ms | ❌ |
| 기기 시계 오차 | 수십 ms ~ | ❌ (오히려 값을 오염시킴) |

근거: `recording_controller.dart:476`에서 `DateTime.now()`를 찍고,
그 뒤 `:494~520`에서 백그라운드 서비스가 뜰 때까지 **최대 2.2초를 기다린 다음**
`audio_recorder_io.dart:70`에서 실제 녹음이 시작된다.

즉 현재 `startedAt`은 **"버튼 누른 시각"이지 "녹음이 시작된 시각"이 아니다.**

## 2. 우선순위 1 — 비프음

### 원리

방장 폰이 스피커로 비프음을 울리고, **방 안의 모든 폰이 그 소리를 녹음한다.**

```
방장 폰   ──🔔────────────▶  소리가 방에 퍼짐
                              │
          ┌───────────────────┼───────────────────┐
          ▼                   ▼                   ▼
       폰 A 녹음            폰 B 녹음            폰 C 녹음
       (비프 5.00초 지점)   (비프 4.26초 지점)   (비프 3.07초 지점)
```

각 파일에서 비프 위치를 찾으면, **그 차이가 곧 녹음 시작 시각의 차이**다.

기기 시계도, 기동 지연도, 마이크 버퍼 지연도 **전부 건너뛴다.**
소리 자체가 기준이기 때문이다. 이게 `startedAt`과의 본질적인 차이다.

### 규격 (확정)

| 항목 | 값 |
|---|---|
| 주파수 | **3000Hz + 4200Hz 동시** |
| 길이 | 250ms (앞뒤 5ms 페이드) |
| 반복 | **3회, 정확히 1000ms 간격** (온셋 기준) |
| 진폭 | -6dBFS |
| 파일 | `newDocs/assets/sync_beep.wav` — 48kHz / 16bit / mono / 2.250초 |
| 재생 시점 | 녹음 시작 후 **5초** |

### 규격 근거

**① 이중음인 이유** — 순음 하나만 찾으면 말소리에 오검출이 난다.
두 주파수가 **같은 순간에 동시에** 튀어야 인정하면 오검출이 사실상 0이 된다.

**② 3000/4200Hz인 이유** — 세 가지 제약의 교집합이다.

```
    0 ─────── 1k ─── 2k ─── 3k ─── 4k ─── 5k ──────── 8k ← 16kHz 녹음의 한계
    [ 사람 목소리 주 에너지 ]        ▲       ▲
                                  3000    4200
```

- **8kHz를 반드시 밑돌 것** — 녹음이 16kHz라 그 위는 아예 기록되지 않는다
- **말소리 주 에너지 위일 것** — 아래 실측에서 1600/2500Hz는 배경음 간섭으로 오차가 2배였다
- **배음이 겹치지 않을 것** — 3000의 배음은 6000/9000, 4200은 8400. 겹치지 않는다

> **1600+2500Hz도 시험했으나 탈락시켰다.** 배경 말소리의 포먼트 대역과 겹쳐
> 협대역 에너지가 흔들렸고, 같은 검출기로 정렬 오차가 두 배였다.

**③ 3회 반복인 이유** — 하나를 기침·문소리에 묻혀도 나머지로 복구한다.
그리고 **1초 간격이라는 패턴 자체가 검증 수단**이 된다. 세 번이 정확히 1초 간격이어야
비프로 인정하므로, 우연히 비슷한 소리가 한 번 났다고 오작동하지 않는다.

**④ WAV여야 하는 이유** — MP3/AAC는 인코딩 특성상 파일 앞에 무음 프리롤이 붙고
온셋이 뭉개진다. 그 양이 기기·디코더마다 달라서 정확도가 깨진다.

**⑤ 3초가 아니라 5초인 이유** — 앱 기동 지연이 최대 2.2초다.
3초 뒤에 울리면 늦게 시작한 폰이 비프를 놓친다.

```
방장 폰   : 버튼 ─0.3초─▶ 녹음시작 ──────3초──────▶ 🔔
느린 폰   : 버튼 ────2.2초────▶ 녹음시작 ─0.8초─▶ (아슬아슬)
더 느리면 : 버튼 ──────────────▶ 녹음시작      🔔 놓침 ❌
```

### 검출 방법

```
FLAC 다운로드 → 16kHz mono wav 정규화 (기존 단계 그대로)
      ↓
0~10초 구간만 읽는다
      ↓
Goertzel 로 3000Hz·4200Hz 두 대역의 프레임별 에너지 계산 (40ms 창 / 10ms 홉)
      ↓
콤필터: 1000ms 간격 3연타가 가장 잘 맞는 위치를 찾는다
        점수 = min(e[i], e[i+1초], e[i+2초])   ← 셋 다 있어야 높음
      ↓
온셋 정밀화: 후보 주변을 2ms 간격으로 다시 훑어 상승 지점을 찾는다
      ↓
3회분 온셋의 중앙값을 취한다 (잡음 평균화)
      ↓
정렬: delay_i = max(비프위치) - 비프위치_i
```

**Goertzel**은 특정 주파수 하나의 에너지만 O(N)으로 뽑는 알고리즘이다.
표준 라이브러리 40줄이면 되므로 **pip 의존성 0개 정책을 유지한다.**

### 검증 결과 (실측)

배경 말소리(핑크노이즈 + 220/700/1900Hz 트레몰로)를 깔고, 기기 세 대가 서로 다른 시각에
녹음을 시작한 상황을 만들어 시험했다.

| 기기 | 비프 감쇠 | 실제 비프 위치 | 검출 | **정렬 편차** |
|---|---|---|---|---|
| A (방장, 가까움) | -6dB | 5000ms | 5016ms | **0ms** |
| B (방 건너편) | -20dB | 4260ms | 4278ms | **-2ms** |
| C (가장 멂) | -26dB | 3070ms | 3088ms | **-2ms** |

- **검출률 100%** — 가장 먼 기기도 배경 대비 1950배로 뚜렷했다
- **정렬 오차 최대 2ms** — 목표(100ms)를 크게 밑돈다
- **비용 트랙당 0.11초** — 5명이면 0.55초. 30분 타임아웃 대비 무시 가능

> 절대 위치가 +17ms 안팎 밀리는 것은 분석 창이 비프로 채워져야 에너지가 오르기 때문이며,
> **모든 트랙에 똑같이 걸리므로 상대 정렬에서 상쇄된다.** 실제로 중요한 건 편차 열이다.

### 결과물에서 비프 처리

**마지막 비프가 끝나는 지점까지 잘라낸다**(`BEEP_TRIM=1`, 기본값).
비프 소리와 회의 시작 전 구간이 한 번에 사라지고, 결과는 회의가 시작되는 지점부터 시작한다.

```
자르기 전                              7.366초
0초        5.016초                       ↓
├──────────┼──────┬──────┬──────┬────────┤
│ 회의 전   │ 비프 │ 비프 │ 비프 │  회의   │
└──────────┴──────┴──────┴──────┴────────┘
                                   ↓ 자른 결과
                                  ├─────────┤
                                  │  회의    │
                                  └─────────┘
```

잘라낸 양은 응답의 **`alignment.trimmedMs`**로 알려준다.
master-api가 STT 타임스탬프를 원래 타임라인으로 되돌릴 때 이 값을 더하면 된다.

| 갈래 | 동작 |
|---|---|
| 정상 | 마지막 비프 끝까지 잘라내고 `trimmedMs`에 그 양을 담는다. 비프는 통째로 사라지므로 무음 처리가 필요 없다 |
| 자른 뒤 5초 미만이 남을 때 | **자르기를 취소**하고 비프 구간만 무음 처리한다. `trimmedMs: 0`. 비프가 늦게 잡힌 짧은 녹음에서 회의 내용까지 날아가는 것을 막는다 |
| `BEEP_TRIM=0` | 자르지 않고 무음 처리만 한다 |

**요청 본문으로는 바꿀 수 없다.** 호출마다 달라지면 master-api 쪽 타임스탬프 환산이
일관되지 않으므로, 서버 설정으로 고정한다.

## 3. 우선순위 2 — `startedAt`

비프를 못 찾았고 `align: "timestamp"`이면 이쪽으로 내려간다. **이미 구현되어 있다.**

```json
{
  "files": [
    { "participantId": "p1", "getUrl": "...", "startedAt": "2026-09-22T14:30:52.104Z" },
    { "participantId": "p2", "getUrl": "...", "startedAt": "2026-09-22T14:30:52.371Z" }
  ],
  "options": { "align": "timestamp" }
}
```

- 가장 이른 `startedAt` 기준으로 차이만큼 각 트랙 앞에 무음(`adelay`)을 넣는다
- 계산된 offset이 `MERGE_MAX_OFFSET_MS`(기본 60초)를 넘으면 그 트랙만 0으로 되돌리고 `fallback: true`로 표시한다 — 시계가 틀어진 기기 하나가 전체를 밀어버리는 것을 막는다
- **`options.align`을 명시하지 않으면 기본값이 `"none"`이라 `startedAt`을 무시한다**

### 현재 막혀 있는 것

master-api가 이 값을 갖고 있지 않다.

- Prisma `File` 모델에 파일별 시작시각 칼럼이 **없다** (`duration`만 있음)
- 파일명 파싱 정규식이 `A.Biz_[wm]_rec_(\d{8})_(\d{6})` — **초 단위**다
- 앱이 `metadata.json`에 밀리초로 저장하지만 **업로드하지 않는다** (`upload_service.dart:250`, `1664`가 `.pcm`만 거름)

> 앱의 그룹녹음 모드에서는 폴더명이 `A.Biz_m_rec_1758531234567`(epoch 밀리초)로 떨어지고
> 그게 `fileName` 필드로 서버에 전송된다. 다만 위 정규식(8자리_6자리)에 걸리지 않아
> master-api가 파싱에 실패하고 `new Date()`로 폴백한다.

## 4. 우선순위 3 — `none`

코드 변경 없음.

### 응답 확장

```json
"alignment": {
  "mode": "beep",
  "reference": "p1",
  "beepAtMs": 5016,
  "trimmedMs": 7366,
  "tracks": [
    { "participantId": "p1", "offsetMs": 0,    "beepAtMs": 5016, "confidence": 194263.7, "fallback": null },
    { "participantId": "p2", "offsetMs": 738,  "beepAtMs": 4278, "confidence": 7554.9,   "fallback": null },
    { "participantId": "p3", "offsetMs": 1928, "beepAtMs": null, "confidence": 0.0,      "fallback": "timestamp" }
  ]
}
```

- `mode` 는 **실제로 적용된** 정렬이다 (`beep` / `timestamp` / `none`). 요청값이 아니다
- 최상위 `beepAtMs` 는 자르기 전 기준으로 비프가 놓인 위치
- **`trimmedMs` 는 결과 파일 앞에서 잘라낸 길이.** master-api 가 STT 타임스탬프를
  원래 타임라인으로 되돌릴 때 이 값을 더한다
- 트랙의 `fallback` 에 어느 단계로 내려갔는지 남는다 (`timestamp` / `none` / `outlier`, 정상이면 `null`)

현장에서 "왜 안 맞았지"를 응답만 보고 판단할 수 있다.

### 앱 (요청)

`05_앱개발요청_동기화비프음.md` 참조. 요약하면:

1. 방장 화면에 "동기화 신호" 재생 기능 + `assets/sync_beep.wav` 탑재
2. `RecordConfig`에 `echoCancel: false`, `noiseSuppress: false`, `autoGain: false` 명시 — **이거 놓치면 기능이 통째로 안 먹는다**
3. (2순위 폴백용) `startTimestamp`를 첫 오디오 샘플 시각으로 교체 + `metadata.json` 업로드

### master-api (요청)

`startedAt`을 밀리초 포함 ISO8601로 채우고 `options.align`을 명시할 것.
비프가 1순위이므로 이건 **폴백 경로**다. 급하지 않다.

### 실기기 검증 방법

위 검증은 합성 음원으로 한 것이다. 실제 회의실에서 한 번 재보는 것이 좋다.

```
1. 폰 N대를 회의실 테이블에 평소처럼 놓는다
2. 전부 녹음 시작
3. 한 대에서 sync_beep.wav 재생 (앱 기능 없이 그냥 파일 재생으로 충분)
4. 몇 마디 대화
5. 녹음 종료 → POST /v1/merge/upload 로 파일들을 올린다
6. 응답의 alignment.tracks[].beepAtMs 가 실제 차이와 맞는지 본다
```

앱 수정 없이 지금도 할 수 있다. **비프 규격이 실제 환경에서 통하는지를 가장 싸게 확인하는 방법이다.**
