# 녹음 업로드 중단 — 원인 분석

서버로 수집된 앱 에러 리포트를 코드와 대조해 실패 지점을 특정한 결과. 서로 다른 두 개의 실패 모드가 확인되었습니다.

- 대상 브랜치: `develop`
- 관련 코드: `lib/services/file_upload_services/upload_service.dart`, `lib/services/app_service.dart`
- 엔드포인트: `POST /api/contents/upload/encryption/files`
- 상태: **실패 모드 2종 확인** — ① 앱 내부 예외(`Bad state: No element`), ② 서버·인프라 측 연결 종료(`Broken pipe`). 4장 참조

> 이 문서는 `docs/업로드-66퍼센트-정체-원인분석.md`를 대체합니다. 그 문서는 *"S3 업로드는 성공했고 DB 등록만 없다"* 는 잘못된 전제 위에 작성되었습니다. 실제로는 **S3 업로드도 실행되지 않았습니다.** 6장에 폐기 항목을 정리했습니다.

---

## 판정

**실패 모드가 두 개이고, 원인이 서로 다릅니다.**

| 로그의 `Error:` 값 | 끊은 주체 | 원인 | 상세 |
|---|---|---|---|
| `Bad state: No element` | **앱** | 진행률 콜백이 던진 `StateError`가 전송을 중단 | 2~3장 |
| `Broken pipe` | **서버·인프라** | 상대가 본문 수신 중 연결을 닫음 (사이즈 리미트·타임아웃 유력) | 4장 |

둘 다 `AppService.to.appLog`로 앱이 서버에 올린 자체 로그이며, 같은 catch 블록(`:1587`)을 통과하므로 **`Error:` 뒤 문자열로만 구분됩니다.** 어느 쪽이든 서버는 multipart 본문을 끝까지 받지 못하므로 첫 공정인 S3 업로드부터 시작되지 않고, 서버 관점 성공률은 0%가 됩니다.

> **인프라 담당자에게 타임아웃·사이즈 리미트를 문의한 것은 올바른 조치입니다.** `Broken pipe`는 앱이 만들어낼 수 없는 신호이며, 4장의 확인 목록이 그 문의에 붙일 구체적인 항목입니다.

### 자주 나오는 반문 — "앱은 66%를 표시했는데 서버 성공률이 0%면 모순 아닌가?"

모순이 아닙니다. 두 숫자가 서로 다른 것을 세고 있습니다.

**첫째, 앱의 진행률은 파일 개수 비율이 아니라 바이트 비율입니다.**

```dart
// upload_progress_widget.dart:542
final progressPercentage = (progress * 100).toInt();
//   progress ← uploadItem.uploadProgress.value  (:525)
//            ← onSendProgress의 sent / total    (upload_service.dart:1510)
```

`sent / total`은 **dio가 소켓에 write한 바이트 / 전체 `Content-Length`** 입니다. 파일을 몇 개 보냈는지와는 무관합니다.

**둘째, `sent`는 서버가 받았다는 증거가 아닙니다.** OS 커널 송신 버퍼와 네트워크 중간 버퍼에 들어간 바이트까지 `sent`로 집계됩니다. 앱이 66%를 표시했다는 것은 **앱이 소켓에 66%까지 써 넣었다**는 뜻일 뿐입니다.

**셋째, 업로드는 1회 multipart 요청입니다**(5-1 참조). 서버는 본문을 끝까지 받아야 파싱을 완료하고 S3에 올립니다. 66%에서 끊기면 서버 관점 성공률은 **정확히 0%가 되는 것이 정상**입니다.

즉 `앱 66% / 서버 0%`는 모순이 아니라 **부분 전송 후 중단의 지문 그 자체**입니다. 반대로 서버가 정상 응답을 줬는데 앱만 66%에 멈춰 있었다면 그때는 UI 갱신 문제로 봐야 합니다.

## 1. 로그 판독

수집된 3줄은 `uploadFolder`의 catch 블록 출력 형식과만 일치합니다. 같은 파일의 `uploadFile` catch(`:1383`)는 `type=`·`statusCode=`를 찍는 다른 형식이라 해당하지 않습니다.

```dart
// upload_service.dart:1581~1589 — 이 로그를 만든 코드
} on dio.DioException catch (e) {
  if (e.type == dio.DioExceptionType.cancel) {
    AppService.to.appLog('파일 업로드 실패: 네트워크 끊김');
    return false;
  }

  final expectHeader = e.requestOptions.headers['Expect'];
  AppService.to.appLog(
      '파일 업로드 중 오류 발생-재시도($retryCount): $e, Expect: $expectHeader');
```

이 형식에 수집된 값을 대입하면 네 필드가 각각 다음을 뜻합니다.

| DioException 필드 | 수집된 값 | 의미 |
|---|---|---|
| `type` | `unknown` | dio가 분류하지 못한 예외. 서버·네트워크가 원인이면 `badResponse`·`connectionError`·`sendTimeout`·`receiveTimeout` 중 하나가 됩니다. `unknown`은 **요청 코드 내부에서 던져진 Dart 예외를 감싼 것** |
| `response` | `null` | 서버 응답을 읽지 못했음. status code를 조회할 대상 자체가 없음 |
| `message` | `null` | dio가 생성한 설명 없음 — 감싸기만 했다는 뜻 |
| `error` | `Bad state: No element` | Dart 런타임의 `StateError`. 빈 컬렉션에 `.first`를 호출했을 때만 발생. **네트워크 스택은 이 예외를 만들지 않음** |

**판단의 근거는 `response`가 아니라 `error`입니다.** `Bad state: No element`는 Dart 코드가 던지는 `StateError`이고, 네트워크 스택은 이 예외를 만들지 않습니다. 그래서 이 로그가 붙은 요청은 앱이 끊은 것으로 확정됩니다.

반대로 **`response == null`이라는 사실 하나만으로는 아무것도 확정되지 않습니다.** 서버가 본문 수신 중 413을 보내면서 소켓을 닫으면, 앱은 아직 본문을 쓰는 중이라 그 응답을 읽지 못하고 `response == null` 상태로 `Broken pipe`만 봅니다. **이런 건은 413일 수 있습니다** — 4장 참조.

> `Expect: null`은 원인이 아닙니다. 과거 `Expect: 100-continue`를 의심해 넣어둔 진단 필드이며(`:1412` 인터셉터는 현재 주석 처리), 값이 `null`이라는 것은 해당 헤더가 애초에 붙지 않았다는 뜻입니다.

## 2. 예외가 발생하는 정확한 지점

`uploadFolder`의 try 블록 안에서 `Bad state: No element`를 던질 수 있는 곳은 한 군데뿐입니다. 나머지 후보인 `:1487`의 `split('/').last`는 항상 원소가 있어 안전하고, 속도·잔여시간 계산 함수(`:898`, `:928`)에는 `reduce`가 없습니다.

```dart
// upload_service.dart:1508~1520
onSendProgress: (int sent, int total) {
  double progress = total > 0 ? sent / total : 0;
  uploadProgress.value = progress;

  var uploadItem =
      uploadList.where((item) => item.id == id).first;   // ← StateError
  uploadItem.uploadProgress.value = progress;

  String speed = _calculateUploadSpeed(sent, total);
  uploadItem.uploadSpeed.value = speed;
```

전송 도중 `uploadList`에서 해당 `id` 항목이 사라지면 이 줄이 예외를 던지고, 그 예외가 dio를 통해 올라오면서 요청 스트림이 끊깁니다. 같은 패턴이 `uploadFile`의 `:1346`에도 있습니다.

## 3. 왜 항목이 사라지는가

`uploadList`에서 항목이 사라지는 경로는 두 갈래이고, **성공률이 0%인 이번 건에 해당하는 것은 A입니다.**

### 3-A. 재전송이 진행 중인 항목을 지우고 새 UUID를 발급한다 (주 원인)

`addUploadItem`(`:968~995`)은 **같은 `file_path`의 미완료 항목이 있으면 그것을 지우고 새 항목을 추가**합니다. 이때 **id가 새 UUID로 바뀝니다.**

```dart
// upload_service.dart:968~999
Future<String> addUploadItem(UploadItem item) async {
  var uuid = const Uuid();

  // 동일 filePath의 미완료 아이템이 있으면 제거 (중복 방지)
  if (item.filePath != null && item.filePath!.isNotEmpty) {
    final hasDuplicate = existingList.any((existing) =>
        existing['file_path'] == item.filePath &&
        existing['upload_yn'] == 'N');          // ← 'N' = 아직 업로드 안 끝난 항목

    if (hasDuplicate) {
      existingList.removeWhere(...);
      await tStorage.setList(AppStorage.upload_list, existingList);

      uploadList.removeWhere((existing) =>
          existing.filePath == item.filePath &&
          existing.uploadYn == 'N');            // ← 전송 중인 항목을 제거

      // 실패한 아이템을 교체하므로 isUploading 리셋하여 재업로드 가능하게 함
      isUploading.value = false;
    }
  }

  String uuidString = uuid.v4();
  item.id = uuidString;                         // ← 새 UUID 발급
  ...
  uploadList.add(item);                         // ← 새 id로 추가
```

**이 경로는 업로드 성공을 전혀 필요로 하지 않습니다.** 조건이 `upload_yn == 'N'`, 즉 *아직 성공하지 않은 항목*이기 때문입니다. 주석의 *"실패한 아이템을 교체하므로"* 가 이것이 실패 상황에서 도는 코드임을 그대로 말해줍니다.

결정적인 부분은 **새 UUID를 발급한다**는 점입니다. 아직 전송 중이던 요청은 옛 `id`로 `uploadList`를 조회하는데, 새로 추가된 항목은 id가 다르므로 **영원히 매칭되지 않습니다.**

```
                              ① 재전송: 옛 항목 제거 + 새 UUID 발급
                                       │        ② StateError
요청 A (진행 중, id=old)  ━━━━━━━━━━━━━━┿━━━━━━━━━━✕
                                       │
요청 B (재전송, id=new)                 ┕━━━━━━━━━━━━━━━→
                                       │
uploadList  [ id=old 존재 ]─────────────┘  [ id=new ]  ← old는 다시 안 돌아옴
                                                             시간 →
```

**트리거 경로**: 서랍 메뉴 > 녹음 실패 > 재전송
→ `recording_failure_page.dart:166` `stopRecording(folderPath:)`
→ `file_picker_service.dart:207` / `:294` `addUploadItem`
→ 위 중복 교체 로직

앞선 업로드가 아직 살아 있는 상태에서 사용자가 재전송을 누르면 그대로 성립합니다. 앞선 요청이 취소되지 않는 이유는 3-C를 보십시오.

### 3-B. 성공 처리가 항목을 지운다 (부차 경로)

한 요청이 성공하면 `:1123`의 `uploadList.removeWhere(...)`가 항목을 지우고, 그 시점에 다른 요청이 아직 전송 중이면 동일하게 `StateError`가 납니다. 다만 **이 경로는 최소 1건의 성공을 전제**하므로, 서버 성공률이 0%인 이번 건에는 해당하지 않습니다. `:755`(포그라운드 복귀, 스토리지 `upload_yn == 'Y'` 기준)와 `:883`(iOS 네이티브 완료)도 같은 이유로 이번 건과 무관합니다.

### 3-C. 진행 중인 요청이 취소되지 않는 이유

| 위치 | 문제 |
|---|---|
| `:576~577` | `_forceResumeUploadsIfNeeded()`가 주석 그대로 *"진행 중이어도 강제 재시작"* 하면서 `isUploading = false`만 세우고 **`_cancelCurrentUpload()`을 호출하지 않습니다.** 기존 요청이 살아 있는 채 두 번째 요청이 시작됩니다 |
| `:528` | `_createCancelToken()`이 `_uploadCancelToken`을 덮어씁니다. 이 시점부터 **요청 A는 취소할 수단이 없어집니다** |
| `:985~990` | `addUploadItem`의 중복 교체가 `uploadList`에서 항목을 제거하면서 **전송 중인 요청이 있는지 확인하지 않습니다.** `isUploading = false`까지 세우므로 이후 중복 실행 가드도 무력화됩니다 (3-A) |
| `:1123` · `:755` · `:883` | 성공 처리·포그라운드 복귀·백그라운드 완료 동기화가 각각 `uploadList`에서 항목을 제거합니다. 마찬가지로 전송 중인 요청을 확인하지 않습니다 (3-B) |
| `:891~895` | `valueInit()`이 전송 중에 `_uploadStartTime = null`, `_fileSizes = []`로 되돌립니다. 예외를 던지지는 않지만 속도·잔여시간 표시가 깨지며, 재시작이 겹쳤다는 부수 증거가 됩니다 |

### 재시작을 부르는 트리거

- **사용자 재전송** (서랍 메뉴 > 녹음 실패 > 재전송) — `recording_failure_page.dart:166` → `addUploadItem` → **3-A 경로.** 성공이 필요 없는 유일한 경로이므로 이번 건의 유력 트리거
- **네트워크 전환** (Wi-Fi ↔ LTE) — `_onNetworkReconnected`(`:534`) → `_resumePausedUpload` / `_forceResumeUploadsIfNeeded`
- **포그라운드 복귀** — `didChangeAppLifecycleState`(`:648`) → `_handleForegroundTransition`(`:736`)
- **프로세스 재시작 추정** — `:795~797`의 Android 분기 → `_resumeFailedBackgroundUploads`

타이밍에 의존하는 레이스이므로 **간헐적으로 발생하는 것이 정상입니다.** 항상 재현되지 않는다는 관찰은 이 가설과 모순되지 않고 오히려 부합합니다.

## 4. 두 번째 실패 모드 — `Broken pipe` (인프라 확인 필요)

같은 catch 블록에서 `Error: SocketException: Broken pipe` 형태의 로그도 수집되었습니다. **이것은 앱이 만들어낼 수 없는 신호입니다.**

`Broken pipe`는 **이쪽이 아직 소켓에 쓰는 중인데 상대가 연결을 닫았을 때** 커널이 돌려주는 에러입니다. 즉 서버·게이트웨이·LB 중 하나가 본문 수신 도중 연결을 끊었다는 뜻이고, 3장의 앱 측 레이스와는 **원인이 완전히 다릅니다.**

### 4-1. 왜 status code가 안 보이는가

인프라가 사이즈 리미트를 감지하면 대개 `413`을 보내면서 **곧바로 소켓을 닫습니다.** 앱은 그 시점에 아직 본문을 쓰는 중이라 응답을 읽지 못하고 `Broken pipe`만 봅니다. 그래서 이런 건은 `response == null`이면서도 **실제로는 413일 수 있습니다.** 앱 로그만으로는 구분되지 않으므로 인프라 측 로그가 필요합니다.

### 4-2. 본문 크기 — 흔한 기본값을 크게 초과합니다

녹음은 16kHz · 16bit PCM이고 3분마다 청크 1개입니다(`audio_recorder_io.dart:15`, `:20`).

```
16,000 × 2 bytes × 180초 = 5,760,000 bytes ≈ 5.76MB / 청크
```

업로드는 폴더 전체를 1회 요청으로 보내므로(5-1) 본문 크기는 녹음 길이에 비례합니다.

| 녹음 길이 | 청크 수 | 요청 본문 크기 |
|---|---|---|
| 9분 | 3 | 약 17MB |
| 30분 | 10 | 약 58MB |
| 50분 | 17 | 약 98MB |
| 60분 | 20 | 약 115MB |

흔히 걸리는 기본값들입니다.

| 계층 | 설정 | 흔한 기본값 |
|---|---|---|
| nginx | `client_max_body_size` | **1MB** |
| nginx | `client_body_timeout` | 60초 |
| Spring Boot | `spring.servlet.multipart.max-file-size` | **1MB** |
| Spring Boot | `spring.servlet.multipart.max-request-size` | **10MB** |
| AWS ALB / ELB | idle timeout | **60초** |
| AWS API Gateway (REST) | 페이로드 하드 리밋 | **10MB** (변경 불가) |

한 군데라도 손대지 않았다면 수십 MB 요청은 통과할 수 없습니다.

### 4-3. 인프라 담당자에게 물어볼 것

1. **`client_max_body_size`(nginx) 및 WAS multipart 최대 크기** — 현재 값. 최소 150MB 이상 필요
2. **본문 수신 타임아웃** — nginx `client_body_timeout`, `proxy_read_timeout`, LB idle timeout. 100MB를 느린 회선으로 올리면 수 분이 걸립니다
3. **리밋 초과 시 어떤 로그·응답을 남기는지** — 413을 보내고 닫는지, 조용히 닫는지
4. **`proxy_request_buffering`** — 켜져 있으면 nginx가 본문 전체를 버퍼링한 뒤 WAS로 넘기므로 디스크·메모리 한계도 함께 봐야 합니다
5. **WAF의 body inspection 크기 제한** — 있으면 초과 시 차단·절단이 발생합니다
6. **앞단 CDN/프록시 유무**

### 4-4. 앱 쪽 타임아웃 불일치도 함께 봐야 합니다

| 앱 설정 | 값 | 문제 |
|---|---|---|
| `sendTimeout` | 10분 | LB idle timeout(기본 60초)보다 훨씬 김. 인프라가 먼저 끊습니다 |
| `receiveTimeout` | **60초** | 서버가 100MB 본문을 받아 S3에 올리고 응답하기까지 60초를 넘으면, **본문을 다 보냈는데도** 앱이 타임아웃 처리하고 전량 재전송합니다 |

`receiveTimeout` 60초는 이 엔드포인트에서 특히 위험합니다. 5분 이상으로 올리는 것을 권합니다.

### 4-5. 두 실패 모드는 연쇄될 수 있습니다

가장 그럴듯한 전체 시나리오입니다.

1. 인프라 리밋으로 본문 전송이 끊김 → **`Broken pipe`** (1차 원인)
2. 앱이 2초 후 자동 재시도, 전량 재전송 → 같은 지점에서 또 끊김 (최대 4회)
3. 그 사이 사용자는 멈춘 것으로 보고 **재전송**을 누름
4. `addUploadItem`이 아직 살아 있던 요청의 항목을 지우고 새 UUID 발급 (3-A)
5. 진행 중이던 요청이 → **`Bad state: No element`** (2차 증상)

이 모델이 맞다면 **근본 원인은 인프라 제한**이고, 앱의 `StateError`는 그 위에 겹친 별개 결함입니다. 앱 수정만으로는 업로드가 성공하지 않으며, 인프라 수정만으로는 재전송 시 진단을 흐리는 문제가 남습니다. **둘 다 고쳐야 합니다.**

## 5. 서버팀에 전달할 사실 두 가지

### 5-1. 청크를 개별 업로드하지 않습니다

녹음은 3분 단위 청크 파일로 **저장**되지만, 업로드는 그 파일 전체를 **단 한 번의 multipart 요청**으로 보냅니다 (`uploadFolder`가 `files` 필드에 `MultipartFile` 배열을 담아 1회 POST).

"청크별 개별 업로드"로 전제하면 서버팀이 *일부는 성공했을 것* 이라는 잘못된 방향으로 조사하게 됩니다. 요청이 1회이므로 중간에 끊기면 **전량 실패**이고, 재시도도 처음부터 전부 다시 보냅니다.

| 설정 | 값 | 영향 |
|---|---|---|
| `connectTimeout` | 30초 | 연결 수립 |
| `sendTimeout` | 10분 | 본문 전송 한도 |
| `receiveTimeout` | 60초 | 대용량 처리 지연 시 헛된 전량 재전송 위험 |
| `maxRetries` | 3회 · 2초 간격 | 전량 재전송을 최대 4번 시도 |

### 5-2. 이 로그는 Hynix 빌드에서만 올라옵니다

```dart
// app_service.dart:264~273
Future<void> appLog(String msg) async {
  final empno = await tStorage.getString(AppStorage.empno);
  final os = UserInfoService.to.appPlatform;
  final message = '[$formattedDate][$empno][$os] $msg';
  debugPrint('$tag appLog: $message');

  if (!AppService.to.serviceType.isHynix) return;   // ← SKT·팀블로는 전송 안 함
```

두 가지가 따라옵니다.

- **"Android만 발생한다"는 관찰은 Hynix 사용자 모수 안에서만 성립합니다.** SKT·팀블로 사용자는 같은 예외가 나도 서버에 흔적이 남지 않으므로, 현재 데이터로는 플랫폼을 단정할 수 없습니다.
- 로그 앞머리에 `[날짜][사번][OS]`가 이미 붙어 있으니 **사번·OS는 추가 요청 없이 바로 필터링**할 수 있습니다.

### 참고 — 업로드 경로 분기

`upload_service.dart:1253`이 `Platform.isIOS && AppService.to.useSSL == true`일 때만 Swift 네이티브로 빠지고, 그 외에는 전부 Dart/Dio(`uploadFolder`)입니다. `useSSL`은 `SERVICE_TYPE`이 아니라 `.env`의 `USE_SSL` 값만 봅니다(`app_service.dart:28`).

| 조건 | 사용 경로 | 이번 에러 해당 |
|---|---|---|
| Android | Dart/Dio | ✅ |
| iOS + `USE_SSL=true` | Swift URLSession | ❌ |
| iOS + `USE_SSL=false` (Hynix 내부망) | Dart/Dio | ✅ |

> `USE_SSL=false`는 "SSL을 안 쓴다"가 아니라 **사설 인증서 검증을 우회한다**는 뜻입니다(`:1252`, `:1307`, `:1424`, `api_service.dart:80` 주석 및 커밋 `49c2cd2`). 이 플래그가 부수적으로 iOS 업로드 경로 분기까지 겸하고 있어 의미가 겹칩니다 — 별도 정리 대상입니다.

## 8. 확정 범위와 검증 방법

### 무엇이 확정이고 무엇이 아닌가

| | 판단 |
|---|---|
| **확정** | `Error: Bad state: No element`가 붙은 요청은 **앱이 끊은 것**입니다. `StateError`는 Dart 코드가 던지는 예외이고, 네트워크 스택은 이 예외를 만들지 않습니다 |
| **확정** | `Error: ... Broken pipe`가 붙은 요청은 **상대가 끊은 것**입니다. 커널이 반환하는 에러이므로 앱이 만들어낼 수 없습니다 |
| **확정** | 항목 제거가 **성공 없이도 일어납니다.** 3-A의 `addUploadItem` 중복 교체가 `upload_yn == 'N'`, 즉 미완료 항목을 대상으로 하기 때문입니다. 성공률 0%와 모순되지 않습니다 |
| **미확정** | **두 모드의 비율.** 어느 쪽이 다수인지에 따라 우선순위가 갈립니다. 아래 1번으로 집계 가능 |
| **미확정** | **인과 방향.** 4-5처럼 broken pipe가 1차이고 StateError가 2차 증상인지, 아니면 서로 독립인지. 아래 2번으로 갈립니다 |
| **미확정** | 3-A(재전송)와 3-C(자동 재시작) 중 어느 쪽이 StateError의 트리거였는지. 아래 3번으로 갈립니다 |

### 검증 방법

수집된 로그만으로 확인 가능하며 서버팀 작업은 필요하지 않습니다.

1. **`파일 업로드 중 오류 발생-재시도` 로그를 `Error:` 문자열로 분류해 집계.** `Bad state: No element` 대 `Broken pipe`의 비율이 곧 두 원인의 설명력입니다. 어느 쪽도 아닌 세 번째 문자열이 나오면 그것도 별도 집계합니다.

2. **연속 로그의 타임스탬프 간격을 봅니다.** 로그 앞머리에 `[yyyy-MM-dd HH:mm:ss]`가 있으므로 바로 확인 가능하며, 이것이 두 모드를 가르는 가장 빠른 판별자입니다.
   - 간격이 **약 2초** — 재시도 딜레이만 지나간 것. 전송을 시도하지도 못하고 즉시 실패 → **StateError 패턴**
   - 간격이 **수십 초~수 분** — 실제로 본문을 전송하다 끊긴 것 → **Broken pipe / 인프라 패턴**

3. **StateError 건에 한해, 같은 사번·시각대의 앞선 로그를 조회.** 무엇이 선행하는지로 트리거가 갈립니다.
   - `녹음실패 파일 재전송`(`recording_failure_page.dart:369`) → **3-A 확정.** 사용자 재전송이 진행 중인 업로드를 밀어냈습니다
   - `업로드 일시 중지` / `Dio 요청 취소됨` / `미완료 업로드 N개 발견, 강제 재시작` → **3-C 확정.** 자동 재시작 경로입니다
   - 앞에 `Broken pipe` 건이 선행 → **4-5의 연쇄 시나리오 확정.** 인프라가 근본 원인

4. **녹음 길이(본문 크기)와 실패의 상관관계를 봅니다.** 이것이 인프라 리밋의 지문입니다.
   - 짧은 녹음은 성공하고 **긴 녹음만 실패** → 사이즈 리미트 또는 타임아웃 확정
   - 길이와 무관하게 실패 → 크기 문제가 아님

5. **서버 액세스 로그에서 해당 요청의 수신 바이트를 `Content-Length`와 비교.** nginx `$request_length`로 확인합니다. 요청이 **아예 1건도 없다면** 앱이 보내기 전에 실패한 것이므로 위 두 원인 모두 해당하지 않습니다.
