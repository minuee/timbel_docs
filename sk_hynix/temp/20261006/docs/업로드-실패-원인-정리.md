# 업로드 실패 원인 정리 (2026-09-03)

## 핵심 결론

**실패 모드는 2개이고, 순서가 있습니다.**

```
① Broken pipe (서버/인프라가 끊음)  ← 1차 원인
   ↓ 2초 후 자동 재시도 (1~3회 반복)
   ↓
② 사용자가 "멈췄네" 하고 재전송 클릭
   ↓
③ Bad state: No element (앱이 끊음)  ← 2차 증상
```

---

## 1. 실패 모드 구분

| 로그 문자열 | 끊은 주체 | 원인 |
|---|---|---|
| `Error: SocketException: Broken pipe` | **서버·인프라** | 본문 수신 중 연결 종료 (사이즈·타임아웃 제한) |
| `Error: Bad state: No element` | **앱** | 진행률 콜백에서 `uploadList`에서 사라진 항목 조회 |

둘 다 같은 catch 블록(`:1587`)을 통해 서버로 올라가 **`Error:` 뒤 문자열로만 구분됩니다.**

---

## 2. 왜 본문 크기가 중요한가

**업로드는 1회 multipart 요청이고, 폴더 전체를 한 번에 보냅니다.**

본문 크기:
```
16kHz × 2byte × 180초/청크 = 5.76MB / 청크

50분 회의
= 50분 ÷ 3분 × 5.76MB 
= 약 16~17개 청크
= 약 98MB (압축 없음)
```

요청 타임아웃:
- `sendTimeout`: 10분 (코드: `:1409`)
- `receiveTimeout`: **60초** (문제!)

서버가 100MB를 받아 S3에 올리고 응답하기까지 60초를 넘으면, **본문을 다 보냈는데도** 앱이 타임아웃으로 전량 재전송합니다.

---

## 3. 인프라 리미트 추정

흔한 기본값들이 이 크기를 막을 수 있습니다.

| 계층 | 설정 | 기본값 | 최소 필요값 |
|---|---|---|---|
| nginx | `client_max_body_size` | **1MB** | 150MB+ |
| Spring Boot | `max-file-size` | **1MB** | 150MB+ |
| Spring Boot | `max-request-size` | **10MB** | 150MB+ |
| AWS ALB | idle timeout | **60초** | 최소 5분+ |
| AWS API Gateway (REST) | 페이로드 하드 리밋 | **10MB** | 변경 불가 (사용 불가) |

한 군데라도 손대지 않았으면 98MB 요청은 통과할 수 없습니다.

---

## 4. 가장 빠른 판별 방법

### 타임스탬프 간격 (로그 앞머리)

```
[yyyy-MM-dd HH:mm:ss]파일 업로드 중 오류...
```

**로그 간 시간 차이를 보면 됩니다:**

- **약 2초** → 재시도 딜레이만 지나감. 전송도 못 하고 즉시 실패 (메모리 부족? 연결 거부?)
- **수십 초~수 분** → 실제로 본문을 보내다 끊김 → **사이즈·타임아웃 유력**

### 녹음 길이 vs 실패

- **짧은 녹음은 성공, 긴 것만 실패** → 사이즈 리미트
- **길이 무관하게 실패** → 다른 원인

## 5. 앱의 문제 (Bad state: No element)

### 발생 지점

`upload_service.dart:1514` — `onSendProgress` 콜백:

```dart
var uploadItem = uploadList.where((item) => item.id == id).first;  // ← 항목이 없으면 StateError
```

### 왜 항목이 사라지는가

**`addUploadItem` (`:985~990`)이 아직 전송 중인 항목을 지우고 새 UUID를 발급합니다.**

```dart
// 동일 filePath의 미완료 항목이 있으면 제거
if (hasDuplicate) {
  uploadList.removeWhere(...);        // ← 전송 중인 항목 제거
  isUploading.value = false;          // ← 재시도 가드도 해제
}

String uuidString = uuid.v4();
item.id = uuidString;                 // ← 새 UUID 발급
```

전송 중이던 요청은 **옛 `id`로 계속 조회**하는데, 새로 추가된 항목은 **새 `id`**라서 영원히 못 찾습니다.

### 트리거

**서랍 메뉴 > 녹음 실패 > 재전송** 클릭
→ `recording_failure_page.dart:166` → `file_picker_service.dart:207` → `addUploadItem`

앞선 업로드가 아직 살아 있는데 재전송을 누르면 그대로 성립합니다.

## 7. 확인은 아직

이 시나리오(**broken pipe → StateError**)는 **가장 유력한 모델**이지 검증된 사실은 아닙니다.

확정하려면:

1. broken pipe와 StateError가 같은 업로드 건에서 나왔는지
2. 타임스탐프 순서가 broken pipe → StateError인지
3. `녹음실패 파일 재전송` 로그가 그 사이에 있는지

이 세 가지를 봐야 합니다. 인프라팀 답변이 나오면 지금 수치(98MB, 60초)와 맞는지 대조하면 됩니다.
