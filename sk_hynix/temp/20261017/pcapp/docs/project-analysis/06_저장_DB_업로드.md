# 06. 녹음 저장 · 로컬 DB · 업로드 · 복구

> 기준: 현재 소스 (2026-10-15 작업분까지). 소스 위치는 `파일 · 함수` 로 표기.

---

## 1. 녹음 파일 저장 위치 (`src/main/recordingDir.js`)

```
1순위  C:\Users\<사용자>\Documents\SKHynixRecApp\recordings\{sessionId}\{sessionId}_1.pcm, _2.pcm …
2순위  C:\SKHynixRecApp\recordings\...      (문서 폴더를 못 얻거나, 그 안에 실제로 파일을 써 보니 실패할 때)
macOS  /tmp/recordings/{sessionId}/...
```
- `SKHynixRecApp` 은 `APP_DISPLAY_NAME` 설정값이다. 폴더 이름에 쓸 수 없는 문자는 지운다.
- 쓰기 가능 여부는 테스트 파일을 실제로 만들었다 지워 보고 판단한다. Windows 에서는 `accessSync` 결과를 믿을 수 없어서다.
- 결정한 경로는 앱이 켜져 있는 동안 캐시한다.
- 녹음 1건 = 폴더 1개(`{sessionId}`), 그 안에 3분짜리 암호화 조각 파일 여러 개가 들어간다.

### 삭제 안전장치 (`isSafeRecordingTarget`)
녹음을 지울 때는 받은 경로가 **녹음 루트 폴더 "아래"인지** 먼저 확인한다.
- 지워도 되는 녹음 루트
  - `문서\SKHynixRecApp\recordings`
  - 옛 위치 `문서\timbloRecApp\recordings`
  - 헬퍼 exe 폴더의 `recordings`
  - macOS 의 `/tmp/recordings`
- 다음 경우에는 지우지 않고 로그(`delete_recording_blocked`)만 남긴다.
  - `recordings` 폴더 자체
  - 상대경로
  - `..` 로 루트 밖으로 벗어나는 경로
- 이 확인이 없을 때는 경로가 잘못 조립되면 다른 녹음까지 모두 지워질 수 있었다(2026-10-15 추가).

## 2. 로컬 DB (`src/main/db/`)

- 파일: `%APPDATA%\timbloRecApp\app.db` (WAL 모드, 외래키 ON). `better-sqlite3` 동기 API.
- 테이블은 `db.js · getDb` 에서 `CREATE TABLE IF NOT EXISTS` 로 만든다.
- 나중에 생긴 칸은 `migrate()` 에서 없을 때만 `ALTER TABLE ADD COLUMN` 한다. 기존 데이터는 유지된다.
- **사용자(사번) 구분이 없다.** PC 한 대의 DB 를 모든 사용자가 같이 쓴다. `users` 테이블과 `created_by` 칸은 있지만 쓰이지 않는다.

| 테이블 | 용도 | 주요 칸 | 실제 사용 |
|---|---|---|---|
| `recordings` | 녹음 1건 | `id`, `file_name`(목록에 보이는 이름), `file_path`(녹음 폴더, UNIQUE), `upload_name`(서버로 보내는 이름), `created_at` | O |
| `jobs` | 업로드 작업 | `job_id`, `recording_id`, `is_uploading` | O |
| `summaries` | 업로드 옵션 | `recording_id`, `lang`, `attendee_num`, `title`, `template_id` | O (재시도할 때 같은 값으로 다시 보내려고 저장) |
| `memos`, `tags` | 메모·태그 | | X (화면 기능이 없어짐. 함수만 남음) |
| `users` | 사용자 | | X |

- 모든 테이블이 `recordings` 를 외래키(ON DELETE CASCADE)로 참조한다. **녹음 행을 지우면 작업·요약 행도 같이 지워진다.**
- `jobs.is_uploading` 의미
  - `TRUE`: 업로드 중
  - `FALSE`: 대기 또는 실패 (업로드 리스트에 "재시도" 버튼이 보임)
- `is_deleted` 칸은 모든 테이블에 있지만 실제 삭제는 대부분 `DELETE` 로 한다.
- 시간 칸은 `datetime('now','localtime')` 문자열이다. 타입 선언(INTEGER)과 다르다.
- DB 를 직접 보려면 `docs/dbeaver/README.md` 를 참고한다.

### 녹음 행의 일생
```
녹음 시작  recording_started  → insertRecording(file_name=녹음이름, file_path=폴더, upload_name=녹음이름)
조각 저장  segment_ready 마다 → upsertRecording (같은 id 행의 경로를 실제 저장 폴더로 고침)
업로드 요청 enqueue-upload     → jobs 행 추가(is_uploading=FALSE) + summaries 행 추가 + (제목 있으면) file_name 변경
업로드 시작                    → is_uploading=TRUE
업로드 성공                    → 녹음 폴더 삭제 + recordings 행 삭제 (→ jobs/summaries 도 함께 삭제)
업로드 실패                    → is_uploading=FALSE (업로드 리스트에 남음)
녹음 취소(삭제)                → 폴더 삭제 + recordings 행 삭제
```

## 3. 녹음 이름 규칙

| 이름 | 값 | 정하는 곳 | 쓰는 곳 |
|---|---|---|---|
| 녹음 이름 (`upload_name`) | `A.Biz_pcapp_rec_YYYYMMDD_HHmmss` (**녹음 시작 시각, 한국 시간**) | `main.js · buildRecordingFileName` — `start` 명령 때 1회 | 서버로 보내는 `fileName`. 재업로드해도 같은 값 |
| 목록 이름 (`file_name`) | 처음엔 녹음 이름과 같음. 업로드 창에서 제목을 넣으면 그 제목으로 바뀜 | `enqueue-upload` | 업로드 리스트 표시 |
| 제목 (`title`) | 사용자 입력(선택) | 업로드 창 | 서버로 보내는 `title`(값이 있을 때만) |
| 세션 ID | uuid | `main.js` `start` 처리 | 녹음 폴더 이름, 조각 파일 이름 |

예전 형식 `aimm_w_rec_YYMMDD_HHmmss` 는 업로드 시각으로 매번 새로 만들었다. 날짜는 PC 시각, 시간은 KST 로 섞여 있었다. 지금은 쓰지 않는다.
`upload_name` 이 없는 옛 녹음은 업로드할 때 현재 시각으로 이름을 만든다.

## 4. 업로드 (`main.js · serverUpload`)

### 요청
`POST {세션서버}/api/contents/upload/encryption/files`, `multipart/form-data`

| 필드 | 값 |
|---|---|
| `files` | 녹음 폴더 안의 **모든 파일** (암호화된 3분 조각들, 16KB 단위 스트림) |
| `lang` | ko / en |
| `attendeeNum` | 0~3 (참석자 수 구간 코드) |
| `deviceId` | **`'1'` 고정** (`authService.getDeviceId`). 로그에 쓰는 `pc-…` 기기 ID 와 다름 |
| `fileName` | 녹음 이름 (`upload_name`) |
| `totalNum` | 파일 개수 |
| `title` | 제목 (있을 때만) |
| `templateId` | 템플릿 code (있을 때만. 없으면 서버가 DEF-BASIC) |

- 서버는 이 조각들을 모바일 앱과 같은 방식(같은 AES 키)으로 복호화·병합해서 회의록을 만든다.
- 업로드 직전에 토큰 만료가 가까우면 미리 갱신한다. 스트림이라 401 을 받으면 재전송할 수 없어서다.
- 진행률(속도·남은 시간)은 form 의 data 이벤트로 계산해 팝업에 보낸다.

### 결과 처리
| 결과 | 처리 |
|---|---|
| 성공 | 진행률 100% → 녹음 폴더와 DB 행 삭제 → 팝업 닫기. 앱 종료 중이었으면 앱 종료. 장치 끊김으로 멈췄던 녹음이면 홈으로 |
| 실패 | 오류를 분류한다(`classifyUploadError`): 서버(5xx·429) / 네트워크 / 기타. 팝업이 실패 화면과 "재시도" 버튼으로 바뀌고, 작업은 대기 상태(`is_uploading=FALSE`)로 돌아간다 |

### 재시도 경로 두 가지
| 경로 | IPC | 차이 |
|---|---|---|
| 업로드 진행 팝업의 "재시도" | `retry-server-upload` | `summaries` 에서 lang·참석자·**제목·템플릿**을 복원해서 보냄 |
| 업로드 리스트의 "재시도" | `retry-server-uploads` | 여러 건을 동시에 백그라운드로 업로드. 결과는 OS 알림으로 모아서(4초 디바운스) 알려 줌. **제목·템플릿을 복원하지 않음** → `08_확인필요.md` |

## 5. 복구 (`services/recoveryService.js · scanAndAutoQueue`)

앱을 시작할 때 메인 창을 만들기 전에 1회 실행한다.
- **대상**: 업로드 작업(jobs)이 하나도 없는 녹음 행. 녹음 도중 앱이 꺼졌거나, 업로드를 고르기 전에 꺼진 경우다.
  - 녹음 폴더가 없으면 → 녹음 행 삭제
  - 녹음 폴더가 있으면 → 업로드 작업 추가 + "복구되지 않은 녹음 파일 발견 (N건)" 팝업
- 업로드 옵션(summaries)이 없으므로 이 작업을 재시도하면 언어·참석자 수가 빈 값으로 간다.

**복구하지 못하는 경우**
- 업로드 도중 앱이 꺼진 작업은 `is_uploading=TRUE` 로 남는다.
- 업로드 리스트에 계속 "업로드 중"으로 보이고 재시도 버튼이 없다(삭제만 가능). → `08_확인필요.md`

## 6. 앱 종료와 녹음 데이터

- 녹음 중에 정상 경로(설정 → 앱 종료)로 끄면 반드시 업로드 또는 삭제를 고르게 한다.
- 트레이 Quit, 작업 관리자 종료, PC 종료처럼 다른 경로로 꺼지면 헬퍼가 `kill` 된다.
  - 그때까지 저장된 3분 조각들은 남는다. 다음 실행 때 복구 팝업으로 올라온다.
  - **아직 메모리에 있던 마지막 조각(최대 3분)은 사라진다.**
