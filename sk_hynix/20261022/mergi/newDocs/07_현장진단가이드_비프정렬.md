# 현장 진단 가이드 — 비프 정렬 (방장 비프 기준)

> 대상: 사내 망분리 서버에서 테스트하는 사람
> 전제: **방장 폰만 비프를 울린다** (`beepSource=leader`). 비프는 녹음 시작 후 약 3초.
> 작성: 2026-10-22

---

## 0. 이번 이미지에서 바뀐 것 (한 줄씩)

| 바뀐 것 | 효과 |
|---|---|
| **비프 2차 탐색** | 방장 트랙에서 비프를 찾으면, 못 찾은 다른 폰 트랙을 그 근처에서 **완화된 기준으로 다시** 찾는다. 귀에는 들리는데 못 잡던 경우를 겨냥한 수정 |
| **진단 명령 `sync-scan`** | 녹음 파일을 넣으면 폰별로 비프를 찾았는지, 왜 못 찾았는지 숫자로 보여준다 |
| **오토믹서** (기본 켜짐) | 순간마다 말하는 사람 앞의 폰만 살리고 나머지를 줄여 울림·반복음을 없앤다. 비교하려면 같은 파일로 `automix=false` 를 한 번 더 돌려 들어 본다 |
| **드리프트 보정** | 앱이 종료 때도 싱크음을 울리면(종료 버튼 → 바로 싱크음 → 5초 뒤 종료) 폰별 시계 오차를 재서 맞춘다. 응답 `alignment.drift.ppm` 에 폰별 오차가 나온다. 앱 변경 전 녹음은 보정 없이 예전과 같다 |
| `beepSource` 기본값 `leader` → `all` | 방장 비프 테스트에도 지장 없다. 앞에서 잘리는 길이가 0.3초 늘어날 뿐이다. 신경 쓰이면 요청에 `beepSource=leader` 를 명시 |

> 왜 2차 탐색인가: 1차 검출은 **두 음(3000Hz·4200Hz)이 둘 다, 세 번 모두** 배경보다 6배 커야
> 인정한다. 방장에서 멀리 있는 폰은 한쪽 음을 약하게 받거나, 폰의 노이즈억제가 2·3번째 비프를
> 깎는 경우가 있다. 사람 귀에는 "삐 삐 삐" 로 잘 들려도 1차 기준은 못 넘는다.
> 2차는 **한쪽 음만**, **첫 번째 비프 + 하나 더** 로 인정하되, 순음인지·250ms 동안 유지되는지를
> 따로 확인해서 말소리를 걸러낸다. 시뮬레이션에서 대화만 있는 구간 104개 중 오검출 0개.

## 1. 평소처럼 병합 테스트

이전과 똑같이 Swagger 또는 Postman 으로 `POST /v1/merge/upload` 를 돌린다.
(방장 비프만 울렸으면 `beepSource` 에 `leader` 를 넣는다.)

완료 응답에서 **`alignment` 만 보면 된다.**

```json
"alignment": {
  "mode": "beep",                     ← beep 이어야 정상. none 이면 아래 2절로
  "beepSource": "leader",
  "syncSound": "beep",
  "trimmedMs": 5384,
  "tracks": [
    { "participantId": "f1", "offsetMs": 0,    "confidence": 265607, "fallback": null },
    { "participantId": "f2", "offsetMs": 526,  "confidence": 177.2,  "fallback": null, "guided": true },
    { "participantId": "f3", "offsetMs": 1274, "confidence": 131.3,  "fallback": null, "guided": true }
  ]
}
```

| 볼 것 | 정상 | 이상 |
|---|---|---|
| `mode` | `beep` | `none` / `timestamp` |
| `tracks[].fallback` | 전부 `null` | `none` 이 있으면 **그 폰만 비프를 못 찾아 0초에 깔린 것** → 결과물 앞에 그 폰 비프가 남는다 |
| `tracks[].guided` | 있어도 정상 | `true` 면 2차 탐색으로 찾은 것. 이번 수정이 효과를 본 트랙 |
| `offsetMs` | 폰마다 0~2200 사이로 흩어짐 | |

**결과 파일을 들어 볼 것**: 맨 앞에 비프가 남아 있지 않고, 같은 말이 겹쳐 반복되지 않으면 성공.

서버 로그에서는 2차 탐색으로 찾은 트랙마다 `beep_guided` 이벤트가 하나씩 찍힌다.

## 2. `mode=none` 이거나 `fallback` 이 남으면 — `sync-scan`

### 2.1 파일을 컨테이너에 넣고 실행

```bash
# 같은 회차의 녹음 파일 전부 (방장 포함)
docker cp phone_A.flac mobile-sync-server:/tmp/
docker cp phone_B.flac mobile-sync-server:/tmp/
docker cp phone_C.flac mobile-sync-server:/tmp/

docker exec mobile-sync-server python -m recog sync-scan \
    --sound beep --source leader \
    /tmp/phone_A.flac /tmp/phone_B.flac /tmp/phone_C.flac
```

아무것도 업로드·저장하지 않는다. 파일 3개에 수 초 걸린다.

### 2.2 출력 예

```
== beep  (기준: 신뢰도 6 이상, 조각 3개 중)
  파일          검출  위치ms   신뢰도        조각   비고
  phone_A.flac  O     3008     265607        3/3    다른 폰 소리: 최대 0ms 먼저 / 52ms 늦게
                └ 음별 1·2·3번째 크기(배경 대비 배수): 3000Hz 295878 / 297331 / 297148  4200Hz 120901 / 121055 / 121421
  phone_B.flac  O     2482     177.191       3/3    2차 탐색으로 찾음 (1차 신뢰도 23.76)
                └ 음별 1·2·3번째 크기(배경 대비 배수): 3000Hz 1200.4 / 266 / 0.9  4200Hz 1 / 1.6 / 1
  -> 정렬: beep  기준=phone_A.flac  offsetMs: phone_A.flac=0, phone_B.flac=526
     trimmedMs=5358
```

### 2.3 읽는 법

**`└ 음별` 줄이 핵심이다.** 비프 세 번 각각에서 두 음이 배경보다 몇 배 컸는지 보여준다.

| 음별 줄의 모양 | 뜻 |
|---|---|
| 두 음 모두 세 번 다 큼 (수십 이상) | 정상. 1차에서 잡힌다 |
| **한 음만 1 근처** (예: `4200Hz 1 / 1.6 / 1`) | 그 폰이 그 음을 거의 못 받는다 (스피커·마이크 특성). 2차가 맡는다 |
| **뒤로 갈수록 작아짐** (예: `1200 / 266 / 0.9`) | 노이즈억제가 비프를 학습해 깎는다. 2차가 맡는다 |
| 전부 한 자리 수 | 너무 작다 (거리·볼륨). 2차로도 어렵다 |

| `비고` | 뜻 | 할 일 |
|---|---|---|
| `2차 탐색으로 찾음` | 이번 수정으로 잡혔다 | 없음 |
| `기준 근처 — 소리는 있으나 약함` | 2차로도 못 넘었다 | 3절 조정 |
| `소리가 거의 없음` | 그 파일 첫 10초에 비프가 없다 | 녹음 시작 시각 확인 (비프 전에 녹음이 켜졌나) |
| 방장 파일이 `X` | 2차 탐색은 **잡힌 트랙이 하나라도 있어야** 돈다 | 방장 폰 볼륨 확인 |

## 3. 조정할 수 있는 값 (`.env`, 컨테이너 재시작 필요)

| 값 | 기본 | 언제 바꾸나 |
|---|---|---|
| `BEEP_GUIDED` | `1` | 2차 탐색을 끄려면 `0` (예전과 동일) |
| `BEEP_GUIDED_MIN_RISE` | `20` | 들리는데 `기준 근처` 로 빠지면 **내린다** (10 미만 비권장). 대화를 비프로 잘못 잡으면 올린다 |
| `BEEP_GUIDED_REACH_SEC` | `3.0` | 폰끼리 녹음 시작이 3초 넘게 차이 나면 올린다 |
| `BEEP_MIN_RISE` | `6.0` | 1차 기준. 건드리지 않는 것을 권장 |
