Audio Sync Merge 프로젝트: 실제 워크플로우와 현재 구현 상태

이 문서는 처음 요청한 프로젝트 목표와 현재 구현된 MVP 사이의 차이를 정리하고, 실제 스마트폰 녹음 파일로 어떤 방식으로 알고리즘을 테스트해야 하는지 전체 흐름을 그림처럼 설명합니다.

원래 요청

원래 만들고 싶었던 것

  • iOS / Android 스마트폰으로 같은 회의를 각자 녹음
  • 파일 타임스탬프나 녹음 시작 정보 등을 참고해서 정렬
  • 싱크 / drift 보정 / loudness 보정 후 믹스
  • 최종 결과를 STT에 넣거나 사람이 다시 들어봄
현재 구현

지금 실제로 구현된 것

  • Python 기반 서버형 MVP
  • 세션 생성 → 파일 업로드 → 비동기 처리 → 결과물 export
  • 오디오 기반 offset/drift 추정과 mix/export
  • synthetic fixture와 자동 검증 도구 다수 포함

현재 구현은 “녹음 앱 + 현장 운영 프로토콜”보다 “업로드 후 처리 엔진”에 더 가깝습니다.

1. 왜 지금 약간 동떨어져 보이는가

  • 현재 서버는 녹음 앱을 만들지 않았습니다. 업로드된 파일을 처리하는 MVP입니다.
  • 현재 정렬은 파일 타임스탬프 중심이 아닙니다. 오디오 내용 기반 정렬이 중심입니다.
  • 현장 운영 규칙 — 예: 같은 앱을 써야 하는지, 시작 박수/비프를 넣는지, recording_started_at을 어떻게 저장하는지 — 가 아직 제품 워크플로우로 고정되지 않았습니다.

코드 근거: 현재 업로드 API는 participant_id와 filename만 받고 있고 (src/recog/api.py:52-67), 정렬은 estimate_alignment_and_drift(...)로 오디오 기반 추정을 합니다 (src/recog/pipeline.py:88-145, src/recog/audio.py:231-258).

2. 실제 프로젝트로 보정한 전체 워크플로우

1

회의 시작 전

  • 세션 생성
  • 참가자별 session code 공유
  • 녹음 앱/설정 통일
  • 가능하면 WAV, 48kHz, mono
→
2

녹음

  • 각자 스마트폰으로 같은 공간 녹음
  • 시작 시 박수 1회 또는 짧은 비프 권장
  • 앱이 recording_started_at 저장
→
3

업로드

  • audio file 업로드
  • session_id / participant_id 첨부
  • recording_started_at / device_id / OS 정보 첨부
→
4

서버 처리

  • canonicalize
  • timestamp 기반 coarse prior
  • 오디오 기반 fine alignment
  • drift correction + loudness normalization
  • aligned tracks + mixdown + manifests
→
5

검증

  • STT 결과 비교
  • listening review 작성
  • 싱크 / loudness / artifact 확인

3. 실제 녹음 파일에 꼭 필요한 정보

항목 필수 여부 설명 비고
session_id 필수 같은 회의의 파일들을 한 세트로 묶기 위한 키 서버 세션과 직접 연결
participant_id 필수 누가 녹음한 파일인지 식별 현재 API도 이 값은 이미 받음
recording_started_at 강력 권장 사용자가 녹음 버튼을 누른 시각 최종 정렬 기준이 아니라 coarse prior로 사용
파일 duration / sample rate / channels 필수 canonicalization과 drift 계산에 필요 서버가 ffprobe로 추출 가능
시작 박수/비프 marker 강력 권장 동기화 anchor를 명확하게 잡는 데 유리 타임스탬프보다 실제 음향 marker가 더 안정적일 수 있음
파일 수정 시각(mtime) 비권장 복사/전송 과정에서 바뀔 수 있음 정렬 기준으로 쓰기 위험
결론: 타임스탬프는 있으면 좋지만, 그것만으로 맞추면 안 됩니다.
가장 좋은 구조는 recording_started_at + 시작 박수/비프 + 오디오 기반 fine alignment의 조합입니다.

4. 지금 구현 기준에서 “무엇이 이미 있고 / 무엇이 비어 있는지”

이미 있음
  • 세션 생성 / 파일 업로드 / 처리 API
  • 파일 canonicalization (48kHz mono PCM)
  • 오디오 기반 offset / drift 추정
  • aligned tracks / mixdown / manifest export
  • synthetic fixture, benchmark, verification scaffold
비어 있음
  • iOS / Android 녹음 앱 자체
  • 업로드 시 recording_started_at를 받는 스키마
  • session join code 기반 모바일 업로드 흐름
  • marker(beep/clap) 활용 프로토콜
  • 실제 현장 녹음 데이터 수집/운영 절차

5. 실제 테스트는 어떤 시나리오로 해야 하나

권장 시나리오 A — 빠른 현장 검증

  1. 같은 회의실에 3~5명 앉음
  2. 같은 앱 / 같은 설정(WAV, 48kHz, mono 권장)으로 녹음
  3. 녹음 시작 직후 모두 들리게 박수 1회
  4. 10~15분 회의 진행
  5. 파일 업로드
  6. 서버는 recording_started_at로 후보 범위 축소 → 박수/오디오로 fine align → drift correction
  7. STT 결과와 listening review 둘 다 평가

권장 시나리오 B — 목표형 검증

  1. 5명 / 1시간 녹음
  2. 중간에 발화 겹침, 작은 목소리, 멀리 있는 화자 포함
  3. 결과물 3개를 비교
    • 중앙 마이크 1개 녹음
    • 그냥 단순 믹스한 결과
    • 현재 알고리즘 처리 결과
  4. STT 누락률과 청취 품질을 비교

6. 지금 바로 수정해야 할 제품 정의

지금 프로젝트는 “녹음 파일 처리 엔진”까지는 왔지만, “실제 운영 워크플로우”는 아직 제품화되지 않았습니다.

그래서 다음처럼 정의를 보정해야 합니다.

  • Step 1: 녹음 앱 자체를 새로 만들지, 기존 앱을 쓸지 결정
  • Step 2: 업로드 payload에 recording_started_at, device_id, os를 추가
  • Step 3: marker(박수/비프) 프로토콜을 명문화
  • Step 4: 실제 현장 테스트 시나리오를 운영 문서로 고정

7. 지금 남은 핵심 작업

우선순위 작업 이유
1 업로드 스키마에 recording_started_at 추가 원래 요청했던 “타임스탬프 참고” 흐름을 진짜로 반영해야 함
2 현장 녹음 프로토콜 문서화 앱/설정/시작 marker 규칙이 없으면 테스트가 흔들림
3 실제 5명 / 1시간 evidence 생성 현재 릴리스 blocker인 AC1 해결
4 사람이 듣는 listening review sign-off 현재 릴리스 blocker인 AC7 해결

8. 한 줄 결론

당신 느낌이 맞습니다. 현재 프로젝트는 “업로드 후 정렬/믹스 엔진” 쪽은 많이 진척됐지만, “현장에서 어떤 앱으로 어떤 메타데이터를 붙여 녹음하고 업로드할지”라는 실제 제품 워크플로우는 아직 덜 연결돼 있습니다.

따라서 다음 단계는 코드를 더 복잡하게 만드는 게 아니라, 녹음 앱/메타데이터/테스트 시나리오를 프로젝트 정의에 다시 붙이는 일입니다.
