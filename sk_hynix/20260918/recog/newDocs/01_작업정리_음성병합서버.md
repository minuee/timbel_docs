## 요약

master-api가 올린 참가자별 녹음 파일을 recog 서버가 받아 **하나로 겹쳐 합치는** API를 만들었다.
설계 확정부터 구현·테스트·배포 준비까지 하루에 마쳤다.

| 단계 | 결과 |
|---|---|
| master-api 소스 분석 | 설계 전제 3개가 틀렸음을 확인 → 수정 |
| 설계 확정 | 만들 코드가 5개 파일 → 3개로 줄어듦 |
| 구현 | 신규 3개 + 기존 3개 수정, 실제 동작 검증 완료 |
| API 문서 | Swagger UI 내장 (의존성 0개 유지) |
| 테스트 경로 | Postman으로 S3 없이 병합 확인 가능 |
| 망분리 배포 | 빌드·설치 스크립트 + 가이드 (서버 빌드 / 오프라인 번들 2경로) |
| 기록 영속화 | SQLite 90일 보관 + 재시작 자동 복구 + 재작업 API |

## 1부 · 분석에서 뒤집힌 것들

작업 시작 시점의 스펙 문서에는 사실과 다른 전제가 있었다. master-api 소스를 직접 읽어 바로잡았다.

### 1-1. "AWS S3" → **MinIO**

```
src/utils/drive.util.js
  import { Client } from '@timbel-timblo-onpremise/minio-js';
```

레포 전체에서 `aws-sdk`, `@aws-sdk`, `S3Client`, `amazonaws` 검색 결과 **0건**.
MinIO 서버도 순정(`FROM minio/minio:latest`)이라 S3 호환 API를 완전히 지원한다.

**영향**: recog 입장에서는 달라질 게 없다. presigned URL은 표준 S3 프로토콜이므로
나중에 진짜 AWS S3로 바꿔도 우리 코드는 그대로다.

### 1-2. "파일이 암호화되어 있다" → **평문이다**

이게 가장 중요한 발견이었다. 암호화되어 있었다면 AES 키를 받아 복호화하는 코드가 필요했다.

```js
// src/services/system/drive.service.js
const decryptedFilePath = await secure.decryptFilesAesCbc(...);  // ① 복호화
const flacFilePath = await convert.convertPcmToFlac(...);        // ② 변환
const result = await uploadContent(uploadFile, ...);             // ③ 업로드
```

복호화(①)가 업로드(③)보다 **앞**이다. AES는 *모바일 앱 → 서버 전송 구간* 전용이고,
저장 시점엔 평문이다. 서버사이드 암호화(SSE) 헤더도 없다.

> `drive.util.js`의 `kms` 변수가 암호화처럼 보이지만, 실제로는
> `generate.keyFromString(salt)` — **사용자별 격리용 경로 prefix**다.
> 오브젝트 키가 `{버킷}/{kms}/{fileKey}` 구조라서 그렇다.

**영향**: 복호화 코드가 통째로 불필요해졌다.

### 1-3. "풀링" → **폴링(polling)**

담당자가 말한 단어가 커넥션 풀링인지 폴링인지 불분명했다. master-api에서 외부 엔진과
비동기로 연동하는 코드를 찾아보니 HAIV STT 엔진 하나뿐이었고, 정확히 폴링이었다.

```js
// src/utils/engines/Haiv/utils/get.js
const interval = setInterval(async () => {
    const { state, fileList } = await progressStateRequest(decodingId, engineOptions);
    if (state === 'DONE' && ...) { clearInterval(interval); ... }
}, 5000);   // ← 5초마다 상태 조회
```

커넥션을 유지하는 게 아니라, **끊고 5초마다 다시 묻는** 방식이다.

**영향**: 콜백 수신 엔드포인트를 만들 필요가 없어졌다. 우리 쪽 `callback.py`,
재시도 로직(10초→30초→2분→5분→15분)이 전부 빠졌다.

## 2부 · 설계 결정과 근거

### 2-1. 정렬을 상호상관에서 timestamp로 바꿨다

원래 설계는 음성 파형을 비교해 시작점을 맞추는 방식(상호상관)이었다. 두 가지 이유로 폐기했다.

**① 너무 느리다.** `normalized_correlation()`이 순수 파이썬 이중 루프다.

| 항목 | 1시간 녹음 기준 |
|---|---|
| envelope 프레임 수 | 3,600초 ÷ 20ms = 180,000 |
| lag 탐색 횟수 | ±30초 ÷ 20ms = 3,001회 |
| lag당 연산 | 180,000 × 3패스 |
| **총 연산** | **약 16억 회** |

참가자 쌍마다 반복하면 작업 타임아웃(30분)을 정렬 단계에서만 넘길 수 있다.

**② 효과가 없다.** 참가자들이 각자 다른 장소에 있으면 녹음 사이에 공통된 소리가 없어
신뢰도 게이트에 걸려 어차피 `offset = 0`으로 폴백한다. 비싼 연산을 돌린 끝에
정렬을 안 한 것과 같은 결과가 나온다.

### 2-2. 파일명 파싱도 폐기했다

대안으로 파일명의 시작시각을 쓰려 했다. 파일명에 이미 들어 있기 때문이다.

```js
// src/utils/generate.util.js
/A\.Biz_[wm]_rec_(\d{8})_(\d{6})\.[a-zA-Z0-9]+$/
//                          ^^^^^^ HHmmss — 초 단위, 밀리초 없음
```

그런데 **녹음은 방장이 시작을 누르면 참가자 전원에게 전파되는 구조**라, 실제 시작 차이는
네트워크 지연 수준인 수백 ms다. 정밀도가 오차보다 거칠다.

초 경계를 사이에 두고 갈라지면 **안 고치느니만 못하다**:

| 실제 시작 | 파일명 값 | 계산 offset | 실제 차이 | 결과 |
|---|---|---|---|---|
| A `10:00:00.900`<br>B `10:00:01.100` | `100000`<br>`100001` | 1000ms | 200ms | ❌ **800ms 더 어긋남** |
| A `10:00:00.100`<br>B `10:00:00.900` | `100000`<br>`100000` | 0ms | 800ms | 보정 없음 |

**→ 요청 본문의 `startedAt`(밀리초 포함)을 받기로 했다.**
파일명 규칙은 master-api 내부 사정이므로 recog가 파싱하지 않는다. 경계가 깨끗해진다.

### 2-3. 최종 정렬 스펙

| 값 | 동작 | 비용 |
|---|---|---|
| `"none"` (기본) | 모든 트랙을 0초 지점에서 겹친다 | 없음 |
| `"timestamp"` | `startedAt` 차이만큼 각 트랙 앞에 무음을 넣는다 | 뺄셈 N회 |

기본값이 `"none"`인 이유: 방장 트리거라 거의 동시에 시작되고, `startedAt`이 없거나
부정확할 때 안전한 쪽으로 떨어진다.

**이상값 가드**: 계산된 offset이 60초를 넘으면 그 트랙만 0으로 되돌리고 `fallback: true`로
표시한다. 시계가 틀어진 기기 하나가 전체를 밀어버리는 것을 막는다.

### 2-4. 그 외 결정

| 결정 | 근거 |
|---|---|
| presigned URL로만 접근 | recog는 pip 의존성 0개. 자격증명 직통 전달은 SigV4 구현이나 minio 클라이언트 추가를 요구한다. 게다가 자격증명이 Consul KV 한 곳에서만 관리되는 현 구조를 열어야 한다 |
| 폴링, 소켓·SSE 미채택 | 연결 유지·재연결·프록시 타임아웃 대응이 붙는데 얻는 건 "5초 빨리 앎" |
| API 인증 없음 | 같은 도커 네트워크 내부 통신 |
| 출력은 믹스 1개 | 화자분리는 master-api의 STT 엔진이 처리 |
| 16kHz 작업 포맷 | master-api가 만드는 flac이 16kHz mono. 48kHz로 올려도 정보량 증가 없이 CPU만 3배 |

### 2-5. 결과: 만들 게 줄었다

```
처음 계획           최종
─────────────      ─────────────
s3_transfer.py      s3_transfer.py
merge_job.py        merge_job.py
api.py 라우트        api.py 라우트
callback.py    ❌   (폴링으로 대체)
정렬 모듈       ❌   (timestamp로 대체)
```

**외부 라이브러리는 여전히 0개다.** 표준 라이브러리 + ffmpeg 바이너리만 쓴다.

### 3-2. 처리 흐름

```
POST /v1/merge
  │
  ├─ 검증 → 큐 적재 → 202 즉시 반환 { jobId, status: "WAITING" }
  │
  └─ 워커 스레드 (동시 3개)
       ① DOWNLOADING   presigned GET으로 병렬 다운로드 (0~40%)
       ② NORMALIZING   16kHz mono 통일        (40~60%)
       ③ MIXING        amix로 겹쳐서 합산      (60~85%)
       ④ UPLOADING     presigned PUT          (85~99%)
       └ 성공·실패 무관하게 작업 디렉터리 삭제

GET /v1/merge/{jobId}   ← master-api가 5초마다 조회
```

### 3-3. ffmpeg 필터그래프

`align: "none"` — 전부 0초부터 겹침

```
amix=inputs=3:dropout_transition=0:normalize=0,alimiter=limit=0.95
```

`align: "timestamp"` — `adelay`로 앞에 무음을 넣고 겹침

```
[0:a]adelay=0:all=1[d0];
[1:a]adelay=267:all=1[d1];
[2:a]adelay=812:all=1[d2];
[d0][d1][d2]amix=inputs=3:dropout_transition=0:normalize=0,alimiter=limit=0.95
```

`normalize=0`으로 자동 감쇠를 끄고, `alimiter`로 클리핑을 막는다.

### 3-4. 구현 중 잡은 버그

**한글 파일명이 HTTP 헤더에 못 들어간다.**

첫 통합 테스트에서 `E5000`으로 터졌다. 스펙에는 `originalname`을 "가공 없이 그대로 보낸다"고만
써놨는데, HTTP 헤더는 latin-1만 담을 수 있다. 두 요구가 충돌했다.

master-api 코드에 답이 있었다:

```js
// src/utils/drive.util.js createPutParams()
originalname: encodeURIComponent(originalname),   // 항상 ASCII
```

이미 퍼센트 인코딩해서 저장하고 있었고, 다운로드 쪽 `ensureEncoded()`도 인코딩된 값을
전제로 동작한다.

**→ 접수 단계에서 `E4007`로 거부하도록 했다.** 우리가 임의로 인코딩하면 presigned 서명이
깨져서 고쳐줄 수가 없고, 업로드 직전에 터지는 것보다 요청 즉시 명확한 코드로 알려주는 게 낫다.

### 3-5. 검증 결과

실제 ffmpeg + 가짜 presigned 서버로 전체 흐름을 돌렸다.

```
⓪ 한글 originalname    -> HTTP 400  code=E4007
① POST /v1/merge      -> HTTP 202  status=WAITING
② 폴링 단계            -> WAITING → NORMALIZING(40→53%) → MIXING(60%) → DONE(100%)
③ output              -> 3812ms / 16000Hz / 1ch / 100996bytes
   alignment          -> p1:0ms  p2:267ms  p3:812ms  (fallback 없음)
④ originalname 일치?   -> True
⑤ 작업 디렉터리        -> 잔여물 없음
```

**겹치기 확인**: 3초 파일 3개 → **3.000초** (이어붙이기였다면 9초)
**밀리초 offset 확인**: 812ms 지연 반영 → 3.812초

테스트 **65개 전부 통과**. 전체 스위트 206개 중 3개 실패는 작업 이전부터 있던
Flutter 스캐폴드 점검 도구 건으로, `git stash` 대조로 확인했다.

## 4부 · API 문서 (Swagger)

### 4-1. 의존성 없이 구현했다

FastAPI·Flask·flasgger 같은 걸 깔면 "pip 의존성 0개" 정책이 깨진다. 그래서 직접 만들었다.

- OpenAPI 3.0 문서를 파이썬 dict로 조립 (`openapi.py`)
- Swagger UI 자산을 **저장소에 내장** (`static/`)

CDN(`cdn.jsdelivr.net`)을 쓰면 망분리 서버에서 빈 화면이 된다. 그래서 파일로 박았다.

### 4-2. 접근

```
http://<서버>:28080/docs          Swagger UI
http://<서버>:28080/openapi.json  OpenAPI 문서
```

**계정: `.env.recog`의 `SWAGGER_USER` / `SWAGGER_PASSWORD` 참조** (HTTP Basic 인증)

브라우저로 여는 유일한 화면이라 여기만 인증을 걸었다. `/v1/merge` 엔드포인트 자체는
인증이 없다 — 도커 네트워크 내부 통신이라는 결정 그대로다.

계정은 환경변수로 바꿀 수 있다:

```bash
SWAGGER_USER=admin
SWAGGER_PASSWORD=<설정값>     # 빈 값으로 두면 인증이 꺼진다
```

> 기본값이 소스에 들어 있으므로, 외부 노출 가능성이 생기면 `.env.recog`에서 반드시 바꿀 것.

## 5부 · Postman 테스트 경로

스토리지 없이 병합만 확인할 수 있는 경로를 추가했다.

```
POST /v1/merge/upload        multipart로 파일 직접 첨부
GET  /v1/merge/{jobId}       상태 조회 (동일)
GET  /v1/merge/{jobId}/download   결과 파일 받기
```

**핵심은 이게 별도 코드가 아니라는 점이다.** 같은 큐·워커·믹싱 코드를 타고
다운로드/업로드 양끝만 바뀐다. 그래서 Postman으로 돌린 결과가 실제 동작 검증이 된다.

```
POST /v1/merge/upload
  ↓ (presigned 다운로드 대신 요청 본문의 바이트를 씀)
  ② NORMALIZING → ③ MIXING     ← 완전히 동일
  ↓ (presigned 업로드 대신 결과를 보관)
GET /v1/merge/{jobId}/download
```

### Postman 설정

```
Method : POST
URL    : http://<서버>:28080/v1/merge/upload
Body   : form-data
         files      [File]  p1.flac      ← key 이름을 files 로 3번 추가
         files      [File]  p2.flac
         files      [File]  p3.flac
         align      [Text]  none
         roomNo     [Text]  TEST-001
```

Swagger UI의 "Try it out"으로도 바로 된다.

> presigned 경로로 만든 job은 결과를 스토리지에 올리고 지우므로 `/download`가 404다.
> 테스트로 만든 것만 받을 수 있다.

## 6부 · 망분리 배포

### 6-1. 왜 별도 절차가 필요한가

현재 이미지는 빌드할 때 세 군데에서 네트워크를 탄다.

| 위치 | 내용 |
|---|---|
| `Dockerfile:17` | `FROM python:3.11-slim` |
| `Dockerfile:51` | `apt-get install ffmpeg curl` |
| `docker-compose.yml` | `ghcr.io/...` 레지스트리 pull |

망분리에서는 셋 다 실패한다. 인터넷 되는 PC에서 이미지를 완성해 파일로 반입한다.

```
[인터넷 되는 PC]                    [망분리 서버]
 build_offline_bundle.sh            install_offline.sh
   docker build                       체크섬 검증
   docker save | gzip     ──USB──►    docker load
   + compose + env + 문서              compose up -d
   → recog-offline-*.tar.gz           /health 확인
```

> recog는 pip 의존성이 0개라 휠 파일을 따로 모아 반입할 필요가 없다.
> Swagger 자산도 내장되어 있어 CDN 없이 `/docs`가 뜬다.

### 6-2. ⚠️ 가장 흔한 실패 — 아키텍처

**M1/M2 맥에서 그냥 빌드하면 arm64 이미지가 나온다.** 서버가 x86_64면 `exec format error`로
기동조차 안 된다.

빌드 스크립트는 기본값을 `linux/amd64`로 두고 빌드 후 실제 아키텍처를 검사해 경고한다.
설치 스크립트는 호스트와 비교해 **불일치면 설치 전에 중단**한다.

```bash
uname -m        # x86_64 → linux/amd64 , aarch64 → linux/arm64
```

### 6-3. 네트워크

`/v1/merge`는 양방향 통신이 필요하다.

```
① recog → MinIO       presigned URL 호스트가 timblo-minio:9000 이므로
                      recog가 그 이름을 해석할 수 있어야 한다
② master-api → recog  폴링으로 상태를 조회하므로 recog에 닿아야 한다
```

그래서 compose에 외부 네트워크를 붙였다.

```yaml
networks:
  - timblo-net-package
```

없으면 설치 스크립트가 중단하고 안내한다. MinIO와 master-api가 이미 떠 있으면 존재한다.

### 6-4. 사용법

```bash
# 인터넷 되는 PC
./scripts/deploy/build_offline_bundle.sh skHynix-v1.0.0 linux/amd64
# → dist/recog-offline-skHynix-v1.0.0.tar.gz

# 망분리 서버
tar xzf recog-offline-skHynix-v1.0.0.tar.gz
cd recog-offline-skHynix-v1.0.0
./install_offline.sh /home/jwpark/timblo-hynix/recog-backend
```

자세한 절차와 문제 해결표는 `deploy/OFFLINE_DEPLOY.md`.

## 6.5부 · 기록 영속화와 재작업

### 왜 넣었나

작업 상태를 메모리에만 들고 있으면 서버가 재시작될 때 통째로 사라진다.
병합이 2~5분 걸리므로 창은 좁지만, 그 사이 재시작되면 작업이 증발한다.

### SQLite를 고른 이유

`sqlite3`가 **파이썬 표준 라이브러리**다. DB를 쓰면서도 의존성 0개 정책이 안 깨진다.
MariaDB나 MongoDB를 쓰려면 드라이버를 pip로 깔아야 해서 불가능했다.

파일은 `runtime/merge.db`에 놓인다. 이 디렉터리는 호스트에 바인드 마운트되어 있어
컨테이너가 죽어도 남는다.

### 무엇이 달라졌나

| 상황 | 이전 | 지금 |
|---|---|---|
| 통신 끊김 | ✅ 24시간 재조회 | ✅ 90일 재조회 |
| 서버 재시작 (완료된 작업) | ❌ 404 | ✅ 기록에서 복원 |
| 서버 재시작 (진행 중 작업) | ❌ 유실 | ✅ **자동 재큐잉** |
| 실패한 작업 재실행 | 요청 재조립 필요 | ✅ `POST .../retry` |
| 통계·감사 | 불가 | ✅ SQL 조회 |

### 재시작 복구 방식

진행 중이던 작업은 임시 파일이 사라져 **이어서 할 수는 없다.** 대신 요청 원본이
기록에 남아 있으므로 **처음부터 다시 실행**한다. presigned URL 유효기간(권장 6시간)
안이면 그대로 성공한다.

`requeue_count`가 재큐잉 횟수다. 계속 올라가면 그 입력에서 crash-loop 중이라는 신호다.

> 업로드 테스트 경로 작업은 원본 파일이 디스크에 남아 있을 때만 재실행한다.
> 없으면 `E5002`로 실패 처리해서 무한 루프를 막는다.

### 영속화는 best-effort다

DB 쓰기 실패가 **진행 중인 병합을 망치면 안 된다.** 실행 중에는 메모리 상태가
정답이고, DB는 복구와 이력을 위한 것이다. 그래서 저장 실패는 경고만 남기고 넘어간다.
기동 시 DB가 깨져 있어도 서버는 뜬다.

### 두 개의 보존 기간

혼동하기 쉬워서 분리했다.

| 설정 | 기본값 | 의미 |
|---|---|---|
| `MERGE_JOB_TTL_SEC` | 24시간 | 메모리 캐시 크기를 제한 |
| `MERGE_RECORD_TTL_DAYS` | **90일** | 실제 조회 가능 기간 |

메모리에서 밀려나도 조회하면 SQLite로 자동 폴백한다. 즉 **사용자가 체감하는 보존
기간은 90일**이다.

### 이력 조회

```bash
# API
curl "http://서버:28080/v1/merge?roomNo=R-20260919-001&limit=50"

# 서버 없이 직접
sqlite3 runtime/merge.db "SELECT room_no, status, finished_at FROM merge_jobs ORDER BY accepted_at DESC LIMIT 20"
sqlite3 runtime/merge.db "SELECT json_extract(error,'\$.code'), COUNT(*) FROM merge_jobs WHERE status='ERROR' GROUP BY 1"
```

### 재작업 API

```
POST /v1/merge/{jobId}/retry
```

저장된 요청으로 다시 실행한다. **새 jobId가 발급되고** 원래 작업은 `retriedFrom`으로
연결되어 두 시도가 모두 이력에 남는다.

본문은 생략 가능하다. 대부분 presigned URL 만료로 실패하므로 새 URL만 실어 보내면
된다. **바꿀 수 있는 건 URL뿐**이고 참가자·정렬 모드·파일명은 원래 요청을 재사용한다 —
재작업이 슬쩍 다른 작업이 되는 것을 막기 위해서다.
