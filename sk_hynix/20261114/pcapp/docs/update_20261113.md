# 회사 반영 목록 ver.17 — 2026-11-13

> ⚠️ **회사에 반입하지 못해 ver.18(`docs/update_20261116.md`)에 합쳐짐 (11-14).** 이 문서 대신 ver.18 을 본다. (아래는 기록용 — DLL 시험 방법은 ver.18 이 최신)

> ver.16(`docs/update_20261112.md`)에 **이어서** 적었다.
> 내용 두 가지:
> ① **AM DLL 을 받으면 회사 PC 에서 할 시험 순서** (11-12 회사 결과 반영: 1번 성공, 2번 실패, 진짜 DLL 아직 없음)
> ② **설정 개발/운영 분리** — `app.config.json` 한 파일 안에서 `APP_ENV` 한 줄로 개발/운영 값을 고른다 (맨 아래 "교체할 파일")
>
> ②를 먼저 반영하면 아래 4단계가 쉬워진다(운영 값 네 줄 대신 `"APP_ENV": "prod"` 한 줄).

**알아 둘 것**
- DLL 은 **밖으로 가져오지 않는다.** 시험은 전부 회사 PC 에서 하고, **결과 한 줄만 적어 온다**(아래 "적어 올 것" 표).
- 담당자에게 헤더(.h)를 받지 못해도 된다. 아래 3·4단계로 함수 모양을 우리가 직접 알아낸다.
- 시험 중 창이 꺼지는 건 시험 창(node) 하나뿐이다. PC·앱에는 영향 없다.
- 모든 명령은 **프로젝트 폴더**에서 실행한다 (명령 프롬프트 `cmd`).
- ★ **내 PC 의 AM-Tray 는 운영 모드**다(11-12 확인). 우리 앱 기본 설정은 개발(`Dev_CASSO`, 31001)이라, 아래 3·4단계에 **운영 값으로도** 시험하는 줄을 넣었다.

## ★ 먼저: 담당자가 C++ 용 문서를 주면 (11-13 공유 예정)

**이게 오늘 가장 중요하다.** 문서 전체를 옮길 필요 없다. **아래만 손으로 옮겨 적는다** (글자 하나하나 그대로 — 특히 `*`, `&`, `const`, 대소문자).

| 옮겨 적을 것 | 예시 (모양만 참고) |
|---|---|
| ① **함수 선언 4개** 그대로 — `GetSystemTokenIT`, `ShowSSOLoginUI`, `SSOLogout`, `GetReturnMessage` | `BOOL WINAPI GetSystemTokenIT(LPCSTR ssoKey, LPCSTR sid, LPCSTR systemID, LPSTR lpToken, LPSTR lpReturnCode);` |
| ② 함수 앞뒤에 붙은 말 | `extern "C"`, `__declspec(dllimport)`, `WINAPI`, `__stdcall` 등 |
| ③ 문자열 형식 | `char*` / `LPSTR` / `LPCSTR` 인지, `wchar_t*` / `LPWSTR` / `LPCWSTR` / `TCHAR` 인지 |
| ④ 버퍼 크기 | 예제 코드에서 `char token[2048]` 처럼 **배열 크기**, 또는 크기를 넘기는 인자가 있나 |
| ⑤ 예제 코드의 호출 몇 줄 | `GetSystemTokenIT(...)` 를 부르는 줄과 바로 앞뒤 (변수 선언 포함) |
| ⑥ 그 밖에 먼저 부르는 함수 | `Init…`, `Open…`, `Release…`, `Free…` 같은 것 |
| ⑦ DLL 파일 이름 | 예제의 `LoadLibrary("…")` 또는 `#pragma comment(lib, "…")` |

> 이것만 있으면 집에서 `amTrayDll.js` "★ 가정" 블록을 **확정**한다 → 아래 3단계의 "두 가지 모양 시험"이 필요 없어진다.
> 담당자가 "C++ 로 개발하냐" 다시 물으면: "**아니요. 그래도 C++ 문서가 맞습니다** — 함수 모양만 보면 됩니다." (더 설명할 필요 없음)

## 1단계. 가짜 DLL 로 시험 도구 확인 (11-12 실패한 것)

```
node scripts\amtray-koffi-test.js token --dll-dir src\helpers\windows\amtray\test\fake-dll --system-id 1
set FAKE_AM=notlogin
node scripts\amtray-koffi-test.js token --dll-dir src\helpers\windows\amtray\test\fake-dll --system-id 1
set FAKE_AM=
```

| 나온 결과 | 뜻 |
|---|---|
| `"kind":"인가토큰"` / 두 번째는 `"result":"504011"` | ✅ 성공 → 2단계로 |
| `"error":"dll_not_found"` | 가짜 DLL 폴더 없음 → 0단계 다시 |
| `"error":"dll_load_failed"` | `"message"` 내용을 그대로 적어 온다 |
| 그 밖 | 화면에 나온 줄을 그대로 적어 온다 |

> 1단계가 안 돼도 2단계(진짜 DLL 함수 보기)는 할 수 있다. DLL 을 실행하지 않는 검사라서.

## 2단계. 진짜 DLL 함수 보기 — 실행하지 않음, 안전

```
node scripts\amtray-exports.js src\helpers\windows\amtray\bin
```

마지막 `[결론]` 아래 몇 줄만 적어 온다. 예:
```
[결론] B — ...
  GetSystemTokenIT 있음(C++)  가정과 다름 → bool GetSystemTokenIT(char const*, ...)
  ShowSSOLoginUI 있음
  ...
```

| 결론 | 뜻 |
|---|---|
| **B** | C++ 방식 — 함수 이름 안에 **인자·반환 형식이 들어 있다 = 헤더를 받은 것과 같다.** "가정과 다름 → ..." 줄이 있으면 **그 줄을 꼭** 적어 온다 |
| A | C 방식 — 이름만 있고 형식은 없다 → 3단계로 형식을 알아낸다 |
| C | 이름이 다르다 → 나온 함수 이름 목록을 적어 온다 |
| D | DLL 을 못 읽음 / 64비트 아님 → 그 줄을 적어 온다 |

## 3단계. 진짜 DLL 호출 — 두 가지 모양으로

AM-Tray 가 PC 에 설치·실행 중이어야 의미 있는 결과가 나온다(트레이 아이콘 확인).
`--system-id` 는 아직 우리 값이 없으니 `1` 로 둔다 → 보통 에러코드(503032 등)가 나오는데, **코드가 나오기만 하면 호출 성공**이다.

```
node scripts\amtray-koffi-test.js token --dll-dir src\helpers\windows\amtray\bin --sso-key Dev_CASSO --sid timbloRecAppDev --system-id 1
node scripts\amtray-koffi-test.js token --dll-dir src\helpers\windows\amtray\bin --sso-key Dev_CASSO --sid timbloRecAppDev --system-id 1 --signature bool_out
```

| 나온 결과 | 뜻 |
|---|---|
| `"result":"504011"`·`"503032"` 처럼 **6자리 숫자** | ✅ **이 모양이 맞다** (어느 명령이었는지 적어 온다) |
| `"kind":"인가토큰"` | ✅ 맞고, 토큰까지 받음 |
| **아무 출력 없이 끝남** | 이 모양은 틀림 → 다른 명령 결과를 본다 |
| `bool_out` 명령에서 `"code":""`, `"result":""` (빈 값) | `bool_out` 모양이 아닐 가능성 큼 → 기본 명령 결과를 본다 |
| 둘 다 이상한 글자 / 둘 다 빈 값 | 각 명령 끝에 `--wide` 붙여 한 번 더 |
| `"error":"dll_load_failed"` | `"message"` 를 적어 온다 (Rathon DLL 이 같은 폴더에 있는지 확인) |
| `"error":"fn_not_found"` | 2단계 결과를 적어 온다 |

**운영 모드 AM-Tray** 라서 위 결과가 이상하면(예: 503035, 509090) 운영 값으로 한 번 더:
```
node scripts\amtray-koffi-test.js token --dll-dir src\helpers\windows\amtray\bin --sso-key Prod_CASSO --sid timbloRecApp --system-id 1
```
(위에서 맞은 모양이 `bool_out` 이면 끝에 `--signature bool_out` 도 붙인다)

**맞는 모양을 찾았으면** 이어서 (같은 옵션으로):
```
node scripts\amtray-koffi-test.js message --dll-dir src\helpers\windows\amtray\bin --code 504011 --locale ko
```
→ 한글 문구가 나오면 성공. 깨지면 `--utf8` 붙여 한 번 더.

> `show-ui`(AM 로그인 창 띄우기)는 **지금 하지 않는다** — 화면이 뜨고 사용자 로그인이 섞여서 헷갈린다. 위 결과를 본 다음에.

## 4단계. 앱에서 (여유 있으면)

`src\config\app.config.json`:
1. 흉내: `"AMTRAY_MOCK": ""` → `"notlogin"` → `npm start` → [시스템 로그인] → 3초 뒤 진행되나 → **끝나면 다시 `""`**
2. 진짜 DLL (②설정 분리를 반영한 경우):
   - 맨 위 `"APP_ENV": "dev"` → **`"prod"`** (내 PC AM-Tray 가 운영 모드라서. `prod` 묶음에 `Prod_CASSO`·`timbloRecApp`·30001 이 이미 들어 있다)
   - `prod` 묶음 안의 `"AMTRAY_SYSTEM_ID": ""` → `"1"`
   - 3단계에서 `bool_out` 이 맞았으면 바깥에 `"AMTRAY_DLL_SIGNATURE": "bool_out",` 한 줄 추가
   - `npm start` → [시스템 로그인] → 나온 문구를 적어 온다 → **끝나면 모두 원래대로**(`APP_ENV` `"dev"`, SYSTEM_ID `""`)
   - 3단계에서 개발 값(`Dev_CASSO`)이 맞았으면 `APP_ENV` 는 `"dev"` 그대로, `dev` 묶음의 SYSTEM_ID 만 `"1"`
   - 왜 `prod` 가 중요한가: 30001(운영)/31001(개발)이 AM-Tray 와 다르면 **AM 로그인 끝났다는 메시지를 앱이 무시**한다

   ②를 반영하지 않았다면: 바깥에 `"AMTRAY_SYSTEM_ID": "1", "AMTRAY_SSO_KEY": "Prod_CASSO", "AMTRAY_SID": "timbloRecApp", "AMTRAY_ENV_CODE": 30001,` 네 줄을 넣고 끝나면 삭제.

> 빌드 전에는 `AMTRAY_MOCK` 이 `""` 인지, 시험용으로 바꾼 값을 되돌렸는지 꼭 확인.

## ② 설정 개발/운영 분리 — 교체할 파일

| 파일 | 내용 |
|---|---|
| `src/main/config.js` | `APP_ENV` 에 따라 `dev`/`prod` 묶음 값을 먼저 읽는다. 다른 코드는 그대로 |
| `src/config/app.config.json` | 맨 위 `"APP_ENV": "dev"`, 맨 아래 `"dev": {…}`, `"prod": {…}` 묶음 추가. **기존 값은 하나도 안 바뀜.** 회사 파일에만 있는 값이 있으면 통째로 바꾸지 말고 이 세 부분만 넣는다 |
| `scripts/build-env.js` | **새 파일.** `build:dev` / `build:prod` 가 쓰는 빌드 도우미 |
| `src/main/main.js` | 시작 로그(`app_started`)에 `appEnv` 한 줄 — 어느 설정으로 떴는지 로그에서 보인다 |
| `.env.example` | `APP_ENV` 설명 (참고용) |
| `.gitignore` | `src/config/app.env.json` (빌드 때 잠깐 생기는 파일) |
| `VERSION.md` | 0.0.12 한 줄 |

> `package.json` 은 통째로 교체하지 말고:
> 1. `version` → **0.0.12** (ver.16 의 0.0.11 을 건너뛰고 바로 반영해도 된다)
> 2. `"scripts"` 의 `"build": …` 줄 아래에 두 줄 추가
> ```json
> "build:dev": "node scripts/build-env.js dev",
> "build:prod": "node scripts/build-env.js prod",
> ```

**쓰는 법**
- 값 찾는 순서: **`dev`/`prod` 묶음 → 바깥(공통) → 코드 기본값.** 묶음의 값이 `""` 이면 바깥 값을 쓴다 → 지금은 URL 이 모두 `""` 라 **지금과 똑같이 동작**한다.
- 묶음에 넣어 둔 것: URL 7개(`SSO_LOGIN_URL`, `HMP_BASE_URL`, `DEFAULT_API_BASE_URL`, `MOBILE_SERVER_URL`, `LOG_SERVER_URL`, `UPDATE_SERVER_URL`, `TERMS_AGREE_URL`) + AM-Tray 4개(`AMTRAY_SSO_KEY`, `AMTRAY_SID`, `AMTRAY_ENV_CODE`, `AMTRAY_SYSTEM_ID`)
  - AM-Tray 값은 개발/운영 모두 채워 둠. **URL 은 개발/운영 주소를 알게 되면 해당 묶음에 넣는다** (예: 운영 `SSO_LOGIN_URL` — 지금 바깥 값은 `amdev` = 개발 주소)
- 개발 실행(`npm start`): 맨 위 `APP_ENV` 를 따른다.
- 설치 파일: **`npm run build:prod`** (운영) / **`npm run build:dev`** (개발) — `APP_ENV` 를 손으로 바꾸지 않아도 된다. 예전 `npm run build` 는 파일의 `APP_ENV` 를 그대로 쓴다.
- 확인: 앱 로그 `app_started` 줄의 `appEnv` 가 `prod`/`dev`.
- 개발판·운영판은 앱 ID 가 같아서 **한 PC 에 같이 설치할 수 없다**(나중 설치가 덮어씀). 같이 깔아야 하면 말해 달라.

| 확인 | 방법 | 적어 올 것 |
|---|---|---|
| 지금과 같은가 | `npm start` → 사번 로그인·녹음 평소대로 | 이상 있으면 그 화면 |
| prod 빌드 | `npm run build:prod` → 설치 → 로그의 `app_started` | `appEnv` 값 |
