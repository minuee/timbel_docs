# 업로드/녹음 이슈 정리 및 수정 요청

로그 및 소스 확인 결과 정리.
1~4번은 즉시 수정 가능. 5번은 전송 구조 개선 건으로 별도 진행.

---

## 1. 실패한 업로드가 앱 실행 시마다 재시도됨

**원인**

`upload_list`에서 항목을 제거하는 지점이 2곳이나 둘 다 성공 항목(`upload_yn == 'Y'`)만 제거.

- `secure_storage_service.dart:172`
- `uploaded_listener.dart:35`

실패 항목은 제거되지 않으며 실패 횟수/만료 조건 없음.
반면 재시도 트리거는 4개.

| 트리거 | 위치 |
|---|---|
| 메인 진입 | `main_container_controller.dart:120` |
| 포그라운드 복귀 | `upload_service.dart:791` |
| 네트워크 재연결 | `upload_service.dart:562` |
| WorkManager | `upload_service.dart:1220` |

**수정 사항**

- `upload_list` 항목에 `fail_count`, `last_try_at` 필드 추가
- 3~5회 실패 시 자동 재시도 대상에서 제외, 사용자 수동 재시도만 허용
- 재시도 간격 백오프 적용 (1분 → 5분 → 30분)
- 7일 경과 미완료 항목 정리

## 2. 파일이 없는 상태에서 업로드 시도하여 400 발생

**원인**

`uploadFolder()`가 전송 전 파일 존재 여부를 검증하지 않음.
`getFilesInFolder()`는 폴더 부재 시 빈 배열 반환(`upload_service.dart:1678`), 그대로 `files: []`, `totalNum: '0'`으로 POST 전송됨(`:1500`).

폴더 소실 경로

- 업로드 성공 후 폴더 삭제(`:1615`) — storage 저장 실패 시 항목만 잔류
- 녹음 원본이 `getTemporaryDirectory()` 하위에 위치하여 OS가 임의 정리 가능 (`main_container_controller.dart:497`)

**수정 사항**

- `uploadFolder` 진입부에 `fileList.isEmpty` 검증 추가 → 즉시 실패 처리 후 큐에서 제거
- 400 / 404 / E2xxx 등 재시도 무의미한 에러를 네트워크 에러와 분리하여 큐에서 제거
- 녹음 원본 저장 위치 변경: `getTemporaryDirectory()` → `getApplicationDocumentsDirectory()`

## 3. 변환 진행률 80%에서 정지

**원인**

진행률이 SSE 이벤트로만 갱신되며 폴백 없음.

- 재연결 25초 후 영구 포기 (`main_container_controller.dart:475`, `maxAttempts: 5` × 5초)
  화면 유지 중에는 포그라운드 복귀 이벤트도 발생하지 않아 복구 불가
- 복귀 시 실행되는 `syncProcessingStatus()`는 DONE/ERROR 제거만 수행, 진행률 미갱신 (`uploaded_listener.dart:203`)
- `'LLM-RUNNING'` 문자열 하드코딩(`uploaded_listener.dart:93`). 서버 값 불일치 시 else 분기로 진입하여 **0%로 리셋**

**수정 사항**

- `maxAttempts` 상향 및 지수 백오프 적용
- 변환 중 항목 존재 시 10~15초 주기 폴링 폴백 추가
- `syncProcessingStatus()`에서 진행률도 서버 값으로 갱신
- 미매핑 status는 0% 리셋 대신 직전 값 유지

**확인 요청**

서버에서 실제 전송하는 status 값 전체 목록 공유 요청 (`LLM-RUNNING` 하이픈/언더스코어 포함).

## 4. send timeout 10분 초과

**원인**

`sendTimeout: const Duration(minutes: 10)` 하드코딩 (`upload_service.dart:1317`, `:1424`).
바디 전송 전체에 적용되는 타임아웃으로, 폴더 일괄 전송 구조에서 파일 크기가 크거나 회선이 느리면 초과.

타임아웃 발생 시 처음부터 재전송하므로, 1번의 무제한 재시도와 중첩될 경우 동일 파일을 반복 재전송하며 사용자 데이터 소모.

**수정 사항**

- `sendTimeout` 10분 → 30분 상향 (2곳: `:1317`, `:1424`)
- 단, 1번의 재시도 제한과 반드시 동시 적용할 것. 재시도 제한 없이 타임아웃만 늘리면 재전송 시간만 3배가 됨

> 근본 해결은 5번. 5번 적용 시 타임아웃이 배치 단위로 적용되어 초과 가능성이 사실상 사라짐.

## 5. 폴더 일괄 전송 → 파일 단위 분할 전송

`Connection reset by peer (errno 54)`와 4번 send timeout의 공통 원인.
녹음 폴더 전체를 멀티파트 단일 요청으로 전송하고 있음 (`upload_service.dart:1485`).
1시간 녹음이면 3분 단위 파일 20개가 한 요청에 실림. 중간 장비의 바디 크기 제한이나 타임아웃에 걸리기 쉬운 구조.

### 현재 API는 이미 분할 전송을 지원함

`POST /api/contents/upload/encryption/files`

**요청 파라미터**

| 필드 | 설명 |
|---|---|
| `files` | 멀티파트 파일 배열 |
| `deviceId` | 기기 식별자 |
| `fileName` | 녹음 폴더명 (세션 키) |
| `totalNum` | 해당 녹음의 **전체** 파일 개수 |
| `lang`, `attendeeNum`, `templateId` | 기타 |

**응답**

| 응답 | 의미 |
|---|---|
| `httpCode == 200` | 전체 수신 완료 |
| `data.missingFiles: [인덱스…]` | 아직 수신하지 못한 파일 |
| `errorCode == 'E2133'` | 이미 업로드된 녹음 |

현재 코드는 1차에 전부 보내고, `missingFiles`가 오면 해당 파일만 재전송함 (`upload_service.dart:1484-1494`).
즉 **서버는 이미 `deviceId` + `fileName` 기준으로 여러 요청에 걸쳐 파일을 누적하고, `totalNum`이 충족될 때까지 대기하는 구조**.
녹음 파일명도 `encrypted_audio_0.pcm`, `encrypted_audio_1.pcm` … 으로 인덱스가 부여됨 (`audio_recorder_io.dart:274`).

→ **처음부터 나눠 보내는 것도 동일 프로토콜. 서버 수정 불필요.**

### 변경 방법

1. `fileList`를 배치로 분할 (파일 5개 또는 누적 20MB 단위 권장)
2. 배치마다 POST 전송. `deviceId`, `fileName`, `totalNum`은 **모든 요청에 동일 값** 유지
   - `totalNum`은 배치 크기가 아니라 항상 전체 파일 개수
3. 마지막 배치 전까지 오는 `missingFiles` 응답은 **정상 응답**. 실패로 처리하지 말 것
4. `httpCode == 200` 수신 시 완료 처리 → 폴더 삭제
5. 배치 실패 시 **해당 배치만** 재전송 (전체 재전송 금지)

```dart
const int batchSize = 5;
final total = fileList.length;

for (int start = 0; start < total; start += batchSize) {
  final batch = fileList.skip(start).take(batchSize).toList();

  final formData = dio.FormData.fromMap({
    'files': [for (final f in batch) await dio.MultipartFile.fromFile(f.path, filename: path.basename(f.path))],
    'deviceId': deviceId,
    'fileName': folderPath.split('/').last,
    'totalNum': total.toString(),   // 항상 전체 개수
    'lang': lang ?? 'ko',
    'attendeeNum': (speaker ?? 99).toString(),
    if (templateId != null) 'templateId': templateId,
  });

  final res = await dioClient.post(endpoint, data: formData, ...);

  // 완료 응답이면 종료
  if (res.data['httpCode'] == 200) break;
  // missingFiles 응답은 정상 — 다음 배치 계속 전송
}
```

### 진행률 처리

현재 `onSendProgress`는 단일 요청 기준이라 배치마다 0%부터 다시 시작함.
배치 누적 오프셋 필요.

```dart
progress = (완료된 배치 바이트 합 + 현재 배치 sent) / 전체 폴더 바이트
```

전체 바이트는 이미 `_totalFolderBytes`로 계산 중 (`upload_service.dart:1466`).

### 적용 범위

동일 로직이 2곳에 중복되어 있으므로 양쪽 모두 반영 필요.

- `uploadFolder()` — `upload_service.dart:1482`
- `_backgroundUploadFolder()` — `upload_service.dart:270` (WorkManager 백그라운드 경로)

### 주의 사항

- `getFilesInFolder()`가 파일 수정시각(mtime) 기준 정렬(`upload_service.dart:1670`)인데, 서버 `missingFiles` 인덱스는 파일명 숫자 기준일 가능성이 높음. 일괄 전송에서는 순서가 우연히 일치했으나 배치 전송 시 어긋날 수 있음 → **파일명 숫자 기준 정렬로 변경 권장**
- 배치는 **순차 전송**. 동시 전송 시 서버 누적 처리에서 경쟁 조건 발생 가능

### 서버 확인 요청

- `missingFiles` 인덱스 기준: 파일명 숫자인지, 전송 순서인지
- 부분 수신 상태 보관 시간(세션 TTL). 배치 간 간격이 벌어질 때 기존 수신분 유실 여부
- 동일 `deviceId` + `fileName`으로 같은 파일 재전송 시 중복 처리 방식

### 기대 효과

- 요청당 바디 크기 감소 → 프록시 바디 제한/타임아웃 회피 (errno 54)
- 타임아웃이 배치 단위로 적용 → 4번 사실상 해소
- 중간 실패 시 해당 배치만 재전송 → 재업로드 데이터량 대폭 감소
- 진행률이 실제 전송량 기준으로 단조 증가

## 6. 통화 종료 후 일시정지 상태로 정지

**원인 (버그)**

자동 재개 로직은 구현되어 있으나 경쟁 조건 존재 (`call_state_service.dart:120`).

```dart
void _autoResumeAfterCall() {
  if (!_pausedByCall) return;
  _pausedByCall = false;    // 플래그 선소비

  if (!isPaused()) return;  // pause 반영 전이면 early return
```

`pauseRecording()`이 await 없이 호출되고 `recordState`는 비동기로 변경됨.
수신 직후 즉시 거절 시 CALL_ENDED가 pause 반영보다 먼저 도착하여 early return 발생.
이때 `_pausedByCall`은 이미 false로 소비된 상태라 재시도되지 않고 일시정지 상태로 고착.

추가로 Android는 `isCalled`가 true로 잔류할 경우 재개 대신 "통화 중" 팝업 노출 (`recording_controller.dart:566`).

**수정 사항 (버그)**

- `_pausedByCall` 소비 시점을 뒤로 이동, pause 반영 대기 재시도 추가 (100ms × 최대 10회)
- 통화 이벤트 누락 대비 `isCalled` 타임아웃 리셋 추가

**수정 사항 (UI)**

정지 사유가 화면에 표시되지 않음. 토스트는 노출되나 사용자가 통화 화면에 있어 확인 불가.

- 통화로 인한 일시정지 시 녹음 화면 상단에 상시 배너 노출: `통화로 일시정지됨 · 탭하여 계속 녹음`
- 일시정지 중 타이머 점멸 및 색상 변경
- 자동 재개 시 `3초 후 자동 재개 [취소]` 카운트다운 노출
- 파형에 통화 구간 회색 처리 (`RecordingSession.pauseEvents` 데이터 활용)

## 우선순위

1. **1번 + 2번** — 데이터/배터리 지속 소모, 사용자 대응 수단 없음. 수정 난이도 최저
2. **6번 경쟁 조건** — 녹음 유실로 직결. 단일 함수 수정
3. **3번 폴백** — 폴링 추가로 해결
4. **4번** — 상수 2곳 변경. 단 1번과 동시 적용 필수
5. **5번** — 작업량 있으나 errno 54 / send timeout 근본 해결. 서버 수정 불필요
