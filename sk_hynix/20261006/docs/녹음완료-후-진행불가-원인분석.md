# 녹음 완료 후 진행 불가 / 앱 종료 — 원인 분석

"녹음 완료"(종료) 버튼을 누른 뒤 다음 단계로 넘어가지 않거나 앱이 꺼지는 현상을 코드만으로 분석한 결과입니다. 기기 로그와 재현 없이 소스만 근거로 삼았습니다.

- 대상 브랜치: `develop` (기준 커밋 `205e5e5`)
- 발생 환경: **iOS / iPad**, 서비스 타입 **Hynix**, 일반 모바일 데이터
- 보고된 증상 (전해 들은 내용)
  1. 확인을 누르면 팝업이 닫히고 홈(녹음 버튼 화면)으로 돌아가는데, 그 뒤 진행되지 않음
  2. 앱이 먹통이 되거나 꺼지는 것처럼 보임
- 관련 코드: `upload_service.dart`, `audio_recorder_io.dart`, `recording_controller.dart`, `record_event_popup.dart`, `FileUploadManager.swift`, `FlutterMethodHandler.swift`
- 상태: **코드상 원인 3건 식별, 수정 미반영** (분석 전용 문서)

---

## 요약

| 증상 | 원인 | 확신도 | 장 |
|------|------|--------|----|
| 홈으로 돌아간 뒤 업로드·변환이 진행되지 않음 | Hynix iOS에서 업로드가 실패한 뒤 처리 경로가 맞지 않아 **업로드 큐가 막힘** | 높음 | 2장 |
| 앱이 꺼지는 것처럼 보임 | 녹음 종료 순간 **메모리가 급증**해 iOS가 앱을 강제 종료(Jetsam) | 중간 | 3장 |
| 업로드는 됐는데 결과가 이상하거나 변환이 실패함 | 녹음 파일 저장의 **경쟁 조건**으로 파일이 덮어써지거나 누락됨 | 중간 (특정 조건) | 4장 |

참고로 확인을 누르면 팝업이 닫히고 홈으로 돌아가는 것 자체는 **정상 흐름**입니다(`recording_controller.dart:952`, `:967`의 `Get.back()`). 문제는 그 뒤 업로드 단계에서 생깁니다.

**권장 수정 순서: 2장 → 3장 → 4장.** 2장은 수정 범위가 작은데 효과는 가장 큽니다.

## 1. 녹음 종료 처리 흐름

```
[종료] 탭 (recording_page.dart:395)
 → pauseRecording()                      (await 없이 호출)
 → stopRecordingDialog()                 (recording_controller.dart:935)
     → _fetchTemplates(): 로딩 표시 + GET /api/template
     → RecordEventPopup 표시
         → [확인] → 콜백 호출 → 팝업 Get.back()
             → 100ms 뒤 await stopRecording(true, ...)
                 → _audioService.stopRecording()        녹음기 정지, 마지막 버퍼 저장 시작
                 → 메타데이터 생성
                 → 저장 완료 대기 (최대 5초)
                 → FilePickerService.folderProcess()     업로드 큐에 등록 (await 없음)
             → Get.back()                                홈으로 이동  ← 여기까지 정상
 → UploadService.handleUploadQueue()                     ← 2장 문제 지점
     → processUploadQueue() → uploadProcess() → uploadFolder() (Dio)
```

## 2. [원인 1] Hynix iOS 업로드 큐가 막힘 — 가장 유력

### 2.1 배경

| 서비스 / 플랫폼 | 업로드 방식 | 근거 |
|------|------|------|
| Android (전체) | Flutter Dio | `upload_service.dart:437` |
| SKT·Timblo iOS (`useSSL=true`) | 네이티브 URLSession 백그라운드 업로드 | `upload_service.dart:1337` |
| **Hynix iOS (`useSSL=false`)** | **Flutter Dio** (SSL 인증서 검증 우회) | `_usesDioUpload` (`upload_service.dart:437`) |

커밋 `913fae2`(9/18, hynix ios 파일 재전송 미실행 오류)와 `0e7c1f2`(네트워크 끊김 중 업로드 팝업 유지)에서 Hynix iOS를 Dio 경로로 다루기 시작했습니다. 그런데 **네트워크 재연결 처리만** `_usesDioUpload`로 분기했고, 업로드 **실패 처리** 분기는 예전 그대로 남아 있습니다.

### 2.2 발생 흐름

| 단계 | 동작 | 코드 |
|------|------|------|
| 1 | 모바일 데이터에서 기지국 전환 등으로 연결이 잠깐 끊기면 진행 중인 Dio 요청이 취소됨. 다른 이유로 Dio가 실패해도 같은 경로를 탐 | `_onNetworkDisconnected()` `upload_service.dart:519` |
| 2 | 실패 분기에서 iOS면 **무조건** 네이티브 `NativeCommunicator.sendUploadList` 호출. 바로 위에서 계산한 `_usesDioUpload` / `keepPopupForNetworkPause`를 iOS 분기는 쓰지 않음 | `upload_service.dart:1225~` |
| 3 | 네이티브 `FileUploadManager`에는 SSL 우회 처리(`didReceive challenge`)가 없음. Hynix 서버로 보내면 인증서 단계에서 실패하고, 오프라인이면 백그라운드 URLSession 특성상 연결될 때까지 계속 기다림 | `ios/Runner/FileUploadManager.swift` |
| 4 | 네이티브 결과를 기다리는 동안 `isUploading`이 **true로 남음** | `upload_service.dart:1119` |
| 5 | 이 상태에서 새 녹음을 완료하면 `handleUploadQueue()`가 `isUploading == true`를 보고 **로그·알림 없이 return** | `upload_service.dart:1067` |
| 6 | 사용자에게는 팝업이 닫히고 홈으로 돌아왔는데 업로드가 시작되지 않는 상태로 보임 | — |

### 2.3 부수 문제

- **템플릿·제목 누락**: 네이티브 경로(`NativeCommunicator.sendUploadList`, `FlutterMethodHandler.swift` `handleUploadList`)는 `templateId`와 `title`을 받지 않습니다. 이 경로로 업로드가 성공해도 사용자가 고른 템플릿과 회의록 제목이 빠집니다.
- **이중 업로드 가능성**: 재연결 시 `_resumePausedUpload()`(`upload_service.dart:646`)가 Dio 업로드를 다시 시작합니다. 네이티브 업로드가 아직 걸려 있으면 같은 항목을 두 경로가 동시에 다룰 수 있습니다.
- **조용한 스킵**: 5단계의 return에는 `appLog`가 없습니다. Hynix는 앱 로그가 서버(`/api/app/log`)로 전송되는데도 이 상황이 기록되지 않습니다.

### 2.4 수정 방향

1. 실패 분기의 `else if (Platform.isIOS)`를 **`!_usesDioUpload`일 때만** 타도록 제한합니다. Hynix iOS는 Android처럼 `keepPopupForNetworkPause`가 아니면 `isUploading = false`만 하도록 합니다.
2. `handleUploadQueue()`에서 다음 세 조건이 모두 맞으면 남은 플래그로 보고 해제한 뒤 업로드를 진행합니다.
   - `isUploading == true`
   - `_activeUploadId == null` (실제 전송 중인 run이 없음)
   - 현재 네트워크가 연결됨
3. 스킵하는 지점에는 `AppService.to.appLog(...)`를 추가해 다음 발생 시 서버 로그에 남게 합니다.

## 3. [원인 2] 녹음 종료 순간의 메모리 급증 — 앱 종료 증상

### 3.1 원인

`audio_recorder_io.dart:23`에서 녹음 데이터를 `List<int>`에 쌓습니다. Dart의 `List<int>`는 바이트 하나를 **8바이트**로 저장합니다.

| 항목 | 크기 |
|------|------|
| 3분 버퍼 실제 데이터 | 16kHz × 2byte × 180초 ≈ **5.76MB** |
| `List<int>`로 보관할 때 | 약 576만 원소 × 8byte ≈ **46MB** |

### 3.2 종료 시점에 한꺼번에 생기는 메모리

녹음 스트림이 끝날 때(`onDone`, `audio_recorder_io.dart:97`) 다음이 짧은 시간에 연달아 생깁니다.

| 단계 | 추가 메모리 | 코드 |
|------|-------------|------|
| `List.from(_currentBuffer)` 복사 | +46MB | `:101` |
| 마이크 증폭이 켜져 있으면 `applyGainToPcm16Bytes` 복사 | +6MB | `:175` |
| `Uint8List.fromList(buffer)` | +6MB | `:191` |
| `compute()`로 isolate에 넘기는 복사본과 AES 암호화 결과 | +6MB × 2 이상 | `:192` |

순간적으로 **100MB 이상**이 추가로 필요해집니다. 같은 시점에 저장 완료 대기, 메타데이터 생성, 업로드 등록도 함께 실행됩니다. iOS는 메모리 한도를 넘는 앱을 경고 없이 종료하기 때문에(Jetsam), 사용자에게는 앱이 꺼진 것처럼 보입니다. 메모리 한도가 낮은 **구형 iPad**에서 더 잘 납니다.

3분마다 하는 중간 저장(`:85`)에서도 같은 급증이 있지만, 종료 시점에 작업이 가장 많이 겹칩니다.

### 3.3 수정 방향

- `_currentBuffer`를 `BytesBuilder`(또는 `Uint8List` 기반 버퍼)로 바꿉니다. 메모리가 약 1/8로 줄고, `List.from` 복사도 `takeBytes()`로 대체할 수 있습니다.
- 같은 패턴이 `restartStreamForRouteChange`(`:369`, `:420`)와 `addSilenceForPausedDuration`(`:478`)에도 있어 함께 바꿔야 합니다.

## 4. [원인 3] 녹음 파일 저장 경쟁 조건 — 특정 길이에서 녹음 손상

### 4.1 원인

| 문제 | 코드 |
|------|------|
| 버퍼별 암호화·저장(`_processBuffer`)을 `unawaited`로 **동시에** 실행 | `audio_recorder_io.dart:177`, `:181` |
| 파일 번호(`encrypted_audio_N.pcm`)를 **암호화가 끝난 뒤에야** 정함 | `_getNewPath()` `:273`, `_writeToNewFile()` `:244` |
| 마지막 파일 저장이 끝나면 `_fileCounter = 0`, `_totalSamples = 0`으로 초기화 | `:259-260` |
| 다른 파일이 아직 암호화 중이어도 "저장 완료"(`_savingCompleter`)를 알림 | `:263-264` |
| 게인 미적용 경로는 마지막 배치의 **모든** 버퍼에 `isFinal=true`를 넘김 | `:181` |

### 4.2 발생 조건과 결과

녹음을 **3분 경계 직후**(3:0x, 6:0x, 9:0x …)에 종료하면, 직전 3분 덩어리가 아직 암호화 중인 상태에서 마지막 덩어리가 먼저 저장될 수 있습니다.

| 결과 | 설명 |
|------|------|
| 첫 파일 덮어쓰기 | 늦게 끝난 덩어리가 초기화된 카운터 때문에 `encrypted_audio_0.pcm`으로 저장되어 첫 파일을 덮어씀 |
| 일부 파일 누락 업로드 | 저장 완료가 일찍 알려져 `folderProcess()`가 모든 파일이 쓰이기 전에 업로드를 시작함 |
| 메타데이터 오류 | `stopRecording`이 저장 완료를 기다리기 **전에** 메타데이터를 만들고 `totalSamples`를 읽음(`recording_controller.dart:664`). 이미 0으로 초기화된 값을 읽을 수 있음 |

사용자 입장에서는 업로드는 됐는데 서버 변환이 실패하거나, 앞부분 음성이 이상한 증상으로 나타납니다.

### 4.3 수정 방향

- 파일 번호는 **암호화 전에** 정해 `_processBuffer`에 넘깁니다.
- 진행 중인 쓰기 작업을 모아 두고, 마지막 저장에서는 **모든 쓰기가 끝난 뒤에** `_savingCompleter`를 완료합니다.
- `_fileCounter`와 `_totalSamples` 초기화는 `_resetState()`(녹음 시작 시)에서만 합니다.
- 메타데이터는 저장 완료를 기다린 뒤에 만듭니다.

## 5. 그 밖의 결함 — 이번 증상과는 맞지 않음

증상과 직접 맞지는 않지만 코드에 남아 있는 결함입니다. 같은 영역을 손볼 때 함께 정리하는 게 좋습니다.

| 결함 | 내용 | 코드 | 이번 증상과의 관계 |
|------|------|------|------|
| 템플릿 조회에 타임아웃 없음 | 종료 팝업 전에 터치를 막는 로딩을 띄우고 `/api/template`을 호출함. Dio에 connect/receive 타임아웃이 없어 응답이 없으면 스피너가 끝나지 않음 | `recording_controller.dart:922`, `api_service.dart:54-82` | 스피너 증상이 아니라고 해서 우선순위 낮음 |
| `stopRecording` 예외 시 화면이 넘어가지 않음 | `Future.delayed` 안에 `try/finally`가 없어 예외가 나면 `Get.back()`이 실행되지 않음. `_recordingSession!.resume()`의 `StateError`(`recording_session.dart:107`)가 보호되지 않음 | `recording_controller.dart:946-968`, `:638` | 이 경우 녹음 화면에 멈춰야 하는데, 홈으로 간다는 증상과 맞지 않음 |
| 녹음기 정지에 타임아웃 없음 | `recorder.stop()`이 네이티브에서 응답하지 않으면 무한히 대기함 | `audio_recorder_service.dart:199` | 위와 같음 |
| 종료 버튼 연타 방지 없음 | 연타하면 템플릿 조회와 팝업이 중복 실행될 수 있음 | `recording_page.dart:395` | — |
| `processUploadQueue`의 `.first` | 항목을 찾지 못하면 `isUploading = true`로 바꾼 뒤 예외가 나서 플래그가 영구히 남을 수 있음 | `upload_service.dart:1104`, `:1124` | 2장과 같은 막힘을 일으킬 수 있는 잠재 경로 |
