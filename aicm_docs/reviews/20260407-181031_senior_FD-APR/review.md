#### RD-FD-01. 비즈니스 규칙 명확성 — 78/100 양호

Round 1에서 가장 큰 결함이었던 에러 코드 매핑과 BR 누락이 대폭 개선되었다.

**잘 된 점:**
- BR 카탈로그가 32건으로 확충되어 승인 도메인의 모든 핵심 시나리오를 커버한다. BR-APR-028~032(필수 승인자 검증, 단계 수 검증, 승인자 권한 검증, 삭제 결재, 필수 단계 vs max_steps)가 추가되어 구현 시 "이 경우는 어떻게 해야 하지?"라는 질문이 크게 줄었다.
- 에러 코드 카탈로그(§에러 코드 카탈로그)가 17개로 확충되어 BR과 1:1 매핑이 충실하다. `APR_MANDATORY_STEPS_MISSING`, `APR_STEP_COUNT_OUT_OF_RANGE`, `APR_APPROVER_NO_PERMISSION` 등 Round 1에서 지적한 누락 에러 코드가 모두 추가되었다.
- BR-APR-012의 철회 허용 범위가 "pending 상태의 승인 건에 한해"로 명확히 한정되었고, 확정 상태(approved, rejected, auto_rejected, bypassed) 철회 불가를 명시적으로 열거하여 구현 시 경계 조건이 명확하다.

**개선 필요:**
- BR 카탈로그의 번호 순서가 비정렬(BR-APR-022 → 027 → 023 → 028~032 → 024~026)이어서 특정 BR을 찾을 때 스캔 비용이 증가한다.
- FD 내 API DTO 테이블에서 Request는 camelCase(`ccUserIds`, `templateId`), Response는 snake_case(`approval_id`, `step_order`)로 혼재한다. api.md는 TypeScript 인터페이스로 일관된 camelCase를 사용하므로, FD의 응답 테이블에서 `approval_id`를 `approvalId`로 정렬해야 구현자 혼란이 없다.

#### RD-FD-03. 데이터 모델 설계 타당성 — 84/100 우수

- **BR-APR-027 유지보수 윈도우 데이터 소스**: rules.md에서 "FD-MON 유지보수 창, `maintenance.started`/`maintenance.ended`"를 참조하지만, FD에서는 "시스템 점검(유지보수 모드)" 한 줄로만 기술한다. `SystemConfig.maintenance_mode` 또는 별도 유지보수 윈도우 테이블 중 어디서 읽는지 FD 수준에서 명시하면 구현 시 모듈 의존성이 명확해진다.
- **BR-APR-032 검증 시점과 기존 데이터**: "게시판 설정 저장 시" 검증만 기술하지만, 기존에 max_steps=5로 운영 중인 게시판을 max_steps=2로 줄이면서 mandatory_steps가 3건인 경우 마이그레이션 전략이 없다.

#### EX-FD-SR-02. 규칙-기능 추적 완전성 — 78/100 양호

#### EX-FD-SR-03. 암묵적 복잡도 노출 — 68/100 양호

8년차 백엔드 개발자 관점에서, 구현 시 "문서에 없어서 코드 레벨에서 즉석 결정해야 하는" 복잡도가 얼마나 남아 있는지 평가한다.

**잘 된 점:**
- §8.5(위임×자기승인 교차) 추가로 가장 흔한 교차 시나리오를 인식했다. 해소 방향("위임 대상에서 작성자를 제외", "해당 단계를 건너뛰기", "사전 차단")을 나열하여 구현자가 선택할 수 있게 한다.
- §11.4(삭제 요청 결재)가 별도 `pending_delete` 문서 상태 없이 Approval(type=DELETE) 존재 여부로 판단하는 전략을 명시적으로 기술한다. 이는 상태 모델 복잡도를 억제하는 좋은 결정인데, 복잡도를 "은폐"하지 않고 "노출 후 선택"했다.

**개선 필요:**
- **§8.5의 해소 전략이 여전히 추상적이다.** "위임 대상에서 작성자를 제외하거나... 사전 차단하는 등으로"라고만 되어 있어, 구현 시 어떤 전략을 선택할지 개발자가 결정해야 한다. NestJS 서비스에서 분기가 3~4가지 발생하며, 이는 별도 BR(예: BR-APR-033)으로 확정해야 할 설계 결정이다.
- **ROLE/TEAM 승인자의 런타임 해결 복잡도**: `approver_source = 'ROLE'`인 단계에서, 승인 요청 시점과 실제 승인 시점 사이에 해당 역할 보유자가 변경되면(인사 이동, 퇴사 등) 승인 대상자 풀이 달라진다. 요청 시점 스냅샷인지 실시간 해결인지가 명시되지 않았다. `ApprovalStepResult.approver_target`에 스냅샷되는 것은 JSONB이지만, ROLE/TEAM은 역할명/팀ID를 저장하므로 실시간 해결로 읽힌다.
- **DELETE + PUBLISH 동시 pending 가능성**: published 문서에 DELETE 승인이 pending인 상태에서 같은 문서의 수정본으로 PUBLISH 요청이 가능한지? `APR_ALREADY_PENDING`이 type 무관하게 작동한다면 불가하지만, type별로 분리한다면 동시 존재가 가능해진다. 이 결정은 `idx_approval_document_status ON (document_id, type, status)` 인덱스가 type을 포함하므로 DB 수준에서는 동시 존재를 허용하는 구조다.
- **관리자 오버라이드 × 자기승인 차단**: §8.5와 동일한 패턴이지만 미기술.
