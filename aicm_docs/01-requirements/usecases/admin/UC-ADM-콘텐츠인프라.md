# 관리자 유즈케이스 — 콘텐츠 인프라

> 게시판 구조, 문서 양식, 공통 컨텐츠, 태그 등 콘텐츠 관리의 기반이 되는 설정을 다룬다.
>
> **비즈니스 목표**: 상담사와 지식 관리자가 체계적으로 문서를 분류·작성·검색할 수 있도록, 콘텐츠의 구조적 기반(분류 체계, 작성 틀, 재사용 블록, 검색 태그)을 관리자가 사전에 설계하고 운영한다.

**관련 기능정의서**: [FD-DOC](../../features/FD-DOC-문서관리.md) §4·§5·§7·§8, [FD-ADM](../../features/FD-ADM-관리자.md) §1.1~§1.3

## UC-ADM-01: 게시판 구조 관리

**비즈니스 목표**: 체계적인 지식 분류 체계를 구축하여, 상담사의 문서 탐색 시간을 단축하고 AI 검색 범위를 정밀하게 제어한다.

**사용자**: 운영 관리자 (게시판 관리 권한 필요)

**사전 조건**:
- 사용자가 운영 관리자이며 게시판 관리 권한을 보유하고 있어야 한다.
- 지식 관리자나 부서장의 게시판 신설/변경 요청, 또는 조직 개편에 따른 분류 체계 재정비 등으로 트리거된다.

**기본 흐름**:
1. 관리자가 게시판 구조 관리 화면에 접근한다.
2. 상위-하위 관계의 트리(계층) 구조로 게시판을 생성·수정·이동·삭제한다.
   - 예: "고객상담 > CS FAQ > 결제 관련"처럼 계층으로 관리할 수 있다.
   - 상위 게시판이 없으면 최상위 게시판이 된다.
   - 게시판의 상/하위 이동은 금지되며 오직 수평이동만 가능하다. (권한 계산 복잡도 방지)
3. 게시판별로 다음 설정을 구성한다:
   - **게시판 유형**: "지식 문서용" 또는 "자유게시판용" 중 선택 (추후 게시판 타입은 늘어날 수 있음)
   - **승인 정책 연결**: 어떤 승인 절차를 따를지 설정 — 연결하지 않으면 승인 없이 바로 게시됨 ([UC-ADM-03](UC-ADM-승인정책.md) 참조)
   - **수정 시 승인 필요 여부**: 이미 게시된 문서를 수정할 때 다시 승인을 받아야 하는지 설정 (기본값: 필요함)
   - **삭제 시 승인 필요 여부**: 문서를 삭제할 때 승인을 받아야 하는지 설정 (기본값: 불필요)
   - **허용 양식 / 기본 양식**: 이 게시판에서 사용할 수 있는 문서 양식과 기본으로 적용되는 양식
   - **내보내기 허용 여부**: 문서를 PDF 등으로 다운로드할 수 있는지 설정
   - **AI 검색 대상 여부**: 이 게시판의 문서를 AI 답변 검색에 포함할지 설정
   - **크로스보드 공지 배너 수신 여부**: 이 게시판에서 크로스보드 공지 배너를 표시할지 설정한다 — 배너 수신을 끄면 이 게시판에서는 다른 게시판의 공지 배너가 표시되지 않는다 ([UC-NTC-07](../user/UC-NTC-공지사항.md) 참조)
   - **배너 최대 표시 수**: 이 게시판에서 동시에 표시할 크로스보드 공지 배너의 최대 건수를 설정한다 (기본값은 관리자 설정에 따름)
4. 게시판에 역할별 접근 권한을 설정한다:
   - 역할을 선택하고 열람 / 편집 / 승인 중 부여할 기능을 지정한다.
   - 여러 역할에 서로 다른 기능을 부여할 수 있다. (예: "상담원" 역할에 열람, "지식관리자" 역할에 열람+편집)

**대안 흐름**:
- **1a. 게시판 복제**: 기존 게시판의 설정(유형, 승인 정책, 양식 등)을 복사하여 새 게시판을 생성한다. 접근 권한은 선택적으로 복제할 수 있다.
- **2a. 게시판 이동**: 다른 상위 게시판 아래로 이동시킬 수 있다. 자기 자신의 하위 게시판 아래로 이동하는 순환 참조는 시스템이 차단한다. 권한은 게시판 자체에 귀속되므로 위치가 바뀌어도 기존 권한이 그대로 유지된다.
- **2b. 게시판 일괄 이동**: 조직 개편 등으로 여러 게시판을 한꺼번에 다른 상위 게시판 아래로 옮길 수 있다. 관리자가 이동 대상 게시판을 다중 선택한 뒤 새 상위 게시판을 지정하면, 시스템이 순환 참조와 깊이 제한을 검증한 후 일괄 이동을 수행한다. 이동 전 "영향받는 게시판 N개, 소속 문서 총 M건"을 안내한다.
- **2c. 게시판 삭제 시 하위 문서 처리**: 게시판을 삭제하려는데 소속 문서가 있을 경우, 관리자가 "다른 게시판으로 문서 일괄 이동" 또는 "전체 문서 삭제 처리" 중 하나를 선택할 수 있다. 문서 이동 시, 이동 대상 게시판의 허용 양식과 승인 정책이 다르면 시스템이 호환성을 안내하고 관리자가 확인한 후 진행한다.
- **2d. 대규모 구조 재편 — 영향도 분석 → 단계적 실행 → 사후 검증**: 조직 개편 등으로 여러 게시판의 위치·권한·승인 정책을 대규모로 변경할 때, 분석 → 실행 → 검증의 전체 흐름을 거친다.
  1. **영향도 분석**: 관리자가 변경 계획(이동 대상, 권한 변경, 정책 교체 등)을 등록하면, 시스템이 영향을 미치는 사용자 수, 게시/승인 대기 문서 수, AI 검색 반영 범위, 사이드바 변경 영향 범위를 보고서 형태로 산출한다.
  2. **시뮬레이션**: 실행 전 "적용 시뮬레이션"을 실행하여 변경 후 게시판 구조 미리보기, 권한 변동 대상 사용자 목록, 승인 정책 변경 영향을 확인한다.
  3. **단계적 실행**: 보고서와 시뮬레이션을 기반으로 관리자가 실행을 결정하면, 게시판 단위 또는 부서 단위로 순차 적용할 수 있다. 각 단계 완료 후 중간 결과를 확인하고 계속 여부를 결정한다. 문제 발생 시 해당 단계까지만 롤백할 수 있다.
  4. **사후 검증**: 전체 실행 완료 후, 시스템이 변경 결과 보고서를 자동 생성한다 — 변경 전후 구조 비교, 영향받은 사용자 수, AI 검색 반영 상태, 미처리 항목(승인 대기 문서 등)을 포함한다. 관리자가 결과를 검토하여 추가 조치 필요 여부를 판단한다.
- **4a. 일괄 권한 부여**: 여러 게시판에 동일한 역할-기능 매핑을 한 번에 설정할 수 있다.
- **4b. 사이드바 영향 미리보기**: 권한을 변경하기 전에 "이 변경이 적용되면 N명의 사용자 사이드바에 영향이 있습니다"라는 안내를 확인할 수 있다.
- **4c. 신규 서비스 오픈 게시판 세팅**: 새로운 서비스를 오픈할 때, 관리자가 "서비스 오픈 체크리스트"를 생성하여 게시판 생성 → 양식 연결 → 승인 정책 연결 → 권한 설정 → AI 검색 대상 설정 순서를 단계별로 확인하며 진행할 수 있다. 체크리스트 완료 전까지 해당 게시판은 비공개 상태로 유지되며, 모든 설정이 완료되면 관리자가 "서비스 오픈" 확인을 통해 한 번에 공개한다.
- **4d. 게시판 설정 스냅샷 및 긴급 롤백**: 관리자가 게시판 설정 변경 이력에서 이전 시점의 설정(유형, 승인 정책, 양식, 권한, AI 검색 대상 여부)으로 즉시 롤백할 수 있다. 설정 변경 후 예기치 못한 서비스 영향이 발생했을 때, 관리자가 롤백을 실행하면 직전 상태가 복원된다. 롤백 시 영향받는 문서 수와 사용자 수가 안내된다.
- **4e. 운영 인수인계용 현황 내보내기**: 관리자 교체나 업무 인수인계 시, 전체 게시판 구조(계층, 양식 연결, 승인 정책, 권한 설정, AI 검색 대상 여부)를 하나의 문서(CSV 또는 PDF)로 내보낼 수 있다. 내보낸 문서는 인수인계 자료로 활용하거나, 다른 환경에 동일한 구조를 복원하는 데 사용할 수 있다.
- **4f. 정기 게시판 구조 점검**: 시스템이 설정된 주기(예: 월 1회)마다 "미사용 게시판(N개월간 문서 등록 없음)", "권한 미설정 게시판", "승인 정책 미연결 관리 모드 게시판" 등 운영상 점검이 필요한 항목을 관리자에게 보고한다. 관리자가 보고를 검토하고 정리 대상을 선택하여 일괄 처리할 수 있다.

**예외 흐름**:
- **3a. 저장 실패**: 네트워크 오류 등으로 저장에 실패하면 "변경사항을 저장하지 못했습니다. 다시 시도해 주세요"라는 안내를 표시하고, 입력 내용을 유지한다.
- **3b. 동시 수정 충돌**: 다른 관리자가 같은 게시판을 먼저 수정·저장한 경우, "다른 관리자가 먼저 수정했습니다. 변경 내용을 확인한 후 다시 시도하세요"라는 안내를 표시한다. (저장 시점에 버전을 비교하여 충돌을 감지)
- **3c. 승인 진행 중 게시판 설정 변경**: 승인 정책이 연결된 게시판의 유형을 변경하려 할 때, 승인 대기 중인 문서가 있으면 "승인 대기 문서 N건이 있습니다. 먼저 처리한 후 변경하세요"라는 안내를 표시한다.
- **2a-1. 트리 깊이 제한 초과**: 게시판을 이동하거나 하위에 새 게시판을 생성할 때, 시스템에서 설정한 최대 깊이(예: 5단계)를 초과하면 "게시판 계층 깊이가 최대 제한을 초과합니다. 구조를 조정하거나 관리자에게 문의하세요"라는 안내를 표시하고 작업을 차단한다.

**사후 조건**:
- 감사 로그에 게시판 변경(생성/수정/삭제/이동) 기록이 남는다. ([FD-AUD](../../features/FD-AUD-감사로그.md) 참조)
- AI 검색 대상 여부가 변경된 경우, 해당 게시판 문서의 AI 검색 반영 작업이 등록 또는 해제된다. — AI 검색 반영이란 문서 내용을 AI가 답변에 활용할 수 있도록 변환·저장하는 과정이다. ([UC-ADM-09](UC-ADM-검색파이프라인.md) 참조)
- 사이드바에 변경사항이 반영된다. 부모 게시판에 권한이 없고 자식에만 권한이 있는 경우, 부모는 폴더 형태로만 표시된다.
- 권한 변경은 다음 페이지 접근 시점부터 반영된다. 현재 열려 있는 세션에서는 기존 권한이 유지된다.
- 게시판 일괄 이동·삭제 시, 이동/삭제된 게시판 목록과 영향받은 문서 수가 관리자에게 결과 보고 형태로 제공된다.

**제약 사항**:
- 하위 게시판이 있는 상태에서는 해당 게시판을 삭제할 수 없다. 하위 게시판을 먼저 정리해야 한다.
- 문서(게시/임시저장/승인 대기 포함)가 존재하는 게시판은 바로 삭제할 수 없다. 문서 일괄 이동 또는 삭제 처리를 먼저 수행해야 한다.
- 각 게시판의 접근 권한은 완전히 독립적이다. 상위 게시판의 권한이 하위 게시판에 자동으로 상속되지 않는다. ([FD-DOC](../../features/FD-DOC-문서관리.md) §7 참조)
- 게시판 트리의 최대 깊이는 시스템 설정으로 제한된다. (기본값: 5단계)
- 자유게시판 유형은 시스템 설정에 따라 제공되지 않을 수 있다.
- 게시판별 내보내기 허용 제어는 시스템 설정에 따라 제공되지 않을 수 있다. 미제공 시 전체 게시판에서 내보내기가 허용된다.
- 관리 화면의 모든 저장은 저장 시점에 버전을 비교하여 동시 수정 충돌을 감지한다.

## UC-ADM-02: 문서 양식 관리

**비즈니스 목표**: 표준화된 문서 양식을 제공하여 지식 관리자의 문서 작성 시간을 단축하고, 문서 품질의 일관성을 확보한다.

**사용자**: 운영 관리자 (문서 양식 관리 권한 필요)

> **문서 양식이란?** 문서를 작성할 때 미리 채워져 있는 기본 틀입니다. 예를 들어 "FAQ 양식"을 선택하면 질문/답변 영역이 미리 준비된 상태에서 작성을 시작할 수 있습니다.

**사전 조건**:
- 사용자가 운영 관리자이며 문서 양식 관리 권한을 보유하고 있어야 한다.
- 지식 관리자의 양식 요청, 새로운 문서 유형 도입, 또는 기존 양식의 오류 발견 등으로 트리거된다.

**기본 흐름**: ([FD-DOC](../../features/FD-DOC-문서관리.md) §4 참조)
1. 관리자가 문서 양식 관리 화면에 접근한다.
2. 블록 편집기를 사용하여 양식의 기본 내용(미리 채워질 틀)을 직접 작성하고, 기본 태그를 설정한다.
3. 양식 분류(SOP(표준 절차서), FAQ(자주 묻는 질문), 체크리스트, 공지, 장애대응 등)를 지정한다.
4. 시스템 설정에 따라, 특정 블록을 "편집 불가 고정 블록"으로 지정할 수 있다. 문서 작성 시 해당 블록은 수정할 수 없다.
5. 저장하면 새로운 양식이 만들어진다.

**대안 흐름**:
- **1a. 양식 복제**: 기존 양식을 복사하여 새 양식을 만든 뒤, 필요한 부분만 수정하여 저장할 수 있다.
- **1b. 비활성 처리**: 더 이상 사용하지 않는 양식을 비활성으로 전환하면 새 문서 작성 시 선택 목록에서 제외된다. 이미 해당 양식으로 작성된 기존 문서에는 영향이 없다.
- **1c. 게시판 연결 현황 조회**: 특정 양식이 어떤 게시판에서 허용/기본 양식으로 설정되어 있는지 확인할 수 있다.
- **1d. 양식 표준화 일괄 전환**: 조직 차원의 양식 표준화 프로젝트 시, 관리자가 기존 양식 A를 비활성 처리하고 새 양식 B를 생성한 뒤, 양식 A가 허용/기본 양식으로 설정된 모든 게시판에 양식 B를 일괄 연결할 수 있다. 시스템은 "양식 A를 사용 중인 게시판 N개에 양식 B가 추가됩니다"라는 안내를 제공한다.
- **1e. 미사용 양식 자동 비활성화 안내**: 시스템이 설정된 기간(예: 6개월) 동안 신규 문서에 한 번도 사용되지 않은 양식 목록을 관리자에게 정기적으로 안내한다. 관리자가 목록을 검토하고 선택한 양식을 일괄 비활성 처리할 수 있다.
- **5a. 양식 변경 시 기존 문서 호환성 관리**: 새 양식을 생성하면서 기존 양식을 비활성 처리할 때, 시스템이 기존 양식으로 작성된 문서의 호환성을 안내한다.
  - "이 양식으로 작성된 문서 N건이 있습니다. 기존 문서는 작성 시점의 양식 구조를 유지합니다"라는 안내를 표시한다.
  - 관리자는 영향받는 문서 목록을 다운로드할 수 있다.
  - 양식 간 구조 차이(추가된 블록, 삭제된 블록, 변경된 고정 블록)를 비교하여 표시한다.
  - 기존 양식으로 작성된 문서를 새 양식 기준으로 수정할 때, 시스템이 새 양식에서 추가된 필수 블록을 안내하여 지식 관리자가 누락 없이 보완할 수 있도록 한다.
  - 양식 버전별 문서 수 현황(양식 A v1: N건, 양식 A v2: M건)을 조회할 수 있어, 관리자가 이전 버전 양식의 문서 잔존 현황을 파악한다.
- **5b. 신규 서비스 오픈 양식 일괄 세팅**: 새 서비스 출시 시, 관리자가 복수 양식을 한 번에 생성하고 대상 게시판에 일괄 연결할 수 있다. 기존 양식을 기반으로 복제 후 수정하는 방식을 지원하여, 반복적인 수작업을 줄인다.
- **5c. 양식 운영 현황 보고서**: 관리자가 전체 양식의 사용 현황(양식별 사용 문서 수, 연결된 게시판 수, 최근 사용일)을 보고서 형태로 조회하고 내보낼 수 있다. 운영 인수인계나 정기 점검 시 양식 운영 상태를 파악하는 데 활용한다.

**예외 흐름**:
- **5a. 저장 실패**: 네트워크 오류 등으로 저장에 실패하면 "양식을 저장하지 못했습니다. 다시 시도해 주세요"라는 안내를 표시하고, 편집 내용을 유지한다.
- **5b. 동시 수정 충돌**: 다른 관리자가 같은 양식 관련 설정을 먼저 수정한 경우, "다른 관리자가 먼저 수정했습니다. 변경 내용을 확인한 후 다시 시도하세요"라는 안내를 표시한다.
- **4a. 고정 블록 오류 발견**: 양식의 고정 블록에 오류가 있는 경우, 기존 양식을 비활성 처리하고 복제하여 수정된 새 양식을 생성한다. 기존 문서의 고정 블록은 작성 시점의 양식 내용이 그대로 유지된다(소급 변경 없음).
- **4b. 필수 블록 포함 양식과 기존 문서 불일치**: 관리자가 고정 블록(필수 섹션)이 포함된 새 양식을 만들고 기존 양식을 비활성 처리한 경우, 기존 양식으로 작성된 문서에는 해당 필수 블록이 없을 수 있다. 시스템은 이를 소급 적용하지 않으며, 관리자가 필요하면 영향받는 문서 목록을 조회하여 지식 관리자에게 개별 수정을 안내할 수 있다.

**사후 조건**:
- 감사 로그에 양식 생성/비활성 기록이 남는다.
- 새로 만든 양식은 게시판의 "허용 양식" 목록에 추가해야 사용 가능하다.
- 양식 비활성 처리 시, 해당 양식이 기본 양식으로 설정된 게시판에 "기본 양식이 비활성 상태입니다"라는 경고가 표시된다. 관리자가 대체 양식을 지정할 때까지 경고가 유지된다.
- 양식 표준화 일괄 전환 시, 변경된 게시판 목록과 영향 범위가 관리자에게 결과 보고 형태로 제공된다.

**제약 사항**:
- 양식은 한 번 만들면 직접 수정할 수 없다. 수정이 필요하면 기존 양식을 비활성 처리하고 복제한 뒤 새로 만들어야 한다 — 이전 양식으로 만든 문서가 의도치 않게 변경되는 것을 방지하기 위함이다. ([FD-DOC](../../features/FD-DOC-문서관리.md) §4 불변 원칙 참조)
- 고정 블록에 오류가 발견되더라도 기존 문서의 고정 블록은 작성 시점의 양식 그대로 유지된다. 기존 문서에 대한 소급 변경은 수행하지 않는다.
- 블록 잠금 기능은 시스템 설정에 따라 제공되지 않을 수 있다.
- 미사용 양식 자동 안내 기능은 시스템 설정에 따라 비활성화할 수 있다.

## UC-ADM-04: 공통 컨텐츠 관리

**비즈니스 목표**: 여러 문서에 반복되는 정보(전화번호, 약관 문구, 공통 안내 등)를 한곳에서 관리하여, 정보 일관성을 확보하고 상담 품질 편차를 줄인다.

**사용자**: 운영 관리자 (공통 컨텐츠 관리 권한 필요)

> **공통 컨텐츠란?** 여러 문서에서 공유하여 사용하는 내용입니다. 예를 들어 "고객센터 전화번호 안내"를 공통 컨텐츠로 만들어 두면, 100개의 문서에서 이를 참조할 수 있고, 전화번호가 변경되면 공통 컨텐츠 하나만 수정하면 모든 문서에 자동 반영됩니다.

**사전 조건**:
- 사용자가 운영 관리자이며 공통 컨텐츠 관리 권한을 보유하고 있어야 한다.
- 공통 컨텐츠 기능이 시스템에서 활성화되어 있어야 한다.
- 지식 관리자의 공통 문구 변경 요청, 정책·약관 변경, 또는 연락처 정보 갱신 등으로 트리거된다.

**기본 흐름**: ([FD-DOC](../../features/FD-DOC-문서관리.md) §5 참조)
1. 관리자가 공통 컨텐츠 관리 화면에 접근한다.
2. 새 공통 컨텐츠를 만든다 — 이름, 설명, 분류, 본문(블록 편집기로 작성)을 입력한다.
3. 수정할 때는 "이 공통 컨텐츠를 참조하는 문서가 N개 있습니다"라는 영향도 안내를 확인한 후 저장한다.
4. 저장 후, 관리자에게 "영향 문서 목록"을 표시한다. 관리자는 참조 문서 중 승인 요청 대상을 선택할 수 있다. (전체 선택 또는 개별 선택)
5. 시스템이 참조 문서의 담당 지식 관리자에게 "공통 컨텐츠 'OOO'이 변경되었습니다. 참조 문서를 확인해 주세요"라는 알림을 자동 발송한다. 알림에는 변경 내용 요약과 해당 문서 바로가기 링크가 포함된다.
6. 시스템은 수정된 공통 컨텐츠를 참조하는 문서에 대해 AI 검색 반영 작업을 자동으로 시작한다. 이 작업은 백그라운드에서 순차적으로 처리된다.

**대안 흐름**:
- **3a. 비활성/대체 처리**: 공통 컨텐츠를 "사용 중단"으로 전환하면 이를 참조하는 문서에 경고가 표시된다. 대체할 새 공통 컨텐츠를 지정할 수 있다.
- **3b. 삭제 차단**: 참조하는 문서가 존재하면 삭제할 수 없다. 먼저 참조를 제거하거나 대체 컨텐츠를 지정해야 한다.
- **3c. 대량 참조 문서 단계적 반영**: 참조 문서가 매우 많은 공통 컨텐츠(예: 100건 이상)를 수정할 경우, 관리자가 "즉시 전체 반영" 또는 "단계적 반영(게시판 단위로 순차 적용)"을 선택할 수 있다. 단계적 반영 시, 다음 게시판 반영 전 관리자가 중간 결과를 확인하고 계속 여부를 결정할 수 있다.
- **2a. 공통 컨텐츠 내 다른 공통 컨텐츠 참조 제한**: 공통 컨텐츠 작성 시 다른 공통 컨텐츠를 참조(중첩)하는 것은 허용되지 않는다. 블록 편집기에서 공통 컨텐츠 참조 블록을 삽입하려 하면 "공통 컨텐츠 안에서는 다른 공통 컨텐츠를 참조할 수 없습니다"라는 안내를 표시한다. 이는 A→B→C→A와 같은 순환 참조를 원천 차단하기 위한 것이다.
- **3d. 정기 공통 컨텐츠 점검**: 시스템이 설정된 주기(예: 분기 1회)마다 "최근 N개월간 참조 문서가 감소한 공통 컨텐츠", "사용 중단 상태로 장기 방치된 컨텐츠" 등을 관리자에게 안내한다. 관리자가 대체·정리 여부를 검토하여 불필요한 컨텐츠를 정리할 수 있다.
- **3e. 공통 컨텐츠 운영 현황 내보내기**: 관리자가 전체 공통 컨텐츠 목록(이름, 참조 문서 수, 최종 수정일, 수정자)을 보고서로 내보낼 수 있다. 운영 인수인계나 정기 감사 대응에 활용한다.

**예외 흐름**:
- **3a. 저장 실패**: 네트워크 오류 등으로 저장에 실패하면 "공통 컨텐츠를 저장하지 못했습니다. 다시 시도해 주세요"라는 안내를 표시하고, 편집 내용을 유지한다.
- **3b. 동시 수정 충돌**: 다른 관리자가 같은 공통 컨텐츠를 먼저 수정·저장한 경우, "다른 관리자가 먼저 수정했습니다. 변경 내용을 확인한 후 다시 시도하세요"라는 안내를 표시한다. 양쪽 변경 내용을 비교하여 관리자가 최종본을 결정할 수 있다.
- **5a. AI 검색 반영 부분 실패**: 참조 문서의 AI 검색 반영 작업 중 일부가 실패하면, 실패한 문서 목록을 관리자에게 안내하고 재시도 버튼을 제공한다. 진행 상황은 AI 검색 데이터 변환 모니터링 화면에서 확인할 수 있다. ([UC-ADM-09](UC-ADM-검색파이프라인.md) 참조)

**사후 조건**:
- 감사 로그에 공통 컨텐츠 변경 기록이 남는다.
- 내용 수정 시 참조 문서의 AI 검색 반영 작업이 순차적으로 등록된다.
- 참조 문서의 담당 지식 관리자에게 공통 컨텐츠 변경 알림이 발송된다. 알림에는 변경 내용 요약과 문서 바로가기가 포함된다.
- 관리자가 승인 요청 대상으로 선택한 참조 문서에는 승인 요청이 발송된다.
- 비활성 전환 시, 참조 문서의 해당 공통 컨텐츠 영역에 "사용 중단된 공통 컨텐츠입니다"라는 경고가 표시되어 지식 관리자가 대체 조치를 취할 수 있다.
- 대량 참조 단계적 반영을 선택한 경우, 반영 진행 상태(완료/진행 중/대기)가 관리자 화면에 표시된다.

**제약 사항**:
- 공통 컨텐츠 기능이 비활성화된 환경에서는 공통 컨텐츠 관리 화면 자체에 접근할 수 없다.
- 참조 중인 공통 컨텐츠는 삭제할 수 없으며, 비활성 전환만 가능하다.
- 공통 컨텐츠 간 중첩 참조(공통 컨텐츠 안에서 다른 공통 컨텐츠 참조)는 허용되지 않는다.
- 관리 화면의 모든 저장은 저장 시점에 버전을 비교하여 동시 수정 충돌을 감지한다.

## UC-ADM-05: 태그 관리

**비즈니스 목표**: 태그 품질(중복 제거, 표준화)을 유지하여 AI 검색 정확도를 보장하고, 상담사와 지식 관리자의 문서 탐색 효율을 높인다.

**사용자**: 운영 관리자 (태그 관리 권한 필요)

**사전 조건**:
- 사용자가 운영 관리자이며 태그 관리 권한을 보유하고 있어야 한다.
- 상담사·지식 관리자의 태그 정리 요청, 주기적인 태그 품질 점검, 또는 새로운 업무 영역에 대한 표준 태그 사전 등록 필요 등으로 트리거된다.

**기본 흐름**: ([FD-DOC](../../features/FD-DOC-문서관리.md) §8 참조)
1. 관리자가 태그 관리 화면에서 전체 태그 목록(사용 건수, 생성일 포함)을 조회한다.
2. 관리자가 표준 태그를 직접 생성한다. 새로운 업무 영역이나 프로젝트에 필요한 태그를 사전에 등록하여 문서 작성자에게 일관된 태그 사용을 유도한다.
3. 유사하거나 중복되는 태그를 병합한다.
   - 예: "CS", "고객서비스" 태그를 "고객서비스"로 병합하면, "CS" 태그가 붙어 있던 문서들의 태그가 자동으로 "고객서비스"로 교체된다.
4. 아무 문서에도 사용되지 않는(사용 건수 0건) 태그를 정리한다.
5. 태그 이름을 변경하면 해당 태그를 사용하는 모든 문서에 즉시 반영된다.

**대안 흐름**:
- **4a. 미사용 태그 일괄 정리**: 사용 건수가 0건인 태그를 한 번에 삭제할 수 있다.
- **3a. 태그 병합 미리보기**: 병합 전에 "이 병합으로 영향받는 문서 N건" 안내를 확인할 수 있다.
- **1a. 문서 작성자 태그 관리**: 문서 작성자가 자유롭게 생성한 태그도 관리 화면에서 조회·병합·정리할 수 있다.
- **1b. 태그 거버넌스 정책 설정**: 관리자가 태그 운영 정책을 종합적으로 설정한다.
  - **기본 정책**: 문서 작성자의 자유 태그 생성 허용 여부, 표준 태그만 사용 강제 여부, 태그 최소/최대 글자 수를 지정할 수 있다. 표준 태그만 강제할 경우, 문서 작성 시 관리자가 등록한 태그 목록에서만 선택 가능하다.
  - **태그 분류 체계**: 태그를 용도별 그룹(예: "업무분류", "서비스", "고객유형", "긴급도")으로 분류하여 관리한다. 그룹별로 "필수 태그 1개 이상 지정" 등의 규칙을 설정할 수 있다. 문서 작성 시 태그 선택 화면에서 그룹별로 태그가 구분되어 표시된다.
  - **승인 필요 태그**: 관리자가 특정 태그(예: "대외비", "규제문서", "법무검토필요")를 "승인 필요 태그"로 지정할 수 있다. 문서 작성자가 해당 태그를 부착하면 관리자에게 승인 요청이 발송되고, 승인 후에만 태그가 적용된다. 무분별한 민감 분류 태그 사용을 방지한다.
  - **게시판별 태그 정책**: 게시판마다 허용 태그 그룹이나 필수 태그 규칙을 다르게 설정할 수 있다. 예: "규제 문서" 게시판에서는 "규제유형" 그룹 태그가 필수이다.
- **1c. 태그 사용 통계 기반 정리 제안**: 시스템이 태그 사용 추이를 분석하여 "최근 N개월간 사용 건수가 급감한 태그", "유사한 이름의 태그 쌍(예: 'CS문의' vs 'CS 문의')" 등을 관리자에게 정기적으로 제안한다. 관리자가 제안을 검토하여 병합·삭제·유지 중 조치를 결정한다.
- **4b. 태그 자동 정리 기준 설정**: 관리자가 "N개월 이상 미사용 태그 자동 삭제" 기준을 설정할 수 있다. 설정된 기준에 도달한 태그는 즉시 삭제되지 않고, 관리자에게 정리 대상 목록으로 안내되어 최종 확인 후 삭제된다.
- **4c. 정기 태그 정리 자동화 스케줄**: 관리자가 태그 정리 스케줄(예: 매주 월요일, 매월 1일)을 설정하면, 시스템이 해당 시점에 미사용 태그 목록, 유사 태그 쌍, 사용 급감 태그를 자동 추출하여 관리자에게 보고한다. 관리자가 보고를 검토하고 일괄 처리를 승인하면 정리가 실행된다.
- **1d. 대규모 환경 태그 운영 대시보드**: 수백 개 이상의 태그를 운영하는 환경에서, 태그 사용 분포(상위 태그, 미사용 태그, 중복 의심 태그)를 시각적으로 파악할 수 있는 대시보드를 제공한다. 태그 수가 시스템이 정한 경고 기준을 초과하면 관리자에게 정리를 권장하는 알림을 보낸다.
- **5a. 태그 현황 보고서 내보내기**: 전체 태그 목록과 사용 통계(사용 건수, 생성일, 최근 사용일, 거버넌스 정책 준수 여부)를 보고서로 내보낼 수 있다. 운영 인수인계나 정기 감사 대응에 활용한다.

**예외 흐름**:
- **2a. 저장/생성 실패**: 네트워크 오류 등으로 태그 생성·변경에 실패하면 "태그를 저장하지 못했습니다. 다시 시도해 주세요"라는 안내를 표시한다.
- **3a. 태그 병합 시 검색 반영 갱신 실패**: 대량 태그 병합 시 일부 문서의 검색 반영 갱신이 실패하면, 실패한 문서 목록을 관리자에게 안내하고 재시도 버튼을 제공한다. 병합 자체는 완료되며, 검색 반영 갱신만 재시도 대상이 된다.
- **5a. 중복 태그명 충돌**: 변경하려는 태그 이름이 이미 존재하면 "동일한 이름의 태그가 이미 있습니다. 병합을 사용해 주세요"라는 안내를 표시한다.
- **3b. 병합 대상 태그가 다수 문서의 태그 수 상한 초과**: 태그 A와 태그 B를 병합할 때, 두 태그를 모두 가진 문서에서 병합 후 중복이 제거되어 문제가 없지만, 병합 결과 일부 문서의 태그 수가 시스템 상한(예: 20개)을 초과할 경우 "N건의 문서가 태그 수 상한을 초과합니다"라는 안내를 표시한다. 관리자가 확인한 후 병합을 진행하면, 초과 태그는 해당 문서에서 제외되지 않고 상한을 임시 초과한 상태로 유지된다.

**사후 조건**:
- 감사 로그에 태그 변경(생성/병합/삭제/이름변경) 기록이 남는다.
- 태그 병합·이름 변경 시 해당 문서의 검색 반영이 갱신된다. 대량 병합 시 갱신은 백그라운드에서 순차적으로 처리되며, 완료 시 관리자에게 알림이 발송된다.
- 태그 거버넌스 정책이 변경되면, 다음 문서 작성/수정 시점부터 새 정책이 적용된다. 기존 문서의 태그에는 소급 적용되지 않는다.
- 태그 분류 체계 변경(그룹 추가/수정/삭제)이 감사 로그에 기록된다.
- 승인 필요 태그의 승인/거부 이력이 감사 로그에 기록되며, 태그 승인 현황 통계가 관리자에게 제공된다.
- 태그 사용 통계 기반 정리 제안은 설정된 주기(예: 월 1회)에 따라 관리자에게 안내된다.

**제약 사항**:
- 태그 병합은 되돌릴 수 없다. 병합 전 영향 범위를 반드시 확인해야 한다.
- 문서당 최대 태그 수는 시스템 설정에 의해 제한된다. ([FD-SYS](../../features/FD-SYS-시스템설정.md) §3.2 참조)
- 태그 거버넌스 정책의 "표준 태그만 강제" 설정은 기존 문서의 비표준 태그를 자동 제거하지 않는다. 기존 비표준 태그는 관리자가 별도로 병합·정리해야 한다.
